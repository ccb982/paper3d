# stickman-lab-v2 架构

> 目的：产出**能站住、能被高层动作驱动**的物理火柴人，作为隐藏 boss 移植回本体游戏。
> 本文是唯一真源。v1（`../stickman-lab/`）冻结留档，只作对照与素材来源。
>
> 2026-10 重写：执行层已完成并验收；本文同时给出**控制层**（执行层之上封装的一层）
> 的架构设计。控制层是唯一发布关节执行命令的地方，并且可以被直接操控。

## §1 总分层（自下而上）

```
┌────────────────────────────────────────────────────────────────────┐
│ 意图层（游戏 / AI / 玩家输入）—— 最高层                              │
│   · 目标与剧情：play("bow") / 攻击 / 受击 / 情绪 / 不许移动           │
└───────────────────────────────┬────────────────────────────────────┘
                                │ 目标 + 约束
┌───────────────────────────────▼────────────────────────────────────┐
│ 动作提案系统（原名"迈步系统"，独立）                                 │
│   · **所有要执行的动作都由它提案**：迈步、摆手、下蹲、起身…          │
│   · **迈步之前先出"重心转移相位"**（comTrack），再出落足点           │
│   · 输出 ActionProposal（相位序列 + 时长 + 预算），只提案不执行      │
└───────────────────────────────┬────────────────────────────────────┘
                                │ ActionProposal
┌───────────────────────────────▼───────────────┐   ┌──────────────────────────────┐
│ 控制层 ControlLayer（唯一裁定者 + 发布者）     │◀──│ 摔倒预警（独立 · 常开伺服层） │
│   · 多传感估计 / 反射弧 / 平衡策略             │   │ 每拍连续出 StabilityCorrection│
│   · 动作程序（执行**被裁定采纳**的提案）        │   │ 提案（修正，不是报警灯）      │
│   · 直控通道（手动/调试）                      │   └──────────────────────────────┘
│   · 裁定：manual > reflex > balance > action > program > posture   │
└───────────────────────────────┬────────────────────────────────────┘
                                ▼ 关节命令（经 Executor）
```

**边界纪律**：
- 执行层只认"每自由度力矩/激活/角目标"，不认任何动作语义；
- **意图层最高**：游戏/AI 的意图在动作提案系统**之前**生效（可禁止/改写任何动作
  请求，如剧情要求"原地受击"）；
- **动作提案系统（原"迈步系统"）**：**所有要执行的动作都由它提案**——迈步、摆手、
  下蹲、起身…，且**迈步之前先出"重心转移相位"**；只出 `ActionProposal`，不写关节；
- **摔倒预警是常开伺服层**：每拍连续出 `StabilityCorrection` 提案，也不写关节；
- 两路提案都进控制层**唯一执行裁定**（可同拍联合执行、逐轴消解冲突），向下只写 Executor
  （账本、τmax、限位由执行层保证）；
- 控制层向上暴露**动作名 + 参数**（`play/abort/status`）与**直控通道**
  （`setAngle/setTorque/setActivation`）。

**两种"优先"不要混淆**（后面仲裁表按此执行）：
- **决策权**（谁定目标与约束）：`意图层 > 控制层判定`；
- **执行优先级**（同一根轴冲突时谁覆盖）：`直控 > 反射 > 平衡 > …`。

## §2 执行层（已建成）

| 模块 | 职责 | 关键设计 |
|---|---|---|
| `core/skeleton.ts` | 骨架数据（不改） | 18 逻辑关节 / 46 自由度、静姿态、限位、τmax |
| `core/body.ts` | 刚体 + 铰链装配 | 球窝 → 原生球铰（3 转）；revolute → 多环链（踝 = 扭+内外翻+屈伸）；柔性足 arch/mfoot 原样（引擎 ForceBased 隐式弹簧） |
| `core/executor.ts` | **唯一 τ 写入口** | 先求和→单点饱和→成对冲量；账本 `cmd/applied/limit/saturated`；每自由度每步恰好施加一次 |
| `core/drive.ts` | 命令通道 | 阻抗伺服（一步收敛护栏 α）、黏性阻尼 τ=−B·ω（显式、限幅）、限位通道（越界冲量，权限压过马达）、激活通道；默认 kd = `0.02·τmax`（反 76Hz 振铃的实测值） |
| `core/actuator.ts` | 人类式执行器 | 黏弹阻尼 + 一阶激活动力学 + Hill 力-长/力-速 |
| `core/world.ts` | 步进循环 | `updateDofState → beginStep → controller → drive → applyAll → step` |
| `core/quat.ts` | 四元数唯一实现 | 含 swing-twist 分解（球铰三轴语义） |

## §3 控制层（ControlLayer）设计

### 3.0 意图层（最高层，在动作提案系统之前）

游戏/AI 的意图**先于**摔倒预警与迈步生效——它不是"另一个平衡策略"，而是
**目标与约束的来源**：

```ts
interface GameIntent {
  // 高层动作（经控制层解算关节）
  play(action: string, params?: object): void;   // 'bow' | 'attack' | 'hit' …
  // 约束（在迈步/预警之前生效）
  allowStepping(on: boolean): void;              // 剧情禁止迈步
  stance(mode: 'free' | 'rooted'): void;         // 站桩/生根
  setFacing(yawRad: number): void;
  setEmotion(tag: string): void;
}
```

- 意图只提交**目标/约束**，不写关节、不写力矩；
- 控制层裁定（§3.4）第一条就是"意图约束优先"：意图禁止某类动作时，即使动作
  提案系统提案且 level=2，也会被 `rejected(reason='intent')`；
- 意图层（决策权）与直控（执行优先级）是两件事，见 §1 的"两种优先"说明。

### 3.1 定位（用户定调）

> "摔倒预警与迈步是两个独立系统，但是都给这个控制层做最后判定。
>  这一层也允许被直接操控。"

翻译成接口：

```ts
interface ControlLayer {
  // ── 消费两个独立系统的输出（都只是提案，本层裁定）──
  ingest(c: StabilityCorrection): void;  // 摔倒预警（常开伺服层）：每拍连续修正提案
  ingest(p: ActionProposal): void;       // 动作提案系统（原迈步）：相位序列，含重心转移
  // ── 直控（最高优先级；调试/手动/游戏特殊输入）──
  setAngle(joint, axis, rad, kp?, kd?): void;
  setTorque(joint, axis, tau): void;
  setActivation(joint, axis, a): void;
  // ── 运行模式：是否走反射弧、谁主导 ──
  //   'reflex' = 反射弧主导（默认）；'assist' = 反射弧只保底、程序/直控主导；
  //   'direct' = **不走反射弧**，命令直通执行层（精细调控/消融/学习策略）
  setMode(mode: 'reflex' | 'assist' | 'direct'): void;
  readonly reflexes: {
    setEnabled(id: string, on: boolean): void;   // 逐条开关（消融）
    setLatency(id: string, s: number): void;     // 延迟可置零
  };
  // ── 动作（高层语义；内部自己解算关节）──
  play(action: string, params?: object): void;
  abort(): void;
  readonly status: { action: string | null; t: number; phase: string; decision: string };
  // ── 判定结果（回读给 UI/探针）──
  readonly decision: {
    accepted: ('stability'|'ankle'|'hip'|'action'|'program'|'manual')[];
    conflicts: { axis: string; winner: string; loser: string; reason: string }[];
    rejected: { kind: string; reason: string }[];
    xcomMargin: number; support: 'both'|'l'|'r'|'none';
  };
}
```

### 3.2 感知与状态估计（Sensors）

每物理步从 Body/Rapier 读取、滤波、延迟分发：

| 量 | 来源 | 用途 |
|---|---|---|
| CoM / CoM 速度 | `body.com/comVel`（质量加权 worldCom） | 平衡主回路 |
| 单脚 ΣFz / CoP | `body.footNormalForce` + 接触流形 | 支撑判定、踝策略 |
| 关节角/角速度/力矩 | `dof.angle/vel` + Executor 账本 | 反射与状态输出 |
| 躯干姿态/角速度 | spine4 刚体 | 翻正反射 |
| XcoM = x + ẋ/ω（ω=√(g/h)） | 计算 | 内部稳定性量（控制层判定用；预警系统另有其评估） |

参考：Peterka 2002（感觉整合 = CoM 误差的 PID + 权重）；Hof 2005（XcoM/动态稳定条件）。

### 3.3 反射层：先把三种东西分开（之前的混乱就在这）

| 类别 | 定义 | 特征 | 归属 |
|---|---|---|---|
| **反射（Reflex）** | 固定"感觉→动作"回路 | 无选择、无状态（或只有固定增益/延迟） | 本节 |
| **恢复策略（RecoveryStrategy）** | 需要分级/锁存/切换的决策 | 调用反射原语，但自己不是反射 | §3.10 |
| **保护程序（ProtectiveProgram）** | 跌倒已不可避免后的急救动作 | 有相位、全权接管 | §3.8 |

> `绷直身子` 在神经科学里可以叫"保护性反射"，但**工程上归入保护程序**
> （有触发状态、有相位、全权接管），不放进反射弧——这就是之前看起来乱的原因。

**反射原语清单（只放真正的固定回路）**

```ts
interface Reflex {
  id: string;
  latency: number;                       // s，感觉延迟（固定环形缓冲）
  update(s: Sensors, dt: number): void;  // 触发条 + 修正输出（写 Executor）
}
```

| 反射 | 生物对应 | 触发 | 输出 | 依据 |
|---|---|---|---|---|
| **垫脚（本阶段重点）** | 踝-足本体/触觉快速回路 | CoM/XcoM 误差（不等预警） | 每脚四向 CoP：踝屈伸（前后）+ 内外翻与柔性足旋前/旋后（左右） | Winter 1995 / Hof 2005；柔性足实测 |
| 牵张 | 肌梭-单突触 | 关节角误差/速度 | 刚度/阻尼调制（Actuator 已内建，暴露为原语） | Nashner 1976 |
| 负载 | 高尔基腱器官 | 支撑脚 ΣFz 骤降 | 伸肌力矩脉冲（防腿软） | Nashner 1976 |
| **落地消力（屈曲→回伸）** | 负载/着陆缓冲（离心-向心） | 单脚触地事件 + 冲击力（Fz/下降速度） | 按力大小自动计算屈曲量 → 再回伸（**函数式原语**，不锁存不选择；§3.12） | Geyer & Herr 2010（正力反馈+阻尼）；Blickhan 1989（SLIP）；Zhang et al. 2000（膝主导消能） |
| 翻正 | 前庭-脊髓 | 躯干倾角/角速度 | 脊柱/髋回正力矩 | Horak & Nashner 1986 |
| 屈曲回撤 | nociceptive | 意外碰撞/夹脚 | 快速屈腿（后续） | — |

**延迟**：每个反射有独立 `latency`（牵张 20–40ms、前庭 60–100ms、长环 100–150ms），
由环形缓冲实现；延迟可调为零做对照。依据：Todorov & Jordan 2002。

**当前模块地图（谁是谁，避免再乱）**

| 文件 | 角色 | 职责 |
|---|---|---|
| `sensors.ts` | 感知 | 读数（CoM/CoP/支撑/姿态），零控制 |
| `footPad.ts` | 反射原语：垫脚 | 四向 CoP 执行器（踝 + 柔性足；侧向限幅/速率已定型） |
| `stability.ts` | **摔倒预警（伺服层）** | `StabilityWarner`：算 CoM/XCoM/CoP，出 `StabilityProposal`（含反射用法与幅度预算），不直接写关节（原 balance.ts 改名） |
| `leanReflex.ts` | 伺服执行方 | 按 directive 执行：髋外展 + 脊柱侧屈 + 摆臂（位置式 + 限速）；bend 为力矩式 |
| `reflex.ts` | **策略选择器**（命名债：应为 `recovery.ts`） | pad→hip（默认关）→giveup 分级锁存，调用垫脚原语 |

### 3.4 摔倒预警（平衡算法在这里，出提案 + 反射用法）

用户定调：**平衡模块属于预警**；**是预警提供提案，提案也包括如何使用反射弧**。
即：预警 = 稳定性的"大脑"——它算 CoM/XcoM/CoP、决定怎么修，并在提案里指定
**调用哪些反射、用什么参数**；反射弧只是它手里的工具箱。

```ts
/** 摔倒预警的提案（每拍连续输出；只读，不直接写关节） */
interface StabilityProposal {
  /** 期望 CoM 修正（世界系加速度或位移目标） */
  comAdjust: { ax: number; az: number };
  /** 期望 CoP（世界系；踝/柔性足的去处） */
  desiredCop?: { x: number; z: number };
  /** ★ 反射用法：本拍要用哪些反射、参数是什么 */
  reflexDirectives: {
    id: 'pad' | 'lean' | 'bend' | 'step' | 'brace' | 'kneel' | string;
    weight: number;                 // 权重/增益
    params?: Record<string, number>;
  }[];
  /** 等级（派生标签，给动作提案/迈步放行用） */
  level: 0 | 1 | 2;
  reason: string;
}
```

- 预警每拍更新提案：正常情况下给"垫脚"指令（`id:'pad'`，四向 CoP）；
  饱和升级时改为 `id:'lean'`（左右侧移：髋外展+脊柱侧屈+摆臂）或
  `id:'bend'`（前后弯腰，力矩式帮助）；出界则给 `id:'step'`（迈步放行用）或放弃；
  跌倒已不可避免时可给 `id:'brace'/'kneel'`（保护程序，见 §3.8）；
  **每个 directive 的幅度由"幅度预算"逐级分配**（踝→髋→脊柱→摆臂；Pai & Patton 1997
  的可恢复幅度上界；细则与标定见 §6.1）；
- 反射弧（§3.3）是**被动工具箱**：只按 directive 运行，不自己做决策；
- 控制模块（§3.6）只负责"收命令 → 整合两提案 → 按 directive 跑反射 → 写关节"。

**两个独立系统的性质不同（一个连续、一个事件；都只提案）**

| 系统 | 性质 | 输出（只读提案） | 内部依据 |
|---|---|---|---|
| 摔倒预警 | **伺服层：常开，每拍连续输出** | `StabilityCorrection { desiredCopShift, comAdjust, gainScale, level }`（连续量；level 只是派生标签） | XcoM 比支撑边距、外推时间；Pratt 2006 / Hof 2005 |
| 动作提案系统（原"迈步系统"） | **事件层：提案制，覆盖所有要执行的动作** | `ActionProposal { 相位序列：重心转移 → 迈步/摆手/下蹲/起身 → 落定；时长；预算 }` | 迈步前重心转移；Maki & McIlroy 1997 |

- **摔倒预警是伺服层**：它自带闭环、每拍连续工作（不是越界才响的报警灯），
  但输出只是**连续修正提案**，**不直接执行**；
- **动作提案系统（原迈步系统）**：**不只是迈步**——你让它做的所有动作都由它提案；
  **迈步之前先出"重心转移相位"**（comTrack / 重心偏移目标），再出落足点与摆动腿
  轨道；它同样只提案、不执行；
- ★ **两者都只是提案，控制层是唯一执行者**：两种提案**可以同拍联合执行**，
  控制层只做**冲突消解**，尽可能保证不打架：
  · **分工**：伺服修正常作用在 CoM/CoP/踝-髋，动作提案作用在轨迹/摆动腿——
    不同轴就直接并行；
  · **融合**：同轴时按增量叠加（伺服修正叠加在动作轨迹上），各自限幅；
  · **让位**：同轴反向冲突超过阈值时按紧迫度裁定（安全优先，或动作降权/暂缓
    该轴），并把冲突记入 `decision.conflicts`；
  · 设计目标只有一个：**不打架**，而不是"不许同时执行"；
- 意图层可以禁止某类动作，但**不能关掉稳定性伺服**（安全提案常开；调试用
  `mode='direct'` 才能旁路，且执行层限额仍在）。

**关于状态机（用户定调）**：v1 的**全局**步态状态机取消——它搬进**动作提案系统
内部**，作为该系统的**相位编排器**，指挥迈步（重心转移 → 摆动 → 落足 → 稳定），
产出 `ActionProposal`。要点：
- 状态机是动作系统的**实现细节**，不是架构的一层，也**不能直接写关节**；
- 控制层不感知它，只消费提案——所以提案可以被替换/打断/与伺服联合执行；
- 动作系统内部可以为每个动作/每个相位序列持有自己的状态机实例（或一个编排器
  管理队列），互不干扰。

**控制层最终裁定（示例策略，可调；判定顺序 = 权限顺序）**
1. 意图层约束（如 `allowStepping=false`）→ `rejected(reason='intent')`，动作提案直接作废；
2. 直控/反射正在接管 → 相关轴上的提案进入 `rejected`（记录原因）；
3. **默认联合执行**：伺服修正作用在稳定轴、动作提案作用在其相位轴——互不冲突就并行，
   互不等待；
4. **同轴冲突 → 逐轴消解**：紧迫度低的一方让位/降权。例：`level=2` 且踝/髋不可行
   （且意图允许）时放行 `ActionProposal`（先重心转移、再迈步），伺服只保留
   该动作轴上的安全兜底；冲突记入 `decision.conflicts`；
5. 裁定结果全部可回读（`decision.accepted/rejected/conflicts`），探针据此打分。

两个系统**不得**绕过控制层直接调用 `Drive/Executor`；物理层只认控制层发布的命令。

### 3.5 动作程序层（MotorProgram，"不必输出详细关节指令"）

分工：**动作提案系统负责"怎么动"**（把意图展开成相位序列，含重心转移等预备相位）；
**本层负责执行"被裁定采纳"的提案**——把相位展开为协同/任务目标，交给平衡/反射/
姿势解算出关节命令。动作 = **闭环控制器**，不是关键帧；对外只有名字与参数。

```ts
interface MotorProgram {
  id: string;
  duration: number;
  start(ctx, params): void;
  step(dt, ctx): ProgramOutput;   // { comTrack?, poseGoals?, synergy?, done }
  abort(): void;
}
```

- **协同（synergy）**：动作给 1~3 个协同通道（如"前屈链""左腿抬起链"），
  由固定权重映射到关节目标/激活 —— 这就是"不输出 44 轴细节"的实现方式。
  依据：d'Avella 2003、Ting & Macpherson 2005（姿势/动作由少量肌肉协同构成）。
- 首批程序：`stand`（重置到静姿）、`bow`（已验证）、`weightShift(side)`、
  `liftLeg(side)`（单腿站立）、`recover(perturb)`（髋策略+可选步）。
- 程序之间可**打断/串联**；被反射打断是正常语义（保护优先）。

### 3.6 控制模块的职责边界（只有四件事）与仲裁

用户定调：**控制模块只做四件事**——

1. **接受命令**（意图层/游戏/直控通道的输入）；
2. **整合两提案**（摔倒预警伺服提案 + 动作提案）；
3. **反射**（垫脚等固定回路；恢复策略/保护程序是反射的延伸，输出同样进整合）；
4. **直接操作关节**（唯一写关节命令的地方，经 Executor）。

不在这四件事里的一律**不属于控制模块**：平衡算法、垫脚执行器、保护程序、
动作程序都是"**产出方**"，它们的输出作为输入进控制模块的整合；
控制模块自己不发明动作，只做"收进来 → 逐轴整合 → 发出去"。

```
意图层 ─命令─┐
预警伺服 ────┤
动作提案 ────┼─→ 【控制模块】收命令 / 整合 / 反射 / 发关节命令 ─→ Executor
反射产出 ────┤
直控 ───────┘
```

**模块归属（和 §3.3 模块地图对应）**

| 属于控制模块（`control.ts` 唯一裁定） | 属于产出方（其输出进整合） |
|---|---|
| 收命令（`manual.ts` 的直控入口 + `pin()` 仲裁标记） | 摔倒预警提案（`stability.ts`） |
| 整合/冲突消解（`control.ts` 的四件事循环） | 垫脚执行器（`footPad.ts`）、伺服执行方（`leanReflex.ts`） |
| 反射登记与运行 | 恢复策略选择器（`reflex.ts`） |
| 唯一写手（`executor/drive`） | 保护程序（`fallGuard.ts`）、动作层（`actionSystem/program/actions.ts`） |


**提案是输入，不占执行优先级**：摔倒预警（每拍连续修正提案）与动作提案系统
（事件提案，含重心转移相位）全部进控制层裁定器；裁定结果决定各提案的
**并行 / 融合 / 让位**方式——**默认联合执行，逐轴消解冲突**。

**整合规则（用户定调：反射也要进整合，不只是直接抢关节）**

- **所有输出都进同一个整合器**：预警提案（含反射用法）、动作提案（迈步/动作）、
  直控命令、姿势基线——没有谁能绕过整合器直接写关节；
- **反射与动作提案一起整合**，只是**反射的优先级通常更高**（安全 > 任务）；
- **逐轴消解**：不冲突的轴**联合执行**（典型：反射占支撑腿/CoP 轴，动作提案占
  摆动腿/轨迹轴，同拍并行）；同轴冲突才按优先级让位，并记入 `decision.conflicts`；
- **动作可钉住自由度**：`ManualControl.pin()`——被动作钉住的轴，反射执行方跳过
  （实测：单脚抬腿侧髋必须钉住外摆，否则脚越中线、支撑多边形全偏、回中必倒）；
- 直控仍然最高（调试/游戏特殊），但正常运行时也只是一个输入。

| 优先级 | 来源 | 作用方式 |
|---|---|---|
| 1（最高） | 直控通道（手动/调试/游戏特殊） | 直接写目标/力矩；覆盖同轴其他来源 |
| 2 | **反射执行**（垫脚等，经整合器） | 力矩/CoP 增量；通常高于动作提案，但不绕过整合 |
| 3 | 平衡策略（+ 裁定采纳的稳定性修正） | CoP/姿态目标；接管踝/髋 |
| 4 | **动作提案（仅裁定放行后，含重心转移相位）** | 只拥有被放行动作涉及的轴（如摆动腿链） |
| 5 | 动作程序 | 任务目标/协同（姿势/关节目标） |
| 6（基线） | 姿势张力 | 未被占用的轴回零位 |

**逐轴示例**：迈步放行后——反射/平衡管支撑腿与 CoP，动作提案管摆动腿与落足，
两者**同时执行互不打架**；只有当摆动腿轴被反射紧急征用（如屈曲回撤）时才让位。

### 3.7 控制层一拍到底干什么（可执行的心智模型）

**每物理步（1/240s）固定五段；除了第 4 段，任何模块都不许碰关节：**

```
1. Sense    Sensors.update(dt)
            → { com, comVel, 双脚 Fz/CoP, 支撑状态(both/l/r/none), 躯干姿态, 关节态 }

2. Propose  各来源只算"想要的"，不写关节：
            · balance  : 重力补偿 + 姿势张力 + CoM/踝修正（`stability.ts` propose/contributeBaseline）
            · reflex   : 力矩增量（可带感觉延迟）
            · program  : 当前相位的任务目标/协同（动作提案的执行侧）
            · servo    : StabilityCorrection（摔倒预警，连续提案）
            · direct   : 直控覆盖表（setAngle/setTorque/setActivation）

3. Decide   Arbiter.resolve(s, proposals)
            → 逐轴：一个主来源 + 增量叠加 + 冲突记录
            → 联合执行是默认；同轴反向冲突才让位

4. Write    apply(cmd) —— 唯一写点：只经 Drive/Executor（τmax/限位/账本）

5. Report   decision/status 回读（UI/探针）
```

```ts
step(dt: number): void {
  const s = this.sensors.update(dt);
  const p = {
    balance: this.balance.compute(s, dt),
    reflex:  this.reflexes.compute(s, dt),
    program: this.programs.compute(s, dt),
    servo:   this.servo.compute(s, dt),
    direct:  this.direct.compute(s, dt),
  };
  const cmd = this.arbiter.resolve(s, p);   // 逐轴主来源 + 增量 + 冲突
  this.apply(cmd);                          // 唯一写点（Drive/Executor）
  this.decision = cmd.decision;             // accepted/conflicts 回读
}
```

**分模块落地顺序（每步都能单独验收，且不破坏现有回归）：**

| 模块 | 文件 | 内容 | 回归 |
|---|---|---|---|
| M1 Sensors | `core/sensors.ts` | 状态估计（com/CoP/支撑/姿态），零控制逻辑 | ✅ 已完成 |
| M2 Arbiter | `core/control.ts`（原计划独立成文件） | 逐轴优先级 + 增量叠加 + 冲突记录（四件事循环） | ✅ 已完成 |
| M3 BalanceCore | `core/stability.ts` | 重力补偿/姿势张力/踝策略改成"提案"（`contributeBaseline` + `propose`） | ✅ 已完成 |
| M4 ReflexArc | `core/reflex.ts` + `leanReflex.ts` + `footPad.ts` | 垫脚已入；牵张/负载/翻正 + 延迟 + 消融开关 | 🟡 部分（垫脚 + lean/bend 已入） |
| M5 ActionSystem | `core/actionSystem.ts` | 相位机 + 动作库（鞠躬/单脚/蹬地挺腰） | ✅ 已完成（A–D） |
| M6 StabilityServo | `core/stability.ts` | 摔倒预警：连续提案 + 反射用法 + 幅度预算（§6.1） | ✅ 基础版（TTB/迈步后置） |
| M7 Mode/Direct | `core/control.ts` + `main.ts` | 直控通道、decision 回读、UI 按钮 | 🟡 direct 模式/decision 回读待补 |

### 3.8 跌倒全权处理（保护反射 → 起身 → 恢复任务）

用户定调：**通用反射先只写"执行方"，提案方后置**；优先保证每个反射动作
单独测对。快跌倒时的保护动作也要做——**绷直身子、转移重心、跪下脚撑地**；
此时反射层**全权处理跌倒**（可中断迈步/动作提案），处理完再恢复之前的任务。

| 保护反射 | 动作（执行方） | 状态 |
|---|---|---|
| 绷直身子 | 全关节锁在当前角 + 高刚度（共收缩），减小落地冲击姿态崩溃 | 实现 |
| 转移重心 | CoM 目标移到支撑脚（配合垫脚），把倒的方向"让"给安全侧 | 实现 |
| 跪下/脚撑地 | 髋屈+膝屈序列，主动降到跪姿，脚/小腿撑地代替脸着地 | 实现 |
| 起身 | 从跪/卧回到站立（后置） | 占位 |
| 恢复任务 | 跌倒处理结束 → 还原 CoM 目标/任务上下文，迈步层继续 | 实现（上下文存取） |

**全权语义**：`FallGuard.takeOver()` 后，平衡/垫脚/动作提案让位（不与其并行），
由保护反射独占执行；`release()` 恢复保存的任务上下文（CoM 目标等）。
依据：Maki & McIlroy 1997（change-in-support 含上肢/躯干支撑）；
Cheng 2015（恢复策略统一框架）。

### 3.9 垫脚（FootPad）—— 平衡的第一执行器（本阶段重点）

用户定调：**平衡/预警最主要的机制是垫脚；垫脚做得好，80% 的情况根本不会倒。**
柔性足（arch/mfoot）支持侧向发力 ⇒ **前后左右四向、左右脚都要写**。

| 方向 | 执行器 | 行程/权限 |
|---|---|---|
| 前（趾侧） | 踝跖屈 `foot_*/2`（+） | CoP 前移 ~14cm（趾侧） |
| 后（跟侧） | 踝背屈 `foot_*/2`（−） | CoP 后移 ~5cm（跟侧） |
| 内（内侧） | 踝内翻 `foot_*/0` + **柔性足旋前**（`arch_*/0` 引擎电机目标） | CoP 内移 ~3.5cm + 弓踩实再 +~1.3cm |
| 外（外侧） | 踝外翻 `foot_*/0` + **柔性足旋后** | 对称 |

- 每只脚一块独立的垫脚执行器：输入 = 该脚 **CoP 目标**（由平衡/反射给出）、
  该脚 Fz、当前 CoP；输出 = 力矩/目标（经提案 → 控制层裁定）；
- **腾空脚自动禁用**（Fz≈0 不垫脚）；
- **驱动方式（2026-10 定型）**：预警提案的 `pad` directive（每拍连续）→ 控制模块
  按要求跑 `FootPad` 四向。反射弧直触路径（不经预警、脊髓级快环）为后续项——
  人类快摔时靠的就是这类脊髓反应，不是算出来的；
- **实测定型**：侧向限幅 copSide=0.02、翻力矩×0.6、aZ 死区 0.25、CoP 目标速率 0.6m/s
  （收敛 3–4Hz 脚部极限环：脚角速 10–13 → 0.03 rad/s）。

### 3.10 通用恢复反射（分级 + 放弃，用户定调）

用户定调：**写通用反射策略，快摔倒时按情况调用；救不过来就算了。**
平地垫脚能解决 80% 的问题；复杂的补救策略不做。

| 级 | 策略 | 触发（阈值，带滞回/锁存） | 执行 |
|---|---|---|---|
| 0 | **垫脚**（默认） | CoP 需求在足底可达范围内 | `FootPad` 四向（踝屈伸 + 内外翻 + 柔性足） |
| 1 | 髋策略 | 垫脚饱和（CoP 持续顶到足缘）且 XcoM 仍在界内 | 髋/脊柱/摆臂（`leanReflex.ts`，位置式+限速；幅度预算 §6.1） |
| 2 | 保护性迈步 | XcoM 出支撑 | 生成 `StepProposal`（**后置占位**，当前直接跳到 3） |
| 3 | **放弃** | XCoM 超出可救界 | 卸力、任其倒地（不挣扎，避免更糟的乱甩） |

规则：
- **单模式，不并行**：同一时刻只有一个恢复级在出力（垫脚/髋/放弃互斥，防打架）；
- **升级锁存**：一旦升到髋/放弃，在"恢复条件"（XcoM 回界 + 需求回落）持续一段时间前不降级；
- 所有阈值可回读（`mode` + 触发原因），探针据此打分。

依据：Micheau 2003（踝策略 λ 模型）；Bayón 2020（动量法预测人类恢复策略，DOI
10.1109/tnsre.2020.3005455）；Cheng 2015（统一恢复策略，DOI
10.1016/j.humov.2015.10.001）；Pratt 2006 / Maki & McIlroy 1997（迈步）。

### 3.11 文献里的控制层是怎么设计的（对照与取舍）

| 范式 | 代表文献 | 机理 | 优点 | 代价 | 我们放在哪 |
|---|---|---|---|---|---|
| 神经肌肉 / 反射 | Geyer & Herr 2010；Song & Geyer 2015；Nashner 1976 | 一组**局部状态反馈律 + 传导延迟**，不做轨迹/优化 | 鲁棒、可解释、天然"封装"（正是你说的反射弧） | 参数多、难以精细调控 | **反射弧层**（默认通道） |
| 层级全身控制 | Sentis & Khatib 2005；Escande/Mansard/Wieber 2014 | 优先级任务栈 → 每步解 QP/HQP，输出关节命令 | 精确、多任务、可加约束 | 依赖模型/求解器/算力 | **精细通道后端**（可选） |
| 预测 / 推恢复 | Pratt 2006；Hof 2005；Shafiee-Ashtiani 2016 | XcoM/Capture Point、MPC 滚动时域 | 抓住"要倒"的本质，判据清晰 | 需状态估计 | **摔倒预警系统**（独立，提交评估） |
| 肌肉协同 / 降维 | d'Avella 2003；Ting & Macpherson 2004 | 少量协同基向量组合出动作 | 动作封装、参数少 | 覆盖率有限 | **动作程序层** |
| 学习 / 最优反馈 | Todorov & Jordan 2002；Kawato 1987；Hwangbo 2019 | 策略网络 / 内模，延迟反馈下最优 | 可达人类级性能 | 训练与验证成本 | **精细通道后端**（可选） |
| 节律 / CPG | Ijspeert 2008 | 相位振荡器产生节律 | 步态节律自然 | 后续 | 程序层相位（未来） |

**综合结论（本项目的双通道设计）**：文献里"反射派"（A）与"模型/优化派"（B/C/D）各有不可替代的
场景，所以控制层不做二选一，而是**两条并行通道 + 逐轴仲裁**：

```
感知 ──┬─▶ 反射弧通道（默认）：ReflexArc ─ 力矩增量 ─────────────┐
       │     可逐条开关 / 延迟置零 / 整层旁路                      │
       └─▶ 精细通道（可选）：程序 / 脚本 / HQP / 学习策略 ─ 关节级命令 ─┤
                                                                    ▼
                                                     逐轴仲裁 ─▶ Executor（τmax/限位/账本）
```

- `mode='reflex'`：默认，反射弧主导；动作程序只给目标；
- `mode='assist'`：反射弧退为安全保底（只处理越界/失稳），精细通道主导；
- `mode='direct'`：**完全绕过反射弧**，命令直通执行层（精细调控、消融对照、
  接未来任何控制器后端）；执行层的 τmax/限位/账本仍然生效（不可绕过）。

- 所有来源最终走 **Executor**（求和 → 单点饱和 → 每自由度每步一次施加）；
- 任何来源都不能绕过执行层的 τmax/限位/账本。

### 3.12 落地消力（Landing absorption，2026-10 用户提出）

用户定调（原话整理）：**伺服提案和反射弧都不行**；缺的是"**屈膝再直起来**"这种
消力机制——以**脚**为单位，不管哪只脚从高处落下都要**先弯曲**，**按力的大小弯不同**，
然后再挺直。**做进反射弧，但处理成函数**：根据脚的力大小，自动算该弯多少、再回伸多少。

**论文里是怎么实现的（三条线）**

| 路线 | 代表 | 机制 |
|---|---|---|
| 神经肌肉/反射 | Geyer & Herr 2010（已引）；Song & Geyer 2015 | 伸肌**正力反馈**（地面反力越大→伸肌激活越大）+ 肌肉**力-速关系（离心制动）与阻尼项**——触地瞬态由反射+肌肉本征特性吸收，不靠"算" |
| 腿弹簧（SLIP） | Blickhan 1989；McMahon & Cheng 1990 | 腿 = 弹簧-阻尼：`F_leg = k(l₀−l) − b·l̇`，落地即压缩；刚度随落地速度/高度增大；回弹无过冲 |
| 人类落地实测 | McNitt-Gray 1993；Zhang et al. 2000；Devita & Skelly 1992 | **膝关节是消能主角**（占比最大），屈膝幅度随落差/冲击速度单调增大；髋/踝分工配角；预激活（落地前伸肌绷紧）降低冲击 |

机器人侧的等价物：Raibert 1986 弹簧腿/腿长伺服、VMC 虚拟腿弹簧-阻尼（Pratt 1997）、
阻抗控制（Hogan 1985）——工程上都是"**力越大，退让（压缩）越多，然后弹回**"。

**我们的实现（`landingAbsorb.ts`，连续力反馈的反射弧，2026-10 实测定型）**

- **粒度**：以脚为单位（per-foot）。任意一脚都连续读该腿法向力 F（脚 Fz 为代理），
  不需要"落地事件"才能工作；
- **连续目标**（主力：**膝受力大就弯**）：
  `depthTgt = perFz·max(0, F/W − fz0) + perV·vImp·e^(−t/0.15)`
  · `fz0 = 2.0W`——超过两倍体重的负载才退让（单脚站立静载 ~1.0W、双支撑 ~0.5W
    都不弯；实测 1.5W 会让转移中的支撑腿闪弯、时序崩坏）；
  · `vImp` 是**触地边沿一次性捕捉的冲击速度**（触地前滑窗最小 vy；要求先"真腾空"
    `airT ≥ 0.08s` 且冲击 ≥0.15 m/s——防抬腿蹭地误触发）；
- **相位**：`depth` 以 `riseRate=16 rad/s` 追赶目标（冲击要快），力退后按
  `reboundTau=0.18s` 指数回伸、不过冲；`maxDepth=0.6 rad` 防跪；
- **联动**：膝为主，髋 `+0.35·depth`（屈）、踝 `−0.18·depth`（**背屈**——正号是跖屈，
  压缩时会把脚趾踩进地面，实测峰值力反升）；被动作 `pin` 的自由度跳过；
  depth≈0 时 `clearAngle` 交还关节；
- **与动作的仲裁（实测必需）**：单脚动作在**抬腿/保持期钉住摆动腿屈伸轴**
  （`pin`），落腿时解钉交给消力——否则反射会把抬腿膝目标 −0.75 抢成 −0.2，
  腿被拉直、动作崩坏。

**探针验证（`_probe-landing`，单脚从两个落高放下，消力开/关对照）**

| 落点 | 峰值力（关→开） | 膝最深屈（关→开） | 回伸残差 |
|---|---|---|---|
| 低落（0.5s 慢放） | 32% → **21% W** | −0.06（轻） | ~0 ✓ |
| 高落（0.2s 快放） | 64% → **59% W** | −0.15 → **−0.47**（随落高单调加深） | ~0 ✓ |

（注：消力"开"的窗末胸高略低于"关"——那是被吸收的冲击换来的下沉。）

**触发与优先级（2026-10 定）**

- **不是"有提案就执行"，也不是电平触发**：连续力反馈本身有 `fz0=2.0W` 的死区
  （站着不动不会弯）；冲击速度项必须"真腾空 + 超阈"才启动（防抬腿蹭地）；
- **优先级 = 反射层（安全类，与垫脚同层），但轴级归属**：只拿**落地腿的
  膝/髋/踝屈伸轴**；垫脚拿 CoP 轴（踝内外翻/足底滚动）——轴正交，可并行；
  直控仍压它；被动作 `pin` 的轴跳过；`fallGuard` 全权时让位；
- **不需要提案**：自触发、自计算（函数 + 最小状态）；出口仍过整合器
  （不绕过），与其它反射/提案逐轴合并；预警若想表达"怎么用"可以带
  `landing` directive 作为**可选**的叠加输入，但缺它照常工作。

**验收判据**：探针从不同高度落单脚——屈膝量随冲击力**单调**；回伸无残余振荡；
落地峰值力相比无消力对照**下降**。

## §6.1 伺服 v2→v4 演进（历史；**当前设计见 `保护预警与反射弧.md` §2**）

> ⚠ 本节记录 v2/v3 的幅度预算演进（planLateral/boost 已随差动加载上线而删除）。
> **当前实现**：侧向 = 差动加载（负载差力环）+ 单支撑门控姿态；矢状 = 垫脚 + bend；
> 目标守护（限幅/限速/回正）在伺服内实现。完整 v4 见设计文档 §2。

**需求**（含动量，替代粗糙 PD；Hof XCoM）：
`q = 目标 − (CoM + v/ω₀)`，`ω₀ = √(g/h_CoM)`。

**幅度分配**（每级饱和则余量传给下一级；Pai & Patton 1997 的"可恢复幅度"
思想——需求超出全部预算时升 level，未来接"迈步提案"）：

|---|---|---|---|

| 髋 | 外展（骨盆） | ≈1.2 rad/m | 0.35 rad |
| 脊柱 | 侧屈/屈伸 | ≈0.27 m/rad·段 | 0.15 rad/段 |
| 摆臂 | 肩水平/前后 | ≈0.0675 m/rad（双肩 0.8 rad → 5.4cm） | 1.0 rad |

**矢状 `bend` 保持力矩式**（位置式会抢动作的屈伸通道，实测把鞠躬/蹬地压没）。

- **去高频反复（用户实测抱怨）**：原始 Fz 逐帧抖 ±30%，硬阈值 0.6 会让辅助
  **每秒切换数次**（腰/肩来回摆）→ 现已：脚力低通 + 线性渐变 + 释放速率降为 1.5 rad/s；
  回读确认轨迹变为 0.1–0.3s 的平滑漂移；

  结束/中止解钉；单脚"回中"结束也解钉（否则后续动作只剩单侧髋可用）；
- ⚠ **已知敏感性**：单脚 D 对腰部参数是刀刃级敏感（`_probe-d-sweep` 扫 12 组仅
  `腰增益2.0+臂0.3` 通过）——当前默认即该组合；要真正稳健需重设单脚保持律
  （如把 CoM 目标放松到 CoP 走廊内而不是脚心），属下一步。

**★ 横向自激（共振）——2026-10 实测头号坑（`_probe-lateral-resonance`）**：
- 现象：横向冲量（0.4 m/s）后摆动包络**指数增长**（8cm→130cm→摔倒）；
  小信号（2cm）也长——是线性不稳定，不是饱和；
- 机理：髋策略**非最小相位**（移 CoM 先反冲骨盆）+ 传感（comVel 低通 100ms）/
  执行（速率限幅）延迟 → ~1Hz 以上相位反转，修正变泵；负载 boost 随摆幅调制
  会加剧；垫脚单独（lean 关）衰减稳定；
- 修法（历史方案，见 5cb 提交；**当前树以"boost 直接关闭"解决**——实测
  `leanBoostSpineGain/ArmBias=0` 时 0.4 冲量包络 **0.061→0.025 衰减稳定**）：
  `leanGain` 环路增益旋钮（当时扫描 1.0/0.7/0.5 全放大、0.35 衰减）+
  boost 滞回锁存 + 动作有意搬移期间临时抬到 1.0（作为对照保留）；
- 副作用（正当的方向）：C 蹬地挺腰从 1.6cm 边缘 → **7.4cm 生效**（此前也是被横向环拖累）；
- **前后对比（`_probe-x-resonance`）**：前后**无小信号共振**——0.2 m/s 冲量下
  完整/bend关/lean关全部衰减✓，**关掉垫脚才放大**（57→116cm）⇒ 前后稳的主通道
  就是踝 CoP（±14cm，最小相位+阻尼环）；0.4 m/s 会倒是**物理边界**（XCoM≈13cm≈趾缘，
  Pai & Patton 的可恢复幅度），不是自激。竖向触地回弹是腿伺服欠阻尼弹簧（能量返还），
  力传递正常，kd 0.02→0.05·τmax 后减半；
- 纪律：**一切侧向/平衡新特性必须过 `_probe-lateral-resonance`（0.4 冲量衰减）**，
  单脚 D 的历史"通过"多为刀刃运气，不再作为稳定依据。

**★ 侧向力"传不到地里"的机理（2026-10，`_probe-inv`）+ 下一专项**：
- 侧向 CoP 被钳 ±2cm ⇒ 踝侧向对地力矩只有 `0.6·Fz·0.02 ≈ 8 N·m`（髋通道 120 的 6%）
  ——这是左右平衡被迫依赖非最小相位髋策略的**根因**；
- 放开到 ±10cm 的实测：**脚内部持续自转**（稳定态 |ω|=2.7 rad/s 而脚角不动；
  全开 |ω| 峰值 25 rad/s、脚角 0.65 rad），黏性阻尼（4/10 N·m·s/rad）不但无效反而更糟
  ⇒ 内力矩没有变成对地滚转/CoP，而是变成踝多环链的内部自转（疑似环轴向/限位/回读
  在链内 wrap 或与 arch 引擎电机耦合）——**力矩在脚里打转，没到地上**；
- 结论：踝侧向是左右平衡的执行层**根瓶颈**，值得单独立项：把内外翻环隔离验证
  （轴、限位、角回读、与 arch 的耦合），修好后左右可以走**最小相位踝通道**，
  髋策略只需低增益兜底。

**单脚 D 现状（2026-10）**：稳定增益下"重心转移"能完成或安全放弃；保持相还存在
摆动脚拖地/CoM 漂到支撑脚外的问题（待重做：静态保持律 + CoP 走廊内目标）。

### 6.3 伺服层设计的文献对照（2026-10 查证）

**我们的伺服层 = 意图/动作发起 + 伺服补偿扰动 + 反射调用 + 目标守护（限幅/回正）。**
文献里最贴的设计范本：

| 设计问题 | 文献方案 | 对我们的映射 |
|---|---|---|
| 意图 vs 扰动的分工 | **Mergner & Lippi 2018（DEC）**：神经系统"估计扰动量并补偿"，主运动由意图发起 | 与"主动侧移/单支撑是动作的、补偿归伺服"**完全同构**——我们的 governor 就是简化的 DEC |
| 传感器如何进伺服 | **van der Kooij 1999**：多感觉加权整合（本体/前庭） | 我们的 CoM/CoP/Fz 估计是雏形；未来加本体-前庭式权重 |
| 精确指令怎么生成 | **Kajita 2003（ZMP 预览控制）**：LIPM 前馈轨迹（CoM/ZMP）+ 反馈稳定，伺服层"预知未来" | 动作给粗目标，伺服把它转成可行的 CoP/CoM 指令（我们目前是纯反馈，预览=未来项） |
| 策略怎么分级触发 | **Stephens 2007**：踝→髋→步 的推恢复层级 | 与反射分级（pad→hip→step/giveup）同源 |
| "力传地面"怎么控 | **Ott et al. 2011**：把接触力作为优化变量做全身姿态平衡 | 差动加载的推广形态（接触力即控制量） |
| 全身伺服的被控对象 | **Orin/Goswami/Lee 2013**：质心动量（centroidal momentum） | CoM/XCoM 层的一般化 |
| 延迟下的增益 | Peterka 2002 / Kuo 1995（已引） | 增益必须尊重延迟（我们实测的相位泵教训） |
| 两层可行化怎么分 | **Sentis & Khatib 2005**（分层全身控制） | 动作=任务层、伺服=稳定性层，**分开实现**（§2.4） |
| 目标守护的文献形态 | **Garone 2017**（参考调速器）/ **Ames 2019**（CBF） | 静默钳制/安全包络 = reference governor 思想 |
| 保护程序设计依据 | **Robinovitch 2013**（真实跌倒观测） | 手撑/屈膝是降低伤害的优势动作（B/C 相） |

**结论**：我们的伺服层结构与文献主线一致（DEC 分工 + 层级策略 + CoM/CoP 反馈）；
差距在（a）**预览/前馈**（Kajita）未做、（b）**接触力级优化**（Ott）未做、
（c）传感器整合（van der Kooij）只有单通道估计。三项都在"伺服层"范围内，按优先级排。
**★ 伺服层架构 v4 已按文献升级，完整版见 `保护预警与反射弧.md` §2.8**
（五段处理链：可行化→扰动补偿→目标守护→反射调用→指令输出；含差距清单）。

### 6.4 抖动彻查结论（2026-10，最高优先级事件的收编）

**回归定位（逐提交二分）**：静站 HF 与挺腰 HF 在**最后一次提交**（5cb22a85）从

（`B·dt/M_uu < 2`），产生 ~80–100Hz 全身微振。

**根修与有效手段（实测排序）**：
1. **回退到干净版 8f7e**（撤销 5cb 的 src；kd 回到 0.02）；
2. **arch 引擎 220/40**（刚度/阻尼共振相消点）：arch 体 HF 18→4.9、挺腰 297→153；

4. **关闭侧移 boost**（`leanBoostSpineGain/ArmBias=0`）：boost 是横向环的参数泵
   （0.4 冲量下增长 1.28；关掉后 0.025 衰减）。

**最终读数（差动加载上线后）**：站立 HF **2.5e-5**、挺腰 HF **13.7**、
横向冲量衰减、单支撑保持（直控验收胸 1.404）、A/B ✓、（C/D 待 480Hz 重标/姿势修正）。

**失败清单（教训，勿重蹈）**：隐式 PD / 隐式阻尼 / HF 阻尼器 / 关节刹车 /
世界翻转吸收——五类"新增反馈或速度改写式耗散"全部把驱动环搞崩。
**耗散只能来自既有稳定通道**（kd 上限、引擎参数、频率余量），
或**前馈**（输入整形/指令滤波）。

**定性（用户问"抖动是否已到控制算法可弥补的程度"）**：是。剩余抖动为**有界极限环**

输入整形/notch（Singer & Seering，避开模态）与指令域平滑，不动反馈环。

**性能（`_perf-final`，本机 Node）**：240Hz 全控 1.61ms/步（实时 2.6×、60fps 6.4ms/帧）；
480Hz 全控 2.4ms/步（实时 0.85×、60fps 19ms/帧）。封装建议：英雄角色 480Hz 独立步进、
背景 NPC 240Hz；求解器 16/8/32 是承重墙（4/2/0 直接站不住）。

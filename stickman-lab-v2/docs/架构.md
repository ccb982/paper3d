# stickman-lab-v2 架构

> 目的：产出**能站住、能被高层动作驱动**的物理火柴人，作为隐藏 boss 移植回本体游戏。
> 本文是唯一真源。v1（`../stickman-lab/`）冻结留档，只作对照与素材来源。
>
> 2026-10 重写：执行层已完成并验收；本文同时给出**控制层**（执行层之上封装的一层）
> 的架构设计。控制层是唯一发布关节执行命令的地方，并且可以被直接操控。

## §1 总分层（自下而上）

```
┌────────────────────────────────────────────────────────────────────┐
│ 意图层（游戏 / AI / 玩家输入）—— 最高层                              │
│   · 目标与剧情：play("bow") / 攻击 / 受击 / 情绪 / 不许移动           │
└───────────────────────────────┬────────────────────────────────────┘
                                │ 目标 + 约束
┌───────────────────────────────▼────────────────────────────────────┐
│ 动作提案系统（原名"迈步系统"，独立）                                 │
│   · **所有要执行的动作都由它提案**：迈步、摆手、下蹲、起身…          │
│   · **迈步之前先出"重心转移相位"**（comTrack），再出落足点           │
│   · 输出 ActionProposal（相位序列 + 时长 + 预算），只提案不执行      │
└───────────────────────────────┬────────────────────────────────────┘
                                │ ActionProposal
┌───────────────────────────────▼───────────────┐   ┌──────────────────────────────┐
│ 控制层 ControlLayer（唯一裁定者 + 发布者）     │◀──│ 摔倒预警（独立 · 常开伺服层） │
│   · 多传感估计 / 反射弧 / 平衡策略             │   │ 每拍连续出 StabilityCorrection│
│   · 动作程序（执行**被裁定采纳**的提案）        │   │ 提案（修正，不是报警灯）      │
│   · 直控通道（手动/调试）                      │   └──────────────────────────────┘
│   · 裁定：manual > reflex > balance > action > program > posture   │
└───────────────────────────────┬────────────────────────────────────┘
                                ▼ 关节命令（经 Executor）
```

**边界纪律**：
- 执行层只认"每自由度力矩/激活/角目标"，不认任何动作语义；
- **意图层最高**：游戏/AI 的意图在动作提案系统**之前**生效（可禁止/改写任何动作
  请求，如剧情要求"原地受击"）；
- **动作提案系统（原"迈步系统"）**：**所有要执行的动作都由它提案**——迈步、摆手、
  下蹲、起身…，且**迈步之前先出"重心转移相位"**；只出 `ActionProposal`，不写关节；
- **摔倒预警是常开伺服层**：每拍连续出 `StabilityCorrection` 提案，也不写关节；
- 两路提案都进控制层**唯一执行裁定**（可同拍联合执行、逐轴消解冲突），向下只写 Executor
  （账本、τmax、限位由执行层保证）；
- 控制层向上暴露**动作名 + 参数**（`play/abort/status`）与**直控通道**
  （`setAngle/setTorque/setActivation`）。

**两种"优先"不要混淆**（后面仲裁表按此执行）：
- **决策权**（谁定目标与约束）：`意图层 > 控制层判定`；
- **执行优先级**（同一根轴冲突时谁覆盖）：`直控 > 反射 > 平衡 > …`。

## §2 执行层（已建成）

| 模块 | 职责 | 关键设计 |
|---|---|---|
| `core/skeleton.ts` | 骨架数据（不改） | 18 逻辑关节 / 46 自由度、静姿态、限位、τmax |
| `core/body.ts` | 刚体 + 铰链装配 | 球窝 → 原生球铰（3 转）；revolute → 多环链（踝 = 扭+内外翻+屈伸）；柔性足 arch/mfoot 原样（引擎 ForceBased 隐式弹簧） |
| `core/executor.ts` | **唯一 τ 写入口** | 先求和→单点饱和→成对冲量；账本 `cmd/applied/limit/saturated`；每自由度每步恰好施加一次 |
| `core/drive.ts` | 命令通道 | 阻抗伺服（一步收敛护栏 α）、黏性阻尼 τ=−B·ω（显式、限幅）、限位通道（越界冲量，权限压过马达）、激活通道；默认 kd = `0.02·τmax`（反 76Hz 振铃的实测值） |
| `core/actuator.ts` | 人类式执行器 | 黏弹阻尼 + 一阶激活动力学 + Hill 力-长/力-速 |
| `core/world.ts` | 步进循环 | `updateDofState → beginStep → controller → drive → applyAll → step` |
| `core/quat.ts` | 四元数唯一实现 | 含 swing-twist 分解（球铰三轴语义） |

执行层**没有**：环境变量开关、隐藏的写 τ 路径、step 后的自研限位冲量。

★ 规划中的**被动元件**（2026-10；文献：Inman 1947 JBJS / McLeish & Charnley 1970 J Biomech /
Prior 2014 BMC SMR）：**髋外展轴的"髂胫束（IT band）"被动力矩**——内收角超过阈值后接入的
非线性被动弹簧。人类单腿站立约**一半**的髋外展力矩由 IT band 被动承担（骨盆下沉姿势臀中肌
激活 −84%、TFL −143% 却站得更稳，就是它）。
**放执行层 = 被动元件、不是控制增益**：不动任何 kp/默认分数，因此**免疫"τmax 派生增益联动"**
（硬抬 τmax 0.60→0.78 导致全局变硬 30%、A 相不收敛的根因）；大角度自动分担、小角度零干扰。
这正是"既增强支撑承载、又不破坏系统调参"的优雅落点。

**实现状态（2026-10 已落地）**：executor 新增**被动并联通道** `addPassiveTorque`——
`applied = clamp(cmd, ±τmax) + clamp(passive, ±τmax)`：**肌肉 τmax 只钳主动，被动组织另计**（与解剖一致）。
已接两条被动链：**髋 IT band**（阈 0.10 rad、k=550；实测支撑髋峰值 127 N·m > 肌肉上限 120、零饱和）
＋**腰椎胸腰筋膜**（阈 0.08 rad、k=600/节、轴0/轴2；实测脊柱峰值 118/113/110 > 上限 102）。
安静行为零回归（站立 HF 2.31e-5、挺腰 HF 29.7）。

## §3 控制层（ControlLayer）设计

### 3.0 意图层（最高层，在动作提案系统之前）

游戏/AI 的意图**先于**摔倒预警与迈步生效——它不是"另一个平衡策略"，而是
**目标与约束的来源**：

```ts
interface GameIntent {
  // 高层动作（经控制层解算关节）
  play(action: string, params?: object): void;   // 'bow' | 'attack' | 'hit' …
  // 约束（在迈步/预警之前生效）
  allowStepping(on: boolean): void;              // 剧情禁止迈步
  stance(mode: 'free' | 'rooted'): void;         // 站桩/生根
  setFacing(yawRad: number): void;
  setEmotion(tag: string): void;
}
```

- 意图只提交**目标/约束**，不写关节、不写力矩；
- 控制层裁定（§3.4）第一条就是"意图约束优先"：意图禁止某类动作时，即使动作
  提案系统提案且 level=2，也会被 `rejected(reason='intent')`；
- 意图层（决策权）与直控（执行优先级）是两件事，见 §1 的"两种优先"说明。

### 3.1 定位（用户定调）

> "摔倒预警与迈步是两个独立系统，但是都给这个控制层做最后判定。
>  这一层也允许被直接操控。"

翻译成接口：

```ts
interface ControlLayer {
  // ── 消费两个独立系统的输出（都只是提案，本层裁定）──
  ingest(c: StabilityCorrection): void;  // 摔倒预警（常开伺服层）：每拍连续修正提案
  ingest(p: ActionProposal): void;       // 动作提案系统（原迈步）：相位序列，含重心转移
  // ── 直控（最高优先级；调试/手动/游戏特殊输入）──
  setAngle(joint, axis, rad, kp?, kd?): void;
  setTorque(joint, axis, tau): void;
  setActivation(joint, axis, a): void;
  // ── 运行模式：是否走反射弧、谁主导 ──
  //   'reflex' = 反射弧主导（默认）；'assist' = 反射弧只保底、程序/直控主导；
  //   'direct' = **不走反射弧**，命令直通执行层（精细调控/消融/学习策略）
  setMode(mode: 'reflex' | 'assist' | 'direct'): void;
  readonly reflexes: {
    setEnabled(id: string, on: boolean): void;   // 逐条开关（消融）
    setLatency(id: string, s: number): void;     // 延迟可置零
  };
  // ── 动作（高层语义；内部自己解算关节）──
  play(action: string, params?: object): void;
  abort(): void;
  readonly status: { action: string | null; t: number; phase: string; decision: string };
  // ── 判定结果（回读给 UI/探针）──
  readonly decision: {
    accepted: ('stability'|'ankle'|'hip'|'action'|'program'|'manual')[];
    conflicts: { axis: string; winner: string; loser: string; reason: string }[];
    rejected: { kind: string; reason: string }[];
    xcomMargin: number; support: 'both'|'l'|'r'|'none';
  };
}
```

### 3.2 感知与状态估计（Sensors）

每物理步从 Body/Rapier 读取、滤波、延迟分发：

| 量 | 来源 | 用途 |
|---|---|---|
| CoM / CoM 速度 | `body.com/comVel`（质量加权 worldCom） | 平衡主回路 |
| 单脚 ΣFz / CoP | `body.footNormalForce` + 接触流形 | 支撑判定、踝策略 |
| 关节角/角速度/力矩 | `dof.angle/vel` + Executor 账本 | 反射与状态输出 |
| 躯干姿态/角速度 | spine4 刚体 | 翻正反射 |
| XcoM = x + ẋ/ω（ω=√(g/h)） | 计算 | 内部稳定性量（控制层判定用；预警系统另有其评估） |

参考：Peterka 2002（感觉整合 = CoM 误差的 PID + 权重）；Hof 2005（XcoM/动态稳定条件）。

### 3.3 反射层：先把三种东西分开（之前的混乱就在这）

| 类别 | 定义 | 特征 | 归属 |
|---|---|---|---|
| **反射（Reflex）** | 固定"感觉→动作"回路 | 无选择、无状态（或只有固定增益/延迟） | 本节 |
| **恢复策略（RecoveryStrategy）** | 需要分级/锁存/切换的决策 | 调用反射原语，但自己不是反射 | §3.10 |
| **保护程序（ProtectiveProgram）** | 跌倒已不可避免后的急救动作 | 有相位、全权接管 | §3.8 |

> `绷直身子` 在神经科学里可以叫"保护性反射"，但**工程上归入保护程序**
> （有触发状态、有相位、全权接管），不放进反射弧——这就是之前看起来乱的原因。

**反射原语清单（只放真正的固定回路）**

```ts
interface Reflex {
  id: string;
  latency: number;                       // s，感觉延迟（固定环形缓冲）
  update(s: Sensors, dt: number): void;  // 触发条 + 修正输出（写 Executor）
}
```

| 反射 | 生物对应 | 触发 | 输出 | 依据 |
|---|---|---|---|---|
| **垫脚（本阶段重点）** | 踝-足本体/触觉快速回路 | CoM/XcoM 误差（不等预警） | 每脚四向 CoP：踝屈伸（前后）+ 内外翻与柔性足旋前/旋后（左右） | Winter 1995 / Hof 2005；柔性足实测 |
| 牵张 | 肌梭-单突触 | 关节角误差/速度 | 刚度/阻尼调制（Actuator 已内建，暴露为原语） | Nashner 1976 |
| 负载 | 高尔基腱器官 | 支撑脚 ΣFz 骤降 | 伸肌力矩脉冲（防腿软） | Nashner 1976 |
| **落地消力（屈曲→回伸）** | 负载/着陆缓冲（离心-向心） | 单脚触地事件 + 冲击力（Fz/下降速度） | 按力大小自动计算屈曲量 → 再回伸（**函数式原语**，不锁存不选择；§3.12） | Geyer & Herr 2010（正力反馈+阻尼）；Blickhan 1989（SLIP）；Zhang et al. 2000（膝主导消能） |
| 翻正 | 前庭-脊髓 | 躯干倾角/角速度 | 脊柱/髋回正力矩 | Horak & Nashner 1986 |
| 屈曲回撤 | nociceptive | 意外碰撞/夹脚 | 快速屈腿（后续） | — |

**延迟**：每个反射有独立 `latency`（牵张 20–40ms、前庭 60–100ms、长环 100–150ms），
由环形缓冲实现；延迟可调为零做对照。依据：Todorov & Jordan 2002。

### 3.4 摔倒预警（平衡算法在这里，出提案 + 反射用法）

用户定调：**平衡模块属于预警**；**是预警提供提案，提案也包括如何使用反射弧**。
即：预警 = 稳定性的"大脑"——它算 CoM/XcoM/CoP、决定怎么修，并在提案里指定
**调用哪些反射、用什么参数**；反射弧只是它手里的工具箱。

```ts
/** 摔倒预警的提案（每拍连续输出；只读，不直接写关节） */
interface StabilityProposal {
  /** 期望 CoM 修正（世界系加速度或位移目标） */
  comAdjust: { ax: number; az: number };
  /** 期望 CoP（世界系；踝/柔性足的去处） */
  desiredCop?: { x: number; z: number };
  /** ★ 反射用法：本拍要用哪些反射、参数是什么 */
  reflexDirectives: {
    id: 'pad' | 'lean' | 'bend' | 'step' | 'brace' | 'kneel' | string;
    weight: number;                 // 权重/增益
    params?: Record<string, number>;
  }[];
  /** 等级（派生标签，给动作提案/迈步放行用） */
  level: 0 | 1 | 2;
  reason: string;
}
```

- 预警每拍更新提案：正常情况下给"垫脚"指令（`id:'pad'`，四向 CoP）；
  饱和升级时改为 `id:'lean'`（左右侧移：髋外展+脊柱侧屈+摆臂）或
  `id:'bend'`（前后弯腰，力矩式帮助）；出界则给 `id:'step'`（迈步放行用）或放弃；
  跌倒已不可避免时可给 `id:'brace'/'kneel'`（保护程序，见 §3.8）；
  **每个 directive 的幅度由"幅度预算"逐级分配**（踝→髋→脊柱→摆臂；Pai & Patton 1997
  的可恢复幅度上界；细则与标定见 §6.1）；
- 反射弧（§3.3）是**被动工具箱**：只按 directive 运行，不自己做决策；
- 控制模块（§3.6）只负责"收命令 → 整合两提案 → 按 directive 跑反射 → 写关节"。

**两个独立系统的性质不同（一个连续、一个事件；都只提案）**

| 系统 | 性质 | 输出（只读提案） | 内部依据 |
|---|---|---|---|
| 摔倒预警 | **伺服层：常开，每拍连续输出** | `StabilityCorrection { desiredCopShift, comAdjust, gainScale, level }`（连续量；level 只是派生标签） | XcoM 比支撑边距、外推时间；Pratt 2006 / Hof 2005 |
| 动作提案系统（原"迈步系统"） | **事件层：提案制，覆盖所有要执行的动作** | `ActionProposal { 相位序列：重心转移 → 迈步/摆手/下蹲/起身 → 落定；时长；预算 }` | 迈步前重心转移；Maki & McIlroy 1997 |

- **摔倒预警是伺服层**：它自带闭环、每拍连续工作（不是越界才响的报警灯），
  但输出只是**连续修正提案**，**不直接执行**；
- **动作提案系统（原迈步系统）**：**不只是迈步**——你让它做的所有动作都由它提案；
  **迈步之前先出"重心转移相位"**（comTrack / 重心偏移目标），再出落足点与摆动腿
  轨道；它同样只提案、不执行；
- ★ **两者都只是提案，控制层是唯一执行者**：两种提案**可以同拍联合执行**，
  控制层只做**冲突消解**，尽可能保证不打架：
  · **分工**：伺服修正常作用在 CoM/CoP/踝-髋，动作提案作用在轨迹/摆动腿——
    不同轴就直接并行；
  · **融合**：同轴时按增量叠加（伺服修正叠加在动作轨迹上），各自限幅；
  · **让位**：同轴反向冲突超过阈值时按紧迫度裁定（安全优先，或动作降权/暂缓
    该轴），并把冲突记入 `decision.conflicts`；
  · 设计目标只有一个：**不打架**，而不是"不许同时执行"；
- 意图层可以禁止某类动作，但**不能关掉稳定性伺服**（安全提案常开；调试用
  `mode='direct'` 才能旁路，且执行层限额仍在）。

**关于状态机（用户定调）**：v1 的**全局**步态状态机取消——它搬进**动作提案系统
内部**，作为该系统的**相位编排器**，指挥迈步（重心转移 → 摆动 → 落足 → 稳定），
产出 `ActionProposal`。要点：
- 状态机是动作系统的**实现细节**，不是架构的一层，也**不能直接写关节**；
- 控制层不感知它，只消费提案——所以提案可以被替换/打断/与伺服联合执行；
- 动作系统内部可以为每个动作/每个相位序列持有自己的状态机实例（或一个编排器
  管理队列），互不干扰。

**控制层最终裁定（示例策略，可调；判定顺序 = 权限顺序）**
1. 意图层约束（如 `allowStepping=false`）→ `rejected(reason='intent')`，动作提案直接作废；
2. 直控/反射正在接管 → 相关轴上的提案进入 `rejected`（记录原因）；
3. **默认联合执行**：伺服修正作用在稳定轴、动作提案作用在其相位轴——互不冲突就并行，
   互不等待；
4. **同轴冲突 → 逐轴消解**：紧迫度低的一方让位/降权。例：`level=2` 且踝/髋不可行
   （且意图允许）时放行 `ActionProposal`（先重心转移、再迈步），伺服只保留
   该动作轴上的安全兜底；冲突记入 `decision.conflicts`；
5. 裁定结果全部可回读（`decision.accepted/rejected/conflicts`），探针据此打分。

两个系统**不得**绕过控制层直接调用 `Drive/Executor`；物理层只认控制层发布的命令。

### 3.5 动作程序层（MotorProgram，"不必输出详细关节指令"）

分工：**动作提案系统负责"怎么动"**（把意图展开成相位序列，含重心转移等预备相位）；
**本层负责执行"被裁定采纳"的提案**——把相位展开为协同/任务目标，交给平衡/反射/
姿势解算出关节命令。动作 = **闭环控制器**，不是关键帧；对外只有名字与参数。

```ts
interface MotorProgram {
  id: string;
  duration: number;
  start(ctx, params): void;
  step(dt, ctx): ProgramOutput;   // { comTrack?, poseGoals?, synergy?, done }
  abort(): void;
}
```

- **协同（synergy）**：动作给 1~3 个协同通道（如"前屈链""左腿抬起链"），
  由固定权重映射到关节目标/激活 —— 这就是"不输出 44 轴细节"的实现方式。
  依据：d'Avella 2003、Ting & Macpherson 2005（姿势/动作由少量肌肉协同构成）。
- 首批程序：`stand`（重置到静姿）、`bow`（已验证）、`weightShift(side)`、
  `liftLeg(side)`（单腿站立）、`recover(perturb)`（髋策略+可选步）。
- 程序之间可**打断/串联**；被反射打断是正常语义（保护优先）。

### 3.6 控制模块的职责边界（只有四件事）与仲裁

用户定调：**控制模块只做四件事**——

1. **接受命令**（意图层/游戏/直控通道的输入）；
2. **整合两提案**（摔倒预警伺服提案 + 动作提案）；
3. **反射**（垫脚等固定回路；恢复策略/保护程序是反射的延伸，输出同样进整合）；
4. **直接操作关节**（唯一写关节命令的地方，经 Executor）。

不在这四件事里的一律**不属于控制模块**：平衡算法、垫脚执行器、保护程序、
动作程序都是"**产出方**"，它们的输出作为输入进控制模块的整合；
控制模块自己不发明动作，只做"收进来 → 逐轴整合 → 发出去"。

```
意图层 ─命令─┐
预警伺服 ────┤
动作提案 ────┼─→ 【控制模块】收命令 / 整合 / 反射 / 发关节命令 ─→ Executor
反射产出 ────┤
直控 ───────┘
```

**模块归属（和 §3.3 模块地图对应）**

| 属于控制模块（`control.ts` 唯一裁定） | 属于产出方（其输出进整合） |
|---|---|
| 收命令（`manual.ts` 的直控入口 + `pin()` 仲裁标记） | 摔倒预警提案（`stability.ts`） |
| 整合/冲突消解（`control.ts` 的四件事循环） | 垫脚执行器（`footPad.ts`）、伺服执行方（`leanReflex.ts`） |
| 反射登记与运行 | 恢复策略选择器（`reflex.ts`） |
| 唯一写手（`executor/drive`） | 保护动作（`step/fallProtect.ts`）、动作层（`actionSystem/program/actions.ts`） |


**提案是输入，不占执行优先级**：摔倒预警（每拍连续修正提案）与动作提案系统
（事件提案，含重心转移相位）全部进控制层裁定器；裁定结果决定各提案的
**并行 / 融合 / 让位**方式——**默认联合执行，逐轴消解冲突**。

**整合规则（用户定调：反射也要进整合，不只是直接抢关节）**

- **所有输出都进同一个整合器**：预警提案（含反射用法）、动作提案（迈步/动作）、
  直控命令、姿势基线——没有谁能绕过整合器直接写关节；
- **反射与动作提案一起整合**，只是**反射的优先级通常更高**（安全 > 任务）；
- **逐轴消解**：不冲突的轴**联合执行**（典型：反射占支撑腿/CoP 轴，动作提案占
  摆动腿/轨迹轴，同拍并行）；同轴冲突才按优先级让位，并记入 `decision.conflicts`；
- **动作可钉住自由度**：`ManualControl.pin()`——被动作钉住的轴，反射执行方跳过
  （实测：单脚抬腿侧髋必须钉住外摆，否则脚越中线、支撑多边形全偏、回中必倒）；
- 直控仍然最高（调试/游戏特殊），但正常运行时也只是一个输入。

| 优先级 | 来源 | 作用方式 |
|---|---|---|
| 1（最高） | 直控通道（手动/调试/游戏特殊） | 直接写目标/力矩；覆盖同轴其他来源 |
| 2 | **反射执行**（垫脚等，经整合器） | 力矩/CoP 增量；通常高于动作提案，但不绕过整合 |
| 3 | 平衡策略（+ 裁定采纳的稳定性修正） | CoP/姿态目标；接管踝/髋 |
| 4 | **动作提案（仅裁定放行后，含重心转移相位）** | 只拥有被放行动作涉及的轴（如摆动腿链） |
| 5 | 动作程序 | 任务目标/协同（姿势/关节目标） |
| 6（基线） | 姿势张力 | 未被占用的轴回零位 |

**逐轴示例**：迈步放行后——反射/平衡管支撑腿与 CoP，动作提案管摆动腿与落足，
两者**同时执行互不打架**；只有当摆动腿轴被反射紧急征用（如屈曲回撤）时才让位。

### 3.7 控制层一拍到底干什么（可执行的心智模型）

**每物理步（1/240s）固定五段；除了第 4 段，任何模块都不许碰关节：**

```
1. Sense    Sensors.update(dt)
            → { com, comVel, 双脚 Fz/CoP, 支撑状态(both/l/r/none), 躯干姿态, 关节态 }

2. Propose  各来源只算"想要的"，不写关节：
            · balance  : 重力补偿 + 姿势张力 + CoM/踝修正（`stability.ts` propose/contributeBaseline）
            · reflex   : 力矩增量（可带感觉延迟）
            · program  : 当前相位的任务目标/协同（动作提案的执行侧）
            · servo    : StabilityCorrection（摔倒预警，连续提案）
            · direct   : 直控覆盖表（setAngle/setTorque/setActivation）

3. Decide   Arbiter.resolve(s, proposals)
            → 逐轴：一个主来源 + 增量叠加 + 冲突记录
            → 联合执行是默认；同轴反向冲突才让位

4. Write    apply(cmd) —— 唯一写点：只经 Drive/Executor（τmax/限位/账本）

5. Report   decision/status 回读（UI/探针）
```

```ts
step(dt: number): void {
  const s = this.sensors.update(dt);
  const p = {
    balance: this.balance.compute(s, dt),
    reflex:  this.reflexes.compute(s, dt),
    program: this.programs.compute(s, dt),
    servo:   this.servo.compute(s, dt),
    direct:  this.direct.compute(s, dt),
  };
  const cmd = this.arbiter.resolve(s, p);   // 逐轴主来源 + 增量 + 冲突
  this.apply(cmd);                          // 唯一写点（Drive/Executor）
  this.decision = cmd.decision;             // accepted/conflicts 回读
}
```

**分模块落地顺序（每步都能单独验收，且不破坏现有回归）：**

| 模块 | 文件 | 内容 | 回归 |
|---|---|---|---|
| M1 Sensors | `core/sensors.ts` | 状态估计（com/CoP/支撑/姿态），零控制逻辑 | ✅ 已完成 |
| M2 Arbiter | `core/control.ts`（原计划独立成文件） | 逐轴优先级 + 增量叠加 + 冲突记录（四件事循环） | ✅ 已完成 |
| M3 BalanceCore | `core/stability.ts` | 重力补偿/姿势张力/踝策略改成"提案"（`contributeBaseline` + `propose`） | ✅ 已完成 |

### 3.8 跌倒全权处理（保护反射 → 起身 → 恢复任务）

用户定调：**通用反射先只写"执行方"，提案方后置**；优先保证每个反射动作
单独测对。快跌倒时的保护动作也要做——**绷直身子、转移重心、跪下脚撑地**；
此时反射层**全权处理跌倒**（可中断迈步/动作提案），处理完再恢复之前的任务。

| 保护反射 | 动作（执行方） | 状态 |
|---|---|---|
| 绷直身子 | 全关节锁在当前角 + 高刚度（共收缩），减小落地冲击姿态崩溃 | 实现 |
| 转移重心 | CoM 目标移到支撑脚（配合垫脚），把倒的方向"让"给安全侧 | 实现 |
| 跪下/脚撑地 | 髋屈+膝屈序列，主动降到跪姿，脚/小腿撑地代替脸着地 | 实现 |
| 起身 | 从跪/卧回到站立（后置） | 占位 |
| 恢复任务 | 跌倒处理结束 → 还原 CoM 目标/任务上下文，迈步层继续 | 实现（上下文存取） |

**★ 2026-10 架构修正（用户定调：架构要干净 / 只改伺服层提案 / Now-Future 双管道）**：
保护处理按提案制重新切开，FallGuard 不再直写：

```
① 预警（预测）= 伺服层 **Future 管道**：TTB/XCoM/risk → 提案的 level/est（唯一出口，
   与 Now 管道在整合层汇合；"坠落在预警"就是这一管道的输出）
② 保护动作（绷直/移重心/跪撑/起身/恢复）= **动作层**：注册为保护动作（相位程序，
   与其它动作同走 ActionProposal：pose/torque/com 目标 + pin，不直写关节）
③ 全权 = **控制层**的紧急裁定：收到 level=2 → 中断当前动作提案、激活保护动作
   （安全最高）；保护动作结束 → release 恢复上下文（CoM 目标/任务）
```

|---|---|---|---|
| 绷直身子 | 全关节锁角+高刚度 | 保护动作「绷直」相（非踝共收缩） | **已迁移** |
| 转移重心 | CoM 目标移到支撑脚 | 保护动作「移重心」相（comTarget） | **已迁移** |
| 跪下/脚撑地 | 髋屈+膝屈序列 | 保护动作「跪撑」相（manual 序列） | **已迁移** |

### 3.11 文献里的控制层是怎么设计的（对照与取舍）

| 范式 | 代表文献 | 机理 | 优点 | 代价 | 我们放在哪 |
|---|---|---|---|---|---|
| 神经肌肉 / 反射 | Geyer & Herr 2010；Song & Geyer 2015；Nashner 1976 | 一组**局部状态反馈律 + 传导延迟**，不做轨迹/优化 | 鲁棒、可解释、天然"封装"（正是你说的反射弧） | 参数多、难以精细调控 | **反射弧层**（默认通道） |
| 层级全身控制 | Sentis & Khatib 2005；Escande/Mansard/Wieber 2014 | 优先级任务栈 → 每步解 QP/HQP，输出关节命令 | 精确、多任务、可加约束 | 依赖模型/求解器/算力 | **精细通道后端**（可选） |
| 预测 / 推恢复 | Pratt 2006；Hof 2005；Shafiee-Ashtiani 2016 | XcoM/Capture Point、MPC 滚动时域 | 抓住"要倒"的本质，判据清晰 | 需状态估计 | **摔倒预警系统**（独立，提交评估） |
| 肌肉协同 / 降维 | d'Avella 2003；Ting & Macpherson 2004 | 少量协同基向量组合出动作 | 动作封装、参数少 | 覆盖率有限 | **动作程序层** |
| 学习 / 最优反馈 | Todorov & Jordan 2002；Kawato 1987；Hwangbo 2019 | 策略网络 / 内模，延迟反馈下最优 | 可达人类级性能 | 训练与验证成本 | **精细通道后端**（可选） |
| 节律 / CPG | Ijspeert 2008 | 相位振荡器产生节律 | 步态节律自然 | 后续 | 程序层相位（未来） |

**综合结论（本项目的双通道设计）**：文献里"反射派"（A）与"模型/优化派"（B/C/D）各有不可替代的
场景，所以控制层不做二选一，而是**两条并行通道 + 逐轴仲裁**：

```
感知 ──┬─▶ 反射弧通道（默认）：ReflexArc ─ 力矩增量 ─────────────┐
       │     可逐条开关 / 延迟置零 / 整层旁路                      │
       └─▶ 精细通道（可选）：程序 / 脚本 / HQP / 学习策略 ─ 关节级命令 ─┤
                                                                    ▼
                                                     逐轴仲裁 ─▶ Executor（τmax/限位/账本）
```

- `mode='reflex'`：默认，反射弧主导；动作程序只给目标；
- `mode='assist'`：反射弧退为安全保底（只处理越界/失稳），精细通道主导；
- `mode='direct'`：**完全绕过反射弧**，命令直通执行层（精细调控、消融对照、
  接未来任何控制器后端）；执行层的 τmax/限位/账本仍然生效（不可绕过）。

- 所有来源最终走 **Executor**（求和 → 单点饱和 → 每自由度每步一次施加）；
- 任何来源都不能绕过执行层的 τmax/限位/账本。

### 3.12 落地消力（Landing absorption，2026-10 用户提出）

用户定调（原话整理）：**伺服提案和反射弧都不行**；缺的是"**屈膝再直起来**"这种
消力机制——以**脚**为单位，不管哪只脚从高处落下都要**先弯曲**，**按力的大小弯不同**，
然后再挺直。**做进反射弧，但处理成函数**：根据脚的力大小，自动算该弯多少、再回伸多少。

**论文里是怎么实现的（三条线）**

| 路线 | 代表 | 机制 |
|---|---|---|
| 神经肌肉/反射 | Geyer & Herr 2010（已引）；Song & Geyer 2015 | 伸肌**正力反馈**（地面反力越大→伸肌激活越大）+ 肌肉**力-速关系（离心制动）与阻尼项**——触地瞬态由反射+肌肉本征特性吸收，不靠"算" |
| 腿弹簧（SLIP） | Blickhan 1989；McMahon & Cheng 1990 | 腿 = 弹簧-阻尼：`F_leg = k(l₀−l) − b·l̇`，落地即压缩；刚度随落地速度/高度增大；回弹无过冲 |
| 人类落地实测 | McNitt-Gray 1993；Zhang et al. 2000；Devita & Skelly 1992 | **膝关节是消能主角**（占比最大），屈膝幅度随落差/冲击速度单调增大；髋/踝分工配角；预激活（落地前伸肌绷紧）降低冲击 |

机器人侧的等价物：Raibert 1986 弹簧腿/腿长伺服、VMC 虚拟腿弹簧-阻尼（Pratt 1997）、
阻抗控制（Hogan 1985）——工程上都是"**力越大，退让（压缩）越多，然后弹回**"。

**我们的实现（`landingAbsorb.ts`，连续力反馈的反射弧，2026-10 实测定型）**

- **粒度**：以脚为单位（per-foot）。任意一脚都连续读该腿法向力 F（脚 Fz 为代理），
  不需要"落地事件"才能工作；
- **连续目标**（主力：**膝受力大就弯**）：
  `depthTgt = perFz·max(0, F/W − fz0) + perV·vImp·e^(−t/0.15)`
  · `fz0 = 2.0W`——超过两倍体重的负载才退让（单脚站立静载 ~1.0W、双支撑 ~0.5W
    都不弯；实测 1.5W 会让转移中的支撑腿闪弯、时序崩坏）；
  · `vImp` 是**触地边沿一次性捕捉的冲击速度**（触地前滑窗最小 vy；要求先"真腾空"
    `airT ≥ 0.08s` 且冲击 ≥0.15 m/s——防抬腿蹭地误触发）；
- **相位**：`depth` 以 `riseRate=16 rad/s` 追赶目标（冲击要快），力退后按
  `reboundTau=0.18s` 指数回伸、不过冲；`maxDepth=0.6 rad` 防跪；
- **联动**：膝为主，髋 `+0.35·depth`（屈）、踝 `−0.18·depth`（**背屈**——正号是跖屈，
  压缩时会把脚趾踩进地面，实测峰值力反升）；被动作 `pin` 的自由度跳过；
  depth≈0 时 `clearAngle` 交还关节；
- **与动作的仲裁（实测必需）**：单脚动作在**抬腿/保持期钉住摆动腿屈伸轴**
  （`pin`），落腿时解钉交给消力——否则反射会把抬腿膝目标 −0.75 抢成 −0.2，
  腿被拉直、动作崩坏。

**探针验证（`_probe-landing`，单脚从两个落高放下，消力开/关对照）**

| 落点 | 峰值力（关→开） | 膝最深屈（关→开） | 回伸残差 |
|---|---|---|---|
| 低落（0.5s 慢放） | 32% → **21% W** | −0.06（轻） | ~0 ✓ |
| 高落（0.2s 快放） | 64% → **59% W** | −0.15 → **−0.47**（随落高单调加深） | ~0 ✓ |

（注：消力"开"的窗末胸高略低于"关"——那是被吸收的冲击换来的下沉。）

**触发与优先级（2026-10 定）**

- **不是"有提案就执行"，也不是电平触发**：连续力反馈本身有 `fz0=2.0W` 的死区
  （站着不动不会弯）；冲击速度项必须"真腾空 + 超阈"才启动（防抬腿蹭地）；
- **优先级 = 反射层（安全类，与垫脚同层），但轴级归属**：只拿**落地腿的
  膝/髋/踝屈伸轴**；垫脚拿 CoP 轴（踝内外翻/足底滚动）——轴正交，可并行；
  直控仍压它；被动作 `pin` 的轴跳过；保护动作（`fallProtect`）运行时让位；
- **不需要提案**：自触发、自计算（函数 + 最小状态）；出口仍过整合器
  （不绕过），与其它反射/提案逐轴合并；预警若想表达"怎么用"可以带
  `landing` directive 作为**可选**的叠加输入，但缺它照常工作。

**验收判据**：探针从不同高度落单脚——屈膝量随冲击力**单调**；回伸无残余振荡；
落地峰值力相比无消力对照**下降**。

| ② 越界·僵直 | > ±10° | **全身绷直**：张力拉满 + 大力矩回拉（危险墙）——不是关节锁死，是全身协同收缩僵直 | Wissmann 2025（威胁→保护性僵直：摆幅↓ 频率↑）/ Lavalle 2025 |
| ③ 回归 | 回到内部 | 恢复慢精修 | — |

**为什么"慢"是前提（第一性原则）**：上身动作慢 → 到达 ±10° 边界时速度/加速度都小 →
边界拦截不需要对抗大动量，②的"绷直 + 力矩"就够。
**快**的代价已在力度战役全部验过：饱和（推不回来）、回拉激起振荡/自旋（§2.276–2.280）。

**测量纠错（2026-10-13，必须记住）**：
- 探针曾用欧拉 roll 公式误读（实际读的是 yaw）——真倾倒必须用 **up 向量倾角**（与 `sensors.torsoTilt` 同款：`atan2(up_z, up_y)`）。
- 纠错后的真实读数（单腿，当前栈）：A/B/C/D 相 = **17.5 / 22.8 / 54.9 / 66.5°**——"急速躺平"是真相，±10° 规格**未达标**。
- 结构本质：`spineSegments=4` 只有 **3 个脊柱关节**（spine1/2/3）控制 4 段（torso/spine2/3/4）——整线倾倒时
  三关节相对角 ≈ 0 → 脊柱伺服"满意"→ **对整线倒结构性无感**；整线倾倒住在**浮动基座（踝/髋）**。
  抓捕要么靠踝/髋力矩，要么靠"下反弯折目标"（§2.287 实验：下目标版更差 61%/161 vs 67%/103，已回退——
  再次证明**必须先慢**，越界时体系已快，反弯折指令自身激起摆动）。

## §6.1 伺服 v2→v4 演进（历史；**当前设计见 `保护预警与反射弧.md` §2**）

> ⚠ 本节记录 v2/v3 的幅度预算演进（planLateral/boost 已随差动加载上线而删除）。

**需求**（含动量，替代粗糙 PD；Hof XCoM）：
`q = 目标 − (CoM + v/ω₀)`，`ω₀ = √(g/h_CoM)`。

**幅度分配**（每级饱和则余量传给下一级；Pai & Patton 1997 的"可恢复幅度"
思想——需求超出全部预算时升 level，未来接"迈步提案"）：

**★ 横向自激（共振）——2026-10 实测头号坑（`_probe-lateral-resonance`）**：
- 现象：横向冲量（0.4 m/s）后摆动包络**指数增长**（8cm→130cm→摔倒）；
  小信号（2cm）也长——是线性不稳定，不是饱和；
- 机理：髋策略**非最小相位**（移 CoM 先反冲骨盆）+ 传感（comVel 低通 100ms）/
  执行（速率限幅）延迟 → ~1Hz 以上相位反转，修正变泵；负载 boost 随摆幅调制
  会加剧；垫脚单独（lean 关）衰减稳定；
- 修法（历史方案，见 5cb 提交；**当前树以"boost 直接关闭"解决**——实测
  `leanBoostSpineGain/ArmBias=0` 时 0.4 冲量包络 **0.061→0.025 衰减稳定**）：
  `leanGain` 环路增益旋钮（当时扫描 1.0/0.7/0.5 全放大、0.35 衰减）+
  boost 滞回锁存 + 动作有意搬移期间临时抬到 1.0（作为对照保留）；
- 副作用（正当的方向）：C 蹬地挺腰从 1.6cm 边缘 → **7.4cm 生效**（此前也是被横向环拖累）；

  完整/bend关/lean关全部衰减✓，**关掉垫脚才放大**（57→116cm）⇒ 前后稳的主通道

  Pai & Patton 的可恢复幅度），不是自激。竖向触地回弹是腿伺服欠阻尼弹簧（能量返还），
  力传递正常，kd 0.02→0.05·τmax 后减半；
- 纪律：**一切侧向/平衡新特性必须过 `_probe-lateral-resonance`（0.4 冲量衰减）**，
  单脚 D 的历史"通过"多为刀刃运气，不再作为稳定依据。

**★ 侧向力"传不到地里"的机理（2026-10，`_probe-inv`）+ 下一专项**：
- 侧向 CoP 被钳 ±2cm ⇒ 踝侧向对地力矩只有 `0.6·Fz·0.02 ≈ 8 N·m`（髋通道 120 的 6%）
  ——这是左右平衡被迫依赖非最小相位髋策略的**根因**；
- 放开到 ±10cm 的实测：**脚内部持续自转**（稳定态 |ω|=2.7 rad/s 而脚角不动；
  全开 |ω| 峰值 25 rad/s、脚角 0.65 rad），黏性阻尼（4/10 N·m·s/rad）不但无效反而更糟
  ⇒ 内力矩没有变成对地滚转/CoP，而是变成踝多环链的内部自转（疑似环轴向/限位/回读
  在链内 wrap 或与 arch 引擎电机耦合）——**力矩在脚里打转，没到地上**；
- 结论：踝侧向是左右平衡的执行层**根瓶颈**，值得单独立项：把内外翻环隔离验证
  （轴、限位、角回读、与 arch 的耦合），修好后左右可以走**最小相位踝通道**，
  髋策略只需低增益兜底。

**单脚 D 现状（2026-10）**：稳定增益下"重心转移"能完成或安全放弃；保持相还存在
摆动脚拖地/CoM 漂到支撑脚外的问题（待重做：静态保持律 + CoP 走廊内目标）。

### 6.3 伺服层设计的文献对照（2026-10 查证）

**我们的伺服层 = 意图/动作发起 + 伺服补偿扰动 + 反射调用 + 目标守护（限幅/回正）。**
文献里最贴的设计范本：

| 设计问题 | 文献方案 | 对我们的映射 |
|---|---|---|
| 意图 vs 扰动的分工 | **Mergner & Lippi 2018（DEC）**：神经系统"估计扰动量并补偿"，主运动由意图发起 | 与"主动侧移/单支撑是动作的、补偿归伺服"**完全同构**——我们的 governor 就是简化的 DEC |
| 传感器如何进伺服 | **van der Kooij 1999**：多感觉加权整合（本体/前庭） | 我们的 CoM/CoP/Fz 估计是雏形；未来加本体-前庭式权重 |
| 精确指令怎么生成 | **Kajita 2003（ZMP 预览控制）**：LIPM 前馈轨迹（CoM/ZMP）+ 反馈稳定，伺服层"预知未来" | 动作给粗目标，伺服把它转成可行的 CoP/CoM 指令（我们目前是纯反馈，预览=未来项） |
| 策略怎么分级触发 | **Stephens 2007**：踝→髋→步 的推恢复层级 | 与反射分级（pad→hip→step/giveup）同源 |
| "力传地面"怎么控 | **Ott et al. 2011**：把接触力作为优化变量做全身姿态平衡 | 差动加载的推广形态（接触力即控制量） |
| 全身伺服的被控对象 | **Orin/Goswami/Lee 2013**：质心动量（centroidal momentum） | CoM/XCoM 层的一般化 |
| 延迟下的增益 | Peterka 2002 / Kuo 1995（已引） | 增益必须尊重延迟（我们实测的相位泵教训） |
| 两层可行化怎么分 | **Sentis & Khatib 2005**（分层全身控制） | 动作=任务层、伺服=稳定性层，**分开实现**（§2.4） |
| 目标守护的文献形态 | **Garone 2017**（参考调速器）/ **Ames 2019**（CBF） | 静默钳制/安全包络 = reference governor 思想 |
| 保护程序设计依据 | **Robinovitch 2013**（真实跌倒观测） | 手撑/屈膝是降低伤害的优势动作（B/C 相） |

**结论**：我们的伺服层结构与文献主线一致（DEC 分工 + 层级策略 + CoM/CoP 反馈）；
差距在（a）**预览/前馈**（Kajita）未做、（b）**接触力级优化**（Ott）未做、
（c）传感器整合（van der Kooij）只有单通道估计。三项都在"伺服层"范围内，按优先级排。
**★ 伺服层架构 v4 已按文献升级，完整版见 `保护预警与反射弧.md` §2.8**
（五段处理链：可行化→扰动补偿→目标守护→反射调用→指令输出；含差距清单）。

### 6.4 抖动彻查结论（2026-10，最高优先级事件的收编）

世界翻转吸收——五类"新增反馈或速度改写式耗散"全部把驱动环搞崩。

## §8 脚踝基础力与侧向力：3D 力矩合成（2026-10-21）

**范围**：只设计 `foot/ankle`；`hip/knee/spine` 不在本节。

**定稿方向**（详见 `docs/脚踝重做-基础力与侧向力-2026-10-21.md`）：

```
GRF = 竖直力；踝输出 = 力矩。
M_GRF = r × N = (−rz·N, 0, rx·N)
M_des = M_base（静态前馈） + M_fb（CoP 反馈）
A = [u0 u1 u2]（foot/0 + foot/1 + foot/2；3D 模式下预环不锁死）
τ = (AᵀA + λI)⁻¹ Aᵀ M_des
```

**基础力的定义（2026-10-21 用户定稿）**：基础力是**不存在的虚拟参考力** `F_base`
（提前标定、矢状面、理想情况下刚好抵消重力）；它映射到脚上就是 `CoP_base`。
脚/踝只闭环 `CoP/M`，不闭环 `F_base` 的竖直分量；竖直分量由腿链/地面（GRF）实现。
“力不够就多蹬地”= 提高 N，需要 hip/knee/leg chain，不是 ankle-only。

四条纪律：

1. **先在 world moment 空间合成，再分配到真实踝轴**；不要分别写 `foot/0`、`foot/2` 的标量通道。
2. **base 是虚拟 `F_base` 映射出的 `M_base`**（推荐只含 pitch），不是固定关节力矩；每帧用当前轴重新分配。
3. **脚踝唯一写手是 3D 分配器**；`squatPairBase` 不再写 foot/ankle，`foot/2` 的 pair PD 关闭。
4. **3D 模式下 foot/1 参与分配，不再物理锁死**；只禁止 pair/PD/FootPad 写它，
   `ankleWrench` 必须写它。单轴过渡模式才锁死。

**解剖轴审查（2026-10-21 查论文）**：当前 `u0/u1/u2` 是 rest-pose 分解，不是解剖轴。
文献：talocrural 轴≈内外踝连线、冠状倾斜 ≈8.6°/−7.3°、横向偏差 ≈0.8°；
subtalar 轴≈42° 水平 / 23° 内偏；两轴 3D 夹角≈62.3°；ISB 踝 JCS 是非正交的
（e1 内外踝、e2 floating、e3 跟骨长轴）。当前 `u2` 横向偏差 24.8°、无冠状倾斜；
`u1` 是外八 rest artifact，不是关节轴。**控制级可先解锁 preRing 用 3 轴合成；
模型级正解需按解剖 landmark 重建轴。** 详见新文档 §3.2c。

文献依据：Winter 1996（A/P 踝、M/L 髋）、O'Connor & Hamill 2005（oblique subtalar axis）、
Hunt & Smith 2001（3D 踝力矩坐标系）、PLOS ONE 2014（3D 力矩矢量/非线性叠加）、
Harter 2024 / Choi 2022（lateral ankle strategy via inversion/eversion）、
McKerahan（multi-directional ankle impedance）、Skoss 2002（co-contraction 跨平面 unintended torque）、
Hof 2005（踝力矩移动 CoP，不是竖直力）。

**分层结论**：

- **动态矢量力矩的策略 + 分配 → 伺服层**（`core/servo/ankle3d.ts`）：base 捕获、CoP 反馈、
  world moment 合成、按当前踝轴最小二乘、可行性钳位、门控。
- **施加 + 限幅 + 账本 → 执行层**（`core/executor.ts`）：只认每自由度力矩，不读 CoP。
- **不要放进 `drive.step`**：`drive` 是执行层阻尼/限位，藏 CoP 控制器会绕过提案总线，
  变成不可审计的隐藏写手。

**当前状态**：`docs/脚踝重做-基础力与侧向力-2026-10-21.md` 是本节的设计真源；
代码已按 3D 分配器重构，`squatAnkleRoll` 已删除，脚踝唯一写手是 `squat.ankleVec`。
**标准拓扑轴默认开启**：`ANKLE_STD_AXES`（`core/body.ts`，默认 1；设 0 回退）——
`foot/0`=局部 X（roll）、`foot/1`=局部 Y（yaw，外八进 rest）、`foot/2`=局部 Z（pitch），
无 preRing。首轮实测：判死 **2.642s offX 5cm**、2.5s 侧移 **51.8mm**
（旧多环 2.581s / 102.4mm）。

**转接口已实现**：`core/servo/ankleAxisAdapter.ts`（纯映射）+ `squatAnkleVector`。
默认开启（`SQC_ANKLE_VEC=0` 回退），只在蹲姿释放后运行，**站立不调用**。
基础力矩只允许 `(0,0,Mz)`，侧向只允许 `(Mx,0,0)`，用当前三轴解最小二乘。
**回正力默认开启**（`SQC_VEC_KP_PITCH=-0.5`、`SQC_VEC_KD=0.2`、`SQC_MUSCLE_F=-230`、`SQC_MUSCLE_MZ=0`）；
`Mdes=Mext=Mapp=(0,0,-8.8)`、残差 **0.00** → 踝基础力确实纯矢状。
**vec 模式基础力只留轴 2**：`squatPairBase` 排除 foot/ankle 与 hip/knee/spine/neck 的轴 0
（上游最大侧向写手）。修正后 base-only：侧移 2.0–2.5s **3.1mm**、判死 **3.021s offX 5cm**；
默认组合 3.085s offX、2.5s 侧移 2.9mm。旧两轴模型残差 **36–48 N·m**（几何不可达），
必须配合标准三轴。
`docs/脚踝基础力与侧向力-力矩合成.md` 与 `docs/脚踝动态矢量力矩-分层与设计.md`
保留作历史记录，不再是目标架构。

**物理边界（2026-10-21 重定）**：关节力矩是内力偶，不能合成竖直力；竖直力是 GRF。
基础力如果定义成“固定竖直力”，那是 `N_des` 外部目标；脚踝只能合成 `M_des`/`CoP_des`。
若 `N_des` 也要闭环，必须引入 hip/knee 的 whole-leg force control。

## §9 蹲姿：静态伺服与回正申请（2026-10-21 目标架构）

> 目标：固定脚、准静态蹲姿。先把“静态保持”做对，再让回正力通过申请制进入。
> 纪律：**任何额外力都必须可追溯：申请 → 分配 → 执行 → 账本**；禁止策略层直接写关节。

### 9.1 两个问题必须分开

| 问题 | 目标 | 是否需要额外地面力 | 控制量 |
|---|---|---|---|
| 静态保持 | 保持 `q_ref` | 不需要净额外力 | `τ_ff` + 关节 PD |
| 小偏差回正 | 把 CoM/CP 拉回容差 | 需要改变 CoP/GRF 分配 | `RightingRequest` |
| 大偏差回正 | 防倒 | 需要净水平力/步进/角动量 | 同上 + 髋/步/臂 |

固定脚时，**静态保持不是回正**：目标姿态唯一，但保持它的关节力矩不唯一（闭合链冗余）。
`base force` 必须是该姿态的**静力平衡解**，不是任意“每个关节一张表”。

### 9.2 分层

```text
意图 / 动作
   │
   ▼
静态计划（释放时一次）
  q_ref、τ_ff、名义接触力分配、CoP_base
   │
   ▼
姿态伺服（局部）
  τ_posture = τ_ff + Kp(q_ref−q) − Kd·q̇
   │
   ▼
回正策略（仅在容差外）
  CP/CoM 误差 + 紧急度 → RightingRequest
   │
   ▼
接触力分配器（唯一腿写手）
  QP：脚反力/CoP/摩擦/力矩 → 关节力矩
   │
   ▼
Proposal Bus / Arbiter → Executor（账本、限幅）
```

### 9.3 静态计划

1. 释放瞬间捕获 `q_ref`（现有 `captureAngFrom`）。
2. 解静力平衡，得到 `τ_ff` 和左右脚名义反力：
   ```text
   Σ f_i + mg = 0
   Σ (p_i × f_i) + Σ τ_contact = 0
   fz_i ≥ 0，CoP_i ∈ 脚掌，|f_xy| ≤ μ fz_i
   τ_min ≤ τ_ff ≤ τ_max
   ```
   冗余解按“最大力矩最小 / 踝力矩最小 / CoP 留边”选一个，不要随机。
3. 姿态伺服：
   ```text
   τ = τ_ff + Kp(q_ref−q) − Kd·q̇
   ```
4. **零反馈验收**：只加 `τ_ff`，脚固定，目标姿态保持 1s。
   1s 都保不住，先查静力解/执行链，不要加回正环。

> 静态实验（τ0/QP）已删除；主路径回到 `pairBase/ankleVec/hipStab`。

### 9.4 回正申请

回正不是“某根轴再给一点力”，而是**申请一个接触力/CoP 变化**：

```text
RightingRequest {
  id, src, reason,
  priority, ttl,
  dp: [x,z],          // 期望 CoP 偏移（脚掌内）
  df: [x,y,z],        // 期望净 GRF 变化
  maxTau, maxCop, maxF,
}
```

规则：

- 低紧急度：只申请踝（`dp`），不申请髋/步；
- 中紧急度：`dp` 饱和后申请髋/角动量；
- 高紧急度：才允许步进/手臂；
- **静态时 `Σdf_y = 0`**：一只脚多发力，另一只脚必须少发力；否则是净加速度，不是静态。
- 水平 `df_xy` 受摩擦锥约束；竖直 `df_y` 受腿链/关节力矩约束。
- 所有请求进提案总线；被拒绝/钳位要写账本，不允许静默改目标。

### 9.5 分配器

唯一腿写手，输入“姿态力矩 + 回正请求 + 当前接触状态”，输出关节力矩：

```text
min  ||Wτ(τ−τ_ff)||² + wp||p−p_req||² + wf||f−f_req||²
s.t. 接触力平衡、CoP 在脚内、摩擦锥、单侧接触、τ 限幅
```

输出：

- 每只脚的法向力/CoP/水平力；
- 每个腿关节的力矩；
- 残差与饱和标记。

若残差超限：**拒绝或升级**，不要用更大增益硬压。目标不可行时，改姿势/CoM/步进。

### 9.6 写手与优先级

- 静态计划：不是写手，只产出 `q_ref/τ_ff/名义分配`；
- `squatPosture`：姿态 PD，唯一腿写手（第一阶段）；
- `rightingPolicy`：只出 `RightingRequest`，不写关节；
- `allocator`：唯一把请求变成关节力矩的写手；
- `ankleVec`、`hipStab`、`support` 不再各自当策略写手，只作为分配器的执行细节；
- 优先级：`安全/接触约束 > 回正 > 姿态 > 基础前馈`；
- 所有请求带 `src/budget/ttl`，进账本。

**执行通道注意（2026-10-21 实测）**：蹲姿 `drive.step` 会把 `tex` 清零，因此
`kind:'torque'` 在蹲姿**不会生效**；静态/回正的唯一写手必须走 `kind:'ext'`
（原始力矩，executor 仍做 τmax 限幅）或 `pair`。不要用 `torque` 通道下发静态基础力。

### 9.7 落地顺序与验收

1. **静态**：`τ_ff` + PD，一个写手；零反馈 1s；1cm 关节扰动恢复。
2. **低紧急度回正**：CP→`p_req`，踝 pitch/roll，双支撑分配；2–3cm 扰动恢复，不饱和。
3. **分配器**：加入髋份额与 QP；检查饱和/残差。
4. **动态权重**：按 `u` 连续调度踝/髋/步/臂；最后才做步进。

验收判据：

- 零反馈 1s 不漂；
- 1cm CoM 偏移能回容差，踝不饱和；
- 2–3cm 偏移时先踝后髋，权重连续、无抖动；
- 所有额外力都有申请记录和账本；
- 脚不动时，CoP 不出支撑多边形。

### 9.8 论文依据

- **Hyon 2006**：重力补偿=接触力分配；balanced squatting。
- **Hyon, Osu & Otaka 2009**：static balancer 在踝/髋之间；局部关节刚度替代 CoM 反馈。
- **Mason et al. 2014**：全动力学 LQR + 接触约束；squatting 与 squat 中推扰。
- **Galdeano et al. 2014**：CoM + 相对脚位 + ZMP；脚固定的 squat-like。
- **Suzuki et al. 2017**：静力学 + 接触力优化，全身力矩。
- **Henze et al. 2016**：PD+ 前馈 + 接触力分配。
- **Wong et al. 2018**：双支撑闭合链的重力补偿/内力分配。
- 人蹲姿：**Straub & Powers 2024**；**Clément et al. 2014**；GRF/CoM/关节力矩随躯干/胫骨倾角变化，静态保持仍需合理载荷分配。

### 9.9 与旧实现的差异

- 不再把 `ankleVec` 当“回正策略”；它只执行分配后的 CoP/力矩。
- 不再把 `hipStab` 当独立稳定器；髋份额由分配器给。
- 不再把 18.2N 虚拟支撑当“支撑力”；它要么并入 `τ_ff` 的静力解，要么删除。
- 不再有 `squatLegForce` 这类独立力写手；所有力走 `RightingRequest` + 分配器。
- `base force` 是 `τ_ff`，不是每帧临时加偏置。

## §9.10 定稿：静态 finePD（2026-10-21）

> §9.1–§9.9 的 QP/τ0 是历史尝试；当前定稿是 **base 前馈 + finePD**。

### 9.10.1 目标

固定脚、准静态蹲姿：

```text
base：保持姿态（前馈，不负责回正）
fine：只修小偏差，小力矩、高精度
```

### 9.10.2 fine 控制律


- `Kp` 小：1° 误差只出几 N·m；
- `Kd` 做临界阻尼，速度低通；

- deadband 0.1–0.2°，防抖；
- 一个 fine 写手，只写 hip/0、hip/2、knee/2、foot/0、foot/2；
- **fine 挡不读 CoP**，CoP 只做监控/中挡。

### 9.10.3 挡位

| 1 fine | 小偏差 | 关节 PD | 小力矩、高精度 |
| 2 中挡 | fine 饱和 | CoP/髋 | 连续过渡 |
| 3 粗挡 | 大偏差 | 髋/臂/步 | 救急，不用于静态 |

### 9.10.4 写手边界

- `base`：前馈保持，不是回正；
- `finePD`：唯一 fine 回正写手；
- `ankleVec/hipStab`：中挡才参与，fine 挡不写；
- 不允许 `hip/0` 的速度阻尼冒充位置回正；
- 所有 fine 力矩走提案/账本，有 `τ_fine_max`。

### 9.10.5 论文

- **Hogan 1985**：Impedance control，小偏差用刚度/阻抗；

## §9.12 定稿：侧向任务空间 fine 阻抗（2026-10-21）

> 取代 §9.11 的“局部关节 P”。局部 P 只看脚自己的 0.4°，看不到 hip 的 5°，所以脚不出力。

### 9.12.1 为什么 pair 行、fine 不行

- pair PD 在矢状大关节上，有 base + 高刚度，直接改 CoM；
- fine 现在只在 `foot/0` 局部角误差上出力；
- 实测冲量后：hip/0 误差 `5.2°`、力矩 `0.91 N·m`；foot/0 误差 `0.4°`、力矩 `0.14 N·m`；
- cap=5 没饱和 → 不是权限，是**用错误差/执行器**；
- 并排蹲姿的侧向主力是**髋 load/unload**，踝 roll 只是补充（Winter 1996；Desai 2014；Harter 2024）。

### 9.12.2 控制律

```text
e_z = z_com − z_ref          // 或 hip/0 的侧向偏差
v_z = comVel_z（低通）

F_z = Kp·e_z + Ki·∫e_z − Kd·v_z
τ   = Jᵀ·F_z
```

- `F_z` 是任务空间侧向力，不是关节力矩；
- `J` = CoM 侧向对 hip/0、foot/0 的雅可比；
- hip/0 主、foot/0 辅；
- 小 Kp、小 Ki（0.1–0.5）、小 cap（5–10 N·m）；
- 一个 task-space fine 写手，映射到 hip/0、foot/0。

### 9.12.3 高精度措施

1. `q_ref/com_ref` 只捕获一次；
2. `J` 的符号/比例用 +ε 标定，不能拍脑袋；
3. 积分只消稳态误差，饱和冻结，防 windup；
4. deadband 0.5mm / 0.05–0.1°，配速度门；
5. 力矩分辨率 0.01 N·m，cap 小但不粗量化；
6. 单写手 + 每轴总阻尼预算；
7. CoP 只监控，不进 fine 高频环。

### 9.12.4 论文

- **Winter et al. 1996**：并排站立 M/L 主要靠髋外展/内收 load/unload；A/P 才靠踝。
- **Desai, Geyer & Hodgins 2014**：侧向 balance 用 task-space virtual model；髋/腿负载转移为主，踝力臂小，髋约 85% 侧向力矩。
- **Harter et al. 2024**：踝内翻/外翻可移 CoP，但权限远小于髋负载/步距，是补充。
- **Boonstra et al. 2013；Hettich et al. 2014**：人用踝-髋耦合/多关节反馈，不是独立关节 PD。
- **Hogan 1985**：小偏差用阻抗；**Park, Horak & Kuo 2004**：小扰动增益缩放；**Horak & Nashner 1986**：踝/髋策略。
- **Torres-Oviedo & Ting 2007**：踝/髋是肌肉协同，不是单轴 PD。

### 9.12.5 验收

1. 1cm 侧向偏移，0.5s 内残差 <1mm；
2. 峰值 ≤ cap；
3. 不反向、不抖、CoP 不出脚掌；
4. 贴 cap 才进中挡；
5. 通过后才替换当前局部 finePD。

```text
dp = Kcop·e
τ_foot0 = Fz·dp        // 小力矩，直接脚发力
τ_hip0  = Kp_h·e
```

## §9.13 上身回正：roll 走髋/腰骶，不走胸段（2026-10-21）

### 9.13.1 新查证

- **Grüneberg et al. 2005**，*Spatio-temporal separation of roll and pitch balance-correcting commands*：  
  人体 roll 校正主要发生在**髋和腰骶（lumbosacral）**，不是小腿/踝；pitch 才以踝/膝为主。低腿肌肉对 roll 贡献很小。
- **Horlings et al. 2009**：roll 平面里骨盆与肩/上躯干有相对运动；低频主要是肩，高频可转为骨盆；不能用单一胸段 PD 代替。
- **Desai et al. 2014**：侧向 task-space 控 CoM + trunk orientation，髋 load/unload 为主。
- **Winter et al. 1996**：并排站立 M/L 主要靠髋外展/内收。
- **Kim et al. 2022**：上身角动量控制选 waist roll/pitch、肩、肘；需要初始姿态回归，不能只写脊柱。
- **Happee et al. 2017**：头颈稳定是独立问题；neck 不应拿来当全身 roll 主执行器。

### 9.13.2 结论

现在把 roll P 平均分给 `spine1/2/3` 是错的：它会把胸段/头甩起来，和实验一致（1 Ns headW 变差）。

正确执行器：

```text
roll 主：hip/0（髋外展/内收，load/unload）
roll 辅：spine1 轴0（腰骶，小权重）
不要用 spine3/neck 当 roll 主执行器
```

### 9.13.3 上身回正伺服设计

```text
Task CoM/CP：foot CoP + hip/0 load
Task roll：
  e_roll = roll_ref − torsoTilt[1]
  τ_hip_roll = Kp_h·e_roll − Kd_h·rollRate
  τ_spine1_roll = 0.2–0.3 × τ_hip_roll   // 腰骶辅助，不是三段平分
Task head/neck：只做局部姿态/稳定，不参与全身 roll
```

- 一个 fine 写手，hip/0 与 spine1 合成；
- 先只开 hip roll，再开 spine1 小权重；
- 小 cap、小 Kp，速度低通；
- CAM/手臂只在大扰动时用，不作为静态主路径。

### 9.13.4 首轮 spine1/2/3 平分失败的解释

- 胸段力矩直接加速头和肩，headW 变大；
- roll 的主要生理执行器是髋/腰骶，不是胸段；
- 因此不是“roll 不该救”，是“roll 救错关节”。


### 9.13.5 首轮 hip/spine1 roll 实测（2026-10-21，默认开）

```text

hip/0  : 0.7·τ_roll
spine1 : 0.3·τ_roll   // 不再平分 spine2/3
Kp=5, Kd=0.5, cap=3
```

| 冲量 | 结果 |
|---|---|
| 0 | 不判死，headW 0.12，torsoW 0.58 |
| 1 Ns | 不判死，headW 0.39，torsoW 0.47，max dz 5.3mm |
| 2 Ns | 3.09s 倒 → 中挡 |
| 5 Ns | 2.76s 倒 |

对比 CoP-only 的 1 Ns：torsoW `1.43→0.47`，躯干明显改善；headW `0.31→0.39` 略差。

### 9.13.6 膝盖内塌：knee/0 写手（2026-10-21）

回读发现 `knee/0` 没有位置写手：`err≈-3.1°`，`ext=0`，所以内侧塌没人管。

### 9.14 侧向腿 IK 首轮：目标捕获时机错（2026-10-21）

已实现 knee 位置 task（hip/0、hip/1、knee/1 雅可比），默认关。

### 9.14.1 IK 目标从 setup 膝点仍无效（2026-10-21）

把 `knee0` 改为 setup 世界 z 后，IK 仍然没有效果；sign ± 输出完全相同。

原因：膝内塌主要是**胫骨/膝的旋转**，膝点 z 几乎不动；位置 task 看到 `e≈0`，所以不出力。  
不是目标时机问题，是 **task 变量选错**：应该用胫骨方向/膝角（orientation），不是膝点位置。

当前默认：legIK 关，knee/1 关节 P（Kp300/cap20）；剩 4.6° 是闭链耦合，不是位置 IK 能解。


### 9.15 基础力对账：髋 base 不再削 0.93（2026-10-21）

之前 `captureSquatBase` 默认 `SQB_SCALE_HIP=0.93`，等于人为把髋基础力削 7%，让膝/踝代偿。  
现在默认 `1.0`。

实测：

| 配置 | 无扰动 | 1 Ns |
|---|---|---|
| 0.93（旧） | headW 0.24，torsoW 0.78 | headW 0.28，torsoW 0.43 |
| 1.0（新） | headW 0.13，torsoW 0.50 | headW 0.35，torsoW 0.46 |

整体 `SQB_SCALE=1.2/1.5` 反而 2.7/2.5s 倒；不是越大越好，是髋 base 不能被削。


### 9.16 hip/0 关节 P 首轮失败（2026-10-21）

给 hip/0 加 q_ref P：

- Kp100/cap20：无扰动 `2.846s offX` 倒；
- Kp20/cap8：无扰动 `3.158s offX` 倒；
- 1 Ns 也倒。

原因：hip/0 的 q 目标会通过闭链把矢状面拉倒；不是 knee 内收的解。  
默认已回退：`SQC_FINE_KP_HIP0=0`。


### 9.17 pelvis 误差 → 脚 CoP 首轮失败（2026-10-21）

给 `dp` 加 pelvis 内移误差后：

- sign=+1：无扰动 `2.906s offX` 倒；
- sign=-1：无扰动 `3.012s offX` 倒；
- 1 Ns 也倒。

原因：髋/骨盆的横向误差经脚 CoP 修正，同样会通过闭链把矢状面拉倒。  
默认已回退 `SQC_FINE_KP_PELVIS=0`。

结论：单点 lateral 修正（hip q、pelvis CoP、knee/1）都试过，都会在矢状面翻。需要**带闭链约束的 whole-body allocator**，或先改支撑姿态（站宽/脚尖），不是再加单轴项。

## §9.18 大腿/小腿矢状锁：缺的不是 PD，是软约束（2026-10-21）

### 9.18.1 现状

- `pair/base` 只写矢状轴 2；
- 没有显式的“frontal 锁”；
- fine 可以自由写 hip/0、hip/1、knee/1；
- 所以腿可以在额状面慢慢内收，pair 只保矢状角。

**结论：当前没有大腿/小腿锁在矢状面的机制。**

### 9.18.2 人类怎么做

- **Hoogenboom et al. 2023**：深蹲最大运动和力矩在矢状面；frontal/transverse 小，但对稳定/足平很重要。
- **Powers 2010**：膝内扣来自髋内收/内旋，不是膝自己。
- **Winter 1996**：M/L 靠髋 load/unload。
- **Escamilla 2001 / How to squat 2018**：站宽、脚尖角度改变额状面力矩和膝内移。

人不是“硬锁 0°”，而是**髋外展/外旋 + 足底 CoP + 小关节刚度**，允许小 frontal 运动。

### 9.18.3 补法：sagittalGuard 软约束

```text
q_ref = 释放时法庭姿态
e = q_ref − q
if |e| < deadband (2–3°): τ=0
else: τ = clamp(Kp·e − Kd·q̇, ±cap)
```

- 轴：`hip/0` 主，`hip/1`、`knee/1` 小权重；
- 不是硬锁；只在偏出 deadband 时拉回；
- cap 5–10 N·m，避免像 knee/1 20 N·m 那样硬拧；
- 一个 guard 写手，和 fine/CoP 分开优先级；
- 目标用 release 法庭姿态，不是 setup。

### 9.18.4 顺序

1. 先改站宽/脚尖外旋，让目标少内扣；
2. 加 hip/0 软 guard（deadband 2–3°，小 Kp）；
3. 不够再加 hip/1/knee/1 小权重；
4. 仍不够才做闭链 IK/QP。

**不要再把 knee/1 当主执行器硬拉；它会把腿拧出矢状面。**


### 9.18.5 passiveLock 首轮实装（2026-10-21，默认开）

```text
knee/1 e = q_ref − q
K_lock = 20 + 400·(Fz/W)
deadband = 1.5°
cap = 20 N·m
```

默认开；fine 里的 knee/1 P 默认关，避免双重写手。

| 场景 | 结果 |
|---|---|
| 0 | 不判死，headW 0.18，torsoW 0.49 |
| 1 Ns | 不判死，headW 0.32，torsoW 0.44，max dz 6.0mm |

比 CoP-only 的 1 Ns `headW 0.31/torsoW 1.43`：头部相近，躯干明显改善。  
knee/1 仍有约 5° 残差；锁是“承重软约束”，不是硬锁。


### 9.18.6 hip/0、hip/1 被动锁首轮失败（2026-10-21，默认关）

人类髋有盂唇/关节囊/韧带/臀肌，承重时 congruency 增加；但 sim 里给 hip/0、hip/1 加 q 锁：

- 无扰动 `2.842s offX` 倒；
- 1 Ns `2.987s offX` 倒。

原因同前：hip q 锁通过闭链把矢状面拉倒。  
默认 `SQC_LOCK_HIP=0`；只保留 knee/1 passiveLock。  
如果以后要做髋锁，必须和 knee/foot 一起做 task-space/IK，不能独立 hip q P。


### 9.18.7 定稿：承重膝只走 passiveLock；fine knee 只给悬空腿（2026-10-21）

- 正常承重：fine 的 knee/1 P 不写；只由 `squatPassiveLock` 管；
- fine knee 仅在 `Fz < 0.1W` 的悬空/卸载腿启用；
- passiveLock 加强：

```text
K_lock = 20 + 800·(Fz/W)
deadband = 1.5°
cap = 30 N·m
```

实测：

| 场景 | knee/1 残差 | headW | torsoW |
|---|---:|---:|---:|
| 0 | 3.9° | 0.22 | 0.49 |
| 1 Ns | 3.9° | 0.29 | 0.36 |

比 KL400 的 5.7° 明显好；KL1200 会 3.19s 倒，800 是当前甜点。


### 9.18.8 hip/0 单独 passiveLock 仍失败（2026-10-21，默认关）

只锁 hip/0（K=10+150·Fz/W，deadband 2°，cap15）：

- 无扰动 `2.860s offX` 倒；
- 1 Ns `3.025s offX` 倒。

结论：髋根“承重大、不侧移”是对的，但**不能用一个 hip q 锁实现**；它同样通过闭链把矢状面拉倒。  
人类髋靠髋臼 congruency、盂唇/关节囊/韧带、臀肌多轴协同，不是单轴角度弹簧。  
默认 `SQC_LOCK_HIP=0`；当前只有 knee/1 passiveLock 开。


### 9.18.9 实装：hip/0 passiveLock 默认开（2026-10-21）

默认同时开启；`SQC_LOCK_HIP=0` 可单独关闭髋锁。  
下一阶段只做矢状 CoP/CoM，不再混入 lateral 实验。


### 9.19 矢状 CP→CoP 实装（2026-10-21，默认开）

```text
targetX = copXBase + (1 + λ/ω)(ξ_x − copXBase)
targetX = clamp(targetX, ankleX ± 0.12m)
M_base = sagittalBaseMoment(FyHalf, targetX, ankleX)

```

固定 CoP 目标时是 `2.86s offX` 倒；现在矢状 CP 闭环后不再倒。

## §9.20 统一脚踝策略：AnkleCoP（2026-10-21 定稿）

### 9.20.1 原则

脚/踝是**第一层 CoP 执行器**，站立和蹲下必须用同一套策略：

```text
状态只改参数（增益/支撑/载荷），不改控制律。
```

当前分裂：

- 站立：`FootPad` 一套 CoP/踝目标；
- 蹲下：`squat.ankleVec` 另一套，且 `kpRoll=0`；
- 两套都写踝，但目标/限幅/反馈不一致。

### 9.20.2 统一控制律

```text
ω = sqrt(g/h)
ξx = comX + vX/ω
ξz = comZ + vZ/ω
pReqX = clamp((1+λ/ω)·ξx, 支撑x)
pReqZ = clamp((1+λ/ω)·ξz, 支撑z)
Δp = pReq − copActual
```

- 双支撑按两脚载荷分配 Δp；
- 踝三轴 `pitch/roll/yaw` 用现有 `ankleAxisAdapter` 分配；
- `pReq` 在脚掌内 → 踝完成；
- `pReq` 贴边/踝饱和 → hip load/unload；
- 还不行 → 步进/加宽站距；
- 基础力、pair、hip/knee 不参与 CoP 目标生成。

### 9.20.3 状态参数

| 参数 | 站立 | 蹲下 |
|---|---|---|
| 支撑多边形 | 双脚/单脚 | 双脚，深蹲 |
| Kp/Kd | 小 | 按承重/深屈调 |
| CoP 限幅 | 脚掌 | 脚掌（可更保守） |
| 翻倒升级 | 髋/步 | 髋/加宽 |

**同一 law，不同 config。**

### 9.20.4 落地结构

```text
AnkleCoP（servo 层，唯一脚踝写手）
  ├─ 输入：com/comVel、cop、support、Fz、state
  ├─ 输出：pReq、Δp、每脚踝三轴力矩
  └─ 饱和：返回 saturation，交给 hip/step
```

- 站立 `FootPad` 不再自己算 CoP；调用 AnkleCoP；
- 蹲下 `squat.ankleVec` 调用 AnkleCoP，不另写一套；
- `ankleAxisAdapter` 保留为纯映射；
- 执行层不变。

### 9.20.5 论文

- Winter 1996：A/P 踝策略，M/L 髋 load/unload；
- Hof 2005：XCoM；
- Pratt 2006：Capture Point；
- Hoogenboom 2023：深蹲矢状主导，额状小但关键；
- Ankle muscles drive M/L CoP（PMC8563802）：踝内翻/外翻调 CoP。

### 9.20.6 验收

- 站立 10s、蹲下无扰动/1 Ns；
- CoP 不出支撑多边形；
- 踝饱和时 hip/step 接管；
- 站立/蹲下同一个 AnkleCoP 实例/接口，只是 config 不同。


### 9.20.7 首轮 AnkleCoP 接入（2026-10-21）

已新增 `core/servo/ankleCoP.ts`（纯 CP→CoP 目标，站立/蹲下共用），
`FootPad` 在 `SQC_ANKLE_COP=1` 时使用。

- 站立：`SQC_ANKLE_COP=1` 通过，10s 站住，com≈0；
- 蹲下：同一目标接 `ankleVec` 的 roll 时，`±sign` 都 2.5–3.1s offZ 倒；z 力矩映射/符号未标定。

默认已改为 `SQC_ANKLE_COP=1`；首轮 z 符号/尺度已在 §9.21 重做。

## §9.21 髋侧移进入 AnkleCoP 目标层（2026-10-21 重构）

### 9.21.1 问题

首轮把 hip 侧移作为**踝力矩后的并联修正**：

```text
pReq = f(CoM/CP)
Mx = Kcop·Fz·(pReqZ − copZ)
Mx += J_hip·F_hip        // ← 错误：目标层之后再加一个小力矩
```

实测 1 Ns：hip 链只出 0.15–0.59 N·m，而 AnkleCoP 出 −4～−6 N·m，
髋误差贡献 <10%，被 CoP 通道淹没。不是“没传”，是**权限顺序错了**。

### 9.21.2 唯一正确顺序

```text
状态层：CoM/CP、CoP、hip 侧移/速度、Fz
   ↓
目标层：balanceTarget = AnkleCoP(CoM/CP) ⊕ hipLateral
   ↓  pReqX/pReqZ（CP 先夹支撑，hip 偏置再加一次，防止贴边时零权限）
执行层：唯一的 ankle/foot 写手 → ankleAxisAdapter → foot/0..2
   ↓
承载层：hip/knee/spine 只做被动锁、承重、载荷转移
```

规则：

- hip 侧移误差必须在 `pReqZ` 生成时进入，**不能在 mapMomentToAxes 之后再补**；
- ankle roll 只有一个写手，禁止 `hipChain → foot/0` 并联通道；
- `pReqZ` 按“CP夹边 → 加hip偏置 → 再夹边”处理；饱和返回 `clampedZ`，交给 hip/step，不叠加；
- hip/0、knee/1、spine1 继续做锁定/承载，不生成第二套脚目标；
- 站立 `FootPad` 不传 hip 项，行为不变。

### 9.21.3 目标合成

```text
e_hipZ = hipZ − hipRefZ
d_hipZ = clamp(sign · (Kp_hip·e_hipZ + Kd_hip·v_hipZ), ±cap_hipZ)
pReqZ_CP = clamp(CP目标, 脚支撑 z 范围)   // 先让 CP 贴边
pReqZ    = clamp(pReqZ_CP + d_hipZ, 脚支撑 z 范围)
```

`hip` 用骨盆/躯干平移 z（root `torso`）作为侧移代理；释放瞬间捕获 `hipRefZ`。

### 9.21.4 参数

| 参数 | 默认 | 说明 |
|---|---|---|
| `SQC_HIP_COP` | 1 | hip 误差进 AnkleCoP 目标 |
| `SQC_HIP_COP_KP` | 0.5 | 米/米 |
| `SQC_HIP_COP_KD` | 0.05 | 阻尼 |
| `SQC_HIP_COP_CAP` | 0.06 | 目标偏移上限 m |
| `SQC_HIP_COP_SIGN` | +1 | CoP 方向 |

删除：`SQC_HIP_CHAIN*`、`hipChainF`、`out.tau[0] += J·F`。

### 9.21.5 验收

- 0/1/2 Ns 蹲下不判死；
- `pReqZ` 不出脚支撑范围；
- 站立 10s 不变；
- 记录 `hipZ/hipRefZ/d_hipZ/pReqZ/Mx`，确认 hip 贡献不再被 CoP 淹没。


### 9.21.6 首轮目标层结果（2026-10-21）

实现：

- `ankleCoP.ts` 增加可选 `HipCoPInput`；
- `squat.ankleVec` 把 hip 误差传入 `ankleCoPTarget`；
- 删除 `hipChainF` / `out.tau[0] += J·F` 并联通道；
- hip 项改为“CP 先夹支撑，再加 hip 偏置，再夹一次”，保证贴边时仍有权限。

默认 `SQC_HIP_COP=1`，Kp=0.5、Kd=0.05、cap=0.06、sign=+1。

结果：

| 冲量 | fall | headW | torsoW |
|---|---|---|---|
| 0 | none | 0.12 | 0.16 |
| 1 Ns | none | 0.67 | 0.32 |
| 2 Ns | none | 0.67 | 0.60 |

- 2 Ns 从 `2.985s offZ` 变为不判死；
- 但 2 Ns 的 hip 关节侧移仍约 67mm，`pReqZ` 约 132mm；
- Kp>0.5 时 1 Ns 会倒，Kp<0.5 时 2 Ns 会倒；0.5 是当前稳定边界；
- 说明目标层链路已通，但**踝的侧向权限/相位仍不足以把 hip 拉回**。

下一步不是继续加 Kp，而是：

1. 用 hip 关节展宽/承重转移（不是 q 锁）减少 hip 侧移；
2. 或加宽站距/步进，给 CoP 更大侧向范围。

## §9.22 蹲下 hip/0 回正审计（2026-10-21）

### 9.22.1 现状

矢状模式 `SQC_ANKLE_VEC=1` 下：

- `squatPairBase` 只写 `axis=2`，**hip/0 不写 base、不写 pair PD**；
- `squatHipStab` 只写 `hip/2`；
- `hip/0` 只剩两个来源：
  1. `squatFineLateral`：`tCopHip = 20·(CoM_z−CoM_ref)` + `0.7·roll` + `kpHip0·q误差`（默认 `kpHip0=0`）+ `kpHipZ·thigh_z误差`（默认 `kpHipZ=0`）；
  2. `squatPassiveLock.hip`：`K=10+150·Fz/W` 的 hip/0 **q 锁**，deadband 2°，cap 15。

`thigh_z` 的 `ePelvis` 虽然算了，但只用于 `dpSide`；`SQC_ANKLE_COP=1` 时 `_fineFoot=0`，所以这条误差实际被丢弃。

### 9.22.2 为什么 CoM 正常、髋不回正

- `tCopHip` 是 **CoM 误差**，不是 hip 侧移目标；CoM 被脚/踝拉回后，hip 误差仍在，hip 项就归零；
- `passiveLock.hip` 是 **关节角锁**，只把 hip 角拉向释放角，不是骨盆/髋位置回正；
- 两者都不是“hip 侧移位置任务”，所以髋可以停在偏位而 CoM/头/脊柱正常。

1 Ns 回读（2.4s）：

```text
hip_l: 119 → 138 mm
hip_r: -119 → -132 mm
```

两侧同时向外，更像**髋展宽**，不是整体平移；因此只控 CoM 的 `tCopHip` 不会把它拉回。

### 9.22.3 位置任务 + 被动锁（2026-10-21 实装）

`hip/0` 增加 opt-in 位置任务（root `torso` z，释放瞬间捕获 ref）：

```text
e_hipZ = torsoZ − torsoRefZ
τ_hip0 = sign · (Kp·e_hipZ + Kd·v_hipZ)
```

参数：`SQC_HIP_POS_KP`（默认 0）、`SQC_HIP_POS_KD`（默认 0）、
`SQC_HIP_POS_CAP`（默认 8）、`SQC_HIP_POS_SIGN`（默认 +1）。

`passiveLock.hip` 保留，默认仍开；位置任务与锁同时写 hip/0（用户要求“都加”）。

实测（AnkleCoP 默认开）：

| Kp / sign | 1 Ns | 2 Ns | 髋（2.4s） |
|---|---|---|---|
| 0 / — | 不判死 | 不判死 | 138 / −132 |
| 50 / − | 不判死 | 不判死 | 136 / −133 |
| 100 / − | 不判死 | 不判死 | 136 / −133 |
| 200 / − | 不判死 | 不判死 | 136 / −133 |

- 位置任务没有把髋拉回，只把 hip/0 力矩从约 0 加到 7 N·m；
- 髋仍是 **两侧外展**，说明 hip/0 扭矩在闭链里被膝/踝/骨盆吸收；
- 因此默认 `SQC_HIP_POS_KP=0`，不把无效任务设为默认；锁保留。

### 9.22.4 结论

- `hip/0` 不是“缺一个 PD”的问题；单独 hip/0 力矩不够；
- 需要 hip/0 + hip/1 + knee/1 的任务空间分配，或直接改站距；
- 继续加 hip/0 Kp 只会增加内耗，不会让髋回正。

## §9.23 髋控制重写：从 CoP 偏置改为 hip 任务（2026-10-21）

### 9.23.1 回退

回退 §9.21/§9.22 的 hip 试验层：

- 删除 `HipCoPInput` / `ankleCoPTarget` 的 hip 偏置；
- 删除 `SQC_HIP_CHAIN*`、`SQC_HIP_POS_*`、`SQC_FINE_KP_HIPZ`；
- `AnkleCoP` 恢复纯 CoM/CP→CoP，脚只负责 CoM；
- 保留矢状 CP、knee/spine 被动锁、supportClean、站立回归。

这些试验的共同错误：把“髋位置”塞进脚 CoP 或 hip/0 q 锁；两者都不是髋位置任务。

### 9.23.2 重写目标

髋是**任务层**，不是脚 CoP 的目标：

```text
状态：hip_l/hip_r 锚点 z，torso z，速度
任务：髋中心 z_c = (zL+zR)/2
      髋宽度 z_w = zL−zR
执行：hip/0 左右协调力矩
       τL = Kc·e_c + Kw·e_w − Kd·v
       τR = Kc·e_c − Kw·e_w − Kd·v
```

- `e_c` 控整体侧移；
- `e_w` 控左右髋展宽；
- 一个写手写 hip/0，不再和 fineTask/passiveLock 抢；
- 脚 CoP 继续管 CoM，髋任务不往脚里塞；
- 饱和/限幅 → 站距/步进，不再加 Kp。

### 9.23.3 首轮结果（2026-10-21）

实现：

- `squatHipTask`：`hip_l/hip_r` 锚点 z → 中心误差 `eC`、宽度误差 `eW`；
- 输出 `hip/0` 左右协调力矩；
- `passiveLock.hip` 保留（默认开）；
- `AnkleCoP` 恢复纯 CoM/CP，不再承接 hip 误差。

默认：`SQC_HIP_TASK=1`，Kc=0，Kw=300，Kd=2，cap=20。

|---|---|---|---|
| 纯 AnkleCoP，无锁 | 2.935s 倒 | 2.740s 倒 | — |
| 锁，无 hipTask | 不判死 | 2.983s 倒 | 138 / −132 |
| hipTask + 锁 | 不判死 | 2.985s 倒 | 138 / −132 |
| Kc=300/Kw=300 + 锁 | 不判死，headW 0.57 | 2.985s 倒 | 138 / −132 |

结论（修订）：

- **不代表脚没有权限**：CoM 余量足够时，脚一蹬地就能建立回正力；
- 2 Ns 仍倒，是因为早期没有建立大回正力，不是物理权限耗尽；

## §9.24 早期大回正力（2026-10-21 修订）

### 9.24.1 修正前提

§9.21–§9.23 的“CoP 贴边 / 权限不足 / 小力矩优先”结论需要修正：

- **CoM 余量是大的**：释放时 CoM 在支撑内，脚有蹬地空间；
- **权限一直在**：脚/踝/髋可以出力，问题不是没有权限；
- `pReqZ` 贴内边是**控制器自己把目标设到边界**，不是物理权限耗尽；
- 只要脚及时蹬地，回正力立刻出现；
- 真正的问题是**力来得太晚、太小、分配太慢**。

### 9.24.2 原则

```text
宁可大，不能小；
宁可早，不能晚；
先饱和，再精细；
先脚/髋大任务，再 QP 分配。
```

- 早期不是“小 PD 慢慢纠”，而是**大前馈/大反馈**；
- 高精度不是“小力矩”，而是**力的方向、时机、上升率、饱和/退饱和**准；
- 晚到的小力矩没有意义；早到的大力矩才改变 CP；
- 早期大，后期再收；不是全程大。

### 9.24.3 时间轴

```text
t < 0（释放前）:
  CoP 目标回脚中心，不要贴边
  hip 外展/踝外翻预紧
  记录 hip/CoM 参考

t = 0+（释放/扰动）:
  速度/CP 触发，不等位置误差
  τ = τ_max_admissible（按方向饱和）
  力矩上升率放到最大允许值
  不做积分、不做慢滤波

0–100 ms:
  保持大回正力
  脚 CoP 快速移到目标侧
  hip 任务同步给骨盆/髋中点

100–300 ms:
  根据 CP/CoP 退饱和
  仍在支撑内 → 降到 fine
  已出支撑 → hip/step，不再加 Kp

>300 ms:
  只做精细保持/步进，不再追加大力
```

### 9.24.4 权限与饱和

- 物理权限由 **CoM 余量 + 脚支撑 + 摩擦** 决定，不由 `pReqZ` 的控制器边决定；
- 早期允许 `pReq` 到支撑边，甚至用脚外侧/内侧；
- 饱和不是失败，是“用满权限”；
- 只有 **CP 出支撑且无法 step** 才是真的没权限。

### 9.24.5 与 QP 的关系

```text
早期：脚/髋大任务（优先级最高）
中期：QP 分配 hip/0、hip/1、knee/1、ankle
后期：fine PD 保持
```

QP 不能替代早期时机；它只负责“大任务怎么分到各关节”。

### 9.24.6 验收

- 扰动后 **1–2 帧内**力矩开始上升；
- 早期峰值达到可用上限，而不是等 20 mm 后才出 7 N·m；
- 0/1/2 Ns 不判死；
- hip 中心/宽度下降；
- 后期不因大力过冲而反向倒。

### 9.24.7 大 hip 基础力试验（2026-10-21）

按“宁可大不能小”把 hip 任务暂时拉到：

```text
SQC_HIP_TASK_KC=1000
SQC_HIP_TASK_KW=3000
SQC_HIP_TASK_KDW=100
SQC_HIP_TASK_CAP=50
```

结果：

- 1 Ns：不判死；3.2s 髋 `110 / −121`，已越过释放位（119/−119），出现过冲；
- 2 Ns：`2.979s offZ` 仍倒；
- 首个 hip 任务日志在 `2.10s`，真正出力在 `2.20s`（τ≈3.6 N·m），
  相对 2.0s 扰动约 **200ms 晚**；
- 2.30s 才到 6.6 N·m，之后才到 50 N·m。

结论：

- **大基础力本身不够，救得晚**；
- 需要释放前预紧/释放瞬间前馈，而不是等误差；
- 当前默认仍是 Kc=0、Kw=300、cap=20，不把 50 N·m 试验设默认。

## §9.25 静态伺服层：预警 → 预紧 → 早期 → 回收（2026-10-21）

### 9.25.1 定位

伺服层不是“一堆 PD”，而是**状态机 + 预测器 + 力整形器**：

```text
传感器 → 预测/观测 → 触发 → 前馈/预紧 → 反馈/QP → 力矩
```

当前问题：伺服层只做 `误差 → PD`，没有预测层；等误差出现才出力，首个 hip 力比扰动晚约 200ms。

### 9.25.2 五个状态

| 状态 | 时间 | 目标 | 特点 |
|---|---|---|---|
| HOLD | 释放前 | 保持蹲姿 | CoP 回脚中心；小预紧；无积分 |
| PRELOAD | 释放前 100–200ms | 建立早期力 | 已知扰动用 preview；未知用共激活 |
| EARLY | 0–100ms | 抢回正 | 早期大、允许饱和；速度/TtC 触发 |
| RECOVER | 100–300ms | 退饱和 | CoP/QP 分配；防过冲 |
| FINE | >300ms | 精细保持 | 小力矩、间歇/死区 |

原则仍是：

```text
宁可早，不能晚；宁可大，不能小；
早期大，后期小；高精度靠时机/力整形，不靠小增益。
```

### 9.25.3 预测/预警层

不要用位置误差当预警；位置已经晚了。用：

```text
CP:      ξ = c + v/ω
TtC:     TtC = (boundary − c)/v        // 可加 0.5·a·t²
CoP 速度: v_cop
干扰观测: d_hat（momentum observer / GRF）
```

触发：

```text
|v_hip| > k·σ
或 TtC < T_react + margin
或 |d_hat| > threshold
带 hysteresis，防止在阈值附近抖动
```

目标：扰动后 **1–2 帧**内进入 EARLY，而不是 200ms 后。

### 9.25.4 预紧层

- **已知扰动/释放时刻**：用 preview，在释放前 100–200ms 预紧；
- **未知扰动**：共激活 + 小预紧，方向不定时不要赌单侧；
- 预紧量：踝/髋各 5–10 N·m 量级，先建立刚度，不追求大位移；
- 释放前把 CoP 目标放回脚中心，保留两侧行程。

### 9.25.5 早期层（EARLY）

```text
τ_early = τ_ff + Kp·e + Kd·v
|τ_early| ≤ τ_admissible
力矩上升率 = 最大允许值
无积分、无慢滤波、无死区
```

- 早期允许大，甚至饱和；饱和是“用满权限”；
- 方向由 `TtC/CP` 决定，不等 `hipZ` 偏 20mm；
- 高精度体现在**方向、起始时刻、上升率、退饱和时刻**，不是把力调小。

### 9.25.6 回收层（RECOVER）

- 当 CP 回到支撑内/CoP 有余量：按比例退饱和；
- 用 QP 把剩余力分配到 `hip/0 + hip/1 + knee/1 + ankle`；
- 防止早期大力造成反向过冲；
- 若 CP 已出支撑：hip/step，不再加 Kp。

### 9.25.7 精细层（FINE）

- 小 PD/阻抗，死区 + 滞回；
- 间歇控制，避免持续噪声/抖动；
- 只做保持，不再承担“救”。

### 9.25.8 代码落点

```text
squatFrame:
  1. courtStep（判死/释放）
  2. servoPredict（CP/TtC/CoP v/d_hat）
  3. servoState（HOLD/PRELOAD/EARLY/RECOVER/FINE）
  4. preload/feedforward
  5. pairBase → ankleVec → hipTask
  6. QP/fine 分配
  7. passiveLock / supportClean
```

约束：

- 伺服层只有一个入口，不允许各关节自己写“早期 PD”；
- 早期力走提案/账本，有 `τ_admissible` 和 rate limit；
- `st.hipRef` 等参考必须在 **扰动前** 捕获，不能释放后第一帧才捕获；
- 预警量只读传感器/状态，不写执行器。

### 9.25.9 验收

- 扰动到首个力矩 **≤ 1–2 帧**（240Hz 下约 4–8ms）；
- EARLY 峰值达到可用上限，而不是 200ms 后 3.6 N·m；
- 0/1/2 Ns 不判死；
- 髋中心/宽度下降，且无反向过冲；
- 后期 FINE 不持续抖动；
- 站立 10s 不变，typecheck/build 通过。

## §9.26 静态 CoP 中心化（2026-10-21）

### 9.26.1 问题

蹲下每只脚的 CoP 目标用全局 CoM 作参考，`pReqZ` 一开始就贴脚掌内边：

```text
pReqZ = refZ + (1+λ/ω)(ξZ − refZ)
→ 每只脚都被夹到内边
→ 踝持续出 ±6 N·m 滚转
→ 两腿外展，髋 119→133（无扰动也发生）
```

### 9.26.2 改法

`ankleCoPTarget` 增加 `neutralZ`：

```text
pReqZ = neutralZ + (1+λ/ω)(ξZ − refZ)
```

- 站立：`neutralZ = refZ`，行为不变；
- 蹲下：`neutralZ = ankZ`（每只脚中心）。

这样无扰动时 CoP 在脚中心，不再有静态侧向偏置。

### 9.26.3 结果

无扰动：

```text
中心化前：hip 133 / −133
中心化后：hip 122 / −122
```

1 Ns（中心化 + 锁，hipServo 关）：

```text
fall = none
headW = 0.63
max|dz| = 1.9mm
```

0 Ns：

```text
headW = 0.07
```

2 Ns 仍倒（2.975s offZ）。

### 9.26.4 结论

- 中心化修掉了“控制器自己制造静态侧向力”的根源；
- 无扰动和 1 Ns 明显改善；
- 2 Ns 仍需要早期大回正/QP/站距；
- 默认回到 `SQC_HIP_SERVO=0`、`SQC_LOCK_HIP=1`，不叠加无效 hipServo。

|---|---|---|---|
| 限位 + hip 共激活 K100 | headW 0.31，torsoW 1.77 | headW 0.45，torsoW 6.33 | 3.169s 倒 |
| 限位，hip 共激活关 | 0.25 / 0.56 | 0.50 / 0.25 | 3.119s 倒 |
| 纯 knee 共激活（当前稳定） | 0.27 / 0.25 | 0.58 / 1.05 | 不判死 |

结论：

- 硬限位确实限制了侧向移动，1 Ns torsoW 从 1.05 降到 0.25（hip 共激活关）；
- 但 2 Ns 会倒，说明只锁侧向、不给 CoP/hip load-unload 不够；
- 和 hip 共激活同开更差；
- 用户要求试看，当前暂设 `SQC_LAT_LOCK=1`、hip 共激活关；2 Ns 仍会倒，仅作观察。

## §9.35 脚局部 CoP/柔性原型（2026-10-21）

在 `squatAnkleVector` 增加 opt-in 脚局部控制器：

```text
pErr = pReqZ − copZ
phiRef = phi0 + Kadm·pErr
Mx = Kspring·(phiRef − phi) − Bspring·phi̇ + Kcop·Fz·pErr
```

默认参数：Adm=0.5，Kspring=30，Bspring=3，Kcop=0.6，cap=40。

结果：

| 配置 | 1 Ns | 2 Ns |
|---|---|---|
| 原 CoP 直控 | 0.49 | 0.50 |
| 脚局部 0.5/0.6 | 0.65 | 0.44 |
| 脚局部 0.2/0.3，CoP±0.05 | 0.50 | 0.54 |

- 2 Ns 略好，1 Ns 变差；
- 还没做到“每脚独立支撑/分配”；
- 默认 `SQC_FOOT_LOCAL=0`，保留 opt-in。

下一步：每脚 CoP 分配器 + 脚局部力控，而不是单脚追全局 target。

## §9.36 每脚 CoP 分配器（2026-10-21）

在 `squatAnkleVector` 增加双足 CoP 分配：

```text
总目标 = 加权脚中心 + CP 偏移
每脚先 clamp 到自身支撑范围
残差按剩余容量转给另一只脚
```

结果与单脚直控完全相同：

| 配置 | 0 Ns | 1 Ns | 2 Ns |
|---|---|---|---|
| 分配器，±90mm | 0.14 | 0.49 | 0.50 |
| 分配器，±50mm | 0.14 | 0.49 | 0.50 |

原因：当前 CP 偏移没有超过单脚容量，分配器没有触发；两只脚都还有余量。

结论：

- 分配器代码保留，但当前测试不触发；
- 脚的问题不在“目标分配”，在实际 CoP 只移动 5–21mm、踝 roll 动态不够；
- 下一步应做脚局部 roll 阻抗/CoP 力控，而不是继续分目标。

## §9.37 双脚支撑的力/CoP 分配与髋 load/unload（2026-10-21 定稿）

### 9.37.1 文献结论

双支撑侧向平衡不是“每只脚自己去追 CoM”：

- **Winter 1996/1998**：双脚并排站立时，M/L 方向 CoP 主要由左右腿承重差
  （hip ab/adduction load/unload）控制；两侧 ankle CoP 在 M/L 上近似反相、互相抵消。
  踝内翻/外翻最大约 10 N·m，超过会翻脚；髋外展/内收可 >100 N·m。
  - https://www.researchgate.net/publication/14409014
  - https://journals.physiology.org/doi/full/10.1152/jn.1998.80.3.1211
- **Lee & Goswami 2010**：双支撑控制每只脚的 GRF + CoP，最小化踝力矩。
  - https://doi.org/10.1109/iros.2010.5650416
- **Wensing 2013**：双支撑 CoP/力分配欠定，用优化分配，惩罚 CoP 靠近脚边界。
  - https://doi.org/10.1142/s0219843613500278
- **Anderson 2006**：双足踝力矩冗余，最优解让每只脚 CoP 对齐；只看总 CoP 不够。
  - https://doi.org/10.1109/ichr.2006.321339
- **Claros 2014**：主控制器 + 每脚局部 CoP 控制器，侧向平衡。
  - https://doi.org/10.1109/icca.2014.6870998
- **González/Zielinska 2012、Zurawska 2015**：弹簧-阻尼脚让 CoP 更平滑；
  但刚度过低会失稳，刚度较高 + 合适阻尼才改善 ZMP。
  - https://doi.org/10.14313/jamris_1-2015/9
- **Eljaik 2013**：SEA 低通滤波 ZMP，恢复更稳，但控制器仍需匹配等效刚度。
  - https://doi.org/10.15607/rss.2013.ix.008
- **Loram 2002**：人体踝固有刚度只有稳定所需约 91%，必须主动调弹簧偏移。
  - https://pmc.ncbi.nlm.nih.gov/articles/PMC2290720/

### 9.37.2 当前实现的问题

```text
AnkleCoP 给每只脚一个全局 CoP 目标
每只脚只追这个目标
```

问题：

- 全局 target 可能超出单脚支撑（当前 CoP ±90mm > 脚掌半宽 50mm）；
- 一只脚装不下时，不会把差额转给另一只脚；
- 没有双支撑的 Fz 分配（hip load/unload）；
- 脚局部 roll 没有独立的目标/边界；
- 脚宽和视觉不一致，会误判“脚不够”。

§9.36 的分配器当前测试不触发，因为 raw CP 偏移没有超过单脚容量；
真正缺的是**双支撑力/CoP QP + 髋 load/unload**，不是继续分 target。

### 9.37.3 新分层

```text
L0  总 CoM/CP → 总 CoP 目标 p_net

L1  双支撑力/CoP 分配（QP）
    变量：Fz_L, Fz_R, p_L, p_R
    约束：ΣFz=mg
          ΣFz_i·p_i = mg·p_net
          p_i ∈ 本脚支撑多边形
          |τ_ankle_i| ≤ τ_max
    目标：min Σ||τ_ankle_i||²
          + w1·edge(p_i)²
          + w2·(dFz_i/dt)²
    一只脚到边 → 另一只脚多承担
    两只都到边 → hip load/unload / step

L2  每脚局部 roll 伺服
    τ_roll = Kp·Fz_i·(p_i − cop_i)
           + Kd·Fz_i·(ṗ_i − ċop_i)
           + Kφ·(φ_ref − φ) − Bφ·φ̇
    只追分配器给的 p_i，不追全局 target

L3  髋 load/unload
    Fz 差 / 总 CoP 误差 → hip/0 力矩
    双支撑 M/L 的主力
```

### 9.37.4 柔性足的位置

柔性足不是“越软越好”：

```text
需要：足够 roll 刚度 + 合适阻尼 + 局部 CoP/GRF 反馈 + 主动弹簧偏移
不需要：纯软脚 + 位置追目标
```

- 脚掌物理宽度保持 100mm（人体参考）；
- CoP 目标必须在半宽内；
- 脚局部弹簧/阻尼只做“柔顺”，不承担全部 CoM。

### 9.37.5 实施顺序

1. `AnkleCoP` 输出总 CoP，不再直接给每只脚；
2. 新增 `doubleSupportAllocator`：QP/解析分配 Fz、p_i；
3. 现有脚局部伺服只接收分配后的 p_i；
4. 新增 hip load/unload：Fz 差 → hip/0；
5. 最后才调脚 roll 刚度/阻尼和站距。

### 9.37.6 验收

- p_i 不出单脚支撑；
- 总 CoP 跟踪 `p_net`；
- 1/2 Ns 不判死；
- 脚不再追不可行目标；
- 一只脚卸载时，另一只脚接管；
- 髋 load/unload 有明确贡献，不再只靠脚踝。

# stickman-lab-v2 架构

> 目的：产出**能站住、能被高层动作驱动**的物理火柴人，作为隐藏 boss 移植回本体游戏。
> 本文是唯一真源。v1（`../stickman-lab/`）冻结留档，只作对照与素材来源。
>
> 2026-10 重写：执行层已完成并验收；本文同时给出**控制层**（执行层之上封装的一层）
> 的架构设计。控制层是唯一发布关节执行命令的地方，并且可以被直接操控。

| 测试 | 命令 | 读数 |
|---|---|---|

引擎限位/限位通道按"限位权限 ≥ 马达权限"推导。

## §1 总分层（自下而上）

```
┌────────────────────────────────────────────────────────────────────┐
│ 意图层（游戏 / AI / 玩家输入）—— 最高层                              │
│   · 目标与剧情：play("bow") / 攻击 / 受击 / 情绪 / 不许移动           │
└───────────────────────────────┬────────────────────────────────────┘
                                │ 目标 + 约束
┌───────────────────────────────▼────────────────────────────────────┐
│ 动作提案系统（原名"迈步系统"，独立）                                 │
│   · **所有要执行的动作都由它提案**：迈步、摆手、下蹲、起身…          │
│   · **迈步之前先出"重心转移相位"**（comTrack），再出落足点           │
│   · 输出 ActionProposal（相位序列 + 时长 + 预算），只提案不执行      │
└───────────────────────────────┬────────────────────────────────────┘
                                │ ActionProposal
┌───────────────────────────────▼───────────────┐   ┌──────────────────────────────┐
│ 控制层 ControlLayer（唯一裁定者 + 发布者）     │◀──│ 摔倒预警（独立 · 常开伺服层） │
│   · 多传感估计 / 反射弧 / 平衡策略             │   │ 每拍连续出 StabilityCorrection│
│   · 动作程序（执行**被裁定采纳**的提案）        │   │ 提案（修正，不是报警灯）      │
│   · 直控通道（手动/调试）                      │   └──────────────────────────────┘
│   · 裁定：manual > reflex > balance > action > program > posture   │
└───────────────────────────────┬────────────────────────────────────┘
                                ▼ 关节命令（经 Executor）
```

**边界纪律**：
- 执行层只认"每自由度力矩/激活/角目标"，不认任何动作语义；
- **意图层最高**：游戏/AI 的意图在动作提案系统**之前**生效（可禁止/改写任何动作
  请求，如剧情要求"原地受击"）；
- **动作提案系统（原"迈步系统"）**：**所有要执行的动作都由它提案**——迈步、摆手、
  下蹲、起身…，且**迈步之前先出"重心转移相位"**；只出 `ActionProposal`，不写关节；
- **摔倒预警是常开伺服层**：每拍连续出 `StabilityCorrection` 提案，也不写关节；
- 两路提案都进控制层**唯一执行裁定**（可同拍联合执行、逐轴消解冲突），向下只写 Executor
  （账本、τmax、限位由执行层保证）；
- 控制层向上暴露**动作名 + 参数**（`play/abort/status`）与**直控通道**
  （`setAngle/setTorque/setActivation`）。

**两种"优先"不要混淆**（后面仲裁表按此执行）：
- **决策权**（谁定目标与约束）：`意图层 > 控制层判定`；
- **执行优先级**（同一根轴冲突时谁覆盖）：`直控 > 反射 > 平衡 > …`。

## §2 执行层（已建成）

| 模块 | 职责 | 关键设计 |
|---|---|---|
| `core/skeleton.ts` | 骨架数据（不改） | 18 逻辑关节 / 46 自由度、静姿态、限位、τmax |
| `core/body.ts` | 刚体 + 铰链装配 | 球窝 → 原生球铰（3 转）；revolute → 多环链（踝 = 扭+内外翻+屈伸）；柔性足 arch/mfoot 原样（引擎 ForceBased 隐式弹簧） |
| `core/executor.ts` | **唯一 τ 写入口** | 先求和→单点饱和→成对冲量；账本 `cmd/applied/limit/saturated`；每自由度每步恰好施加一次 |
| `core/drive.ts` | 命令通道 | 阻抗伺服（一步收敛护栏 α）、黏性阻尼 τ=−B·ω（显式、限幅）、限位通道（越界冲量，权限压过马达）、激活通道 |
| `core/actuator.ts` | 人类式执行器 | 黏弹阻尼 + 一阶激活动力学 + Hill 力-长/力-速 |
| `core/world.ts` | 步进循环 | `updateDofState → beginStep → controller → drive → applyAll → step` |
| `core/quat.ts` | 四元数唯一实现 | 含 swing-twist 分解（球铰三轴语义） |

执行层**没有**：环境变量开关、隐藏的写 τ 路径、step 后的自研限位冲量。

## §3 控制层（ControlLayer）设计

### 3.0 意图层（最高层，在动作提案系统之前）

游戏/AI 的意图**先于**摔倒预警与迈步生效——它不是"另一个平衡策略"，而是
**目标与约束的来源**：

```ts
interface GameIntent {
  // 高层动作（经控制层解算关节）
  play(action: string, params?: object): void;   // 'bow' | 'attack' | 'hit' …
  // 约束（在迈步/预警之前生效）
  allowStepping(on: boolean): void;              // 剧情禁止迈步
  stance(mode: 'free' | 'rooted'): void;         // 站桩/生根
  setFacing(yawRad: number): void;
  setEmotion(tag: string): void;
}
```

- 意图只提交**目标/约束**，不写关节、不写力矩；
- 控制层裁定（§3.4）第一条就是"意图约束优先"：意图禁止某类动作时，即使动作
  提案系统提案且 level=2，也会被 `rejected(reason='intent')`；
- 意图层（决策权）与直控（执行优先级）是两件事，见 §1 的"两种优先"说明。

### 3.1 定位（用户定调）

> "摔倒预警与迈步是两个独立系统，但是都给这个控制层做最后判定。
>  这一层也允许被直接操控。"

翻译成接口：

```ts
interface ControlLayer {
  // ── 消费两个独立系统的输出（都只是提案，本层裁定）──
  ingest(c: StabilityCorrection): void;  // 摔倒预警（常开伺服层）：每拍连续修正提案
  ingest(p: ActionProposal): void;       // 动作提案系统（原迈步）：相位序列，含重心转移
  // ── 直控（最高优先级；调试/手动/游戏特殊输入）──
  setAngle(joint, axis, rad, kp?, kd?): void;
  setTorque(joint, axis, tau): void;
  setActivation(joint, axis, a): void;
  // ── 运行模式：是否走反射弧、谁主导 ──
  //   'reflex' = 反射弧主导（默认）；'assist' = 反射弧只保底、程序/直控主导；
  //   'direct' = **不走反射弧**，命令直通执行层（精细调控/消融/学习策略）
  setMode(mode: 'reflex' | 'assist' | 'direct'): void;
  readonly reflexes: {
    setEnabled(id: string, on: boolean): void;   // 逐条开关（消融）
    setLatency(id: string, s: number): void;     // 延迟可置零
  };
  // ── 动作（高层语义；内部自己解算关节）──
  play(action: string, params?: object): void;
  abort(): void;
  readonly status: { action: string | null; t: number; phase: string; decision: string };
  // ── 判定结果（回读给 UI/探针）──
  readonly decision: {
    accepted: ('stability'|'ankle'|'hip'|'action'|'program'|'manual')[];
    conflicts: { axis: string; winner: string; loser: string; reason: string }[];
    rejected: { kind: string; reason: string }[];
    xcomMargin: number; support: 'both'|'l'|'r'|'none';
  };
}
```

### 3.2 感知与状态估计（Sensors）

每物理步从 Body/Rapier 读取、滤波、延迟分发：

| 量 | 来源 | 用途 |
|---|---|---|
| CoM / CoM 速度 | `body.com/comVel`（质量加权 worldCom） | 平衡主回路 |
| 单脚 ΣFz / CoP | `body.footNormalForce` + 接触流形 | 支撑判定、踝策略 |
| 关节角/角速度/力矩 | `dof.angle/vel` + Executor 账本 | 反射与状态输出 |
| 躯干姿态/角速度 | spine4 刚体 | 翻正反射 |
| XcoM = x + ẋ/ω（ω=√(g/h)） | 计算 | 内部稳定性量（控制层判定用；预警系统另有其评估） |

参考：Peterka 2002（感觉整合 = CoM 误差的 PID + 权重）；Hof 2005（XcoM/动态稳定条件）。

### 3.3 反射弧层（ReflexArc）

**每个反射 = 独立模块**，统一接口：

```ts
interface Reflex {
  id: string;
  latency: number;                       // s，感觉延迟（固定环形缓冲）
  update(s: DelayedSensors, dt): ReflexOutput; // 触发条 + 力矩/激活增量
}
class ReflexArc {
  add(r: Reflex): void;
  step(dt: number): void;                // 写入 Executor 的 reflex 通道
}
```

内置反射清单（各有论文依据）：

| 反射 | 生物对应 | 触发 | 输出 | 依据 |
|---|---|---|---|---|
| 牵张反射 | 肌梭-单突触 | 关节角误差/速度 | 刚度/阻尼调制（Actuator 已内建，暴露为反射） | Nashner 1976 |
| 负载反射 | 高尔基腱器官 | 支撑脚 ΣFz 骤降 | 伸肌力矩脉冲（防腿软） | Nashner 1976 |
| 翻正反射 | 前庭-脊髓 | 躯干倾角/角速度 | 脊柱/髋回正力矩 | Horak & Nashner 1986 |
| 踝策略 | 本体+触觉 | 小幅 XcoM 越界 | CoP = x − (h/g)·a_des 的踝力矩 | Winter 1995 / Hof 2005 |
| 髋策略 | 同上 | XcoM 越界 > 阈值 or CoP 饱和 | 髋屈伸/外展力矩突发 | Horak & Nashner 1986 |
| 保护性迈步 | change-in-support | XcoM 出支撑且回收不可行 | 上报裁定；放行后由动作提案执行 | Maki & McIlroy 1997 |
| 屈曲回撤 | nociceptive | 意外碰撞/夹脚 | 快速屈腿（后续） | — |

**延迟**：每个反射有独立 `latency`（牵张 20–40ms、前庭 60–100ms、长环 100–150ms），
由环形缓冲实现；延迟可调为零做对照。依据：Todorov & Jordan 2002（延迟反馈下的最优控制）。

### 3.4 平衡策略 + 两个独立系统的接入（摔倒预警伺服层 / 动作提案系统）

**平衡策略（控制层自有）**
- **主回路**：CoM PD → 期望质心加速度 a_des（先按足底 CoP 可达范围限幅）；
- **踝策略**：LIPM 关系 p = x − (h/g)·a_des，由踝屈伸/内外翻实现 CoP；
- **髋策略**：当 CoP 饱和（|Δp| 顶到足缘）或躯干倾角阈值触发。

**两个独立系统的性质不同（一个连续、一个事件；都只提案）**

| 系统 | 性质 | 输出（只读提案） | 内部依据 |
|---|---|---|---|
| 摔倒预警 | **伺服层：常开，每拍连续输出** | `StabilityCorrection { desiredCopShift, comAdjust, gainScale, level }`（连续量；level 只是派生标签） | XcoM 比支撑边距、外推时间；Pratt 2006 / Hof 2005 |
| 动作提案系统（原"迈步系统"） | **事件层：提案制，覆盖所有要执行的动作** | `ActionProposal { 相位序列：重心转移 → 迈步/摆手/下蹲/起身 → 落定；时长；预算 }` | 迈步前重心转移；Maki & McIlroy 1997 |

- **摔倒预警是伺服层**：它自带闭环、每拍连续工作（不是越界才响的报警灯），
  但输出只是**连续修正提案**，**不直接执行**；
- **动作提案系统（原迈步系统）**：**不只是迈步**——你让它做的所有动作都由它提案；
  **迈步之前先出"重心转移相位"**（comTrack / 重心偏移目标），再出落足点与摆动腿
  轨道；它同样只提案、不执行；
- ★ **两者都只是提案，控制层是唯一执行者**：两种提案**可以同拍联合执行**，
  控制层只做**冲突消解**，尽可能保证不打架：
  · **分工**：伺服修正常作用在 CoM/CoP/踝-髋，动作提案作用在轨迹/摆动腿——
    不同轴就直接并行；
  · **融合**：同轴时按增量叠加（伺服修正叠加在动作轨迹上），各自限幅；
  · **让位**：同轴反向冲突超过阈值时按紧迫度裁定（安全优先，或动作降权/暂缓
    该轴），并把冲突记入 `decision.conflicts`；
  · 设计目标只有一个：**不打架**，而不是"不许同时执行"；
- 意图层可以禁止某类动作，但**不能关掉稳定性伺服**（安全提案常开；调试用
  `mode='direct'` 才能旁路，且执行层限额仍在）。

**关于状态机（用户定调）**：v1 的**全局**步态状态机取消——它搬进**动作提案系统
内部**，作为该系统的**相位编排器**，指挥迈步（重心转移 → 摆动 → 落足 → 稳定），
产出 `ActionProposal`。要点：
- 状态机是动作系统的**实现细节**，不是架构的一层，也**不能直接写关节**；
- 控制层不感知它，只消费提案——所以提案可以被替换/打断/与伺服联合执行；
- 动作系统内部可以为每个动作/每个相位序列持有自己的状态机实例（或一个编排器
  管理队列），互不干扰。

**控制层最终裁定（示例策略，可调；判定顺序 = 权限顺序）**
1. 意图层约束（如 `allowStepping=false`）→ `rejected(reason='intent')`，动作提案直接作废；
2. 直控/反射正在接管 → 相关轴上的提案进入 `rejected`（记录原因）；
3. **默认联合执行**：伺服修正作用在稳定轴、动作提案作用在其相位轴——互不冲突就并行，
   互不等待；
4. **同轴冲突 → 逐轴消解**：紧迫度低的一方让位/降权。例：`level=2` 且踝/髋不可行
   （且意图允许）时放行 `ActionProposal`（先重心转移、再迈步），伺服只保留
   该动作轴上的安全兜底；冲突记入 `decision.conflicts`；
5. 裁定结果全部可回读（`decision.accepted/rejected/conflicts`），探针据此打分。

两个系统**不得**绕过控制层直接调用 `Drive/Executor`；物理层只认控制层发布的命令。

### 3.5 动作程序层（MotorProgram，"不必输出详细关节指令"）

分工：**动作提案系统负责"怎么动"**（把意图展开成相位序列，含重心转移等预备相位）；
**本层负责执行"被裁定采纳"的提案**——把相位展开为协同/任务目标，交给平衡/反射/
姿势解算出关节命令。动作 = **闭环控制器**，不是关键帧；对外只有名字与参数。

```ts
interface MotorProgram {
  id: string;
  duration: number;
  start(ctx, params): void;
  step(dt, ctx): ProgramOutput;   // { comTrack?, poseGoals?, synergy?, done }
  abort(): void;
}
```

- **协同（synergy）**：动作给 1~3 个协同通道（如"前屈链""左腿抬起链"），
  由固定权重映射到关节目标/激活 —— 这就是"不输出 44 轴细节"的实现方式。
  依据：d'Avella 2003、Ting & Macpherson 2005（姿势/动作由少量肌肉协同构成）。
- 首批程序：`stand`（重置到静姿）、`bow`（已验证）、`weightShift(side)`、
  `liftLeg(side)`（单腿站立）、`recover(perturb)`（髋策略+可选步）。
- 程序之间可**打断/串联**；被反射打断是正常语义（保护优先）。

### 3.6 仲裁与优先级（唯一的最终命令发布）

**提案是输入，不占执行优先级**：摔倒预警（每拍连续修正提案）与动作提案系统
（事件提案，含重心转移相位）全部进控制层裁定器；裁定结果决定各提案的
**并行 / 融合 / 让位**方式——**默认联合执行，逐轴消解冲突**。

| 优先级 | 来源 | 作用方式 |
|---|---|---|
| 1（最高） | 直控通道（手动/调试/游戏特殊） | 直接写目标/力矩；覆盖同轴其他来源 |
| 2 | 反射弧 | 力矩增量；可短时突破平衡/程序的目标 |
| 3 | 平衡策略（+ 裁定采纳的稳定性修正） | CoP/姿态目标；接管踝/髋 |
| 4 | **动作提案（仅裁定放行后，含重心转移相位）** | 只拥有被放行动作涉及的轴（如摆动腿链） |
| 5 | 动作程序 | 任务目标/协同（姿势/关节目标） |
| 6（基线） | 姿势张力 | 未被占用的轴回零位 |

**优先级是逐轴仲裁**：动作提案放行后只接管提案涉及的轴（如摆动腿链），
支撑腿与 CoM 仍在平衡策略手里。

### 3.7 控制层一拍到底干什么（可执行的心智模型）

**每物理步（1/240s）固定五段；除了第 4 段，任何模块都不许碰关节：**

```
1. Sense    Sensors.update(dt)
            → { com, comVel, 双脚 Fz/CoP, 支撑状态(both/l/r/none), 躯干姿态, 关节态 }

2. Propose  各来源只算"想要的"，不写关节：
            · balance  : 重力补偿 + 姿势张力 + CoM/踝修正
            · reflex   : 力矩增量（可带感觉延迟）
            · program  : 当前相位的任务目标/协同（动作提案的执行侧）
            · servo    : StabilityCorrection（摔倒预警，连续提案）
            · direct   : 直控覆盖表（setAngle/setTorque/setActivation）

3. Decide   Arbiter.resolve(s, proposals)
            → 逐轴：一个主来源 + 增量叠加 + 冲突记录
            → 联合执行是默认；同轴反向冲突才让位

4. Write    apply(cmd) —— 唯一写点：只经 Drive/Executor（τmax/限位/账本）

5. Report   decision/status 回读（UI/探针）
```

```ts
step(dt: number): void {
  const s = this.sensors.update(dt);
  const p = {
    balance: this.balance.compute(s, dt),
    reflex:  this.reflexes.compute(s, dt),
    program: this.programs.compute(s, dt),
    servo:   this.servo.compute(s, dt),
    direct:  this.direct.compute(s, dt),
  };
  const cmd = this.arbiter.resolve(s, p);   // 逐轴主来源 + 增量 + 冲突
  this.apply(cmd);                          // 唯一写点（Drive/Executor）
  this.decision = cmd.decision;             // accepted/conflicts 回读
}
```

**分模块落地顺序（每步都能单独验收，且不破坏现有回归）：**

| 模块 | 文件 | 内容 | 回归 |
|---|---|---|---|
| M1 Sensors | `core/sensors.ts` | 状态估计（com/CoP/支撑/姿态），零控制逻辑 | `probe-sensors` 读数与现有探针一致 |
| M2 Arbiter | `core/arbiter.ts` | 逐轴优先级 + 增量叠加 + 冲突记录 | 站立/鞠躬行为不变（读数逐位对照） |
| M3 BalanceCore | `core/balance.ts` 拆分 | 重力补偿/姿势/踝策略改成"提案"，不再直接写 | stand 10s、idle 0.0000° |
| M4 ReflexArc | `core/reflex.ts` | 牵张/负载/翻正 + 延迟 + 消融开关 | 站立+推力扰动 |
| M5 ActionSystem | `core/actionSystem.ts` | 状态机搬入；actions.ts 升级为相位提案 | 鞠躬验收 |
| M6 StabilityServo | `core/stability.ts` | 摔倒预警：连续 StabilityCorrection 提案 | 60N 推力 2s 恢复 |
| M7 Mode/Direct | `core/control.ts` | `setMode`、直控通道、decision 回读、UI | 全按钮 |

### 3.8 文献里的控制层是怎么设计的（对照与取舍）

| 范式 | 代表文献 | 机理 | 优点 | 代价 | 我们放在哪 |
|---|---|---|---|---|---|
| 神经肌肉 / 反射 | Geyer & Herr 2010；Song & Geyer 2015；Nashner 1976 | 一组**局部状态反馈律 + 传导延迟**，不做轨迹/优化 | 鲁棒、可解释、天然"封装"（正是你说的反射弧） | 参数多、难以精细调控 | **反射弧层**（默认通道） |
| 层级全身控制 | Sentis & Khatib 2005；Escande/Mansard/Wieber 2014 | 优先级任务栈 → 每步解 QP/HQP，输出关节命令 | 精确、多任务、可加约束 | 依赖模型/求解器/算力 | **精细通道后端**（可选） |
| 预测 / 推恢复 | Pratt 2006；Hof 2005；Shafiee-Ashtiani 2016 | XcoM/Capture Point、MPC 滚动时域 | 抓住"要倒"的本质，判据清晰 | 需状态估计 | **摔倒预警系统**（独立，提交评估） |
| 肌肉协同 / 降维 | d'Avella 2003；Ting & Macpherson 2004 | 少量协同基向量组合出动作 | 动作封装、参数少 | 覆盖率有限 | **动作程序层** |
| 学习 / 最优反馈 | Todorov & Jordan 2002；Kawato 1987；Hwangbo 2019 | 策略网络 / 内模，延迟反馈下最优 | 可达人类级性能 | 训练与验证成本 | **精细通道后端**（可选） |
| 节律 / CPG | Ijspeert 2008 | 相位振荡器产生节律 | 步态节律自然 | 后续 | 程序层相位（未来） |

**综合结论（本项目的双通道设计）**：文献里"反射派"（A）与"模型/优化派"（B/C/D）各有不可替代的
场景，所以控制层不做二选一，而是**两条并行通道 + 逐轴仲裁**：

```
感知 ──┬─▶ 反射弧通道（默认）：ReflexArc ─ 力矩增量 ─────────────┐
       │     可逐条开关 / 延迟置零 / 整层旁路                      │
       └─▶ 精细通道（可选）：程序 / 脚本 / HQP / 学习策略 ─ 关节级命令 ─┤
                                                                    ▼
                                                     逐轴仲裁 ─▶ Executor（τmax/限位/账本）
```

- `mode='reflex'`：默认，反射弧主导；动作程序只给目标；
- `mode='assist'`：反射弧退为安全保底（只处理越界/失稳），精细通道主导；
- `mode='direct'`：**完全绕过反射弧**，命令直通执行层（精细调控、消融对照、
  接未来任何控制器后端）；执行层的 τmax/限位/账本仍然生效（不可绕过）。

- 所有来源最终走 **Executor**（求和 → 单点饱和 → 每自由度每步一次施加）；
- 任何来源都不能绕过执行层的 τmax/限位/账本。

## §5 验收判据（每一层）

- 执行层：T1 = 0.0000°、逐轴下发比 = 1.0000、不变量每步通过（已达成）；
- 平衡层：站立 ≥ 60s 不掉（当前 10s 已过）、水平推力扰动 60N 后 2s 内恢复、XcoM 边距有界；
- 反射层：延迟与增益可回读；撤掉任一反射的对照实验（消融）；
- 动作层：每个动作有 accept/reject 判据（如鞠躬 = 前弯 >0.15m 且回位 <0.12m，已过）；
- 直控：任何关节任何轴可被外部直接支配，回读 `applied == cmd`（已通过）。

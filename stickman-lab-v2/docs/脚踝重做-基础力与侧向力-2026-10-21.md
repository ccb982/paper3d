# 脚踝重做：基础力与侧向力（2026-10-21）

> **旧脚踝架构全部作废。** 本文从零定义 `foot/ankle` 的基础力、侧向力、分层与接口。
> 范围只含 `foot/0`、`foot/1`、`foot/2` 与 `arch/mfoot` 的接触；`hip/knee/spine` 不在本文。
>
> **2026-10-21 默认已开**：`ANKLE_STD_AXES` 默认 1、`SQC_ANKLE_VEC` 默认 1、
> `SQC_MUSCLE_F=-230`、`SQC_MUSCLE_MZ=0`、`SQC_VEC_KP_PITCH=-0.5`、`SQC_VEC_KD=0.2`。
> 回退：`ANKLE_STD_AXES=0` / `SQC_ANKLE_VEC=0`；站立不受蹲姿前馈影响。

---

## 0. 不可违反的物理事实

先钉死三条，否则后面一定走偏：

1. **关节力矩是内力偶**。所有关节力矩的矢量和是**净力矩**，不是净力。
2. **竖直力只能来自地面反力 `N`（外力）**。关节力矩不能凭空产生一个竖直向上的净力。
3. **踝关节能控制的是力矩/CoP，不是竖直力**。竖直力由腿链 + 地面接触决定；踝只决定它作用在哪里（CoP）。

所以：

```text
“各关节矢量合成为一个竖直向上的力”  ❌ 物理上不成立
“各关节矢量合成为一个期望的力矩/CoP”  ✅ 这才是踝能做的
```

**用户 2026-10-21 定稿：基础力是一个“不存在的力”。**
它是提前标定好的**虚拟参考力**，全在矢状面，理想情况下刚好抵消重力。
它不是关节力，也不是实际 GRF；实际 GRF 是它的物理实现。
脚/踝的目标是让实际接触力/CoP 尽可能逼近这个虚拟基础力。

## 1. 基础力的定义（虚拟参考力）

基础力 `F_base` 是虚拟、预标定、矢状面的参考力：

```text
F_base = (Fx_b, Fy_b, 0)
Fy_b = m·g          // 抵消重力；Fx_b 可取 0 或期望的前后分量
```

它映射到脚上 = `CoP_base`（基础力作用线在脚上的落点）：

```text
r_base = CoP_base − ankle = (rx_b, 0, rz_b)
M_base = r_base × F_base
       = (−rz_b·Fy_b, 0, rx_b·Fy_b)      // Fx_b = 0 时
```

- `CoP_base` 就是“基础力映射到脚上的 CoP”。
- `M_base` 是脚/踝要逼近的**基础力矩**。
- 实际 GRF 的 CoP 与 `CoP_base` 的差，就是脚/踝要纠的误差。

分解：

| 量 | 谁负责 | 说明 |
|---|---|---|
| `F_base` 虚拟力 | **参考目标** | 不是实际力；实际力是 GRF |
| `CoP_base` | **脚/踝力矩** | 通过 `foot/0 + foot/2` 的 3D 力矩合成 |
| `M_base` | **脚/踝力矩** | `τ0·u0 + τ1·u1 + τ2·u2` 去逼近 `M_base` |
| 实际 `N` | **腿链 + 地面** | 踝不能直接设定；踝只保证 CoP/力矩 |

**只看脚踝时，能闭环的是 `CoP`/`M`，不是 `F_base` 的竖直分量。**
如果竖直分量也要闭环，必须把髋/膝拉进来（whole-leg force control），那超出本文范围。

## 2. 分层：策略在伺服层，施加在执行层

| 层 | 模块 | 职责 | 不做什么 |
|---|---|---|---|
| 感知 | `Sensors` / `Body` | CoM、fz、CoP、`axisWorld`、`anchorWorld` | 不做控制 |
| **伺服层** | `core/servo/ankleWrench.ts`（新） | `F_base/CoP_base` 读取、`M_des` 合成、`A=[u0,u2]` 最小二乘、可行性钳位、门控 | 不直接写 executor |
| 控制层 | `ControlModule` | 提案仲裁、优先级 | 不发明踝策略 |
| **执行层** | `Executor.applyAll` | clamp、成对力矩冲量、`cmd/applied` 账本 | 不读 CoP、不算 `M_des` |
| 执行层 | `Drive` | 阻尼/限位/阻抗 | 不藏 3D 控制器 |
| 执行层 | `Body` | 刚体/铰链、`preRing` 标记（3D 模式可解锁）、轴/锚点回读 | 不做平衡 |

**结论**：动态矢量力矩的“策略 + 分配”放**伺服层**；“施加 + 限幅 + 账本”放**执行层**。
不要放 `Executor`，也不要放 `drive.step`。

原因：

- `Executor` 的契约是“只认每自由度力矩”，放 CoP 反馈会变成不可审计的隐藏写手；
- `drive` 是执行层阻尼/限位，藏 3D 控制器会绕过提案总线；
- 伺服层可以打印 `F_base/CoP_base/M_base/M_fb/M_des/A/τ/residual`，执行层只打印 `cmd/applied`，审计边界干净。

## 3. 数学

### 3.1 坐标与符号

```text
+X 前，+Y 上，+Z 侧向
r = CoP − ankle = (rx, 0, rz)
N = (0, N, 0)
M_GRF = r × N = (−rz·N, 0, rx·N)
```

### 3.2 踝轴与分配

```text
u0 = foot/0.axisWorld   // roll 主分量
u1 = foot/1.axisWorld   // preRing；3D 模式下解锁并参与分配
u2 = foot/2.axisWorld   // pitch 主分量

A = [u0  u1  u2]        // 3×3
τ = argmin ||A·τ − M_des||² + λ||τ||²
  = (AᵀA + λI)⁻¹ Aᵀ M_des
```

- `τ = [τ0, τ1, τ2]ᵀ`
- 每个轴 clamp 到 `tauMax`
- 回读残差 `E = A·τ − M_des`；三轴满 rank 时纯矢状 `M_des` 可以达到
- `foot/2` 的 pair PD 关闭；脚踝唯一写手是 `ankleWrench`（写 `foot/0/1/2`）
- 预环 `foot/1` 不再物理锁死；只禁止其他写手（pair/PD/FootPad）写它

### 3.2b 踝轴审查：为什么必须用三轴（2026-10-21 实测）

当前标准蹲姿释放时：

```text
u0 = (0.80, −0.47, 0.37)
u2 = (0.42,  0.00, 0.91)
u0·u2 = 0.673      → 夹角 47.7°，cond(A) ≈ 5.1
```

两轴张成的平面法向量：

```text
n = u0 × u2 ≈ (−0.577, −0.772, 0.266)
```

对纯矢状目标 `M=(0,0,Mz)`，两轴最小二乘的残差是 `M` 在 `n` 上的投影：

```text
||E|| / Mz = |n_z| ≈ 26.6%
E ≈ (−0.154, −0.206, +0.071)·Mz
```

也就是说：**两轴（foot/0+foot/2）无法产生纯矢状力矩**；残差主要是 yaw（y）和 roll（x）。
2.35s 时两轴几乎正交（`u0·u2≈0.039`），但法向量 `n≈(−0.339,−0.876,−0.343)`，
纯 `Mz` 残差仍有 **34.3%**。条件数好了，但平面本身不含 z 轴。

**结论**：

- 3-DOF 踝的**拓扑**是对的（talocrural + subtalar + 预环）。
- **锁死 preRing 对 3D 矢量合成是错的**：它把唯一能补 yaw/roll 残差的第三轴拿掉了。
- 单轴 PD 时代锁 preRing 是有效的（消掉了 21 N·m yaw）；但 3D 分配器里 preRing 是
  **解的一部分**，不是脏写手。它应该参与 `A=[u0,u1,u2]`，由分配器统一给力矩。
- 如果 preRing 的行程/力矩不够，再考虑改骨架；不要再用“锁死”来掩盖几何残差。

### 3.2c 解剖轴审查：当前轴不是解剖轴（2026-10-21 查论文）

把当前模型轴和解剖文献对一下：

| 轴 | 当前模型（释放时） | 解剖文献 | 差异 |
|---|---|---|---|
| talocrural / pitch | `u2=(0.42, 0, 0.91)`：横向偏差 **24.8°**，冠状倾斜 **0°** | 内外踝连线（intermalleolar axis）；冠状倾斜约 **+8.6°（背屈）/ −7.3°（跖屈）**，横向偏差约 **0.8°**（[Talar Dome/TCJ Axis, PMC6885182](https://pmc.ncbi.nlm.nih.gov/articles/PMC6885182/)） | 偏航太大；没有冠状倾斜 |
| subtalar / roll | `u0=(0.80, −0.47, 0.37)`：与水平面 **28.0°**，横向内偏 **24.8°** | Inman：与水平面约 **42°**，横向内偏约 **23°**（[The subtalar joint, PMC5549175](https://pmc.ncbi.nlm.nih.gov/articles/PMC5549175/)） | 太水平；横向偏差接近 |
| pre-ring | `u1` = rest 外八轴 | **不是解剖关节轴**；外八是 rest orientation，不是第三个 DOF | 建模 artifact |
| 两轴夹角 | `u0·u2=0.673` → **47.7°** | talocrural–subtalar 3D 夹角平均 **62.3°**（[J Biomech 2012](https://www.sciencedirect.com/science/article/pii/S0021929012000322)） | 偏小约 15° |

文献要点：

- 踝不是简单铰链：talocrural 轴随运动连续变化（[Lundberg 1989](https://doi.org/10.1302/0301-620x.71b1.2915016)）。
- 踝的解剖轴**不相交、远非正交、随运动变化**（[Lee et al. 2013](https://doi.org/10.1109/tnsre.2013.2262689)）。
- ISB 的踝 JCS 是**非正交**的：`e1` 内外踝轴（背屈/跖屈）、`e2` floating（内翻/外翻）、`e3` 跟骨长轴（内旋/外旋）（[Wu et al. 2002](https://doi.org/10.1016/s0021-9290(01)00222-6)）。
- 当前模型的 `u0/u1/u2` 是**rest-pose 分解**的产物，不是从内外踝/距下关节 landmark 建的；因此“轴都错了”这个判断，**在解剖意义上基本成立**。

**两条路线**：

1. **控制级临时解**：保持当前 3-ring，解锁 preRing，用 `A=[u0,u1,u2]` 合成纯矢状力矩。
   能消残差，但轴仍然不是解剖轴。
2. **模型级正解**：按解剖重建踝轴——
   - talocrural：内外踝连线 + 约 8° 冠状倾斜；
   - subtalar：Inman 约 42° 水平 / 23° 内偏；
   - 外八（splay）烧进 rest pose，不做第三个 DOF；
   - 若需要完整 3D 力矩基，加 ISB `e3`（跟骨长轴内旋/外旋）作为第三轴。
   这时“基础力锁死矢量轴、侧向力用侧向轴”才有解剖意义。

**对“基础力锁死矢量轴、侧向力用侧向轴”的建议**：
不要锁死**物理关节轴**；锁死的是**目标方向**：

```text
M_base  = (0, 0, Mz)      // 纯矢状目标（锁方向）
M_lat   = (Mx, 0, 0)      // 侧向目标（允许 roll 轴参与）
M_des   = M_base + M_lat
τ       = A⁺ M_des        // 用可用解剖轴一起合成
```

如果锁死某个物理轴，`A` 就少一列，纯矢状目标又会出残差——这正是 26.6%/34.3% 的来源。

### 3.2d 采用标准拓扑轴（2026-10-21 已实现，门控）

用户决定不走解剖轴，改用**标准拓扑轴**：三个正交局部轴，外八作为 rest 偏置，不做 preRing。

| 逻辑轴 | 轴 | 含义 | rest |
|---|---|---|---|
| `foot/0` | 局部 X | 内外翻 / roll | `p1` |
| `foot/1` | 局部 Y | 内旋/外旋 / yaw（外八） | `p2` |
| `foot/2` | 局部 Z | 屈伸 / pitch | `p3` |

实现（`core/body.ts`，默认开；`ANKLE_STD_AXES=0` 回退旧多环）：

```text
qRelPC = qRel(qParent, qChild)
[p1,p2,p3] = qEulerXYZ(qRelPC)

P  --X(p1)-- mid1
mid1 --Y(p2)-- mid2
mid2 --Z(p3)-- C
```

- 不再用 `preRing` 吸收 ±25° 外八；外八进入 `p2` 的 rest。
- 三个轴都是标准 revolute；`preRing` 标记为 false。
- 世界系轴会因 rest/外八/小腿前倾而不完全正交；3D 分配器必须用**当前 `axisWorld`**，不能假设正交。
- **默认开**；`ANKLE_STD_AXES=0` 回退旧多环模型。

**首轮实测**（当前过渡控制器：pair foot/2 + ankleRoll foot/0，没有 3D 分配器）：

| 指标 | 旧多环（`ANKLE_STD_AXES=0`） | 标准拓扑（默认） |
|---|---:|---:|
| max\|dz\| 2.0–2.35 | 13.7 mm | 30.6 mm |
| max\|dz\| 2.0–2.5 | 102.4 mm | **51.8 mm** |
| 判死 | 2.581s | **2.642s offX 5cm** |

结论：标准拓扑能跑、姿势不炸，侧移和判死时间都优于旧多环；但当前控制器还是过渡单轴版本，
下一步接 `ankleWrench` 的 3 轴分配器，才会发挥标准拓扑的作用。

### 3.2e 转接口：标准方向力矩 → 踝轴（2026-10-21 已实现）

文件：`core/servo/ankleAxisAdapter.ts`（**伺服层**，纯函数，不碰执行器）。

```ts
mapMomentToAxes(Mdes, axes, lambda)
  // axes: [{ u: [x,y,z], tauMax, available }]
  // 返回 { tau, residual, residualNorm }
```

- 输入是世界系目标力矩 `Mdes`（标准方向），不是关节力矩。
- 用当前真实 `axisWorld` 解 `A·τ ≈ Mdes`；`available=false` 的轴（preRing/锁死）不参与。
- 回读 `residual`：三轴满 rank 时接近 0；两轴时会有几何残差。
- 本文件只做映射；谁来写、写哪轴、门控，由 `squatAnkleVector` 决定。

`core/servo/squat.ts` 新增 `squatAnkleVector`：

```text
M_base = (0, 0, Mz)          // 基础力只允许矢状轴
M_lat  = (Mx, 0, 0)          // 侧向回正允许 roll
M_des  = M_base + M_lat
τ      = mapMomentToAxes(M_des, [foot/0, foot/1, foot/2])
```

门控：

- **默认开**；`SQC_ANKLE_VEC=0` 回退旧路径。
- 只在 `baseState() === 'squat' && st.released && st.fall < 0` 时运行。
- **站立完全不调用**；站立路径原样。
- 启用时 `squatPairBase` 不再写 foot/ankle，`squatAnkleRoll` 不运行；脚踝唯一写手是 `ankleVec`。
- 旧模型 `foot/1` 是 preRing（available=false），只剩两轴；残差会很大。
  必须配合 `ANKLE_STD_AXES=1`（三轴满 rank）才能把残差压到 ~0。

**默认回正**：`SQC_VEC_KP_PITCH=-0.5`、`SQC_VEC_KD=0.2`；侧向 roll 反馈 `SQC_VEC_KP_ROLL=0`。

**关键修正：vec 模式基础力只留轴 2**（`squatPairBase`：`vecMode && d.axis !== 2 → continue`）。
hip/knee/spine/neck 的轴 0 基础力/PD 也全部排除——它们才是上游最大的侧向写手。

**首轮实测**（默认：标准拓扑 + vec + 肌肉前馈，已跳过 drive 对 foot/ankle 的写入）：

| `SQC_VEC_KP` | `SQC_VEC_KD` | max\|dz\| 2.0–2.35 | 2.0–2.5 | 判死 |
|---:|---:|---:|---:|---|
| **0（默认，base only）** | 0 | **2.6 mm** | **3.1 mm** | 3.021s **offX 5cm** |
| 0.1 | 0.5 | 2.8 | 3.2 | **none（>3.2s）** |
| 0.3 | 0.5 | 2.9 | 3.3 | **none（>3.2s）** |
| 1.0（过激，旧口径） | 0.5 | 20.5 | 115.0 | 2.079s foot/2Δ21° |

- 排除 hip/knee 轴 0 基础力后，侧移从 **91.7mm → 3.1mm**，判死从 2.579s → **3.021s**。
- `SQC_VEC_KP=0.1`（很小的侧向回正）已经能站满 3.2s 窗口（`fall=none`）。
- 对照：旧模型 + 转接口（foot/1 锁死，两轴）残差 **36–48 N·m**，判死 2.613s。
  说明转接口本身没问题，**必须三轴满 rank**；两轴残差是几何不可达，不是增益问题。

### 3.2f 为什么之前“踝基础力没走矢状面”

实测日志（base only，`SQC_VEC_KP=0`）：

```text
Mdes=(0.0, 0.0, -8.8)
Mext=(0.0, 0.0, -8.8)
Mapp=(0.0, 0.0, -8.8)
res = 0.00
```

- `Mdes`：目标只有 z。
- `Mext`：转接口分配的关节力矩合成的世界力矩，只有 z，残差 0。
- `Mapp`：实际施加（ledger.applied × axisWorld）也只有 z。

**结论：现在踝基础力确实纯矢状。** 之前看起来“没走矢状面”，根因是：

1. **drive 的 `td` 阻尼还在写 foot/ankle**——`Mext` 是纯 z，但 `Mapp` 多了 drive 的隐藏力矩，x/y 就出来了。
   已在 `drive.step` 加门控：默认 vec 模式 + squat + foot/ankle → skip。
2. **旧模型只有两轴可用**：`foot/1` 是 preRing（available=false），两轴张成的平面不含 z，
   残差 26.6%/34.3%，无论怎么调增益都补不成纯矢状。
3. **pair/preRing/FootPad 的残余写手**：vec 模式下 `squatPairBase` 排除 foot/ankle，
   `squatAnkleRoll` 不运行，FootPad 蹲姿早退；脚踝唯一写手是 `ankleVec`。
4. **上游 hip/knee 轴 0 的基础力/PD**（最大侧向写手）：
   `squatPairBase` 原本还写 hip/knee/spine/neck 的轴 0。实测 2.30s：
   `hip/0 pairBase=∓9 N·m, app=±37~40 N·m`；`knee/0 pairBase=∓2 N·m, app=±263 N·m`。
   这些不是脚踝，但会把整条链往侧向推。vec 模式加 `d.axis !== 2 → continue` 后，
   侧移从 **91.7mm → 3.1mm**，判死从 2.579s → **3.021s**。

**残余写手清单（vec 模式）**：

| 写手 | 对 foot/ankle 的状态 |
|---|---|
| `drive` 的 `td` 阻尼 | **已 skip**（`drive.ts`：squat + 默认 vec + foot/ankle） |
| `squat.pairBase` | vec 模式**只写轴 2**；foot/ankle 与 hip/knee/spine/neck 的轴 0 全部排除 |
| `squat.ankleRoll` | **不调用**（vec 模式由 `ankleVec` 取代） |
| `FootPad` | **蹲姿 early return**（不写 foot/0、foot/2、arch） |
| `tension` | 蹲姿对 foot/ankle/spine/hip/knee **skip**（stability.ts:855） |
| `supportClean` 腿 PD | 蹲姿 `!isSquat` **不 propose** |
| `leanReflex` | `__PRED_OFF_RT=true` → **无 reflex 指令** |
| `actions` / `manual` / `pairBank` | 蹲姿无 active 动作；pair 目标 0 |
| `drive`（hip/knee/spine 轴 0） | 仍有被动阻尼/限位；不是主动发力，不会主动制造侧移 |

**不建议删模块**：`drive`、`tension`、`FootPad` 在站立/非 vec 蹲姿仍需要。
保留门控即可；如果要做硬保证，可以在 `control.ts` 加 vec 模式白名单：
**只有 `src === 'squat.ankleVec'` 的 foot/ankle 提案允许通过**，其余直接丢弃。
再加一条断言：`‖Mapp − Mext‖ < 0.5 N·m`，超了就报错/打日志。

所以“基础力走矢状面”现在成立（净 `Mapp` 纯 z）。base-only 仍会在 **3.021s offX 5cm** 失败——

### 3.2h 膝横向位移：不是力矩问题，是“腿外展模式”

### 3.2i 力链回读：到底谁在推膝

`hip_l/r` = 骨盆/躯干 ↔ 大腿的关节；`hip/0` = 外展/内收，`hip/2` = 屈伸。
`knee_l/r` = 大腿 ↔ 小腿；`knee/2` = 屈伸，`knee/0` = 辅助/扭转（轴主要沿 Y）。

力链：

```text
地面接触 → 足/踝 → 小腿 → 膝（力+力矩）→ 大腿 → hip/0 → 骨盆
```

左腿 base-only 的力矩账本（负号 = 膝向 +z 外移方向）：

| t | hip0 执行器 Mact | 惯量矩 Minertia | 非执行器 Mres | 膝力矩反作用 MkTorque | 远端质量×加速度 |
|---:|---:|---:|---:|---:|---:|
| 2.05 | **+15.9**（抵抗） | −8.7 | **−24.6**（驱动） | +5.3（抵抗） | 7.0 N |
| 2.10 | **+12.3**（抵抗） | +1.1 | **−11.1**（驱动） | +9.5（抵抗） | 3.3 N |
| 2.15 | **+8.3**（抵抗） | +2.1 | **−6.2**（驱动） | +10.3（抵抗） | −5.6 N |

判断：

- **hip0 执行器在抵抗**（Mact 与 hv 反号）。
- **膝/0、膝/2 的力矩反作用也在抵抗**（MkTorque 与运动反号）。
- **Mres 才是驱动项**，它来自非执行器：膝关节**反力**（不是力矩）+ 地面接触侧向力 + 重力/骨盆反作用。
- 远端 `Σm·a_z` 只有 3–7 N，说明净加速度很小；但膝反力可以很大，因为它被**地面摩擦**抵消。
  当前账本没有 foot/arch/mfoot 的**接触切向冲量**，所以这一项还没闭环。

结论：**不是 hip 主动推，也不是 knee/0 在推；驱动是足-地侧向力经膝反力传到 thigh。**
左右对称（左 hip0 负、右 hip0 正），所以是“双腿外展”模式，CoM z 仍≈0。

**力链闭合估算**（左腿，负号=向 +z 外移方向）：

|---:|---:|---:|---:|---:|---:|---:|---:|
| 2.05 | −24.6 | +1.0 | +5.3 | −30.8 | −206 N | 7.0 N | −199 N |

- hip0 执行器只有 **+16 → +5.6 N·m** 的阻尼（抵抗），远小于膝反力/地面侧向力的量级。
- 膝反力估算 **100–200 N**；远端 `Σm·a_z` 只有 **3–7 N**，说明绝大部分被**地面摩擦**抵消。
- 所以是“地面侧向力 ↔ 膝反力”这一对内力在传力，hip0 只是被动外展。
- 符号/方向还需读 `contactTangentImpulse` 确认；量级已经足够说明 hip0 阻尼不是对手。

### 3.2l 谁出力：GRF 还是关节力矩

| 方案 | 控制量 | 横向力谁出 | 性质 |
|---|---|---|---|
| 基础力 | `M_base`/`CoP_base` | 地面 GRF（竖直） | 虚拟参考，不凭空 |
| 踝策略 | 踝 roll 力矩 → `CoP_des` | 地面 GRF 的侧向分量/摩擦 | 地面出，踝只移 CoP |
| hip 前馈 bias | `hip/0` 力矩 | 髋关节内力，地面反作用 | 真实关节力矩，但预计算常值，感觉“凭空” |

**要“像基础力一样不凭空”，就不该预计算 hip 力矩，而应预计算 CoP 偏移：**

```text
CoP_des_z = CoP_base_z + ΔCoP_knee     // 左内侧 −，右内侧 +
M_roll    = N · (CoP_des_z − ankleZ)   // 踝 roll 目标
τ         = mapMomentToAxes(M_des, 踝三轴)
```

- 预计算的是**CoP 目标**，和基础力映射到 CoP 同一套语言。
- 横向力由**地面 GRF/摩擦**出；踝力矩只是把 CoP 移过去。
- 脚宽限制：`|ΔCoP_knee| ≤ halfWidth`；超了就会饱和，需要 hip 策略兜底。
- 人类对应：直接拉膝内侧的是鹅足肌群（缝匠/股薄/半腱）；踝策略对应胫骨后肌/腓骨长肌/短肌移动 CoP。
  两者都真实存在；这里走踝/GRF 这条路。

### 3.2m 虚拟肌肉线 → 踝前馈（按用户“斜着向下、模仿肌肉”）

不预计算 hip 常值力矩；预计算一条**虚拟肌肉线**，把它产生的力矩放进回正层的侧向前馈。

```text
p_foot_medial  ：内侧足/踝附着点
p_knee_medial  ：内侧膝附着点
L = p_knee_medial − p_foot_medial
d = L / |L|                    // 斜向内下（从膝指向足）
Fm = 预计算力大小（N）
F  = Fm · d                    // 肌肉对膝的拉力方向
M_pre = (p_knee_medial − ankle) × F   // 对踝的力矩
      → 只取额状面/侧向分量，加到 M_fb_roll
```

- 这条力是斜着向下的：**内侧分量**产生膝内向力矩；**向下分量**是腿的压缩（由 GRF/腿链承担，踝不直接控制）。
- 踝只负责把 `M_pre` 变成 CoP 偏移：
  ```text
  ΔCoP_z = M_pre_z / N
  CoP_des_z = CoP_base_z + ΔCoP_z
  M_roll = N · (CoP_des_z − ankleZ)
  ```
- 力来自地面 GRF/摩擦；踝力矩只是把 CoP 移过去。不是凭空在 hip 或膝上写力。
- 支撑面钳位：`|ΔCoP_z| ≤ halfWidth`；超了就需要腿链压缩/hip 策略兜底。
- 生物对应：鹅足肌群（缝匠/股薄/半腱）从内侧胫骨拉向内侧膝，方向就是斜向内下；
  踝策略用胫骨后肌/腓骨肌移动 CoP 来复制它的**力矩效果**。

### 3.2k 基础力 / 回正力分离（2026-10-21 定稿）

```text
基础力（固定、只矢状）:
  M_base = (0, 0, Mz_base)

回正力（全部纠偏，独立层）:
  M_fb_pitch = -Kp_pitch·fz·(rx - rxBase) - Kd·ω_pitch
  M_fb_roll  = +Kp_roll ·fz·rz            - Kd·ω_roll
  M_pre_lat  = hip/0 预计算前馈（左 -J，右 +J）

M_des = M_base + M_fb_pitch + M_fb_roll
τ     = mapMomentToAxes(M_des, 踝轴)
```

- 基础力不包含任何侧向/offX 纠偏；它只负责固定的矢状支撑。
- 回正力负责：pitch/offX、roll、以及预计算侧向 bias。
- 代码：`SQC_VEC_KP_PITCH` / `SQC_VEC_KP_ROLL` 分开；`SQC_HIP_LAT_BIAS`
  是回正层的侧向前馈，不是基础力。

| +0.1 | 5.1 | 2.962s offZ |
| +0.2 | 5.1 | 3.031s offX |

| −0.5 | 4.8 | 3.179s offZ |
| +1.0 | 34.7 | 2.098s foot/2Δ20° |

结论：

- **分层方向正确**：基础力纯矢状；侧向预计算放回正力；pitch/offX 也放回正力。
- 侧向预计算 `hip bias=-5` 有效：膝横向被压住，整体 3.09–3.13s。

### 3.3 基础力矩

```text
F_base = (Fx_b, Fy_b, 0)          // 虚拟、预标定、矢状面
CoP_base = (copX_b, copZ_b)       // 基础力映射到脚上的 CoP
M_base = (CoP_base − ankle) × F_base
       = (−(copZ_b−ankleZ)·Fy_b, 0, (copX_b−ankleX)·Fy_b)
```

- **提前标定**：`F_base`、`CoP_base` 是常量；不在运行时反解。
- 推荐 `Fx_b=0`、`Fy_b=mg`、`CoP_base.z = 脚中心`，则 `M_base` 只有 pitch 分量。
- 每帧用当前 `u0,u2` 重新分配；轴旋转时净 base 力矩不变。
- `M_base` 是目标，不是“实际关节力矩”；实际关节力矩由 `A⁺M_des` 得到。

### 3.4 侧向回正

```text
rz = copZ − ankleZ
rx = copX − ankleX

M_fb_x = Kp_z·(rz − rz_target) + Kd_z·(−ω_roll)
M_fb_z = Kp_x·(rx − rx_target) + Kd_x·(−ω_pitch)
M_fb   = (M_fb_x, 0, M_fb_z)
```

- `Kp_z ≈ N`、`Kp_x ≈ N` 起；`Kd` 按临界阻尼起。
- 符号必须用 ±5 N·m 的 CoP 响应实测标定。
- 钳位：`|M_fb_x| ≤ N·halfWidth`，`|M_fb_z| ≤ N·halfLength`。
- 门控：`fz > 10% 体重`；`court.fall >= 0` 时零输出。

### 3.5 合成

```text
M_des = M_base + M_fb
τ     = A⁺ M_des
```

base 和 righting **先在 world moment 空间相加，再一次性分配**。
不要分别写 `foot/0`、`foot/2` 两个独立关节通道。

### 3.6 力不够怎么办：调 CoP / 多蹬地

基础力是虚拟目标；实际能不能实现，取决于两个约束：

```text
1. 踝力矩上限：|τ0| ≤ τmax0，|τ1| ≤ τmax1，|τ2| ≤ τmax2
2. 支撑面：|M| ≤ N × 支撑面尺寸（CoP 不能跑出脚）
```

如果 `M_des` 超出可行域，按顺序做：

1. **调整 CoP**（脚/踝可做）：把目标 `CoP_base` 往支撑面内拉，直到 `M_des` 可行；
   这就是“基础力映射到脚上就是 CoP”的实际含义。
2. **多蹬地**（需要腿链）：提高实际 `N`。同样力臂下 `N` 越大，踝能提供的力矩越大；
   但 `N` 是 GRF，由腿链/地面决定，**踝不能单独提高 N**。所以“多蹬地”是 leg-chain 命令，
   不是 ankle-only。
3. **降级/迈步**（更高层）：如果 CoP 已在支撑面边缘、N 也加不上去，基础力不可实现。

所以脚/踝的完整目标是：

```text
CoP → CoP_base（脚/踝力矩）
N   → F_base 的竖直分量（腿链/地面，不是脚踝单独）
```

## 4. 与“固定竖直力”说法的对齐

| 说法 | 正确版本 |
|---|---|
| “基础力是固定竖直力” | 这是虚拟 `F_base`，是参考目标；实际力是 GRF |
| “各关节矢量合成这个力” | 关节只能合成 `M_base`/`CoP_base`；`F_base` 的竖直分量由腿链/地面实现 |
| “脚踝负责基础力” | 脚踝负责 `CoP_base/M_base`；竖直分量不是脚踝单独能闭环的 |
| “力不够就多蹬地” | 提高 N 需要 hip/knee/leg chain；脚踝只能先把 CoP 拉到支撑面内 |

**只看脚和踝**时，设计目标是：

```text
F_base 固定（虚拟参考，不闭环）
CoP_base 固定（由踝力矩追踪）
M_base 由 τ0/τ2 合成
```

如果 `F_base` 的竖直分量也要闭环，必须引入 `hip/knee` 的 whole-leg force control；本文不做。

### 5.3 伪代码

```ts
// release（提前标定，之后常量）
Fbase = [0, m*g, 0];              // 虚拟基础力：矢状面、抵消重力
copBase = { x: copX0, z: footZ0 }; // 基础力映射到脚上的 CoP
M_base = (-(copBase.z - ankZ)*Fbase[1], 0, (copBase.x - ankX)*Fbase[1]);

// each frame
const M_fb = [
  Kp_z*(rz - copBase.z) - Kd_z*omegaRoll,
  0,
  Kp_x*(rx - copBase.x) - Kd_x*omegaPitch,
];
const M_des = M_base + M_fb;
const [tau0, tau1, tau2] = solve3x3([u0, u1, u2], M_des, lambda);
propose(foot0, 'ext', clamp(tau0, tauMax0));
propose(foot1, 'ext', clamp(tau1, tauMax1));
propose(foot2, 'ext', clamp(tau2, tauMax2));
```

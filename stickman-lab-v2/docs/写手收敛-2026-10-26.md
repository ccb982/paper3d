# 写手收敛：统一指挥，不拆机制（2026-10-26 · rev2）

> **rev1 里"删 18 个死写手"的计划已撤回。**
> 用户原话：「你删一堆写手不会是想把我的目前还好不容易建好的机制全拆了吧」——是的，那是错的动机。
> 现在这份的立场是：**一个写手都不删、不改名、不动数值**；只做三件事——
> ① 把"回正力"从"基础力"里剥出来（改归属，不改数值）；
> ② 五套分层 PD 换成**一套统一指挥 + 一张分配系数表**；
> ③ 回正力加**安全区两档**。
>
> 硬约束（沿用，不撤销）
> 1. 「别乱加写手，我只想让你修正已有写手」——本文产线写手数**不变**，新增的全是**不调 `propose` 的纯函数**。
> 2. 「无论是髋还是背肌、脊柱的调整，都要脚发力传到上身」——上身预算由地面反力余量显式给出。
> 3. 「有的写手可能是站立要用的，就别动了」——站立链（`drive.tex`、`supportClean` 非蹲姿分支、`stability`、`rightingController`）**一行不动**。
> 4. 「删完一个写手必须完整检查蹲下和站立等等」——本文不删写手；但仍然要用多状态闸门（§7）。

## 1. 先回答：基础力是 pair PD 还是被动刚度？

**都不是。** 三条证据。

> ★★ **2026-10-26 用户补正（本节结论要按这句读）**：**「矢状面的 pair pd 可以算进基础力」**
> ⇒ 完整定义是 **基础力 = 矢状面 pair PD + 常数前馈 `ch.base`**。
> 下面 1.2 证明的只是"`ch.base` 这一项**不是 PD**"（它无 θ/ω 依赖、不随 `sgn` 翻、
> 被 `c<1e-3` 门控），**不等于**"基础力不是 PD"。见 §6 组 2 的取消说明。

### 1.1 被动刚度在蹲姿根本不上线

`drive.ts:500`：

```ts
let out = baseState() === 'squat' ? bd.ff + bd.act + td : tex + td;
```

而 `tex` 是**累积了 stiff/itb/lum/act/servo/ff 的总和**（`drive.ts:321` 起逐项 `tex += ...`）。
蹲姿走的是左支：**`tex` 整条丢弃**。所以 `bd.stiff`（`kpNorm·(target−θ)`）、`bd.servo`（`manual.setAngle` 的目标）、
`bd.itb`、`bd.lum` 在蹲姿**全都不参与**——这也正是 squat.ts 里那句注释「`manual.setAngle` 在蹲姿被 drive 的 `tex=0` 清零（等于没写）」的由来。

蹲姿真正剩下的只有三项：

```text
out(蹲姿) = bd.ff          ← kind:'torque' 提案（赋值语义）+ antiG
          + bd.act         ← 站立 legReflex 的 pelvisDamp（只 hip/0 支撑侧；蹲姿通常 0）
          + td             ← 阻尼
```

### 1.2 基础力是 pair 通道里的一口"纯前馈力矩"

`squatPairBase` 把 `baseBuf[dofIndex]` 当 `tau` 传进 `propose({kind:'pair', ...})`，
经 `control.ts:249` → `executor.commandPair` → `pairBank.command(dof, c, ref, base)`，最后在 `musclePair.ts:62` 用掉：

```ts
const tauDes = (kp * dev - kd * d.vel) * sgn + ch.base;   // ★ 基础力不随 PD 符号翻转
```

所以：

| 问题 | 答案 |
|---|---|
| 是 PD 吗？ | **不是**。它对 `θ`/`ω` 没有依赖，是个常数。 |
| 是被动刚度吗？ | **不是**。被动刚度是 `bd.stiff`，蹲姿被丢弃（§1.1）。 |
| 它是被谁"付钱"的？ | **共激活 `c`**。`c < 1e-3` 时 `pairTorque` 直接 `return 0` ⇒ **基础力完全不生效**。 |
| 幅度上限？ | 软饱和在 `2c·f0`（`c=0.7, f0=600` ⇒ 840 N·m，实际由 `τmax` 先卡住），超过后按 50% 斜率传递。 |

**结论**：基础力 = **pair 通道里的常数前馈力矩，靠共激活付账**。
它和回正力**共用同一条 `pair.tau` 通道**——这就是为什么两者调参互相干扰（你调共激活刚度，基础力的手感和它一起变）。

### 1.3 因此三件套应该落在三条不同的通道上

这是本文的**唯一结构性改动**，且不改任何数值：

| 件 | 通道 | 现状 | 改法 |
|---|---|---|---|
| 基础力 | `pair.base`（`ch.base`） | 常数前馈 + **被 `tco` 污染** | 把 `tco` 拿出去，`base` 回到纯常数 |
| 回正力 | `ext` → `l.cmd`（相加桶） | 腿侧向/扭转已经在这 | 膝/髋矢状 `tco` 也搬到这 |
| 阻尼 | `drive` 的 `td` | 已经是 | 不动 |

`tco` 搬家是**纯归属调整**：`base += tco` → 同一帧再提一条 `kind:'ext', tau: tco`。
两者在 `applyAll` 里同样是相加（`t = clamp(l.cmd + l.pair) + passive`），**物理结果不变**，
但从此基础力是常数、回正力可单独开关/限幅/进安全区。

### 2.3 提案制在执行层被打破了（你指出的那一刀）

你的设计是**提案制**，且**执行层与伺服层分开**。现状只满足了一半：

| 层 | 应该做什么 | 实际做了什么 | 合规 |
|---|---|---|---|
| 伺服层 | 算"想要多少" → `propose` | `controller.step` 里的伺服律 + `drive.step`（`stiff/servo/itb/lum` + 阻尼 `td`） | ✅ 基本合规 |
| 执行层 | 只读账本 → 饱和 → 成对冲量 | `executor.applyAll` 里 **读 `d.angle` / `d.vel` / `d.inertiaLow`**，跑 **`activationOf`（一阶滤波）** 和 **`pairTorque`（PD）** | ❌ **伺服律住在执行层里** |

证据（`executor.ts:186-201`）：

```ts
const cNow = this.pairBank.activationOf(i, dt, Number(envP.PAIR_TAU ?? 0.06));   // ← 伺服状态机
const ch   = this.pairBank.channel(i);
const pq   = pairTorque(
  { angle: d.angle, vel: d.vel, inertia: d.inertiaLow, pairAxis: true },          // ← 伺服输入
  { c: cNow, ref: ch.ref, base: ch.base }, ...);                                   // ← 伺服律
```

`d.angle` / `d.vel` 在 `executor.ts` 里只出现在这一段——而且要靠 `as unknown as` 强转才能读到
（`DoF` 类型根本没声明这两个字段）⇒ **这个越界是"偷偷"发生的，类型系统本来拦住了它**。

**按你的分层重新判（我先前的判断是错的）**

你说的是「伺服层、动作层给出提案 → 汇总到执行层 → 最后由执行层操作写手」。
那么 **肌肉对就是一个写手，执行层操作它是对的**。rev2 里我把 `applyAll` 里算 `pairTorque` 判成"伺服律越界"，
是拿"执行层应该是个傻子"这个更严的口径去套你的架构——**判错了，撤回**。
`activationOf`（激活动力学）和 `pairTorque`（平衡点）都是**写手内部状态**（Zajac 1989：激活是肌肉属性，不是控制器），
住在执行层不违反你的分层。

**真正的判据是"绕不绕过提案"**：

> 凡改变关节力矩的代码，必须由「伺服层 / 动作层」以提案形式交上来。
> 直接调 `executor.addTorque` / `drive.setTorque` / `manual.setTorque` / `applyImpulseAtPoint` 的，都是越界。

按这条判：`pair` 合规（它确实走 `propose({kind:'pair'})`，执行层拿它当写手的配置）；

## 3. 五个病根（只修，不拆）

### P1 侧向 CoP 目标有两个写手，后者把前者整段丢掉（最严重）

`squat.ts:206-225` 已经在算**论文形式的 DCM CoP 目标**：

```ts
const omega = Math.sqrt(9.81 / com.y);                                    // ≈3.19
const rawZ  = (1 + lambdaCp / omega) * (com.z + comVel.z / omega - c0.z); // =(1+λ/ω)·Δξ, λ=1
// 逐脚 ±9cm 钳位 + 按 fz 权重 3 次重分配 ⇒ zAlloc{l,r}
```

`squat.ts:289` 一句把它扔掉：

```ts
targetZ = servoOn ? ankZ + servoCop : zAlloc[side];
```

`servoOn` 来自 `LateralServo` 的 `postCop` 分支：**只按 roll、钳位 ±6mm、实测符号是反的、且 `return` 掉真 CP 环**。

| 观测 | 值 |
|---|---|
| `comZ=+39mm, velZ=+21mm/s` | 应给正向 → 实际 `copReq=−6mm`（反号） |
| `Mdes[0]` | 2~11 N·m，其中 ≈+6.4 是 `SQC_MUSCLE_F=-230` 的**常值**前馈（占一多半） |
| `SQC_COP_Z_LIMIT 0.09→0.15` | **逐位零变化**（9cm 钳位不在生效路径上） |
| `SQC_LAT_SERVO_POST_ROLL=0` | 3.98→**4.84 s**，roll 峰值 51°→24° |

**修法（不改写手，不改数值）**：`postCop` 分支关掉（默认值改成 0），让 `targetZ` 回到 `zAlloc`。
`copReq` 全项目**只有一个消费点**（`squat.ts:230`），`footPad.ts` 用的是独立的 `ankleCoPTarget`，
所以这一步**不可能影响站立**——但按你的规矩，仍然要过闸门验证。

### P2 躯干每轴被两条定律并联，永不仲裁

| DoF | 定律 A | 定律 B |
|---|---|---|
| spine1-3 轴 0/1 | `passiveLock.spine`（ext, K=100） | `supportClean.arm`（torque, `I·ω²·0.5`） |
| spine1-3 轴 2 | `pairBase`（pair, kp≈280） | `supportClean.arm`（torque） |
| neck 轴 2 | `pairBase`（pair） | `supportClean.arm`（torque）**×2 次** |

`ext`/`torque`/`pair` 相加 ⇒ 调 A 会改 B 的表现。

### P3 `ARM_AXES` 里 neck 写了两遍，`supportClean` 每帧调 4 次

`supportClean.ts:51-55` 里 `['neck',0..2]` 出现两次；调用点在 `main.ts:628/641` + `court.ts:594/595`。
⇒ 蹲姿每帧 **27×4 = 108** 条躯干提案，其中 60 条是同帧重复（`torque` 是赋值语义，前 3 遍白算）。

### P4 `hip/0` 侧向锁被 `knee/1` 扭转门嵌套（`squat.ts:588-591`）

```ts
if (fz < 0.1 * W) continue;
const e = (baseAng(`knee_${side}`,1) ?? d.angle) - d.angle;   // ← knee 轴 1 的误差

```

膝盖扭转稳定 ⇒ 髋侧向锁不跑。实测 `HIPCM t=4.10 raw=50,−50 common=0 diff=50` 只在触发时才出现纯滚转力偶。

### P5 `base` 与 `tco` 塞进同一个字段

实测 `base` 占 `τ` 的 78~99%，闭环项只占 1~22%；且 **`SQC_COACT_HIP_K` 默认 0**（膝是 200）
⇒ 矢状髋**完全没有误差反馈**。单变量实测 `COACT_HIP_K=600/B=40` ⇒ 3.98→**5.73 s**。

## 4. 新架构：一个指挥官 + 四层 + 三条通道

> ★★ **范围声明（2026-10-26 用户：「我们只做的蹲姿伺服啊」）**
> 本节及 4.1–4.4 **只描述蹲姿伺服**，不涉及站立、不涉及行走/迈步。
> 再收一层：**本轮只做侧向**。用户原话「矢状只要有基础力基本没问题，现在是侧向的问题，
> 等矢状出问题了再补矢状的回正力」⇒

#### 4.2.1 为什么不写常数：支撑多边形骗人（我们自己的实测）

论文里所有"CoP 必须落在支撑多边形内"的判据，都隐含假设 **CoP 可以在支撑多边形内任意瞬移**。
真实双足做不到——侧向要挪 CoP 必须**差动卸载**一只脚，而卸载有**时间常数**（Jonsson 2007
把体重转移分成"初始推力 + 卸载相"两段，卸载相**有明确时长**，正是这个时间常数在限制）。

我们自己的实测（`probe-push [Z]`）把这个失真量测出来了：

| 轴 | 支撑多边形（论文口径） | 实际被动（等载荷） | 失真 |
|---|---|---|---|
| 前后（矢状） | ±0.110 m | **±0.110 m** | **1.0×（没失真）** |
| 侧向 | ±0.266 m | **±0.070 m** | **3.8×** |

★★ **这个不对称恰好是模型的验证**：矢状面 CoP 挪动是**两脚同向**（不用改载荷比），所以没有速率限制
⇒ 被动 = 主动；侧向必须**改载荷比**（一脚卸载）⇒ 被卸载速率卡住 ⇒ 被动只有主动的 26%。
也就是说，"用支撑多边形当阈值"在矢状面**恰好**对，在侧向**高估 3.8 倍**——
这正是蹲姿侧向一直救不回来的结构性原因。

#### 4.2.2 论文给了什么

| 文献 | 给的东西 | 在**蹲姿侧向**里用在哪 |
|---|---|---|
| **Hof 2005**（J Biomech 38:1-8）《The condition for dynamic stability》 | `XCoM = c + ċ/ω`，`ω = √(g/l)`；稳定裕度 `b` = XCoM 到支撑边界的距离；还给了**时间裕度 τ** = 不干预时多久到边界 | 安全区的**判据变量**（不是位置误差，是侧向 DCM 余量 + 时间裕度） |
| **Patton 1999** | 实测轨迹证明力矩边界有效；**力矩边界上的裕度与"CoP 安全裕度"（CoP 到脚缘最近距离）高度相关** | 用侧向 CoP 余量做可观测量是对的；不用另建状态估计 |
| **Caron 2019 / IPM**（capture problem） | 变高度倒立摆的可行性 = CoP 在接触面内 **且** `λ ∈ [λmin, λmax]`，`λ` 由 CoM 高度范围给出 | ★ 蹲姿**高度在变** ⇒ `ω` 在变 ⇒ 可行集随蹲深变。这是"动态"的**正规来源**，而且蹲姿正好是它要解决的情形 |
| **HULK 2026**（arXiv 2610.08970） | 安全函数 `h_cp = dist(ξ, 可行支撑域)`，当 CBF 用 | 现代做法：**拿"到可行域的距离"当安全函数**，不是拿坐标当阈值 |
| **Jonsson 2007**（Gait & Posture） | 体重转移 = 初始推力 + **卸载相**，卸载相**有明确时长**（老人更长）；力的幅值/速率与年龄无关 | 卸载速率 `ρ` 是**独立的设计量**，不能从支撑面几何推 |
| **Pai & Patton 1997**（J Biomech 30:347-354） | 可行稳定域边界**先由执行器能力（摩擦/肌力）决定，而不是纯几何支撑面** | ★ 这是"**按 fz 实时分配**"的依据：权限随当前载荷变，不是常数表 |

> 不采纳：Koolen 2012 的 n 步可捕获性（那是迈步恢复的框架，蹲姿原地不发生迈步）。

#### 4.2.3 由此得到的动态安全区（**只算侧向**，可直接实现）

```text
① 侧向 DCM（Hof 2005；蹲姿高度实时变 ⇒ ω 实时变）
   ω(t)  = √( g / z_c(t) )              z_c = 当前 CoM 高度（蹲深一毫米它就变）
   ξ_z(t) = c_z(t) + ċ_z(t)/ω(t)        只取侧向分量（矢状本轮不进安全区）

② 侧向可达 CoP 半宽（**零标定**，全部实测）
   ★★ 2026-10-26 修正：原方案要标定"卸载速率 ρ"。用户指出「这个是动态的吧，需要你根据实际
      情况来定吧」⇒ 改成**瞬时可达口径**，ρ 直接取消。

   净 CoP 侧向位置有一条**恒等式**（力矩平衡，不是近似）：
        z_p = (fz_L·z_L + fz_R·z_R)/W  +  (τ_L + τ_R)/W
   ② 项的上限当场可算：`min(τmax, fz_side·半脚宽)` ——
      后一项就是"CoP 不能跑到鞋底外面"，是几何硬约束（`supportClean` 的 fw=0.045）。

        reach(t) = Σ_side [ min(τmax_side, fz_side·0.045) − |τ_side| ] / W
        zCop0(t) = (fz_L·z_L + fz_R·z_R)/W        （零踝力矩时的净 CoP）

   ★ 这条**一个标定常数都没有**：fz、已用力矩、力矩上限、脚宽全是实测/几何量。
     蹲深一变（z_c、τmax、fz 全变），reach 自动跟着变。实测蹲姿全程 reach ∈ **3.2–4.4 cm**。
   ★ 代价 = **故意保守**：它不含"靠差动卸载把 CoP 摊到整个支撑面"的那部分
     （实测被动 0.070 → 主动 0.266 的差额），因为那才需要 ρ。
     低估只会让回正力更早介入；高估才会让系统以为还救得回来 —— 现在的 `fall=3.98s` 就是高估造成的。
     若以后确认太保守（表现为长期贴边界），再按 `p_avail = p_foot + (p_stance−p_foot)·min(1, 2ρ/ω)` 把 ρ 项加回来。
   ★ 矢状面不动：实测 被动 = 主动 = ±0.110，本条对矢状无影响，故本轮不接。

③ 安全函数（HULK 2026 的 h_cp 形式，但用"可达域"替掉"几何支撑域"）
   h(t) = reach(t) − |ξ_z(t) − zCop0(t)|     ← h ≤ 0 表示这一瞬间已无 CoP 权限截住发散
   ★ 实测：h 直到 **t=3.98s（= 倒下的同一刻）** 才穿零 ⇒ **权限从来不是瓶颈**（第三次独立确认 P1）。
   ★ 所以**档位判定不该用 h**（它只在最后一刻才有区分度），要用**归一化偏离**：
       ratio(t) = |ξ_z(t) − z_站心| / reach(t)        ← 偏离站心 = 还没被权限吃掉的量
       进区 ratio < 0.5；出区 ratio ≥ 1.0（+ 连续 6 帧去抖）
   ★ 实测：ratio 在 **t=3.60s** 穿 0.5，比 fall 早 **0.38s（182 帧）**
     ⇒ 够做**档位切换**（这是它的用途），但**不能**当"提前预警"。

④ 时间裕度（Hof 2005 的 τ，做第二判据/去抖）
   b = zCop0 ± reach（可达边界）
   τ(t) = (1/ω)·ln( (b − z_p) / (ξ_z − z_p) )      z_p = 当前实测净 CoP
   实测：τ 从 0.85s 一路掉到 0.11s（t=3.62）—— 与 ratio 同量级的预警能力。
```

| | 区内（`level=0`） | 区外（`level=1`） |
|---|---|---|
| 目标 | **高精度**压到 0，消稳态 | **不做高精度**，只求缩短回到区内的路程 |
| 增益 | 小 P + I | 大 P，无 I，**限速** |
| 力矩上限 | **小**（≤8 N·m） | 按权限余量（各层实际的 fz·力臂） |
| 抖动防护 | 积分抗饱和 | 限幅 + 限速，避免硬掰 |

**为什么区内必须小力矩**：侧向被动权限只有 ±0.070 m、单脚半宽 5 cm。
大扭矩只会顶到权限边界 → 饱和 → 变成 bang-bang 抖动。**小力矩 + 积分**才是唯一能在 ±5 cm 内精确收敛的形态。
**为什么区外不做高精度**：误差已大于权限，精度没意义；唯一目标是**缩短回到区内的路程**。

> ★ `ρ`（卸载速率）是这套公式**唯一还没定的数**，而且它决定一切：
> `ρ = 0.5 /s` ⇒ `p_avail` ≈ 0.131 m（只比被动多 6 cm）；`ρ ≥ 1.6 /s` ⇒ 直接饱和到 0.266 m。
> **必须从我们自己的机体里量，不能从文献抄**（文献只说"有卸载相、有时长"，没给我们的机体的数）。
> 量法：命令一脚卸载，记录 `|d(fz_l/W)/dt|` 的最大值 = `ρ`。

### 4.3 统一指挥：一套增益 + 按 fz 实时分配，代替五套 PD

现在的五套（全部**保留为数值，不删**，只是不再各自充当控制器）：

|---|---|---|

| 髋 | `Kh=10+150·fz/W` / `cap=50` | `a_hip` |
| 膝（仅蹲姿） | `SQC_COACT_K=200` / `B=20` / `cap=30` | `a_knee` |
| 踝 | `rollK=0.9` / `Mx≤40` | `a_ankle` |

> ★★ **分配系数按 fz 实时算，不是常数表**（用户 2026-10-26：「按 fz 载荷实时分配」）。
> 依据 Pai & Patton 1997：可行域边界由**当前执行器能力**决定而非几何。
> 常数表（我原来写的 0.55/0.20/0.18/0.07）作废。

```ts
// ── 单一增益（全部从 env 读，便于扫参）：只有一套，不再分层各算各的 ──
const g = level === 0
  ? { kp: 6,  kd: 0.6, ki: 1.2, cap: 8  }     // 区内：小力矩高精度，I 消稳态
  : { kp: 24, kd: 1.2, ki: 0,   cap: 60 };    // 区外：大但限速，不求精度

const tauTotal = clamp(g.kp * e + g.kd * v + g.ki * intE, ±g.cap);

// ── 分配：每层的"权限"∝ 该层当前能产生的侧向 CoP 位移量 ──
//    踝：直接搬 CoP，权限 ∝ fz_side · 脚半宽
//    膝/髋：只能靠差动卸载改净 CoP，权限 ∝ 该脚当前承载 fz_side（卸载余量）
//    背肌：不接触地面，改的是躯干角动量，没有 fz 可依 ⇒ 单独一项，不吃 fz 权重
const W = w.sk.massTotal * 9.81;
const fzL = body.footNormalForce('l', w.dt);
const fzR = body.footNormalForce('r', w.dt);
const auth = {
  ankle: (fzL + fzR) * FOOT_HALF_W,                    // 两侧踝合计
  knee:  Math.min(fzL, fzR) * KNEE_LEVER,              // 差动卸载只受"弱侧"限制
  hip:   Math.min(fzL, fzR) * HIP_LEVER,
};
const sumA = auth.ankle + auth.knee + auth.hip;
const a = {
  ankle: auth.ankle / sumA,
  knee:  auth.knee  / sumA,
  hip:   auth.hip   / sumA,
  back:  BACK_SHARE,                                   // 独立项，默认 0.05，不进 fz 归一
};
```

★ 注意 `min(fzL, fzR)` 而不是 `(fzL+fzR)/2`：**差动卸载的上限由承重少的那只脚决定**——
想往左挪 CoP 就得让左脚多承、右脚少承，右脚一旦离地就没有"再少"的余量了。
这一条是从实测（等载荷时侧向只有 ±0.070）反推出来的，不是猜的。

### 4.3.4 「侧偏后无回正」的真相：不是力矩不够，是**没有载荷差**

三条硬事实：

1. **踝从 2.02s 就已是 11.2°，2.45s 起稳在 13.8°**（限位 ±14°），而力矩只用 **7~40%** 预算。
   ⇒ 一开始它**根本没被要求去推**（CoP 需求≈0），不是推不动。
2. **把限位放宽到 ±20°/±25°，结果与 ±14° 逐位相同** ⇒ **限位不是瓶颈**（这条排除了"行程不够"）。
3. **`fz` 全程 50/50，一次都没变过** ⇒ **从来没有"脚多发力"**。到最后（5.30s）需求上来了，

#### 算一笔账：为什么必然走到这一步

DCM 律的需求量是 `rawZ = (1 + λ/ω)·ξ`，实测 `λ=1.0`、`ω≈3.19` ⇒ **`rawZ ≈ 1.31·ξ`**。
当 `ξ = 4.77 cm` 时需求 **6.2 cm**，而**单脚鞋底半宽只有 4.5 cm**。
等载荷下净 CoP 只能在**单脚半宽**内动 ⇒ **6.2 > 4.5，物理上无解**，踝只能拧到边。

要让净 CoP 到 6.2 cm，必须做**载荷差**：

```text
净 CoP = w_L·copL + w_R·copR,  copL/R 最多到 ±(脚心 ± 半宽) = ±0.21 m
求 w:   w_L·0.21 − w_R·0.21 = 0.062  ⇒  w_L − w_R = 0.295  ⇒  载荷比 65 : 35
```

而实测载荷比恒为 **50 : 50**。⇒ **缺的正是一个"申请"环节：当 CoP 需求超过单脚半宽时，
先把载荷比推过去（脚多发力），踝才有权限可用。**

#### 因此下一步（改成"申请制"，不是再加一条力矩写手）

```text
① 需求  d = (1 + λ/ω)·ξ                        现成（squat.ts:210 rawZ）
② 被动可给 p_pass = 单脚半宽 ±0.045             （等载荷）
③ 若 |d| > p_pass  ⇒ **申请**：要的载荷比
      w_L − w_R = clamp(|d| / 0.21, 0, 1) · sign(d)
   由**膝/髋伸展差**去实现（哪边要重就哪边多伸），不是继续拧踝。
④ 踝只在 |d| ≤ p_pass 时才用角度/力矩去追 —— 超出就交给载荷差，踝保持不偏。
```

> 关键：③ 的"多发力"是**改变竖直力分配**，不是加力矩。`τmax` 再大也没用（那是执行器上限），
> 真正限制是**鞋底几何 + 载荷比**。这也解释了为什么前面把 `cap_out` 从 40 提到 60 完全没变化。

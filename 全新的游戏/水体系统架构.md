## 0. 一句话架构

**水体是地图里的独立实体；所有水体共用一张"公用水纹理"；每个水体独立存储自己的几何与状态。**

```
公用水纹理（静态 clipmap，全局共用）      每个水体（独立存储）              涟漪（世界坐标解析场）
  R=水深 G=到岸距离 B=掩码 A=泡沫/湿边  →  几何：规则网格（body 包围盒内）   →  CPU 池 + 16 槽叠加
        │                                        │                              │
        └──────────── 采样同一 uv / 同一 mip ─────┘                              │
                     ⇒ 岸线只有一处定义 ⇒ 不会有缝                              │
```

**不变的东西**：求解算法（探针/安定/增量 dig）· 水位语义 · 玩法查询接口 · 挖坑联动流程 · worker 协议。

## 3. ★ 定稿架构

### 3.0 架构总览（v3：两级水体）

```
┌ 公用 FFT 大纹理（全局、只读、一次烘）★ 波形主来源 ─────────────┐
│  多层波高/位移/法线（现有 OceanBaker 那套，可加大）              │
│  采样：世界坐标平铺 uv = wp.xz / layerScale ⇒ 跨 chunk 无缝     │
└───────────┬──────────────────────────────┬─────────────────────┘
            │                              │
   ┌────────▼─────────┐        ┌───────────▼──────────────────┐
   │ WaterBody（shared）│        │ WaterBody（dedicated）         │
   │ 默认档：只采样公用 │        │ 精细档：**自己一张局部 RT**     │
   │ 远处 = 裁一块      │        │  · 涟漪写进这里（掩码化）       │
   │ 近处 = 裁自己那块   │        │  · 岸交界细节也在这里算         │
   │ 无 RT、零额外开销  │        │  · 坐标系 = **body 局部**（世界锚定）│
   └───────────────────┘        └──────────────────────────────┘
            │                              │
            └────────► 水面几何 ◄─────────┘
                 近处：细网格（body 内 16m tile）
                 远处：大 quad / 粗网格（1 个 draw call）
```

**一句话**：**每个水体默认复用公用 FFT 大纹理；需要精细（近处 / 有涟漪 / 岸交界复杂）时，该水体自己重算一张专属纹理。**

> ★ 这版比早期方案**更简单**：砍掉了「公用水属性图 + clipmap 烘焙管线」——
> 波形单一来源（FFT）、岸的形状靠几何、跨 chunk 一致性由世界坐标采样白送。

### 3.1 三个层次（互不重叠）

| 层 | 是什么 | 生命周期 | 归属 |
|---|---|---|---|
| **① 公用 FFT 大纹理** | 一张（组）全局只读贴图：多层波高/位移/法线 | 启动时烘一次（现状已有） | **全局共用**，所有 body 都可采样 |
| **② 共享涟漪场** | 一张**世界对齐**的可写 RT：涟漪（+ 岸交界细节可后加） | 常驻（玩家移动时滚动内容） | **全局共用**（远近水面都按世界坐标采它） |
| **③ 水面几何** | 近处细网格 / 远处大 quad | 随 body，按 LOD 档重建 | body 私有 |

**body 档位（tier）**：

| 档 | 拥有 | 什么时候 | 成本 |
|---|---|---|---|
| `shared`（默认） | ① + ②（共享涟漪场） | 永远 | 零额外开销 |
| `dedicated` | ① + ② + **自己的局部 RT** | 需要更精细的**岸交界/波形**时 | 一张局部 RT |

> ★ 涟漪**不进** dedicated RT（远处 body 巨大，局部 RT 覆盖不了）⇒ 涟漪走**共享场**。
> dedicated 档留给"近岸精细化"这类需求（可后置）。

### 3.2 ① 公用 FFT 大纹理（只读，预制/一次烘）

```
内容：多层波高(HD) + 位移(GB) + 法线(N)，每层 2 个相位变体
现状：3 层 × 64²/128² × 2 变体 = 12 张 HalfFloat（OceanBaker，Worker 烘，5s 超时回退同步）
采样：uv = wp.xz / uLayerScale + scroll × t   ← 世界空间平铺 ⇒ 跨 chunk 无缝 ✔

★ 本方案要做的是【把它做大 + 远处也用它】：
  · 近处：照旧，顶点位移（现状）
  · 远处：裁一块（**按 body 给确定性随机偏移**，种子 = body id ⇒ 可复现）
    ⚠️ 偏移必须**按 body 整体**给；若每个 quad 各自随机 ⇒ body 内相邻 quad 波形在接缝跳变 ⇒ 可见断裂
  · 远处若用大 quad（4 顶点）→ **没有顶点位移**，只剩片元法线 ⇒ 远海偏平
    ⇒ 建议远处用 8~16m 格网格（几百顶点）+ 顶点采样本纹理 ⇒ 有起伏、仍 1 个 draw call
```

```

**归属合并**：union-find，**union-by-min**（块坐标字典序小的当 root ⇒ 最终 root 与 union 顺序无关 ⇒ id 稳定可复现）。

### 3.5 ★★ body 级统一水位（用户设计的核心：「整个连通的 body 水位一起下降」）

> ★ 2026-10-27 用户指出：**「我的设计是整个连通的 body 水位一起下降，现在只有 4×4 的区域才下降」**
> ⇒ 架构顺序纠正：**body 级水位是第一步，不是最后一步**。

#### 为什么之前只有 4×4 区域降

```
挖坑 → patchRebuildChunk(cx,cz,dirty) → waterSolve.compute({cx,cz,dirty})
     → computeWaterOnly → buildWaterSurface(table, src, patch, dirty)
     → updateSolve → settleComp   ← ★ BFS 被 occ 锁死在本 chunk 内
⇒ 只有那个 chunk 的 L 变，body 的其它 chunk 不变 ⇒ 水面出现台阶
```
根因：**求解的状态与作用域都是 per-chunk**（`waterStates` 按 chunkKey、`initSolve` 的 BFS 出不了 chunk）。
body 只是**存储归属**，求解层根本不知道 body 存在。

#### 改法：不重写求解器，只把「L 的决定权」提升到 body 级

| | 改前 | 改后 |
|---|---|---|
| 探针采样（唇位） | per-chunk | **不变** |
| **水位 L 的决定** | per-chunk 分量各自算 | **body 级：min(所有成员的唇)** |
| 干块 / deep / 几何 | 用本 chunk 的 L | **统一用 body.L**（`forcedLevel`） |
| L 变化时 | 只有本 chunk 重发 | **body 内所有 chunk 重发** |

**实现**：
```
① 求解器加 forcedLevel（外部水位覆盖）：
   settleComp(..., forcedLevel)  → L = min(0, forcedLevel)，**跳过探针唇位计算**
   （探针是 5cm 采样，最贵的一步；body 统一水位时唇位由协调器汇总给出）
   ★ no-patch 基线路径也要吃 forcedLevel（否则没被挖过的 chunk 不会跟着降 ⇒ 两层水）
② 求解结果带 level（本次用的水位）⇒ 主线程当「本 chunk 的唇候选」
③ WaterStore 记 chunkLip[chunkKey] ⇒ bodyLevelOf(bodyId) = min(所有成员的唇)
④ ChunkManager.onWaterSolved：唇更新 → body.L 变了 ⇒ flushBodyResend：
   对 body 内每个已加载 chunk 排 waterSolve.compute({..., dirty:null, forcedLevel: body.L})
   ⇒ 干块/deep/几何一并统一 ⇒ **整个连通水体一起升降**
⑤ 收敛：重发后各 chunk 报告 level = body.L ⇒ min 不变 ⇒ 不再触发
```

**固有边界（已知取舍）**：
- 远处**未加载**的 chunk 不参与 min（只有已知成员）⇒ 它加载后会带来更低的唇 ⇒ 再触发一次全体重发（一次性成本）
- body.L 只降不升的假设在物理上成立（玩家只能挖）

#### ★★ body 的分组语义（用户定，2026-10-27）

> 用户原话：「我的设计就是水体脱离chunk，**一个水体可以跨越多个chunk**」、
> 「现在初始就是各个chunk的水体独立」、
> 「**一个水位下降，同一个body内的水体一起降**」、「**取最body内小高度**」。

| | 旧口径（我写错的） | **新口径（用户设计）** |
|---|---|---|
| chunk 内 | 水块按 **4 邻域连通分量**分组 ⇒ **岛/沙洲把一片湖切成 N 个 body** | **chunk 内的所有水 = 一体**（岛只是湖里的陆地，不该分裂水体） |
| 跨 chunk | 相邻块 4 邻域相接才合并 | 保持（相邻 chunk 的水相接 ⇒ 合成一体） |
| 水位 | 每个分量各自算 | **body.L = min(body 内所有成员的唇)**（用户：「取最body内小高度」） |

> ★ 实机证据（2026-10-27 HUD 诊断）：玩家所在 chunk **同时属于 9 个 body**，且各 body 的
> 成员 chunk 集合互相重叠 ⇒ 一个带岛的湖被切成了 9 个 body ⇒ **各自算水位 ⇒「各降各的」**。
> ⇒ 改成「chunk 内一体」后，带 3×3 大岛的湖 = **1 个 body**（离屏探针已验证）。

#### 实现
```
WaterStore.registerChunkWater(chunkKey, worldBlocks):
  ① 逐块登记（union-find，parent/block 集合/chunk 集合）
  ①b ★★ 本 chunk 的所有水块 union 到同一 root ⇒ chunk 内一体
  ② 与 4 邻方向的**已登记**块合并 ⇒ 跨 chunk 的同一片水域合成一体
  ★ union-by-min ⇒ bodyId 与登记顺序无关（稳定可复现）
```

#### 水位如何驱动「一起降」
```
每 chunk 求解完成 → 报告自己的唇（raw.level）
  → WaterStore.setChunkLip
  → bodyLevelOf(bodyId) = min(0, 所有成员的唇)     ← 「取最body内小高度」
  → 若变化：WaterStore.setBodyLevel(bodyId, lvl)
       ├─ 重建该 body 的**粗面**（远景）：y = body.L - WATER_Y_EPS
       └─ 排**精细面重发**：body 内水位不一致的 chunk 用 forcedLevel = body.L 重算
            （forcedLevel 下跳过探针唇位计算 ⇒ 很便宜）
  → 收敛：重发后各 chunk 报告 level = body.L ⇒ min 不变 ⇒ 不再触发
```

### 3.6 岸线与缝隙（核心问题）

#### 问题的精确表述

「公用水纹理内部的掩码」与「外部靠近岸边单独算的部分」之间可能有缝。

#### 三个根因

| # | 根因 | 为什么会错位 |
|---|---|---|
| **① 精度不同** | 纹理掩码边缘 0.125m 级；水面几何边缘 1m/4m 级 | 同一条岸线被两种精度各描述一遍 ⇒ 错位 |
| **② 采样不同** | 水面层与近岸层取到不同 mip / 不同 uv 变换 | 同一世界点采到不同掩码值 ⇒ 错位 |
| **③ 语义不同** | 水面用「掩码=0」，近岸用「到岸距离<阈值」 | 两个判定标准各判各的 ⇒ 错位 |
| **④ ★ 位移不受岸线约束**（现状已存在） | FFT 位移有 `border < 0.5` 约束（`WaterMaterial.ts:273`），**涟漪 shake 没有**（`:270-271`，注释明说「不再受 border 静止约束」）；片元涟漪法线也没有（`:448-457`） | 涟漪把**岸边顶点抬起来**、岸线像素法线被打乱 ⇒ 岸线抖动/锯齿 ⇒ 看起来就是「岸线有缝」 |

> ★ **根因 ① 是致命的**：只要在 **CPU 侧按掩码裁几何**，边缘精度就等于几何精度，**永远对不上纹理边缘** ⇒ 必然有缝。

#### 解法（五条，一起才成立）

| # | 解法 | 消灭哪个根因 |
|---|---|---|
| **A. 单一岸线真源** | 岸线**只由公用水纹理的掩码定义**。所有层（水面/近岸/水帘）采样**同一 uv、同一 mip 级** | ② ③ |
| **B. 几何不裁、像素裁** | 水面几何 = 规则网格**全覆盖** body 包围盒，**不做 CPU 侧掩码裁剪**；片元里 `alpha = mask`（`discard` 或 blend） | **①（致命项）** |
| **C. 近岸是叠加层，不是拼接层** | 近岸**不另起几何与水面拼**，而是**同一张网格上多画一层**（泡沫/湿边/亮边），由同一掩码的「近岸带」（G 通道 < 阈值）驱动 | ③ |
| **D. 边界处重叠 + 交叉淡化** | 若确有必须分离的几何（如竖直的水帘），在分界处让两层**重叠一小段**，并用**同一掩码值**做 alpha 交叉（一层淡出、另一层淡入）⇒ 数学上连续 | ① ③ |
| **E. ★ 所有几何位移都服从掩码** | **FFT 位移与涟漪位移用同一把尺子**：用 G 通道「到岸距离」调制 ⇒ 离岸近时位移衰减到 0 ⇒ 岸线顶点完全不动 | **④** |

#### ★ 涟漪与公用水纹理的关系（不是「替代」，是「叠加」）

```
公用水纹理（静态空间属性）：水深 / 到岸距离 / 岸掩码 / 泡沫   ⇒ 决定「水在哪儿、多深、离岸多远」
涟漪场（动态扰动）：      波高 / 法线                        ⇒ 决定「水此刻怎么动」
FFT 海况（现状已有）：     波高 / 法线                        ⇒ 大尺度海况
```

**原则：涟漪只改「水怎么动」，绝不改「水在哪儿」。**
- 岸线（alpha）**只**由公用水纹理决定 ⇒ 涟漪再猛也撕不开岸线
- 涟漪在采样层面与公用水纹理**同源**（同一个世界坐标 → 同一个 clipmap uv）⇒ 天然无缝
- ⇒ **不需要**把涟漪塞进公用水纹理（那会把「静态增量烘的 clipmap」变成「每帧要写的动态图」+ ping-pong，更贵）

#### 判据（可测，不是"看着像"）

| 判据 | 做法 |
|---|---|
| **掩码一致性断言** | 探针：对同一世界点，水面层与近岸层采样到的掩码值必须**逐位相等**（同 uv、同 mip）⇒ 不等即 FAIL |
| **岸线零位移断言** | 探针：在掩码=岸 的像素上，涟漪位移与 FFT 位移之和必须 **= 0**（岸线顶点完全不动）⇒ 不等即 FAIL（现状会 FAIL） |
| **边缘连续性** | 岸线处放大 4 倍截图，检查有无 1px 亮/暗缝 |
| **无 CPU 侧裁剪** | 代码审查：`WaterSurface` 侧不得再出现「按掩码决定三角形取舍」的逻辑（现有 `filled` 标记要退化为「只发水块」而不是「决定边缘」） |

> ★ **一句话**：**只要"裁剪"发生在片元 alpha，而不是几何取舍，缝就不可能存在** —— 因为那时边缘的分辨率是像素，与掩码完全同源。

### 3.6 LOD 与档位

| | 几何 | ① 公用 FFT | ② body 专属 RT | draw call |
|---|---|---|---|---|
| **近处**（< 80m） | 细网格（body 内 16m tile） | 三层全量 | 采（涟漪 + 岸交界） | 近处 tile 数 |
| **中处**（80~250m） | 粗网格（body 合并） | L0+L1 | 采（若 dedicated） | 1 / body |
| **远处**（> 250m） | 大 quad / 8~16m 格 | 裁一块（body 随机偏移） | 不采 | 1 / body |
| **极远** | 无（超出 clipmap） | — | — | 0 |

- **切换**：滞回带（对齐地形 60/70m 做法）+ **分帧预算**（每帧最多重建 N 个 body）
- **tier 升降**与 LOD 解耦：tier 管「有没有专属 RT」，LOD 管「几何精度」
  - 升级：玩家进入 body 包围盒扩张区 / 发生涟漪
  - 降级：涟漪衰减完（2s）且玩家离开 ⇒ 回收 RT
- ★ **离屏图 = 内容，LOD = 采样精度**，两者正交（比"raw 后处理降采样"干净）

### 3.7 生命周期与 chunk 解耦

| 事件 | 现状 | 目标 |
|---|---|---|
| chunk `park`（>4 块） | 水 mesh 随 group 离场 | **水不动**（只隐藏） |
| chunk `destroy`（>6 块） | 水几何被 dispose | **不动水**；只从 `body.chunks` 减引用 |
| chunk 重建 | 水重算 | 不变 |
| 挖坑 | 水重解该 chunk | 不变（worker 协议不动） |
| 模式退出 | 水随 chunk dispose | `WaterStore.dispose()` 一次性释放 |

### 3.8 ★ 涟漪：一张**世界对齐的共享涟漪场**（不是每 body 一张）

> ★ 2026-10-27 用户定调（v4）：
> 「远处的水还是要有子弹击中的涟漪、突起之类的，**敌人进入远处的水也要有反应**，只是距离远精度可以差一点」
> ⇒ 涟漪**不能是 body 私有的**（远处 body 可能巨大如一片海，局部 RT 覆盖不了）
> ⇒ 但**也不能是「围着玩家转」**（涟漪会跟着玩家跑）

**正解：载体跟玩家走，内容世界对齐。**

```
涟漪场 RT（512²，覆盖玩家周围 256m ⇒ 0.5m/texel）
  载体：跟随玩家（覆盖「战斗区」——涟漪只发生在有活动的地方）
  内容：**世界对齐**（玩家移动时把内容按位移 blit 过去 ⇒ 涟漪固定在世界坐标上）
  采样：所有水面按**世界坐标**采样同一张 ⇒ 远近一致、位置正确
```

| | 被否掉的方案 | **本方案** |
|---|---|---|
| 载体（RT 在哪） | 围着玩家 | 围着玩家（一样） |
| **内容（涟漪在哪）** | **跟着玩家跑** ✗ | **世界对齐** ✓ |

**写入流程**：
```
① 事件源（4 类，见下）→ 世界点 (x,z)
② 世界点 → 所属 body（bodyIdOf）→ 局部 uv（若该 body 无专属 RT，用共享场）
③ 在涟漪场对应位置画一圈（additive）
④ 每帧衰减（ping-pong 或 decay pass）
⑤ 所有水面 shader 按世界坐标采样 ⇒ 近处精细、远处稍粗（精度差一点无妨）
```

**事件源（现状 4 类，全部走 `sharedWaterMaterial.addImpact`）**：

| 事件 | 强度 | 现状 |
|---|---|---|
| 玩家走进水面 | 0.8 | ✓ |
| 玩家高处落水 | ≤1.6 | ✓ |
| 玩家水中移动泛波 | 0.28~0.55 | ✓（**每 0.2~0.34s 一次** ⇒ 刷槽大户） |
| 子弹落水 | 1.4 | ✓ |
| **L3 敌人入水** | 0.8 | ✓（`WorldMode.ts:1635` 喂 `this.enemies`） |
| L2 代理入水 | — | **不做**（用户定：L2 不管） |

#### ★★ 已实施的缓解（2026-10-27）：涟漪槽位改「强度优先」

**问题**：6 个 uniform 槽会被「玩家水中移动泛波」（每 0.2~0.34s 一次、强度仅 0.28~0.55）刷满
⇒ **子弹落水（1.4）/ 敌人入水（0.8）这类强事件被弱涟漪挤掉** ⇒ 看起来「完全没反应」。

**改法**（`WaterMaterial.addImpact`）：
```
① 有空槽 ⇒ 直接占
② 无空槽 ⇒ 找【最弱】的槽；新涟漪比它更弱 ⇒ 放弃（不挤掉更强的）
              强度相同 ⇒ 替换其中【最旧】的（保证新事件可见）
```
**另**：敌人**只在入水瞬间**给一次波纹，之后涉水不再周期性冒泡（`WaterFx.entry` 的移动泛波分支加 `isPlayer &&`）
⇒ 几十个敌人涉水时不再每 0.2s 抢一次槽 ⇒ 事件量骤降，视觉噪音也降。

> ★ 这只是**缓解**；根治仍是「涟漪掩码化」（P2b）—— 纹理化后无槽位上限、天然干涉。

#### ★★★ 已实施：**先视锥裁剪，再 LOD**（2026-10-27 用户定）

**判据链**（`WaterMaterial.addImpact`）：
```
① 距离闸：> RIPPLE_VIEW_DIST(60m) ⇒ 直接丢
   （与 shader 的 uLodFar=55m 对齐：更远的涟漪本来就被 lodW 淡成 0 ⇒ 零视觉损失）
② 视锥判定：视锥外 ⇒ 直接丢（用涟漪半径 6m 做球，避免边缘误杀）
③ 无相机（基地/室内）⇒ 保守接受（不丢效果）
④ 过了裁剪 ⇒ 才谈占用：空槽优先 → 否则**强度优先**（见上）
⑤ LOD（shader 侧）：lodW = 1 - smoothstep(12, 55, camDist)
   近处全量（顶点抬起 + 法线扰动）→ 远处幅度衰减（仍有"突起"，只是弱）
```
**收益**：视野外的涟漪**不占槽** ⇒ 有限的 6 个槽全留给"看得见的"涟漪
⇒ 子弹落水 / 敌人入水这类强事件被挤掉的概率大幅下降。

**相机喂值**：`WorldMode.render()` 每帧 `sharedWaterMaterial.setViewCamera(this.camera)`。

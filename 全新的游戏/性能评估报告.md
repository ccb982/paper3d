# 性能评估报告

> ★ 2026-09-14 · 采集设备：本机（AMD Radeon(TM) Graphics 集成显卡，ANGLE/D3D11，Chrome headful），主测 1280×800，1080p 对照。
> 目的：对「当前性能有点差」做**可复现的量化归因**。全部数字来自 `scripts/perf/data/*.json` / `*.cpuprofile`。
> **更新记录**：2026-09-14 —— ① 图标烘焙同步回读已改**异步 PBO + 不可见暂停**（§6 P0，已落地）；
> ② 新增「采集物专项评估」（§6.5，含 VAT/不透明管线/纹理数组优化前后实测）。

## 1. 结论先行

| 维度 | 客观数据 | 判定 |
|---|---|---|
| 稳态帧耗时 | wall p50 ≈ **6.6–6.8ms**（≈142–145fps，贴近 144Hz 预算） | 稳态**良好**，非瓶颈 |
| CPU 逻辑 | WorldUpdate 均值：idle 0.59 / run 0.86 / cbt150 1.73ms | **轻**，远低于预算 |
| 渲染 | render 均值 ≈ 3.1–3.7ms @800p；1080p 墙钟几乎不变（均值 7.05ms） | 中等；0.81–0.88M 三角/帧偏高 |
| **周期性尖峰** | 每秒 1–2 次 **17–52ms 单帧毛刺**（>16.7ms 掉帧率 ≈ 0.9%） | **「卡」的主因** |
| GC | 8s 内停顿 48–56ms，最长连续 **8.6ms**；usedJSHeap **370–416MB** | 分配压力大 |

一句话：**稳态帧率够高，「性能差」= 周期性单帧掉帧 + 高帧率模式下的合成/GPU 同步开销**。60Hz 屏上 p99 已达 12.8–16ms，再叠每秒 1–2 次尖峰，掉帧必现 → 表现为「跑图偶尔卡一下」。

## 4. 尖峰归因（CPU Profile × 帧级时序交叉验证）

### 4.1 CPU 热点（自耗时，8.3s/场，逐帧锲入）

| 热点 | run | cbt150 | 说明 |
|---|---|---|---|
| `readPixels`（native） | 346ms | 392ms | 最长连续 5.7 / 5.1ms —— 图标烘焙同步回读（**✅ 2026-09-14 已修复**：异步 PBO + 可见性暂停，见 §6 P0） |
| three.js 矩阵 `updateMatrixWorld` | ~521ms（3 处合计） | ~551ms | 场景图层级每帧全量同步 |
| `projectObject` | ~540ms | ~500ms | Object3D 遍历投影 |
| `getParameters` | 469ms | 486ms | 程序参数获取（three 缓存未命中面） |
| `queryFrustum` `RasterMap.ts:636` | 182ms | 200ms | 实体/块视锥查询（每帧） |
| `interpEdge` `Refinements.ts:84` | 155ms | 213ms | 地形贴地表面采样 |
| `readPixels` 时的引擎侧 `getProgram`/`getBindingState`/`renderBufferDirect` | ~430ms | ~390ms | 渲染绑定点 |
| `putImageData` | 68ms | 76ms | 小地图每帧全量 160×160 上传 |
| `update @ AmmoPanel.ts:34` | 44ms | 50ms | 弹药面板每帧刷新 |
| `get baseRgb @ Tiles.ts:17` / `blockAt` | 47ms | 50/65ms | 逐帧区块色彩/方块采样 |
| `(garbage collector)` | 48ms | 57ms | **最长连续 8.6 / 5.7ms** |

### 4.2 三类尖峰（run_spikes.capture，25s 内 20 次 >15ms 帧）

1. **`ui` 段尖峰 17–23ms，每 2–3s 一次**：与「跑图跨格」同步 → 小地图 `reveal`＋`rebuildBase`（跨格重建 25600px 底图）+ 每帧 `putImageData` 全量重传 + `AmmoPanel` 每帧刷新 + 段内堆分配。
2. **`ai`/`swarmBrain` 单帧尖峰 27–52ms**（idle/run 下 nA 仅 5、无增员）：
   - 采样 profile 中**未出现**相同时长的连续 JS 执行（最长连续 8.6ms 为 GC）→ 该读数 = 段内触发的一次性 **GC 主收集（≈9ms）＋ JIT 编译涨级 ＋ 帧交界合成等待** 的叠加，被计时窗口整体吸收；
   - cbt150 大战场（52–60 代理同帧决策）时真实蜂群成本会放大，测得 46.9ms。
3. **渲染侧单帧尖峰 15–34ms（update<2ms）**：GPU/合成器侧停顿（`readPixels` 5.7ms、`putImageData`、baseRgb 5.7ms 的连续锲入集中在这些帧）。

> 归因口径：**“46ms 的单个 JS 函数”不成立（profile 无对应长连续段）；真实原因是堆分配驱动的 GC + 编译涨级 + 小地图回读/上传的合成停顿**。治理方向因此明确：减分配、减每帧 UI 重绘/回读，而非优化蜂群算法本身。

## 6. 优化建议（按 ROI 排序）

### P0 · 消除「每帧」UI 全量重绘／回读（收益最大，风险低）
- **小地图 `update()`（`Minimap.ts:60`）无条件 `putImageData` 整幅 160×160（25600px）** —— **✅ 已落地并验证（2026-09-14）**：
  改**双层画布**（底图层：跨格时滚动 `copyWithin` + 只补新进窗口条带 ≈320px，另有"点亮圈边带"补画 |d−90m|≤4m；标记层：每帧 `clearRect` 重绘实体点/箭头）。
  三个正确性要点：雾圈中心**格量化**（跨格才变，无亚像素漂移）、滚动门收紧为 **≤4px 位移**（大位移/传送走全量，避免 reveal 点亮的中部像素不重画）、隐藏即零开销（舰内 return）。
  **验证**：跑动/斜走/回走 5s 后，增量图 vs 同参数全量重绘**逐像素 0 差异**。待办：`AmmoPanel.ts:34` 每帧 DOM 刷新（仅数值变化/按 interval）。
- **图标烘焙同步 GPU 回读（`readPixels` 346–392ms/8s、最长连续 5.7ms 的来源）** —— **✅ 已落地（2026-09-14）**：
  `DynamicIconAnimator.paint()`（`DynamicIconAnimator.ts:208`）与 `FluidIconAnimator.ts:154` 原在 rAF 循环里执行
  「离屏渲染 → `renderer.readRenderTargetPixels`（同步）→ flip → `putImageData` → `drawImage`」（~30Hz/生产线，只要 canvas 挂在 DOM 就持续回读）。
  现改为：**异步 PBO 回读**（`readRenderTargetPixelsAsync` + fence，失败回退同步；对齐 `DroneIcon.ts:183` 既有模式）+
  **IntersectionObserver 不可见即暂停**（无可见画布停 rAF，重见即续）+ 上屏缓冲零拷贝（ImageData 直接背在 flip 上）。
- 预期：p95/p99 明显回落；`putImageData`（68–76ms/8s）、`readPixels` 对应的合成锲入一并减少。

### P0 · 降低堆分配（GC 是尖峰最大的单点依归）
- 排查 `ai/ui` 段的逐帧闭包与临时对象：`WorldUIManager.update` 里的每帧 `buildAmmoEntries()` 数组、蜂群 think/move 的 `map/filter`、`allBases()` 迭代器；统一复用预分配 buffers / 简单 for 循环。
- 期望：GC 自耗时与 "最长连续 8.6ms" 均缩减，idle/run 的 ai 尖峰（27–52ms）大概率消失。

### P1 · 蜂群决策运行期预算化
- 把《蜂群架构.md》的 ≤4ms 预算落实为代码门：`SWARM_BUDGET_MS`，进入 think 循环前取 `performance.now()`，累计超预算即截断本帧剩余 agent（降档到下帧）。cbt150 已见真实蜂群成本放大（46ms），预算门直接封顶。

### P1 · 三角形/绘制预算
- 0.81–0.88M 三角、158–191 调用与敌人规模无关 → 地形主导。复核远景环（>30m）细分等级是否能再降一档 / 使用 instancing；剔除以 60m 为最细的全细节 chunk 面数。可压低 iGPU 填充与绑定（`getParameters/getProgram` 469ms/8s）。
- **2026-09-14 补充**：`rushTerrain` 强制精细化 + 全装饰在场的场景可达 **2.55M 三角 / 251 绘制调用**（§6.5）——地形仍是绝对大头。
- **✅ 已落地（2026-09-14，用户定调）**：弧面细分**双档 + 按距离切换**——
  **≤60m 用 0.125m 细弧**（原观感）、**≥90m 用 0.25m 粗弧**（省三角）、60–90m 滞回带保持现状（防边界反复重建）。
  实现：`FaceBuild.setFineS()`（8/4 段每 1m cell）+ 档位随几何构建贯通（worker 消息、`IncrementalGeometry` 基座缓存键、挖坑增量、物理分区）；
  `ChunkManager.updateChunkDetail` 按「玩家→chunk 矩形最近距离」巡检；**档位切换 = 轻量原地换装（`requestDetailRebuild`）**——只重算地形几何并复用破坏重建的 `applyTerrainPatchInPlace`（`decorMode:'none'`，装饰层不动、不重烘焙；布局漂移走 `applyGeoInPlace` Tier B 整 geometry 替换）；失败才回退整块标准重建。实测降档 17 块装饰对象全部保留（22 中 20 保留，2 块走回退）。
  实测：站定后近块 [8]、远块 [4]、滞回块 [8]，pending 归零；强制精细化场景 top **2.71M → 2.24M（近细远粗）**；全局 0.25m 时曾达 1.35M/136FPS（纯性能上限对照）。

### P2 · three.js 矩阵同步与逐帧查询
- `updateMatrixWorld` 三段合计 ~521ms/8s：对纯静态/院落装饰用 `matrixAutoUpdate=false`＋按需 `updateMatrixWorld(true)`；运行态对象仅在移动帧标 dirty。
- `queryFrustum`（RasterMap）、`interpEdge`、`get baseRgb`：将每帧多次的同网格查询去重（帧内缓存），或改半频。

### P2 · 渲染管线微调（尚需按机器复测）
- 阴影图/后处理降半频或降分辨率；`getParameters/getProgram` 处三级程序缓存命中率。
- 剩余 `readPixels` 仅剩调试路径（F9 颜色回读 / `?dbg=1` 按钮回读），非常规开销，无需处理。

### P3 · heap / 监控
- 压到 <300MB：已用堆 370–416MB，主战场更伤 GC；推进纹理/缓存释放路径（换天、离开基地、实体消亡）。
- 建议把 `scripts/perf` 工具链保留为常驻 CI：`?perf=1` 钩子为**URL 门控、默认零足迹**（`main.ts`），不会污染正常游戏。

## 6.5 采集物（植被纹理卡）专项评估（2026-09-14）

**背景**：采集物从程序化几何改为纹理卡 + 摆动后，用户体感"变卡"。

**优化三步（均已落地）**
1. **透明管线 → 不透明管线**：植物曾全部 `transparent:true`（alpha 混合 + 早深度失效 + 填充带宽翻倍）→ 改为 `transparent:false`，边缘 `c.a<0.5` 硬裁切（防"透明描边"），末端 120→140m 雾隐改**抖动渐隐**（屏空间 hash 阈值，不混合）；
2. **摆动改 VAT 顶点位移**（`getPlantVat` 预烘焙偏移纹理；卡片竖直 8 分段；风归零的远处跳过 VAT 采样）——片元不再有 sin/smoothstep，贴图不变形；
3. **4 帧桶并成 1 个 draw call**：4 帧合为 `DataArrayTexture`（4 图层，`sampler2DArray` 取帧）+ 实例色 `instanceColor.r` 存帧号 → 每采集物每 chunk 仅 1 个 InstancedMesh。

**实测（1280×800，真机 iGPU；`rushTerrain` 强制精细化 + 全装饰在场，短窗）**

| 检查点 | wall 均值 | HUD | 植物网格 |
|---|---|---|---|
| 优化前（透明管线，4 帧桶） | 14.4–20.8ms | 75–83 FPS | 239 |
| 优化后（不透明 + VAT + 纹理数组） | **10.93ms**（峰值 9.1ms） | **109 FPS** | **93（-61%）** |
| 诊断 A/B（同版本内）：采集物**隐藏** | 16.1ms vs 显示 20.8ms（波动大，落噪声内） | 67 FPS | — |

**结论**
1. 采集物**不是主因**：A/B 差异落在测量噪声内（植物三角占比仅 0.6%，约 1.6 万）；
2. 该场景主负载 = **地形精细化**（2.55M 三角 vs 无装饰基线 ~0.85M）——见 §6 P1；
3. 本轮三步优化把植物自身开销（透明填充 + 绘制调用）压到可忽略：**同场景 20.8ms → 10.93ms**；
4. 测量口径提醒：短窗（4–5s）+ 机器热状态导致波动大（A/B 更明显），结论以"优化前后同口径对比"为准。

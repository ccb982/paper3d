# 性能评估报告

> ★ 2026-09-14 · 采集设备：本机（AMD Radeon(TM) Graphics 集成显卡，ANGLE/D3D11，Chrome headful），主测 1280×800，1080p 对照。
> 目的：对「当前性能有点差」做**可复现的量化归因**。全部数字来自 `scripts/perf/data/*.json` / `*.cpuprofile`。

---

## 1. 结论先行

| 维度 | 客观数据 | 判定 |
|---|---|---|
| 稳态帧耗时 | wall p50 ≈ **6.6–6.8ms**（≈142–145fps，贴近 144Hz 预算） | 稳态**良好**，非瓶颈 |
| CPU 逻辑 | WorldUpdate 均值：idle 0.59 / run 0.86 / cbt150 1.73ms | **轻**，远低于预算 |
| 渲染 | render 均值 ≈ 3.1–3.7ms @800p；1080p 面板几乎不变 | 中等；0.81–0.88M 三角/帧偏高 |
| **周期性尖峰** | 每秒 1–2 次 **17–52ms 单帧毛刺**（>16.7ms 掉帧率 ≈ 0.9%） | **「卡」的主因** |
| GC | 8s 内停顿 48–56ms，最长连续 **8.6ms**；usedJSHeap **370–416MB** | 分配压力大 |

一句话：**稳态帧率够高，「性能差」= 周期性单帧掉帧 + 高帧率模式下的合成/GPU 同步开销**。60Hz 屏上 p99 已达 12.8–16ms，再叠每秒 1–2 次尖峰，掉帧必现 → 表现为「跑图偶尔卡一下」。

## 4. 尖峰归因（CPU Profile × 帧级时序交叉验证）

### 4.1 CPU 热点（自耗时，8.3s/场，逐帧锲入）

| 热点 | run | cbt150 | 说明 |
|---|---|---|---|
| `readPixels`（native） | 346ms | 392ms | 最长连续 5.7 / 5.1ms —— 画面回读 |
| three.js 矩阵 `updateMatrixWorld` | ~521ms（3 处合计） | ~551ms | 场景图层级每帧全量同步 |
| `projectObject` | ~540ms | ~500ms | Object3D 遍历投影 |
| `getParameters` | 469ms | 486ms | 程序参数获取（three 缓存未命中面） |
| `queryFrustum` `RasterMap.ts:636` | 182ms | 200ms | 实体/块视锥查询（每帧） |
| `interpEdge` `Refinements.ts:84` | 155ms | 213ms | 地形贴地表面采样 |
| `readPixels` 时的引擎侧 `getProgram`/`getBindingState`/`renderBufferDirect` | ~430ms | ~390ms | 渲染绑定点 |
| `putImageData` | 68ms | 76ms | 小地图每帧全量 160×160 上传 |
| `update @ AmmoPanel.ts:34` | 44ms | 50ms | 弹药面板每帧刷新 |
| `get baseRgb @ Tiles.ts:17` / `blockAt` | 47ms | 50/65ms | 逐帧区块色彩/方块采样 |
| `(garbage collector)` | 48ms | 57ms | **最长连续 8.6 / 5.7ms** |

### 4.2 三类尖峰（run_spikes.capture，25s 内 20 次 >15ms 帧）

1. **`ui` 段尖峰 17–23ms，每 2–3s 一次**：与「跑图跨格」同步 → 小地图 `reveal`＋`rebuildBase`（跨格重建 25600px 底图）+ 每帧 `putImageData` 全量重传 + `AmmoPanel` 每帧刷新 + 段内堆分配。
2. **`ai`/`swarmBrain` 单帧尖峰 27–52ms**（idle/run 下 nA 仅 5、无增员）：
   - 采样 profile 中**未出现**相同时长的连续 JS 执行（最长连续 8.6ms 为 GC）→ 该读数 = 段内触发的一次性 **GC 主收集（≈9ms）＋ JIT 编译涨级 ＋ 帧交界合成等待** 的叠加，被计时窗口整体吸收；
   - cbt150 大战场（52–60 代理同帧决策）时真实蜂群成本会放大，测得 46.9ms。
3. **渲染侧单帧尖峰 15–34ms（update<2ms）**：GPU/合成器侧停顿（`readPixels` 5.7ms、`putImageData`、baseRgb 5.7ms 的连续锲入集中在这些帧）。

> 归因口径：**“46ms 的单个 JS 函数”不成立（profile 无对应长连续段）；真实原因是堆分配驱动的 GC + 编译涨级 + 小地图回读/上传的合成停顿**。治理方向因此明确：减分配、减每帧 UI 重绘/回读，而非优化蜂群算法本身。

## 6. 优化建议（按 ROI 排序）

### P0 · 消除「每帧」UI 全量重绘／回读（收益最大，风险低）
- **小地图 `update()`（`Minimap.ts:60`）无条件 `putImageData` 整幅 160×160（25600px）** → 改为脏标记：仅当 `baseImg` 重建、实体位置变化、朝向变化时才重绘；站立/少动时降为「坐标相等则跳过」；必要时节流到 8–15Hz。顺手去掉 `AmmoPanel.ts:34` 每帧 DOM/文本刷新（仅数值变化/按 interval 刷）。
- 预期：p95/p99 明显回落；`putImageData`（68–76ms/8s）、`readPixels` 对应的合成锲入一并减少。

### P0 · 降低堆分配（GC 是尖峰最大的单点依归）
- 排查 `ai/ui` 段的逐帧闭包与临时对象：`WorldUIManager.update` 里的每帧 `buildAmmoEntries()` 数组、蜂群 think/move 的 `map/filter`、`allBases()` 迭代器；统一复用预分配 buffers / 简单 for 循环。
- 期望：GC 自耗时与 "最长连续 8.6ms" 均缩减，idle/run 的 ai 尖峰（27–52ms）大概率消失。

### P1 · 蜂群决策运行期预算化
- 把《蜂群架构.md》的 ≤4ms 预算落实为代码门：`SWARM_BUDGET_MS`，进入 think 循环前取 `performance.now()`，累计超预算即截断本帧剩余 agent（降档到下帧）。cbt150 已见真实蜂群成本放大（46ms），预算门直接封顶。

### P1 · 三角形/绘制预算
- 0.81–0.88M 三角、158–191 调用与敌人规模无关 → 地形主导。复核远景环（>30m）细分等级是否能再降一档 / 使用 instancing；剔除以 60m 为最细的全细节 chunk 面数。可压低 iGPU 填充与绑定（`getParameters/getProgram` 469ms/8s）。

### P2 · three.js 矩阵同步与逐帧查询
- `updateMatrixWorld` 三段合计 ~521ms/8s：对纯静态/院落装饰用 `matrixAutoUpdate=false`＋按需 `updateMatrixWorld(true)`；运行态对象仅在移动帧标 dirty。
- `queryFrustum`（RasterMap）、`interpEdge`、`get baseRgb`：将每帧多次的同网格查询去重（帧内缓存），或改半频。

### P2 · 渲染管线微调（尚需按机器复测）
- 阴影图/后处理降半频或降分辨率；`getParameters/getProgram` 处三级程序缓存命中率。
- `readPixels`（若有局部拾取/aim 像素查询）改 GPU 侧/仅事件触发。

### P3 · heap / 监控
- 压到 <300MB：已用堆 370–416MB，主战场更伤 GC；推进纹理/缓存释放路径（换天、离开基地、实体消亡）。
- 建议把 `scripts/perf` 工具链保留为常驻 CI：`?perf=1` 钩子为**URL 门控、默认零足迹**（`main.ts`），不会污染正常游戏。

## 7. 复测方法

```bash
npx tsc --noEmit                     # 门禁

node scripts/perf/measure.mjs        # headful 真 GPU，产出 data/{idle,run,cbt150}.json
```

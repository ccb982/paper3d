└─────────────────────────────────────────────────────────────────────┘

数据流（纵向）：
 配置 JSON（内容）→ 系统层读取 → 核心运行时调度 → 服务层执行 → 平台层输出
 事件（横向）：系统间通过 EventBus 解耦通信
 状态（Session）：纯数据，贯穿模式切换，可序列化存档
```

**架构分层原则**
```
① 上层依赖下层，下层不依赖上层（单向依赖）
② 应用层/系统层只消费抽象（InputActions/Services 接口），不碰平台 API
③ 平台层 = 唯一接触 wx./tt./浏览器 API 的地方
④ 内容配置只被系统层读取，不进核心运行时
⑤ 换平台/换设备 = 只改平台层；加内容 = 只改配置
```

## 1. 核心运行时（★ 全部已实现）

### 1.1 游戏循环（GameLoop.ts）
```
rAF 驱动（浏览器/小游戏统一）
 ├ fixedUpdate(dt=1/60)   # 物理/战斗/逻辑（固定步长，可多次追赶）
 ├ update(dt)            # 渲染同步/特效/相机/UI（可变步长）
 └ render()              # three.js render（各模式自管理）
```
- 物理固定步长 + 累积器（rapier 需要稳定步长，如 60Hz）
- `dt 限幅`（切后台恢复时防爆炸，max 0.1s）
- 防死亡螺旋：最大追赶 5 步后丢弃累积
- 暂停时只跑 render（UI 动画继续），物理/逻辑冻结

```
类结构（GameLoop.ts）：
 GameLoop
  ├ start() / stop() / setPaused(bool)
  ├ onFixedUpdate(cb) / onUpdate(cb) / onRender(cb)  # 注册回调，返回 unsubscribe
  └ 内部：tick() → rAF → accumulator → dispatchFixed → dispatchUpdate → dispatchRender
```

### 1.2 模式接口（IGameMode.ts）—— 解耦的核心

```
核心原则："谁创建，谁销毁；谁拥有，谁负责"
main.ts 只做"路由器"，不做"管家"
```

```
每个 Mode 拥有自己的"私有领地"：
├ ShipMode：舰船 3D 场景 + UI 面板（不拥有物理世界/输入绑定）
├ WorldMode：PhysicsWorld + DesktopBinding + EntityManager + 地形（完全自包含）
└ 彼此不感知对方存在，只通过 IGameMode 接口与 main.ts 通信
```

```
接口（IGameMode.ts）：
interface IGameModeContext {
  scene: THREE.Scene;           // 共享渲染场景
  camera: THREE.PerspectiveCamera;  // 共享相机
  renderer: THREE.WebGLRenderer;    // 共享渲染器
  session: GameSession;            // 唯一共享状态
  onReturn?: () => void;           // 返回回调（WorldMode → ShipMode）
  onDepart?: (day, stats) => void; // 出击回调（ShipMode → WorldMode）
}

interface IGameMode {
  enter(context: IGameModeContext): void;  // 进入模式（创建私有资源）
  exit(): void;                            // 退出模式（完整清理私有资源）
  update(dt: number): void;
  render(): void;
}
```

```
★ 与旧架构的核心区别：
┌──────────────────────┬──────────────────────────────┐
│ 旧架构（ModeManager） │ 新架构（IGameMode）           │
├──────────────────────┼──────────────────────────────┤
│ main.ts 持有全局变量 │ main.ts 只有 currentMode     │
│ worldPhysics/worldBinding │ PhysicsWorld/Binding 私有于 WorldMode  │
│ 输入处理在 main.ts 中  │ 输入处理在 WorldMode.update() 内 │
│ 物理步进在 main.ts 中  │ 物理步进在 WorldMode.update() 内 │
│ WorldModeAdapter 桥接 │ WorldMode 直接实现 IGameMode │
│ 切换散落多函数互相调用  │ 统一 enterShipMode/enterWorldMode │
│ 资源清理依赖手动置 null │ exit() 强制自清理           │
└──────────────────────┴──────────────────────────────┘
```

```
模式切换流程（main.ts 内）：
  enterShipMode():
    → currentMode?.exit()    // 清理旧模式
    → new ShipMode().enter({ scene, camera, renderer, session, onDepart })
    → currentMode = ship

  enterWorldMode(day, combatStats):
    → currentMode?.exit()    // 清理旧模式
    → new WorldMode().enter({ scene, camera, renderer, session, day,
                              combatStats, assets, onReturn })
    → currentMode = world

  main 主循环（animate）：
    currentMode?.update(dt);
    currentMode?.render();
  // 不需要知道当前是哪个模式，也不处理物理/输入
```

```
★ 适配器模式已不再需要：
  WorldMode 直接实现 IGameMode，不再需要 WorldModeAdapter 桥接。
  WorldMode 的 enter() 内部创建 PhysicsWorld 和 DesktopBinding，
  exit() 内部完整销毁，main.ts 完全无感知。
```

### 1.3 事件总线（EventBus.ts）
```
类型安全的事件（映射键 + 泛型负载）
 ├ 拾取事件：'pickup' → { itemId, position }
 ├ 守卫警报：'ship_alert' → { wave, direction }
 ├ 抽卡结果：'gacha_result' → { result }
 ├ 对话/事件：'dialogue' / 'story_event'
 ├ 死亡/结算：'death' / 'run_end'
 ├ 背包变动：'inventory_change' → { layer }
 ├ 遗物获得：'relic_acquired' → { relicId }
 ├ 科技树解锁：'tech_unlock' → { nodeId }
 ├ 模式切换：'mode_switch' → { from, to }
 ├ 存档变更：'save_complete'
 └ 每日进度：'day_advance' → { day }

接口：
 EventBus
  ├ on<K>(key, handler) → unsubscribe 函数
  ├ emit<K>(key, payload)
  └ clear()  # 清除所有订阅

全局单例：eventBus
```

★ 事件总线使用规则（谁走总线，谁直接调用）：
```
判断标准 = "有没有非战斗系统要听这个事件"，不是频率

走总线（跨系统解耦）：
 ├ UI 需要监听：拾取/抽卡/警报/对话/死亡/结算
 └ 跨模块通知：背包变动/遗物获得/科技树解锁

不走总线（模块内部直接调用）：
 ├ 战斗内部一切：伤害/子弹命中/受击/死亡判定
 │   - 战斗 = 专门模块（combat/），所有战斗逻辑集中处理
 │   - 战斗模块内部直接调用（StatsCalculator/BulletSystem/AIStateMachine）
 │   - 不 emit 到总线，其他系统也不需要听
 └ 每帧高频路径（移动/特效/相机）直接调用
```

## 2. 实体系统

### 2.1 实体定义（组合式，非继承）
```
Entity = { id, kind, transform, components[] }
组件（每个都是纯数据 + 可选 Update）：
 ├ Transform    # 位置/旋转/缩放
 ├ RigidBody    # rapier 刚体引用 + 物理参数
 ├ Billboard    # 2D 贴片渲染组件（动画/翻转/阴影）
 ├ Weapon       # 攻击/开火逻辑
 ├ Health       # 血量/受击/死亡
 ├ AI           # 状态机（敌人用）
 ├ Inventory    # 可拾取物品
 └ EffectSlot   # 特效挂点（播放器）
```
- **组合优于继承**：角色/敌人/子弹/箱子都是 Entity + 组件组合
- 组件可持有运行时引用（rapier handle / THREE mesh / 播放器 controller）——正常

★ 物理实体判定（按 kind 自动挂 RigidBody）：
```
不是"所有物体都有 rapier 刚体"——按 kind 配置决定：
├ 需要物理（自动挂 RigidBody 组件）：
│   - 角色/敌人/友军：移动碰撞、被击退
│   - 子弹：飞行 + 命中判定
│   - 掉落物：落地、被爆炸推飞
│   - 可破坏物（箱子/栅栏）：被攻击、被打飞
│   - 地形/墙/舰船/炮塔：固定刚体（碰撞拦截/目标）
├ 不需要物理（不挂 RigidBody）：
│   - 特效/粒子/拖尾（播放器视觉）
│   - 布料（GPU verlet 独立模拟）
│   - 水（Gerstner shader，只采样高度做浮力）
│   - 资源点/采集点（逻辑交互判定）
│   - 装饰物（纯贴图）
└ 判断标准："会不会被撞/撞别人/被力推"——需要才建

 实现（EntityManager.create）：
  实体配置表（entities.json）每条目带 physics 标记：
   { "kind": "enemy", "physics": "dynamic-capsule" }
   { "kind": "bullet", "physics": "dynamic-sphere" }
   { "kind": "wall", "physics": "fixed-box" }
   { "kind": "resource_spot", "physics": null }   # 无物理
  创建时按配置：有 physics → 调 PhysicsWorld.addBody 挂 RigidBody
  无 → 只创建渲染/逻辑组件
```

### 2.2 实体基类体系（管线驱动 + 继承扩展）
```
★ 实体管线 = EntityManager（创建/遍历）+ PhysicsWorld（物理）+ 基类体系（行为骨架）
  组合式数据（2.1）负责"有什么"；基类负责"怎么活"（生命周期/管线联动）。

★ 组合 vs 继承的边界（2.1 与 2.2 并存）：
  ├ 继承（基类体系）= 公共骨架：生命周期 / 管线联动 / 更新顺序
  │   —— EntityBase → CharacterBase/BulletBase/ItemBase → 具体实体
  ├ 组合（组件）= 能力细节：Health/AI/Weapon/Inventory 等
  │   —— 挂在基类实例的组件集合上（data 字段/组件表）
  ├ 规则：行为骨架走继承（每类实体骨架不同），
  │        能力复用走组合（多类实体共享同一组件）
  └ 例：Player 继承 CharacterBase（骨架），挂 Health/Ammo（组件）；
       Enemy 继承 CharacterBase（骨架），挂 Health/AI（组件）
```
 ├ 数据：Entity（id/kind/position）+ 可选 RigidBodyRef（handle 由 PhysicsWorld 分配）
 ├ ★ 动画管线联动（宿主角色）：
 │    assetRef（FtxAsset/Asset）+ FrameAnimator（时间轴/状态/朝向/翻转）
 │    FrameState（frameIndex/facing/flipX/lodLevel，见 3.3.3）
 ├ ★ 渲染管线联动（宿主角色）：
 │    FXRenderer（FTXQuad 纯纹理 / 特效网格）
 │    读 FrameState → 取纹理 → 贴片 → 挂场景（见 3.3.2）
 ├ 生命周期：
 │    spawn(pos, asset) → 建动画/渲染/物理 → update(dt) 每帧 →
 │    死亡 → dispose()（动画/渲染/物理资源全释放）
 ├ 更新骨架（update 模板方法）：
 │    ① 子类行为逻辑（覆写 onUpdate）
 │    ② 物理同步（玩家：位置→刚体；敌人：刚体→位置）
 │    ③ 动画推进（anim.update(dt) → FrameState.frameIndex）
 │    ④ 渲染同步（renderer 位置/朝向/翻转 → render）
 ├ 事件：onDeath / onTakeDamage（子类覆写；跨系统走 EventBus）
 └ 注册：EntityManager.create() 返回 EntityBase 实例（进管线统一驱动）

### 2.2.1 子类体系（细分基类）
```
EntityBase
 ├── CharacterBase（角色基类）
 │     ├ 控制：CharacterController（相机相对移动/跳跃/朝向——已有）
 │     ├ 属性组件：Health / Ammo / Skill（后续）
 │     ├ 挂接：EffectSlot（技能特效挂点）
 │     └ 子类：
 │         ├ Player  —— 输入驱动（PlayerController 包装）
 │         ├ Ally    —— AI 守卫/跟随（AIStateMachine）
 │         └ Enemy   —— AI 巡逻/索敌/攻击（AIStateMachine）
 ├── BulletBase（子弹基类）
 │     ├ 物理：dynamic 球体 + 初速（直线/追踪/重力）
 │     ├ 生命周期：命中/超时/超距 → 回池（EntityManager 池化）
 │     ├ 阵营：创建时锁定（碰撞过滤在 PhysicsWorld 层）
 │     └ 特效：飞行/命中特效（EffectSlot）
 ├── ItemBase（物品基类）
 │     ├ 掉落物：物理落地 + 拾取传感器（onSensor）
 │     ├ 资源点：静态 + 采集交互
 │     ├ 视觉：ftx 单帧/帧动画（icon，走管线渲染）
 │     └ 数据：itemId 引用配置表
 └── EffectBase（特效实体，后续）
       ├ 无物理（纯视觉）
       └ 播放器资产 + 生命周期（一次/循环/受击触发）
```

### 2.2.2 实体管线的完整数据流（与动画/渲染/物理联动）
```
EntityManager.create(kind, pos, physics?, asset?) → EntityBase
  ├ 物理：collisionVolume 属性（基类声明）→ PhysicsWorld.addBody（y = 脚底+bodyOffsetY）
  ├ 动画：asset → FrameAnimator（FrameState 衔接层）
  ├ 渲染：FXRenderer（FTXQuad/特效网格）
  ├ 碰撞分发：bodyMap（handle → 实体）注册
  └ 空间索引：SpatialGrid 注册（4.1a）

每帧（EntityManager.update(dt) 遍历）：
  entity.update(dt)：
    ① 行为逻辑（子类 onUpdate：AI/控制/子弹飞行/拾取判定）
        ★ CharacterBase：moveDir×speed → 位置推进（kinematic）
        ★ EnemyBase：super.onUpdate 必须先调（移动链路）
    ② 物理同步（kinematic：setKinematicPosition；read：纯读回）
    ③ 动画推进（FrameAnimator.update → 写 FrameState）
    ④ 渲染同步（renderer 位置/朝向/翻转 → 读 FrameState 画）
    ⑤ 附属特效驱动（updateEffects：血条/技能/受击——跟随实体位置
        + 时间轴 + 播完回收；特效管线属于实体基类，与主贴片渲染分开）
    ⑥ 空间索引移块（onEntityMoved，hash 比较静止零成本）

★ 附属特效管线（EntityEffect，属于实体基类）：
  ├ effectSlots: Map<name, EntityEffect>（血条/技能特效/受击/光环）
  ├ attachEffect / detachEffect / getEffect
  ├ EntityEffect 接口：update(dt, x, y, z) → boolean（跟随 + 播完回收）
  │   / render(camera)（billboard 自行处理）/ dispose
  ├ render：主贴片之后渲染特效（独立于主渲染）
  ├ dispose：特效全部释放（随实体销毁）
  └ 实例：HealthBar（头顶血条，跟随 + 读实体 hp 比例；已挂敌人/物品）
     后续：技能一次性特效（播完自动移除）、受击闪白、光环
     ★ 脱手特效（无实体：爆炸/地面圈）= EffectBase + 管理器（池化），另做

销毁（entity.dispose()）：
  anim.dispose / renderer.dispose（mesh+几何+材质）
  / 特效槽全部 dispose
  / em.unregister（空间索引/碰撞分发注销）
  / em.destroy → physics.removeBody（★ 刚体释放，防物理世界泄漏）
  → 资源全释放（模式切换/场景卸载时 EntityManager.clear() 批量）

★ 解耦原则（已落实）：
  ├ EntityBase 不碰 rapier（唯一封装 PhysicsWorld）
  ├ EntityBase 不碰具体渲染器（FTXQuad 只在子类构造）
  ├ 动画/渲染只依赖 FrameAssetSource 统一接口（FtxAsset/Asset 一视同仁）
  ├ 碰撞体积 = 基类声明属性（EntityBase.collisionVolume），
  │   物理创建/刚体偏移/碰撞处理统一从属性取
  └ 碰撞事件 = 管线分发（EntityManager → onCollision 钩子），游戏层只管处理

★ 已知限制与后续方案（当前实现边界）：
  ├ 子弹回池：当前超时销毁；池化（复用内存/刚体）后续补
  ├ 资产释放：FtxAsset/Asset 全局常驻（无引用计数）；模式切换手动释放
  │   （架构 9.3 计划：引用计数归零 → dispose）
  └ 事件（onDeath 等）：当前基类回调；EventBus（1.3）就绪后走总线
```

★ 序列化边界（实体与存档）：
```
游戏运行：全部内存数据（组件带引用，无约束）
存档 = 安全点时把内存"写一下"：只提取描述字段
 ├ 存：kind + configId + 位置 + 可存数值（hp/ammo/堆叠…）
 ├ 不存：handle/mesh/controller 等运行时引用
 └ 背包/遗物 = id 列表（配置重建）
读档 = 仅启动时一次：JSON → 按描述重建实体 → 重新分配引用
之后运行：全内存，存档不再参与
```

### 2.2 实体管理（EntityManager）
```
├ 池化：子弹/粒子类高频实体用对象池（预分配，复用）
├ 遍历：按组件类型分组索引（需要 AI 的组 / 需要物理的组…）
├ 创建/销毁：统一入口，销毁时回收组件资源（物理体/网格/特效）
└ 数量上限：同时活跃实体数预算（见性能预算）
```

### 2.3 物理与渲染同步
```
RigidBody 持有 rapier 句柄（userData = entityId）
每 fixedUpdate 后：物理步进 → 把刚体 transform 写回 Entity.transform
渲染层只读 Entity.transform（billboard 面相机/网格变换）
 ├ 被动跟随：物理体写回 → 渲染体跟随（角色/子弹）
 └ 主动驱动：渲染体写回 → 物理体（摄像机/不参与碰撞的装饰）
```

## 3. 渲染架构

### 3.1 场景组织
```
一个主场景（three.Scene）+ 按需子容器：
 ├ RenderScene  # 地形/装饰（静态合并）
 ├ EntityLayer  # 所有实体（billboard/网格）
 ├ FXLayer      # 特效（播放器实例/粒子）
 └ SkyLayer     # 天空/远景
```
- 静态地形合并网格（每 chunk 一个 merged mesh，减少 draw call）
- 实体渲染：billboard 用 InstancedMesh 或合并批次（同类精灵合并）

### 3.2 Billboard 精灵系统
```
BillboardComponent（角色/道具/敌人的世界贴片）
 ├ ★ 动画源 = 播放器资产（ftx3 纹理包，见 3.3.1 动画管线）
 │   - assetRef（FtxAsset）+ controller（帧播放）+ resolver（帧名→索引）
 │   - 不再使用"精灵图集"（textureAtlas）——帧内容全部来自 ftx 包
 ├ currentFrame   # 当前帧（动画状态机驱动）
 ├ facing         # 朝向（前/后/左/右 → 帧组选择，帧名带朝向前缀如 前0/后0）
 ├ flipX          # 移动方向翻转
 ├ facingMode     # always-camera（永久面相机）
 ├ shadow         # 贴地剪影影子（SilhouetteShadow 统一机制，地面锚点与精灵分离）
 └ sortLayer      # 排序层（y-sort：角色/子弹/特效前后遮挡）
```
- **y-sort**：2D 贴片在 3D 场景的遮挡用「y 值排序」模拟（类八方旅人）
- 渲染排序：每帧按 transform.y 排序批次（数量可控，性能可接受）
- Billboard = 贴片容器（位置/朝向/阴影/排序）；帧内容由播放器提供，二者解耦

### 3.3 特效挂接（播放器桥接）
```
★ 落地状态（EntityEffect 附属特效体系，属于实体基类——见 2.2.2）：
  EntityBase.effectSlots + attachEffect/detachEffect/getEffect
  EntityEffect 接口（services/fx/EntityEffect.ts）：
    update(dt, x, y, z) → boolean（跟随实体 + 时间轴 + 播完回收）
    render(camera)（billboard 自行处理）
    dispose()
  已实现实例：
    - HealthBar（头顶血条：跟随 + 读实体 hp 比例；
      已挂敌人 offsetY 2.8 / 物品 offsetY 0.75）
    - HitEffectView（矢量动画播放器，见 3.3.3a）——击中特效，
      实体命中走 attachEffect（击中点跟随实体走），播完自动回收
  规划实例：技能一次性特效、受击闪白、光环（同一 attachEffect 骨架）

★ 击中特效挂载（服务层公共函数 attachHitEffect，services/fx/attachHitEffect.ts）：
  attachHitEffect(scene, shapes, hitPoint, target, options?)
    ├ 命中实体 → 内部计算「击中点−实体位置」偏移 + target.attachEffect(slot)
    │   （实体槽每帧传实体位置 → 特效 = 实体位置 + 偏移 = 击中点跟随实体走；
    │     播完/实体销毁由实体骨架自动回收）→ 返回 null
    └ 命中地形 → 返回播放中的 HitEffectView，调用方进固定点列表
      （每帧重传同一命中坐标，原地播放，播完移除）
  任何弹体/近战/范围技能共用，不再各自复制创建+偏移+挂载逻辑

EffectSlot 规划（完整版，渐进实现）：
  ├ assetId     # 资产引用：.ftx3.gz（纹理包）或 .scene.zip（特效包）
  ├ controller  # FramePlaybackController（播放器实例）
  ├ attachPoint # 挂点（头顶/手部/胸口——相对 transform 偏移）
  ├ loopMode    # 循环/一次/受击触发
  ├ physics     # ★ 当前注入的物理参数（公共库引用或内嵌覆盖，见 9.4）
  └ 生命周期：生成时创建 → 播放 → 结束销毁（或跟随实体）
- 播放器输出直接进 FXLayer
- 特效不参与物理，纯视觉（内容设计已确认：实体 vs 特效分离）
- ★ 所有美术 = 播放器格式（ftx3 / .scene.zip），游戏内可函数编辑：
   注入/取消物理参数、修改扭动（distort）、换皮（见 9.4 运行时编辑）
```

### 3.3.3b 流体 LevelSet 与合成公式（四端统一约定）
```
★ 四端 = 流体编辑器 / 绘画主页面 / 特效播放器(effects-player) / 游戏端。
  修改任何一处必须同步其他三处（详见另起的绘画网页/src/fluid/fluidConfigIO.ts 顶部注释）。

① 残差纹理 alpha 约定（背景透明 + 残差流动可见的关键）：
   alpha = "区域存在度"：shape 外（regionIdTex=0/多边形外/纹理透明像素）= 0，
   shape 内 = 255；RGB 中性 128（delta≈0），shape 外填 128。
   → 合成 alpha = max(baseA, residual.a)：
       shape 外 max(0,0)=0 → 纯透明背景；
       残差平流时 alpha 随速度扩散 → 基础色=0 区域可见流动渐变（尾迹雾气）
   四端位置：
     ① 编辑器 buildFluidTexturesFromRawFrame（区域外默认 0）
     ② 主绘画页面 useAppStore residTex/residBase + buildBaseHslFromFrame 不反推 alpha
     ③ 特效播放器 effects-player/src/core/ftx.ts buildResidualData
     ④ 游戏端 vendor/player/core/ftx.ts buildResidualData（与③同款）
   ★ 实体 shader 流体模式禁止 discard（alpha<0.5 丢弃会切掉流动渐变）——
     用 alpha 混合保留（FTXQuad.ts / vendor/player/gl/renderer.ts）

② 合成公式（MCSDA scalar / vector）：
   vector: finalA = max(baseA, residual.a)
   scalar: final = base + delta + off（×通道开关 uChannels，静态 delta 始终参与）
   sub（减去）模式：H/S/L 取 -|factor×mul|（残差为 0 处依旧被密度拉出雾气），
     A 通道取 +|factor×mul|（雾气越浓越实，不被减去模式压没）
   factor = density / baseline
   位置：FluidEditorUI(显示) / 各端 FluidSolver buildCompositeMat(计算)

③ LevelSet 模块（流体编辑器 → 主绘画页面 → 播放器 → 游戏端已同步）：
   ├ reinit：Godunov 上风格式 + φ₀ 快照（原中心差分不收敛/界面漂移）
   ├ 双模式：约束模式（constrainLiquid=每帧 φ 重建+reinit+液体约束）/
   │   追踪模式（φ 平流 + 每 reinitInterval 帧重建，注入即同步）
   ├ 表面张力：CSF δ(φ) 归一化（F=σ·κ·δ·n̂），σ 需极大才可见（≈6000+，
   │   旧 UI 0~10 量级完全不够，现已 0~100000、默认 10000）
   ├ φ 后处理：空气钳制（clampAirPhi）+ 水体补偿（compensateWaterPhi）
   └ 参数导出：levelSetConfig{reinitIterations, surfaceTension, smoothingRadius,
       reinitInterval, narrowBandWidth, constrainLiquid, clampAirPhi, maxAirPhi,
       compensateWaterPhi, waterCompensationRate} —— config.ts 解析键名必须一致

④ 参数流转链路：
   流体编辑器 buildRecipe → 只给绘画主页面（parseImportedFluidConfig）
   → 绘画主页面导出最终版（assetBundleExport 写进 per_frame_data.physics，
     内部扁平格式）→ 播放器/游戏端 parsePhysicsConfig 读取同一格式
```

### 3.3.1 动画管线（角色/道具帧动画，播放器驱动）
```
FrameAnimator（动画状态机组件，驱动 Billboard 帧内容）
 ├ 输入：动画配置 anims.json（角色/道具的动画表）
 │   { "protagonist": {
 │       "facing": { "前": ["前0","前1"], "后": ["后0","后1","后2"] },
 │       "states": {
 │         "idle":   { "facing": "前", "loop": true,  "fps": 3 },
 │         "walk":   { "facing": "auto", "loop": true, "fps": 6 },
 │         "attack": { "facing": "auto", "loop": false, "fps": 10 }
 │       } } }
 ├ 状态切换（实体行为驱动）：
 │   - 移动 → walk / 静止 → idle / 攻击 → attack（播一次回 idle）
 │   - 朝向：facing 决定帧组（前0/后0...）——帧名 = 朝向前缀 + 帧号
 ├ 播放驱动：state → 帧名列表 → resolver 查索引 → controller.goto 逐帧
 │   - 循环：controller loop；单次：播完回调切回 idle
 ├ 帧内容：FtxAsset（纯纹理包）→ Billboard 贴片纹理
 └ 换皮/形态：切换 asset 或 setFrameTextures（见 9.4）

 动画数据流：
  实体行为(移动/攻击) → FrameAnimator.setState('walk')
  → 查 anims.json 帧名列表 → resolver.resolve('前1')
  → controller.goto(index) → Billboard 显示该帧纹理

★ 时间轴与帧播放控制（复用播放器内核 core/time.ts + core/controller.ts）：
 ├ 三层分工：
 │   ├ 语义层（FrameAnimator）："播什么" —— 状态机 → 帧名列表
 │   ├ 时间层（Controller/TimeState）："播到哪了" —— 时间 → 帧索引
 │   └ 显示层（FrameState）："显示啥" —— 帧索引 → 纹理 → 画面
 ├ 时间轴（TimeState，每动画实例私有一份）：
 │   ├ localTime / frameIndex / fps / state / loopCount / order
 │   ├ order：loop / linear / reverse / pingpong
 │   └ 推进：advance(dt) —— 游戏循环每帧调用，唯一时间入口
 ├ 帧播放控制（Controller）：
 │   ├ play/pause/stop/hold(冻结帧)/goto/gotoTime/stepForward/stepBackward
 │   ├ 回调：onFrameChange / onComplete / onStateChange
 │   └ 单次动画：onComplete → 状态机自动切回 idle（闭环）
 ├ 每帧流程：
 │   GameLoop.update(dt) → FrameAnimator.update(dt)
 │     → 状态转移检查（行为层 setState）
 │     → controller.advance(dt)（★ 时间轴推进）
 │     → frameIndex 写入 FrameState
 │   → 渲染管线读 FrameState.frameIndex → 取纹理 → 画
 ├ LOD 与时间轴（不打断时间轴，只调速率/暂停）：
 │   ├ LOD 0：advance 正常（全速）
 │   ├ LOD 1：fps 减半（时间轴变慢，不跳帧）
 │   └ LOD 2：controller 暂停（时间轴冻结，保持当前帧画面）
 └ 原则：每个动画实例独立时间轴，互不干扰；advance 唯一时间入口；
     暂停/冻结/跳转改状态不改 time；LOD 降级不 reset 时间轴
```

### 3.3.2 渲染管线（播放器输出 → 画面）
```
两层渲染输出，统一进 FXLayer：

① 纯纹理帧（FtxAsset / ftx3 包）—— FTXQuad 渲染器
   ├ quad + 合成 shader：base(HSL) + residual(残差) → RGB（GPU 每帧合成）
   ├ bbox 区域映射到贴片（帧内容只占 bbox 区域，透明外延）
   ├ ★ 纹理反转（渲染层应用，读 FrameState.flipX/flipY）：
   │    ├ flipX：quad.scale.x = -1（左右反转——脸朝右的帧朝左走时用）
   │    └ flipY：quad.scale.y = -1（上下反转，预留）
   ├ 流体注入：uFluidTex 分支（注入物理参数时直接采样流体合成结果）
   └ 纹理数据 row0=顶部 + shader 内翻转 v（防上下颠倒，统一约定）

② 特效包（Asset / .scene.zip）—— 实体网格渲染（已有）
   ├ VAT 位移（扭动/变形）+ 模板裁剪 + 每帧变换 + distort
   └ 输出同 FXLayer

FXLayer 集成（世界空间）：
 ├ 实例化：播放器实例输出 → FXLayer 子容器
 ├ 世界变换：实体 transform → 贴片位置/缩放（billboard 面相机）
 ├ 排序：与实体统一 y-sort（批次级，见 3.7）
 ├ LOD：距离 → 减帧（4→2 帧）/ 停流体 / 单帧静态（见 3.6）
 └ 剔除：视锥外不更新/不渲染（见 3.5）

渲染数据流（每帧）：
  FrameAnimator 驱动帧索引 → 播放器输出纹理/网格 → FXLayer
  → RenderManager：剔除 → LOD → 分组 → 批次 y-sort → draw

★ 深度测试与地形遮挡（当前实现）：
  ├ FTXQuad 材质：depthTest=true + depthWrite=false（transparent 保持）
  │   ├ 地形网格（opaque）先渲染写深度 → 实体贴片后渲染读深度 →
  │   │   高台/墙后的实体被深度自动裁剪（GPU 免费，零逐实体判定）
  │   └ depthWrite 保持 false：透明贴片不写深度（透明排序安全）
  ├ HealthBar 同步：depthTest=true + depthWrite=false（被遮挡时正确隐藏）
  ├ ★ 相机不做拉近（用户决策）：相机位置不因地形遮挡而收缩，
  │   遮挡时实体被地形裁掉属预期表现（后续可选：方舟轮廓线双 pass）
  └ 注意：贴片脚底与地面同平面有极小 z-fighting 风险——出现时加
     polygonOffset 微调，当前未启用
```

### 3.3.2a 朝向与翻转决策（控制解耦）
```
★ 帧名语义约定：
 ├ "前"帧 = 脸朝相机（正面）→ 游戏里"向下移动"时使用
 ├ "后"帧 = 背对相机 → "向上移动"时使用
 └ 左右移动 → 延续当前 facing 帧组 + flipX 反转

★ 输入完全解耦（双端：桌面/触屏走同一抽象）：
 输入层：InputActions.moveAxis（抽象方向，WASD / 虚拟摇杆 → 同一语义）
   ↓ 游戏控制层不碰具体按键
 角色移动系统：消费 moveAxis → 移动
   ↓
 朝向逻辑（FrameAnimator.setFacing）：
   moveAxis.y > 0 → facing = 前（"前"帧组）
   moveAxis.y < 0 → facing = 后（"后"帧组）
   moveAxis.x < 0 → flipX = true（脸朝左）
   moveAxis.x > 0 → flipX = false（脸朝右）
   ↓
 FrameState 写入 { facing, flipX }
   ↓
 渲染管线：facing 已由动画管线转成 frameIndex（帧组选择）；
           flipX 应用 quad.scale.x = ±1（反转在渲染层）

★ 翻转状态延续（切换动画不重置）：
 动画状态切换（idle→walk）时 flipX 保持上一帧的值，
 只由新输入方向修改——状态切换不碰 flipX。

★ 分层归属：
 flipX 决定 = 控制/动画层（moveAxis 派生，逻辑）
 flipX 应用 = 渲染层（quad.scale.x，表现）
 FrameState 为传递者 —— 决策与表现解耦，与输入解耦一致
```

### 3.3.3 动画管线与渲染管线的关系（FrameState 衔接）
```
★ 两条管线解耦，通过每帧更新的"帧状态 FrameState"衔接：
   动画管线（逻辑侧）写，渲染管线（表现侧）读，单向数据流。

职责划分：
 ├ 动画管线（逻辑侧）："现在该播哪一帧"
 │   FrameAnimator(状态机) → resolver(帧名→索引) → controller(时间轴推进)
 │   驱动者 = 行为层（移动/攻击/状态）
 ├ 渲染管线（表现侧）："这一帧怎么画出来"
 │   FTXQuad / 实体网格 → 合成 shader → FXLayer → y-sort → draw
 │   被动消费（只画"当前帧"，不关心时间）

FrameState（每实体一份，动画写 / 渲染读）：
 ├ assetRef     # FtxAsset 或 Asset（纹理/网格数据源）
 ├ frameIndex   # 当前帧（动画管线每帧写入）
 ├ facing/flipX # 朝向（贴片翻转/帧组）
 ├ lodLevel     # 渲染侧下发（反向控制）
 └ 渲染句柄     # quad/mesh/纹理缓存（渲染侧持有）

每帧数据流（单向）：
 行为层(移动/攻击/中毒)
   → 动画管线：setState → resolveFrame('前1') → controller.advance(dt)
   → 写 FrameState.frameIndex
   → 渲染管线：读 FrameState → 取纹理/网格 → 合成 → FXLayer → 排序 → draw

LOD 反向控制（唯一反向通道）：
 RenderManager（渲染侧）每帧评估距离 → LOD 等级 0/1/2
   → setLodLevel 下发：
      动画管线：降帧率 / 减帧 / 停流体步进
      渲染管线：减细节 / 静态单帧
 其余全部单向（渲染不驱动动画）

解耦收益：
 ├ 改动画实现（换状态机/配置）不影响渲染
 ├ 改渲染实现（换 shader/合批）不影响动画
 └ LOD 逻辑集中：渲染侧评估 → 等级下发 → 双侧响应
```

### 3.5 视锥剔除（Frustum Culling）
```
★ 现状：SpatialGrid.queryVisible（视锥 8 角点投影到 y=0 → AABB 覆盖块）粗筛
  + three.js frustumCulled 精剔兜底。
★ 演进：3.10 统一空间层落地后，由 RasterMap 2D 距离/梯形剔除替代
  （决策更便宜、无 AABB 冗余、覆盖身后/远处）；本节的 chunk 级剔除
  在地形 chunk 化后保留（chunk AABB vs 视锥）。

三层剔除（每帧在 render 前执行）：
 ├ ① Chunk 级：相机视锥 vs chunk AABB → 视锥外的 chunk 整块跳过
 │   - 每个 chunk 维护一个粗 AABB（地形 + Actors 范围）
 │   - 视锥外 chunk：不更新 Actors、不渲染网格（省 CPU + GPU）
 ├ ② 实体级：three.js 自带 frustumCulled（per-mesh AABB）
 │   - 实体超出视锥 → 跳过渲染（省 draw call）
 │   - billboard 用自身 AABB（贴片矩形包围盒）
 └ ③ 特效级：特效实例位置 vs 视锥 → 视锥外不实例化/不渲染
```

### 3.6 LOD 系统（与剔除联动）
```
LODManager（每帧或每 N 帧评估一次）：
 ├ 评估：实体/地形到相机的距离 → 确定 LOD 等级
 ├ 地形：chunk 按距离选网格精度（近/中/远三级）
 │   - 近：全精度（贴图+法线+细节装饰）
 │   - 中：简化块（合并网格，去法线）
 │   - 远：低面数 + 贴片蒙版
 ├ 实体（billboard）：按距离切换表现
 │   - 近：全帧动画 + 剪影影子（随帧变化）+ 特效挂点
 │   - 中：减帧动画（4→2 帧）+ 影子半透明 + 停特效
 │   - 远：静态单帧 + 无阴影（SilhouetteShadow LOD≥3 隐藏）
 ├ 切换策略：异步换（延迟一帧，避免瞬间 pop）/ 渐变（可选）
 └ 与剔除协同：视锥外的直接跳过 LOD 评估（省计算）
```
- 视锥剔除 = 每帧"看不见的别渲染"；LOD = "看得见的按距离降成本"
- 两者在 `RenderManager` 统一入口执行：`updateVisible() → 剔除 → LOD → 排序 → draw`

### 3.7 排序与合批（方案 B：批次间 y-sort + 实例合并）
```
★ 取舍决策：y-sort（逐实例遮挡）与 InstancedMesh（少 draw call）互斥
   采用方案 B —— 粗排序（批次级）+ 细合并（实例级）：

渲染流程（RenderManager 统一入口）：
 updateVisible() 每帧：
  ① 视锥剔除：相机视锥 vs chunk/实体 AABB → 剔除不可见（见 3.5）
  ② LOD 评估：仅对"可见"实体评估距离 → 定 LOD 等级（见 3.6）
  ③ 分组：按「图集 × LOD 等级」分组
     - 同图集 + 同 LOD → 合并批次（InstancedMesh 一次绘制）
     - 不同 LOD 的同一图集 → 分到不同批次（近远不同细节）
  ④ 批次排序：批次之间按「代表 y 值」排序（粗遮挡）
     - 每个批次取一个代表 y（如平均 y）
     - 批次间正确遮挡（地面批次 < 角色批次 < 空中特效批次）
  ⑤ 绘制：按排序后的批次依次 draw（同批次内不细排遮挡）

方案 B 的效果：
 ├ draw call：批次数 = 图集数 × LOD 级数（个位数~十位数，可接受）
 ├ 遮挡：批次间正确，批次内小误差（角色/敌人数量少，视觉可接受）
 └ 与 LOD/剔除协同：剔除在前（省 LOD 计算）→ LOD → 分组 → 排序 → draw

静态合批：地形/装饰 chunk 内合并为单 mesh（构建时做一次）
```

### 3.8 地形生成架构（chunk 流式）
```
生成流水线（异步队列，避免卡顿）：
 chunk 请求 → 生成器(seed, chunkX, chunkZ, 主题) → 网格/碰撞/布点 → 激活
 ├ ① 高度场：噪声函数叠加（Perlin/Simplex，多倍频 octaves）
 │   - 主题参数化：龙门外环=平台地形 / 迷宫=走廊骨架
 │   - 噪声输入 = (seed, chunkX, chunkZ) 确定性 → 可复现
 ├ ② 网格构建：高度场 → BufferGeometry（顶点/UV/法线）
 │   - 近处全精度 / 远处低细分（LOD 联动，见 3.6）
 ├ ③ 碰撞：rapier 碰撞体
 │   - 地形用 trimesh（合并进 chunk）或 heightfield（高度场直接转）
 │   - 静态刚体，只建一次，chunk 卸载时释放
 ├ ④ 布点（Actors）：资源点/敌人/箱子/装饰
 │   - 由 (seed, chunk, 主题, day) 确定性采样
 │   - chunk 激活时才实例化，卸载时回收
 └ ⑤ 衔接：chunk 边界用连接点（门/坡道/路径）对齐

生成队列：
 ├ 优先级：近 chunk（玩家周围）> 远 chunk
 ├ 预算：每帧最多生成 N 个 chunk（如 1~2 个），防止卡帧
 └ 内存：只保留视距内 chunk 的 Mesh/Actors，ChunkData 可保留

★ 坐标约定与剔除策略（已踩坑）：
  ├ 视觉坐标 = 逻辑坐标：地形网格顶点必须平移/映射到世界坐标
  │   （PlaneGeometry 本地 [-32,32] → 世界 [0,64]），
  │   只把偏移用于"高度采样"而不写回顶点 → 实体在网格外（视觉虚空）
  ├ 顶点平移后必须重算 boundingSphere/boundingBox（否则视锥剔除误剔）
  ├ ★ 地形永不参与视锥剔除（frustumCulled=false）——大地物包围球剔除不可靠；
  │   剔除策略交给 chunk 级（chunk AABB vs 视锥，见 3.5①）
  ├ 地形材质 DoubleSide（不剔背面，防法线方向问题）
  └ 顶点平移逻辑后续 chunk 化时改为"chunk 偏移"（本地坐标 + chunk 原点）

### 3.7b Three.js OrthographicCamera Y 轴约定（UI 层）

```
Three.js 的 OrthographicCamera 在 UI 层使用 `(0, 1, 1, 0)` 时：
  Y=0 在顶部，Y=1 在底部 —— 与标注 JSON（Y=0 底部，Y=1 顶部）相反。

处理规则：
  ├ 纹理渲染位置：使用原始 JSON Y 坐标，Three.js 渲染管线自动翻转显示
  └ 点击检测区域（hit area）：需要手动 Y 翻转
       camera_y = 1 - json_y_end
       其中 json_y_end 是标注区域的 Y 上限（底部坐标）

典型案例：抽卡按钮 hit area 的 y 坐标计算
  ├ JSON 标注：抽卡按钮 y:0.103~0.236（Y=0 底部）
  ├ 纹理渲染：btnArea.y = 0.103（原始值，Three.js 自动翻转）
  └ hit area：hitOffY = 1 - 0.236 + (areaH - textureH) / 2

详见：文档/架构文档.md
```

### 3.8a 地形生成落地（最终形态：分块迷宫生成器）

```
★ 设计哲学：用"端口+迷宫"替代"噪声+模板"
  旧方案（已废弃）：Perlin 噪声 → 5 种竞技场模板 → 硬编码布局
  新方案：端口派生 → 迷宫生成（Growing Tree）→ 地形分类 → 高度分配

★ 核心数据模型（15×15 格，每格 4m，chunk 60×60m）
  enum TileType { UNKNOWN=0, ROAD=1, WATER=2, PIT=3, PLATFORM=4 }

  ports: { top, bottom, left, right }  // 每条边 2 个出口（确定性哈希）

★ 生成流水线（5 阶段）
  阶段 0 ─ 端口派生（边界协议）
    每条边生成 2 个出口位置（1~13 格，不贴角，间隔 ≥ 3）
    对称性保证：Chunk(cx,cz).right = Chunk(cx+1,cz).left
    → 跨块时道路无缝，玩家不会遇到断头路

  阶段 1 ─ 迷宫生成（Growing Tree 算法）
    从端口出发，逐步向相邻"墙"单元格挖路，直到目标路占比
    ★ 可变密度：每 chunk 随机 30%~70%（hash2(seed+cx+cz+1818)）
      低密度（30%墙）→ 开阔地，像广场
      中密度（50%墙）→ 标准迷宫，走廊+墙均衡
      高密度（70%墙）→ 狭窄迷宫，巷战感
    → 返回值：passage[i]=1 表示格子 i 是路（可通行）

  阶段 2 ─ 地形分类（墙区 → 高台迷宫墙 + 少量水坑）
    墙区（~30%~70% 格子）按比例分配：
    ├ 60% → 高台（PLATFORM，+1.8m）   = 迷宫墙
    ├ 15% → 水体（WATER，-0.5m）       = BFS 生长 3~6 格连续湖泊
    ├ 15% → 坑洞（PIT，-3.0m 秒杀）    = BFS 生长 2~4 格连续陷阱
    └ 10% → 死路平地（ROAD，0m）       = 视觉死胡同

    ★ 高台就是迷宫的墙：走廊（ROAD）是平地，墙（PLATFORM）是高台，
      玩家走在走廊里，两边是 1.8m 高的墙，形成迷宫式战斗空间
    ★ 水/坑用 BFS 生长成连续集群，不再单格散落

  阶段 3 ─ 端口连通性兜底
    只保证 8 个端口格子不被水/坑堵死，不强制全局连通
    → 每个连通分量可独立生长，端口必须可通行

  阶段 4 ─ 高度分配（绝对平整）
    ROAD：0m（端口无扰动，内部 -0.1~+0.3）
    PLATFORM：1.8m + 0.0~+0.4 随机
    WATER：-0.5m（无扰动）
    PIT：-3.0m（无扰动）

★ 确定性保证
  所有随机选择（端口位置、迷宫游走方向、墙区分类洗牌、BFS 种子、
  高度扰动）全部基于种子：(day, chunkX, chunkZ) → 唯一结果
  不依赖任何外部状态或邻居数据

★ 跨 Chunk 全局连通性证明
  块内：迷宫生成树连接了所有 ROAD 格子，且至少连接到 8 个边界端口
  块间：对称哈希保证端口对齐，两边都是 ROAD 且连通到各自生成树
  → 无限网格上的所有 Chunk 通过"端口握手"形成无限连通图

★ 出生安全区
  Chunk(0,0) 中心 6×6 格（24m×24m）强制平地，无论抽到什么密度，
  玩家出生和摔死传送点都保证平坦（防出生即死循环）
```

★ chunk 视觉网格（buildChunkMesh，已实现）：
  ├ PlaneGeometry(60,60,60,60) + rotateX(-π/2) → 顶点高度 = 世界采样

  ├ ⚠ 踩坑（已修）：顶点局部坐标映射必须用旋转后的坐标直接平移

  │   统一函数）→ 直角立面：数据二值（块内 1.5/块外 0），单格采样时
  │   块边界顶点=0 → 视觉斜坡 → 角色站在斜坡上方悬空（"站虚空"）
  ├ ★ 角色脚底采样 = surfaceHeightAt（顶点值三角形插值 = PlaneGeometry 真实
  │   剖分，2026-08-26 实测修正）→ 角色 y 永贴视觉面——角色采样与视觉采样

  ├ 顶点色 = terrainColorAt（块类型三色：高台沙黄/平地绿/坑洞深黑）
  ├ 法线 = 跨 chunk 世界高度差分（±1m 采样）→ 边界光照连续
  ├ frustumCulled=false（大地物不做包围球剔除，chunk 级管理）
  └ 邻居加载 → 重建旧网格（生成时邻 chunk 未加载 → 边界顶点 heightAt
    兜底 0 → 低带；邻居加载后必须重建，这是正确性需要而非修补）

★ 角色垂直运动（WorldMode.clampCharacter，kinematic 模式层驱动，极简）：
  ├ 采样 = surfaceHeightAt（与视觉网格同一插值函数）→ 脚底永贴视觉面
  │   （不陷地/不悬空——角色采样与视觉采样必须共用同一函数）

  ├ 角色（kinematic）与 trimesh 重叠无副作用（位置纯代码驱动，fixed
  │   推不开）；攀爬机制照旧（立面碰撞对 kinematic 不构成阻挡）

  │   12m/s 步长 0.2m/帧，掠面有低概率隧穿，实弹测试监控
  └ 管理：chunkBodies Map<chunkKey, entityId>（每 chunk 1 刚体），天内

  │   （移速 2.5m/s × 300s ≈ 最大 750m 直线，实际围飞船绕圈更短）

  │   卸载（卸载反而引入"回程地形重建不一致"风险，无收益）
  └ 若未来开放"长途远征"模式再启用 chunk 卸载（3.8 原规划）

### 3.9 水体生成架构（Gerstner 波）
```
大世界水面 = 网格 + Gerstner 顶点波（shader 计算，非 CPU）
 ├ ① 水面网格：大型平面（随 chunk 生成/跟随玩家），细分可控
 │   - 近处高细分（波浪细节）/ 远处低细分（LOD）
 │   - 或全屏 quad + 顶点置换（相机空间，视距无关）
 ├ ② 波形（顶点着色器，每顶点算）：
 │   y = Σ A_i · sin(k_i·(x,z) + ω_i·t + φ_i)   （多层叠加，如 6 层）
 │   法线 = 解析导数（cos 组合），不额外差分
 ├ ③ 着色：
 │   - 基色（深/浅水区参数化）
 │   - 高光（Blinn-Phong，法线来自波形导数）
 │   - 泡沫（浪尖：高度/曲率阈值 + 噪声）
 │   - 反射/折射：SSR（屏幕空间）或 cube map 近似
 ├ ④ 交互：
 │   - 浮力：采样水面高度 → 浮力公式（阿基米德）驱动实体
 │   - 涟漪：实体入水/攻击 → 叠加局部波形（衰减）
 ├ ⑤ 性能：
 │   - 波形全在 vertex shader（GPU），CPU 零开销
 │   - 近处 512 细分 / 远处降采样
 │   - 水仅在有水的主题区启用（如龙门外环有河，实验室无）
 └ 实现位置：services/render/WaterSystem.ts（独立模块，可插拔）
```

### 3.10 光栅化地图与小地图（RasterMap + Minimap）
```
★ 动机：
  ① 射击检测要覆盖"非实体阻挡"（墙/障碍物可能不是实体、没有刚体，
     物理 castRay 检测不到 → 子弹穿墙）→ 阻挡数据与"实体/刚体"解耦
  ② 左上角小地图：整图光栅化，天然数据源
  ③ 远距离 LOD：远处角色不渲染大世界贴片，小地图仍保留其信息（渲染裁剪，
     逻辑实体照常存在——AI/碰撞/伤害不受影响）

★ RasterMap（services/map/，★ 升级为统一空间层，1m cell）：
  ├ cell = { height（地形高度）, blockHeight（阻挡顶高,0=无阻挡）,
  │          entities: Set<实体引用>, lodLevel }
  ├ 粒度 1×1（64×64 地图 → 4096 cell；1 地块 = 1 像素 = 小地图一像素）
  ├ 静态：地形高度图 + 静态阻挡标记 → 构建（启动一次）
  │   ★ 双通道同源：墙既有刚体（挡角色移动）又有 cell（挡射击），
  │     从同一配置生成，运行时统一更新（破坏/开门 → cell + 刚体同步改），防漂移
  ├ 动态：实体引用注册（insert/move/remove，哈希移块）
  ├ ★ 视锥梯形查询（queryFrustum，已实现）：
  │   - 梯形顶点 = near 底边两角投影（近边）+ far 顶边两角投影（远边），
  │     投影到 y=0 → 严格【凸四边形】→ 行扫描（每 z 行边插值圈 x 区间）
  │     → 遍历区间 cell
  │   - 成本 O(梯形行数 + 区间 cell)，与实体总数解耦
  │   - 实体位置在 insert 时降维为 2D cell → 剔除全程在小地图 2D 数据上做
  │   ⚠ 踩坑记录（已修）：
  │     ① dir 必须归一化再乘 t（t 是真实距离语义）——未归一 → 投影点
  │        上万单位外 → 行扫描迭代爆炸 → 主线程卡死
  │     ② 梯形顶点必须构成凸四边形——此前 far 4 角 + 相机 ±1 兜底点
  │        = 6 点乱多边形 → 行扫描交点 2~4 个取前两个 → 区间错乱
  │        → 大量可见 cell 漏遍历 → 子弹等小物体 3D 不可见（小地图独立
  │        逻辑正常 → "小地图能看到、3D 看不到"）
  │     ③ 扫描范围钳到相机 ±2×maxDist（防投影异常迭代爆炸）
  │   - three.js per-mesh frustumCulled 已关闭（FTXQuad）——单一 2D 剔除，
  │     无双系统不一致；代价是梯形边缘（屏幕外 1-2 行）实体被渲染
  │   ★ 边缘冗余 = 主动设计：快速转视角时边缘实体提前加载，
  │     避免"转头瞬间来不及加载"（LOD3 距离截断兜底远距离）
  │   ★ 子弹排除在裁剪/LOD 之外：生命周期短（2s）+ 数量少 → renderAll
  │     全量直接渲染（applyViewDistance(0)，不裁剪不衰减）——高速小物体
  │     不依赖裁剪判定，保证飞行可见
  ├ rayMarch(origin, dir, maxDist) → { t, hitY }（3D 射线 DDA）
  │   ★ 高度判定：射线在 cell 处 y < blockHeight → 阻挡（俯射/仰射正确）
  └ 运行时更新：破坏物/可开门 → 改 cell + 同步刚体

★ 关键原则（防双源）：
  ├ 实体对象（EntityManager 驱动）= 唯一数据源 + 执行层
  │   （HP/AI 状态/动画进度/冷却 全在实体，不复制进 cell）
  └ cell 只存【实体引用 + LOD 状态】——索引与决策层，不是数据仓库

★ LOD 决策（★ 2D 小地图统一管理，优于 3D 空间判定——地面玩法，
  xz 平面距离决定一切）：
  ├ ★ 决策顺序（已实现）：先视锥剔除、后 LOD 分级——与常规相反，效果更好：
  │   常规（先 LOD 后视锥）：对【全部实体】算距离分级（O(N)），再视锥剔除
  │   本方案（先视锥后 LOD）：① 2D 梯形圈定可见范围（行扫描，O(区域)，
  │     与实体数解耦）→ ② 只对【梯形内实体】算距离分级（O(N_visible)）
  │   → 一次遍历完成"裁剪 + 分级"（单系统），LOD 评估对象从 O(N) 降到
  │     O(N_visible)，远处实体（梯形外）零评估成本
  ├ ★ 纯响应式（实体不持有 LOD 状态，只接收距离）：
  │   决策（唯一评估点 = renderAll，以相机为中心）：
  │     queryFrustum 圈定 → xz 距离 → levelForDistance（services/lod 距离表
  │     [20,40,60]）→ applyViewDistance(d)
  │   执行：
  │     EntityBase.applyViewDistance(distance)：内部算级 → 联动
  │       anim.setLodLevel（动画：lod1 节流 / lod2 时间轴暂停）
  │       renderer.setLodLevel（渲染：lod2 渐隐 / lod3 全透明）
  │     子类覆写做表现降级：EnemyBase 私有 viewLod，lod1+ 关扭曲
  │     lod3 由 renderAll 跳过渲染（消失；只在小地图标点）
  │   意义：其他实体（物品/子弹）零改动——只需要"被传距离"；
  │     无状态 = 无同步问题、无缓存失效
  ├ 为什么比视锥剔除复杂度低：
  │   - 视锥：每实体 6 平面投影判定 + 包围体测试，还依赖相机矩阵每帧更新
  │   - 2D LOD：一次距离计算（行扫描 + levelForDistance），
  │     地面玩法 y 影响可忽略 → 判定成本与实体数量解耦
  │   - 视锥只有"视野内/外"二值；2D LOD 四级连续，还能顺带覆盖
  │     "视野外但距离近"的实体（转身即见，提前降级不突兀）
  ├ ★ 复杂度实测评估（每帧，60fps 预算 16.6ms）：
  │   │ 环节              │ 复杂度                  │ 实测成本    │
  │   │ 投影(4 unproject) │ O(1)                    │ ~5μs        │
  │   │ 行扫描            │ O(梯形行数+区间cell)    │ ~30-60μs    │
  │   │ LOD 分级          │ O(N_visible)            │ 微秒级      │
  │   │ 子弹全量渲染      │ O(N_bullet ≤ 100)       │ 微秒级      │
  │   ├ 行扫描是最大项（~0.2-0.4% 帧预算）；分级 O(可见实体)——先视锥后 LOD
  │   │   的顺序收益兑现（远处实体零评估）
  │   ├ 总 LOD 成本 ~0.05-0.1ms/帧，距离瓶颈（3-5ms 预算）有 50-100 倍余量
  │   └ 可优化空间（当前不必动）：梯形顶点可每 2-4 帧重算（只随相机变）；
  │     实体多时 queryFrustum 结果数组改复用缓冲
  ├ 渐隐表现（渲染层实现）：FTXQuad 距离驱动 uniform（uFadeAlpha）——
  │   lod2 → 半透明（0.45），lod3 → 全透明（+渲染跳过）
  │   后续扩展：雾颜色混合（黑雾）/ 采样模糊（mip 偏移）由可视度系数驱动
  ├ 大实体（Boss 跨多 cell）：按中心 cell 注册 + 查询半径放宽，不做多 cell 注册
  └ 逻辑不受影响：AI/碰撞/伤害照常（LOD 只影响表现，不影响实体存在）

## 4. 战斗系统架构

### 4.1 伤害结算流程
```
★ 已落地（services/combat/DamagePipeline.ts）——可插拔 modifiers 结算链：

命中（碰撞/近战范围判定）
 → applyDamage(base, source, target, type?)
 → 按序执行 modifiers（顺序即语义，加机制 = 插入一个 modifier）：
     ① 闪避  dodgeRate   → dodged（伤害归零，中断）
     ② 格挡  blockRate   → 伤害 × blockMult
     ③ 护盾  shield      → 先扣护盾值（超出穿透）
     ④ 防御  attackPower - defense（减法）
     ⑤ 暴击  critRate    → × critMult（作用于净伤害）
     ⑥ 下限  取整，最小 1
 → 结果 { final, crit, dodged, blocked } → target.onTakeDamage（未闪避才扣）
 → 死亡判定 → onDeath（掉落/清实体/结算）

实体战斗属性（EntityBase，全部可调参）：
  hp / attackPower / defense / critRate / critMult /
  dodgeRate / blockRate / blockMult / shield

★ 扩展方式（撑到后面）：
  遗物"受伤+10%"、元素相克、真伤无视防御、Boss 专属减伤…
  = 各写一个 modifier 函数插入 PIPELINE 链，核心零改动；
  DamageContext 携带 { base, source, target, type, damage, 状态标记 }
```

★ 攻击抽象（services/combat/Attack.ts）——三种攻击统一为"攻击意图"：
```
AttackOptions（联合类型）→ executeAttack(em, bullets, opts) 分派：
  ├ projectile 弹道：BulletManager.spawn（飞行 → 接触命中 → 伤害管线）
  ├ melee 近战：★ 范围瞬时判定（RasterMap.querySphere 以自身为中心，
  │   范围内敌对目标立即结算——不生成 hack 子弹，挥击语义正确）
  └ aoe 范围：落点范围结算（delay 延迟预留）
AI 行为/玩家技能只发意图（ctx.attack / executeAttack），不碰实现细节：
  ├ 敌人近战：meleeSwing → { type:'melee', range 1.8, damage 8, camp:'enemy' }
  ├ 玩家射击：firePlayerBullet → { type:'projectile', speed 12, damage 10 }
  └ 未来技能/Boss：同一入口加参数
★ 统一收益：命中判定与伤害结算只有一条链路，加攻击方式不改结算
```

### 4.2a 子弹管线落地状态（当前实现，已评估三全）
```
★ 结论：子弹 = 四个模块，数据契约解耦：
   ① BulletVisual   离屏子弹实体（继承 OffscreenBake：流体 + 蒙版/VAT → 一张纹理）
   ② BulletEntity   纯物理实体 + 基类公共函数（位置/速度/碰撞/寿命 + 全部渲染数学）
   ③ BulletRenderer InstancedMesh 一次 draw call（消费①纹理 + ②快照）
   ④ BulletManager  组合层（池化 + 每帧串联 + 生命周期）

★ 数据契约：
   - ①→③：getTexture()（纹理引用，零拷贝）
   - ②→③：{ position, velocity, isActive } 快照（渲染器不持有实体）
   - ①与②互不感知；③不知道纹理怎么烘焙、实体怎么运动

★ OffscreenBake 基类（services/render/OffscreenBake.ts，离屏 RT 管线通用底座）：
   - RT（纹理同尺寸，透明底，模板缓冲）+ 正交 0..1 相机
   - begin()/end()：切 RT + 透明清屏 + 还原 clear color / autoClear / RT
   - getTexture()/dispose()；子类只需往 scene 放内容、在 begin/end 间渲染
   - 不知道 3D 世界/相机/实体——纯 2D 纹理空间的画面生产者

★ ① BulletVisual（services/combat/BulletVisual.ts，继承 OffscreenBake）：
   - 流体：素材包 physics → FluidEffect（残差流动/注入；开火 reset）
   - 烘焙：区域实体 → 模板裁剪（fill/color 两遍）+ VAT 顶点位移 + 流体合成
   - 无蒙版实体 → 全幅合成 quad（base+residual/流体）同一 RT
   - 扭曲关闭（交给 ③ 的 UV 空间）

★ ② BulletEntity（services/combat/BulletEntity.ts）：
   - EntityBase 无 asset（不建动画/渲染器）→ 纯物理实体
   - 物理 read 模式 + 碰撞（rapier 事件分发）+ 伤害管线 + 寿命/阵营
   - ★ 基类公共函数（纯数学，可单测，渲染器直接消费）：
     ├ resolveFlightDirection(速度, 上次) —— 3D 方向；零速保持上次（反弹/静止无跳变）
     ├ computeRenderTransform(位置, 速度, 相机) —— 头尾轴 = 速度全 3D 共线
     │   （头向前、尾向后，反弹自动跟随）+ 绕头尾轴滚转使平面法线尽量朝相机
     │   （摄像机看到的面积最大，标准 velocity-aligned billboard）
     ├ writeRenderMatrix(target, offset, …) —— 基 + 弹头锚点 + 缩放 → 列主序 16 元素，
     │   零分配写入（弹头锚点：quad 中心 = 位置 - long×半高，碰撞点 = 视觉弹头）
     └ computeWorldSize(asset, 宽=2/3) —— 世界尺寸按纹理宽高比

★ ③ BulletRenderer（services/render/BulletRenderer.ts）：
   - InstancedMesh（capacity 实例 = 池容量）+ 材质（采样烘焙纹理 + 呼吸扭曲
     + 纹理旋转（绕平面法线 Z 轴 2D UV）+ 深度遮挡）
   - sync：调基类函数（resolveFlightDirection → writeRenderMatrix），
     自身只保留每实例 dirs 状态；失活实例矩阵 scale 0（隐藏）

★ ④ BulletManager（组合层）：池化 + 每帧串联
   visual.step(dt)（有子弹在飞）→ renderer.sync(allBullets, camera)

★ 命中特效（已接，见 3.3.3a 矢量动画播放器）：
   - BulletEntity.hitFx 回调（与 recycle 同注入模式，纯数据无渲染依赖），
     每次碰撞 started 只触发一次
   - BulletManager.spawnHitEffect → 服务层函数 attachHitEffect（services/fx）：
       实体命中 → 击中点偏移 + attachEffect（击中点跟随实体走，播完自动回收）
       地形命中 → 固定点列表（terrainFxViews，每帧重传同一命中坐标）
   - 特效 = 主角子弹击中特效.scene.zip（hit_effects.json，2 形状：
     白「图层3」1.3x 固定外扩 + 金「帧1」1.9~2.5x 随机外扩）

★ 架构评估（已评审）：
   ├ 达标：四层职责分离 / 数据契约解耦 / 渲染数学全在基类纯函数（可单测）/
   │   热路径零分配 / 1 draw call + 1 烘焙 / OffscreenBake 可复用
   ├ 已知瑕疵（暂不改）：
   │   - render ↔ combat 轻量循环依赖（BulletRenderer→BulletEntity 静态函数；
   │     BulletVisual→OffscreenBake）——类型层面可编译；未来方向：
   │     渲染数学移入 render 层独立模块，或在组合层注入
   │   - 静态函数与实体同住一个类（领域内聚，可接受）
   │   - OffscreenBake 目前单一消费者（抽象略早，方向正确）
   └ 性能：GPU 成本与"唯一视觉状态数"成正比（100 子弹 = 1 状态）

★ 发射（WorldMode.firePlayerBullet，粗暴稳定版）：
   - 方向默认 = 相机准星方向（无条件发射）；落点命中作修正
   - 0.45s 冷却 / 速度 15 / 寿命 2s / 枪口高 1.1 / CCD / 反弹 0.8

★ 未接（按优先级，架构 4.2 规划）：
  ├ 飞行特效（子弹拖尾，播放器 EffectSlot）
  ├ 敌人死亡掉落（onDeath → 掉落物品，ItemBase 复用）
  ├ 玩家/敌人血条 UI
  └ 数值配置化（伤害/血量/闪避/暴击 → 配置表，当前实体属性字段）
```

### 4.1a 实体空间索引（SpatialGrid，分块遍历）
```
★ 动机（在子弹系统之前落地，子弹/技能/AI 索敌全部依赖）：
  EntityManager 每帧 O(n) 全量遍历的三类开销随实体增长失控：
  ① 渲染：视野外实体也走 billboard + 绘制管线
  ② AI 索敌：将来"找最近目标/范围内敌人"需全量距离计算
  ③ 交互查询：子弹命中、掉落拾取、范围技能
  物理碰撞已由 rapier 承担，不重复做。

★ 算法选型：均匀网格（Uniform Grid），不用四叉树/八叉树
  ├ 运动实体多（子弹/敌人每帧变位置）→ 换块 O(1) 哈希移动，
  │   树结构要频繁更新节点（分裂/合并），重
  ├ 地面玩法为主 → xz 平面 2D 网格足够（y 影响小）
  └ 实现简单、查询半径/矩形/视野覆盖一致

★ 结构（src/services/space/SpatialGrid.ts）：
  blockSize = 8（地图 64×64 → 8×8 块，共 64 块；块大小可配，实测调优：
   太大=接近全量遍历，太小=换块频繁）
  blocks: Map<blockKey, Set<EntityBase>>   # key = (cx,cz) 编码（负数安全）
  cellOf:  Map<EntityBase, blockKey>       # 实体当前块缓存（移块判定用）

★ 更新策略（集中刷新点，最稳的钩子方案）：
  ├ EntityBase 位置有多个写入方（输入驱动/物理 read/AI moveBy）
  │   → 在 EntityBase.update 末尾（syncRender 后）统一调
  │     em.onEntityMoved(base)：算新块 key，与缓存比较，变化才移块
  ├ 每实体每帧成本 = 一次哈希 + 一次比较（O(1) 均摊）
  └ 静止实体（站桩敌人/落地道具）零移块成本

★ 查询 API（分块的核心价值）：
  querySphere(x, z, r) → EntityBase[]      # 覆盖圆的所有块 → 块内距离过滤
  queryRect(x0,z0,x1,z1) → EntityBase[]    # 区域/扫掠
  queryVisible(camera) → EntityBase[]      # 视锥 8 角点投影到 y=0 平面 →
                                            AABB → 覆盖块集合（保守不误剔除）
    ⚠ 实现注意（已踩坑）：
      ① queryVisible 开头必须 camera.updateMatrixWorld()——
         renderAll 在 renderer.render 之前调用，矩阵未更新 = 用上一帧
         姿态裁剪 → 快速转头时边缘实体闪没
      ② 角点射线向上（仰视/平视）时钳制到 maxQueryRange（默认 128），
         不能把 far 平面上的点直接当投影点（AABB 失控 → 裁剪失效）
      ③ 已知项：每帧 Vector3 分配（GC 压力，中期对象复用）；
         同步时序：aiSystem 必须跑在实体管线之前（移动零滞后，见 4.9）

★ 接入点：
  ├ 渲染：EntityManager.renderAll(camera) → grid.queryVisible(camera)
  │   （视野外实体完全跳过；与 3.5 三层剔除联动：网格 = 遍历裁剪层，
  │     three.js frustumCulled = per-mesh 层）
  ├ AI 索敌：seePlayer/findTarget 改为从 grid 按 camp 查询（泛化索敌）
  ├ 子弹/技能/拾取：querySphere
  └ 物理：不动（rapier 已有）

★ 收益与阈值：
  ├ 实体 < 200 时纯遍历无压力——分块为渲染裁剪 + 索敌查询而做
  ├ 视野覆盖 64×64 地图约 1/4~1/3 → 渲染实体数直接 -60%+
  └ AI 索敌从 O(n) → O(块内数量)，敌人 30 个几乎免费
```

### 4.3 AI 架构（共用行为库 + 阵营标签）
```
AIStateMachine（每实体一个实例，配置驱动）
 ├ 读配置：状态机结构（状态/转移/行为名/条件名）
 ├ 执行：当前状态的行为（查行为表取函数）→ 每帧检查转移条件
 └ 切换：条件满足 → 切状态（通用解释器，敌人/友军同一套）

配置 = 状态机结构（数据，可加敌人不改代码，参数全可调）：
 "grunt": { ai: {
   states: {
     "patrol": { behaviors:["wander(speed:2,targetBias:0.04,biasCamp:player)"],
                 transitions:[{"cond":"seePlayer(radius:8,camp:player)","to":"chase"}],
                 minStay:3 },   // ★ 最短停留：保证脱离战斗后真的游走
     "chase":  { behaviors:["moveToTarget(speed:2.5)"],
                 transitions:[{"cond":"inRange(radius:1.5)","to":"attack"}] },
     "attack": { behaviors:["meleeSwing(duration:0.6)"],
                 transitions:[{"cond":"attackFinished","to":"patrol"},  // ★ 挥完一次回游走
                              {"cond":"outOfRange(radius:2)","to":"patrol"}] }
   }, initial:"patrol" } }

代码 = 行为注册表 + 条件注册表（名字 → 函数）：
 behaviorTable = { wander, moveToTarget, meleeSwing, shootBurst, rangedShot,
                   charge, suicideBoom, knockback, shieldBlock, heal, summon,
                   deployGuard, followFormation, death ... }
 conditionTable = { seePlayer, inRange, outOfRange, hpLow30, hitEnd ... }

★ 共用行为库（敌人/友军同一套函数）：
 移动类：wander / patrol / moveToTarget / follow / flee
 攻击类：meleeSwing / shootBurst / rangedShot / charge / suicideBoom
 受击类：knockback / stagger / shieldBlock
 辅助类：heal / buff / summon
 状态类：deployGuard（站桩守点）/ followFormation（阵型跟随）

★ 阵营标签（camp）决定"对谁反应"：
 ├ camp: 'player' → 玩家（维什戴尔）
 ├ camp: 'ally'   → 友军（部署/跟随）
 ├ camp: 'enemy'  → 敌人
 ├ 行为执行时按阵营查目标：
 │   - 索敌：敌对阵营（enemy 索敌 player/ally；ally 索敌 enemy）
 │   - 伤害：碰撞时同阵营不伤（过滤在碰撞层）
 └ 同一个行为，不同阵营反应不同：
     - 例：shootBurst → 敌人朝玩家射 / 友军朝敌人射（同一函数，目标选择按阵营）

 加新敌人/友军：
 ├ 复用行为 → 只改配置（组合已有行为/参数）
 ├ 全新行为 → 写一个函数注册进行为表（少量）
 └ 阵营差异 → 不改代码，靠 camp 标签（行为内查目标）
```

### 4.3a AI 模块落地设计（可实现级）
```
★ 目的：给 EnemyBase/Ally 提供自主行为（巡逻/索敌/攻击），
   替代当前"相机决定朝向"的占位逻辑（修复"敌人盯着玩家"）。

文件结构（src/systems/ai/）：
 ├ AISystem.ts        # 管理器：维护所有 AI 实体，每帧驱动 update
 ├ AIStateMachine.ts  # 状态机解释器（读配置 → 执行行为 → 查条件 → 转移）
 ├ behaviors.ts       # 行为注册表（名字 → 函数）
 ├ conditions.ts      # 条件注册表（名字 → 函数）
 └ aiconfig.ts        # AI 配置类型 + 敌人默认状态机表

★ 完全数据驱动 / 敌人-队友共用：
  ├ 行为/条件 = 查表函数（behaviorTable / conditionTable），新增 = 注册函数
  ├ 敌人/队友共用同一套注册表 + 同一 AIStateMachine 解释器
  │   - 敌人：巡逻/索敌/攻击（见下）
  │   - 友军：守卫/跟随（后续配新状态表即可，不改框架）
  └ 一切参数在配置里调整（每个实体可覆盖，见示例注释）：
      行为参数（wander：speed/turnRate/turnInterval/targetBias/biasCamp；
               moveToTarget：speed；meleeSwing：duration）
      条件参数（seePlayer：radius/camp；inRange/outOfRange/loseTarget：radius）
      状态参数（minStay：最短停留秒数）

接口设计：
  AIComponent（挂在 EnemyBase/Ally）：
    { configId, stateMachine, camp, targetId, lastMoveDir, update(dt, ctx) }
  BehaviorContext（行为/条件统一上下文，模式层每帧注入）：
    { dt, time(累计), target(索敌目标), findTarget(camp → 位置) }
    └ 索敌完全解耦：findTarget 由 WorldMode 注入（camp='player' 查玩家），
      行为/条件只按阵营查，不依赖具体实体 → 敌人找玩家、友军找敌人
      只需换注入实现
  行为签名：behavior(entity, ctx, params) → void（移动/攻击 = 调实体公开方法）
  条件签名：condition(entity, ctx, params) → boolean

★ 关键机制（已实现并验证）：

  ① 状态流转（基准敌人普瑞赛斯，HUD/日志可观察）：
       patrol(游走) ──seePlayer(radius:8)──▶ chase(追击)
          ▲                                  │ inRange(1.5)
          │                                  ▼
          └──── attackFinished(挥完0.6s) ◀── attack(一次性挥击)
              or outOfRange(2) 或 loseTarget(12)

  ② minStay（防状态抖动）：
      AIStateMachine 记录进入状态的停留时间；未满 minStay 不转移。
      例：patrol.minStay=3 → 脱离战斗后至少真实游走 3 秒才重新索敌，
      否则 patrol 会被 seePlayer 一帧拉回 chase（"追击后不游走"的根因修复）。

  ③ 一次性攻击：
      meleeSwing 播完（duration 秒）标记 aiSwingDone → attackFinished 条件
      自动退出 attack 回游走。不再无限循环挥击（"永远卡 attack"的根因修复）。
      重新进入 attack 自动重开一轮挥击（自愈）。

  ④ 游走轻微偏向目标（targetBias/biasCamp）：
      Reynolds Wander 转向时刻，把随机转向角向指定阵营目标拉回 targetBias 比例
      （0=纯随机，0.04≈轻微）→ 巡逻路径整体缓慢倾向目标，但仍随机弯绕。
      注意：不能逐帧混合（每帧 8% 在 60fps 下也会秒级转向 = 直追玩家），
      只在周期转向时偏置才自然。biasCamp='' → 完全纯随机。

  ⑤ 状态播报（调试用）：
      WorldMode 左上角 HUD（0.2s 刷新）实时显示每个 AI 实体当前状态；
      EnemyBase 每秒 [AI] 日志（状态/坐标/刚体/显示帧/yaw）。

★ 与实体管线集成（EnemyBase）：
  ├ 构造：opts.aiConfig 传入 → 建 AIStateMachine + 注册 aiSystem（无配置 → 无 AI 静止）
  ├ updateAI：AISystem 每帧驱动（行为 → minStay 检查 → 条件 → 转移）
  ├ 移动：行为调 moveBy → CharacterController.moveToward（与玩家同一套位置逻辑）
  └ ★ 朝向由移动方向决定（非相机）：
      moveDir 与当前朝向夹角 → facing（前/后帧组）+ setYaw（0/π）
      静止 → 保留最后移动朝向（不面相机）→ 玩家绕背仍可看后帧

★ 与相机解耦（关键）：
  AI 实体朝向 = 移动方向（自主）
  玩家相机 = 纯观察者（facing 判定不再依赖相机位置）
  → 敌人巡逻时自然转身，玩家绕背看后帧（AI 不动时朝向固定）

性能：AI 实体 < 30（预算内）；每帧行为/条件 = 查表函数调用（轻量）
```

★ 玩家控制/攻击：单独一套代码（不套 AI 解释器）
```
AI 状态机 = 给"自主决策实体"用的（敌人/友军：自动索敌/巡逻/守卫）

玩家（维什戴尔）= 输入驱动实体，独立实现：
 ├ 输入 → InputActions（move/look/attack/dodge/skill/interact）
 ├ 玩家控制脚本：直接消费输入 → 移动/闪避/攻击/技能（无状态机）
 ├ 受击/死亡：独立流程（不套 AI 状态）
 │   - 受击：无敌帧 + 受击动画 + 特效（PlayerController 处理）
 │   - 死亡：死亡流程（结算/局结束）
 └ 与 AI 系统的关系：只共享"行为函数库"里的数值函数
     （如伤害计算、击退），不共享状态机
```

- ★ **AI 框架通用：角色/敌人/友军共享同一套 AIStateMachine**
  - 敌人用：巡逻/索敌/攻击/技能/死亡
  - 友军用：守卫模式（deployGuard）/ 跟随模式（followFormation）
  - 玩家用：独立 PlayerController（输入驱动，不套 AI 状态机，见上）
  - 差异全在状态表配置 + camp 标签，不是不同实现

### 4.8 rapier 使用总览（特效 vs 物理分工）
```
★ 分工原则：特效（视觉）= 编辑器/播放器做；物理交互（力/碰撞/运动）= rapier 做

哪里用 rapier（物理交互）：
 ├ 移动碰撞：角色/敌人走路不穿墙、不穿地形
 │   - 动态刚体 + 地形固定刚体 → 碰撞拦截
 ├ 子弹：动态刚体 + 速度（物理推动飞行 + 碰撞命中判定）
 ├ 爆炸冲击：querySphere 找范围刚体 → applyImpulse（被炸飞）
 ├ 重力：世界重力 + 每刚体 gravityScale（Boss 局部重力场）
 ├ 击退/受击：命中时 applyImpulse（敌人被击退/击飞）
 ├ 掉落物：物品实体动态刚体（掉地上、物理堆叠）
 ├ 浮力：水面上实体 → 施加浮力（Gerstner 高度采样）
 ├ 拾取/交互：碰撞触发（走近箱子触发拾取）
 └ 移动平台/机关：运动学刚体（自己控制移动）

哪里不用 rapier（纯特效/表现）：
 ├ 特效：粒子/光/拖尾/爆炸视觉（编辑器 .scene.zip + 播放器）
 ├ 布料：GPU verlet（ClothSystem，独立模拟）
 ├ 水：Gerstner 顶点波（shader，不是物理流体）
 ├ 2D 贴片形变：软体形变（7.3，不是刚体动画）
 └ 动画：帧动画/位移（billboard 动画，非物理）

典型组合（爆炸 = 特效 + 物理）：
 ├ 特效层（编辑器/播放器）：爆炸火球/冲击波视觉
 ├ 物理层（rapier）：范围刚体被冲击力推飞
 └ 伤害层（游戏代码）：范围伤害结算
```

### 4.9 PhysicsWorld 封装（接口级）
```
PhysicsWorld（services/physics，唯一接触 rapier API 的地方）：
 ├ init()                      # 创建 world，设置重力（全局 -9.8；子弹 gravityScale=0）
 ├ addBody(entity, opts)       # 创建刚体+碰撞体（userData=entity.id）
 │   - dynamic（物品/子弹/掉落物：纯物理）
 │   - kinematic（角色/敌人：位置 100% 代码驱动，推挤 dynamic，不受力/重力）
 │   - fixed（地面/边界墙/静态障碍）
 ├ setKinematicPosition(id)    # 运动学位置驱动（step 前；rapier 自动推挤 dynamic）
 ├ removeBody(id)              # ★ 移除刚体（实体销毁联动，防止物理世界泄漏膨胀）
 ├ step(dt)                    # 固定步长物理步进（1/60，main.ts 每帧驱动）
 ├ setLinvel(id, vel)          # 设速度（子弹发射）
 ├ applyImpulse(id, force)     # 施力（击退/爆炸/被击飞）
 ├ querySphere(pos, radius)    # 球体查询 → 命中实体 id 列表（userData）
 ├ castRay(ray, maxToi, excl)  # 射线查询（摄像机→准星落点；返回 userData+落点）
 ├ onCollision(handler)        # 碰撞事件（实体管线订阅并分发）
 └ getPosition / setPosition   # 位置读写（初始修正/边界同步）

★ 刚体身份（踩坑总结，最重要的决策）：
  ├ ⚠ rapier 0.14.0 wasm 绑定缺陷：createRigidBody 返回的 handle 是错读值——
  │   早期创建碰巧读到小整数（≈索引）才"能玩"，后续创建读到递增垃圾值
  │   （栈内数据）→ Coarena 索引越界 → 刚体"找不到"
  │   ★ 处理：PhysicsWorld 内部自管 id → RigidBody 映射（id 从 1 递增不复用），
  │     对外接口不变（仍返回 number）；绝不信任/归一化 body.handle
  ├ 碰撞事件身份 = userData（entity.id，desc 注入 RigidBody）——
  │   handle 会被 rapier 复用，旧事件按 handle 查会误伤新实体
  └ 查询类（castRay/querySphere/intersects）返回 userData 而非 handle

★ 碰撞事件处理（两大约束，都踩过坑）：
  ├ ① drainCollisionEvents 回调中禁止修改物理世界（add/remove 刚体）——
  │    破坏 narrow-phase 迭代 → wasm 内存损坏 → 后续创建刚体返回垃圾
  │    → 回调只收集事件（userData 对），step 返回后统一派发
  └ ② 派发后"良性残余访问"：事件批次内先销毁后查 / 上一帧遗留 →
     getBody 判空静默返回（不告警；正常销毁流程的防御）

★ 刚体生命周期（实体管线联动，防泄漏）：
  EntityBase 构造（em.create）→ 建刚体（y = 脚底 + bodyOffsetY）
  EntityBase.dispose → em.destroy → physics.removeBody（自管 id 回收）
  ⚠ 漏掉 removeBody = 每颗子弹/每次销毁泄漏一个刚体（物理世界膨胀）

★ 角色碰撞方案（当前实现，无补丁）：
  ├ 角色/敌人 = kinematic 刚体：位置 100% 代码驱动
  │   - x/z：输入/AI 移动（位置直接推进）
  │   - y：模式层设地形高度（纯位置数据，物理不参与）
  │   - 每帧 setNextKinematicTranslation → step
  │   - 物理自动推挤物品/子弹（kinematic vs dynamic 标准行为）
  ├ 物品/子弹 = dynamic（纯物理，零代码干预）
  ├ 地图边界 = 4 面物理墙（fixed 围栏，物理自然挡住）
  ├ 碰撞体声明 = 实例基类属性（EntityBase.collisionVolume：形状 + offsetY），
  │   物理创建与刚体偏移统一从属性取；★ 子类覆写 physicsBodyOffsetY 时
  │   fallback 模块常量（collisionVolume 在 super 后初始化，构造期读不到）
  ├ 角色间推挤 = 实体层（kinematic vs kinematic 无物理响应）：
  │   每帧 querySphere 分块查邻近角色 → 水平 AABB 重叠 → 最小分离轴推开
  │   （公共规则库 separateXZ，各推一半）
  └ 碰撞事件：EntityManager 订阅 onCollision → 按 userData=entity.id 查 bases
      → EntityBase.onCollision(other|null, started) 钩子（null=静态世界）

★ 主循环时序（main.ts → WorldMode.update）：
  ① AI 驱动（aiSystem.updateAll：索敌/行为 → 本帧移动方向）
  ② 实体管线（entities.update：onUpdate 位置推进/角色推挤 → syncPhysics
     → 动画 → 渲染 → 空间索引）
  ③ 角色位置控制（clampCharacter：y 地形 + xz 边界，纯位置数据）
  ④ 物理步进（physics.step 固定 1/60）
  ⑤ 渲染（renderAll 视野块裁剪 → renderer.render）
  ⚠ AI 必须在实体管线之前：否则移动方向滞后 1 帧

### 4.9b 公共碰撞规则库（Collision.ts）
```
★ 目的：碰撞形状工具与判定函数公共化（最大化复用，可调参），
  实体基类/瞄准服务共用，避免各写一份。

services/physics/Collision.ts：
  shapeExtents(shape) → { hx, hy, hz }
    # 碰撞形状 → 三轴半宽（ball=半径；capsule=半径/半高+半径；cuboid=hx/hy/hz）
  estimateRadius(shape) → number

  overlapXZ(ax,az,ahx,ahz, bx,bz,bhx,bhz) → boolean
    # 水平 AABB 重叠判定
  separateXZ(ax,az,ahx,ahz, bx,bz,bhx,bhz) → 位移对 | null
    # 水平最小分离轴（各推一半；可调分配权重）

消费者：
  ├ CharacterBase.separateFromOthers：querySphere 分块查邻近角色 →
  │   公共 overlapXZ/separateXZ 推挤（查询半径余量 0.6 可调参）
  ├ Targeting：estimateRadius（球近似，替代各类型 switch）
  └ 后续：拾取判定/技能范围/陷阱触发统一复用
```

### 4.9a 瞄准/射线检测服务（Targeting）
```
★ 用途：任何发射者（主角/敌人/友军）射击前的"射线 → 落点"判定，统一走这里。
  管线归属：服务层（services/combat/）——实体管线的【消费者】，
  不是实体管线内部：调用 em.queryRay（空间索引）+ physics.castRay（物理）查候选/遮挡。

接口：
  aimRaycast(em, { origin, dir, maxDist?, exclude?, filter? })
    → { point, target, distance } | null
  ├ origin/dir = 3D 射线（发射者视角/准星）
  ├ exclude = 发射者（排除自身刚体与实体检测）
  ├ filter = 附加过滤（默认排除飞行子弹；敌人射击传 camp 过滤只锁玩家）
  ├ point = 落点（实体命中点在碰撞体上 / 遮挡物 / 地面墙）
  ├ target = 命中实体（null = 静态世界；伤害系统据此结算）
  └ distance = 命中距离

算法（三级）：
  ① 实体优先（辅助瞄准）：SpatialGrid.queryRay 分块遍历射线路径
     → 候选实体 3D 射线-球测试（球按碰撞体类型估：capsule=offsetY+radius，
       ball=2r，cuboid=对角线半）→ 最近命中必中（不受几何盲区影响）
  ② 遮挡校验（防穿墙）：实体命中后复核——命中点距离 < 目标距离 → 被遮挡
     → 落点 = 遮挡物
     ★ 遮挡来源（按 3.10 双通道）：
       - RasterMap.rayMarch（光栅化 DDA：覆盖非实体墙/障碍物）
       - 物理 castRay（刚体墙，可选兜底）
  ③ 物理兜底：无实体命中 → rapier castRay（地面/墙落点）
     ★ 落点防御（保证"无条件发射"的下游可靠性）：
       - 飞行中的子弹不算落点（命中 kind='bullet' → 视为无命中，
         否则向天打时新子弹会"追着上一发子弹"飞）
       - 落点距射线起点 < 0.5m（射线起点在碰撞体内 → rapier TOI≈0）
         → 视为无命中（避免子弹朝自己脚下打）

踩坑记录：
  ├ 纯物理射线有几何盲区（角度/高度掠过）→ 实体优先数学检测兜底
  ├ 实体检测必须加遮挡校验（否则墙后目标穿墙命中）
  ├ 遮挡校验必须覆盖非实体阻挡（墙不做成刚体时物理射线查不到）
  │   → 光栅化 rayMarch 补位（3.10）
  ├ 球近似略大于碰撞体（吸附感）——要精确可换射线-胶囊相交
  └ ★ 发射侧双保险（WorldMode.firePlayerBullet）：方向默认 = 相机准星方向
      （无条件可发射），aimRaycast 落点只作"修正"；射线抛异常/落点异常
      （NaN/离枪口<1m）→ 保持相机方向照常发射，绝不阻断开火

调用方：
  ├ 主角：WorldMode 准星瞄准（摄像机 → 落点）
  ├ 敌人/友军（后续）：origin=自身位置，dir=朝向，filter=敌对阵营过滤
  └ 命中特效/子弹追踪：hit.target
```

### 5.1 数据结构
```
InventoryGrid = 网格（如 6×8 格），每格可空/占位
ItemInstance（物品实例，运行时）：
 ├ itemId        # 配置表引用（尺寸/图标/可堆叠数）
 ├ gridSize      # 占格尺寸（w×h，如 1×2 / 2×2 / 3×1）
 ├ rotation      # 0° / 90°（是否旋转，占格交换 w/h）
 ├ stackSize     # 当前堆叠数（可堆叠物品用）
 └ slots[]       # 占用的网格坐标（由 gridSize+rotation+anchor 计算）

物品类型（内容设计）：
 ├ 不可堆叠：武器/装备/遗物（各占一格或多格）
 ├ 可堆叠：弹药（60 个一组）/ 食物（可叠放）/
 │        材料（合成用）
 └ 堆叠上限：按物品类型配置（stackable.maxStack）
```

### 5.2 拖动交互状态机（鼠标/触屏通用）
```
状态：IDLE → HOLDING(暂存) → DRAGGING(移动) → DROPPING(旋转检测) → IDLE
 ├ IDLE → 点击物品 → HOLDING
 │   - 物品进入"暂存区"（视觉上跟随指针）
 │   - ★ 原位置被"清空"（记录原位置 backRef，网格该处变空）
 ├ HOLDING → 移动指针 → DRAGGING（物品跟随指针，可旋转）
 │   - 旋转：按键 R（桌面）/ 双击或按钮（触屏）→ rotation 切换 0°/90°
 │   - 拖到目标网格：实时高亮"可放置区域"（绿=能放，红=不能）
 ├ DRAGGING → 松开 → 放置检测
 │   - 检测：目标锚点 + 旋转后占格 全部在网格内 且 全部为空
 │   - 能放 → 放入该位置（占用格子，记录新位置）
 │   - 不能放 → ★ 返回原位置（backRef 恢复）
 └ 任意状态 → 取消（ESC/右击）→ 返回原位置

检测算法：
 canPlace(grid, item, anchor, rotation):
   for each 占格(由 size+rotation 算出的相对偏移):
     if 越界 → false
     if 该格被占用 → false   （或：目标是堆叠同物品 → 走堆叠逻辑）
   return true
```

### 5.3 堆叠逻辑
```
拖到"同物品 + 已存在堆"时：
 ├ 若目标堆 stackSize < maxStack → 合并（目标堆 + 拖拽堆）
 │   - 超出部分：留在原位置（或剩余量继续拖）
 │   - 例：拖 30 弹药到已有 40 的堆（上限60）→ 合并到 60，剩 10 回原位
 ├ 若目标堆已满 → 按普通放置处理（不能叠就找空位）
 └ 快捷操作：双击堆 → 拆分（如 60 → 30+30，拆一半到相邻空位）
```

### 5.4 交互事件流（与输入抽象解耦）
```
触屏/鼠标 → InputActions（抽象）→ InventorySystem
 ├ 触屏：长按物品 = 拾取（进入 HOLDING）/ 拖动 = DRAGGING
 │      双击 = 旋转 / 双击堆 = 拆分
 └ 桌面：左键拾取 / 移动 / R 旋转 / 右键或 ESC 取消
- 具体映射在 InputBindings，背包逻辑只消费语义（pickup/drop/rotate/cancel）
```

### 5.5 与携带限额/舰船仓库联动
```
两个网格容器：
 ├ 随身背包（外出携带，体积有限 → 每日带出/带回限额）
 └ 舰船仓库（本舰，容量大 → 囤积）
- 转移：背包 ↔ 仓库 拖动（同一套拖动系统，跨容器放置）
- 战利品拾取：找到空位放入
- ★ 放不下 → 留在原地（箱子/地上原样保留），不销毁不丢弃
- 数据都在 Session（可序列化，存档兼容）
```

### 5.6 遗物专属栏（即时生效的被动位）
```
遗物有专属装备栏（类似防具槽），但只是"组织方式"：
 ├ 专属栏：遗物槽（如 3~5 格，独立于背包网格）
 │   - 拖动放入 = 装备上（有图标展示，视觉上"穿戴着"）
 │   - 从槽位拖出 = 卸下（可放回背包）
 ├ 放不下 → 塞背包：背包里的遗物同样生效（无差别）
 │   - 遗物 = 即时生效的被动物品（持有即生效）
 │   - 装备栏 vs 背包 = 只有"整理"区别，无效果区别
 ├ 效果：持有即生效（无需"激活"操作）
 │   - 黑王冠（非携带型）：开局即在，永不占槽
 │   - 携带型遗物（能天使/塞雷娅等）：槽位 or 背包都生效
 └ 设计含义：
 │   - 遗物槽 = 快速查看/美观（"穿戴着谁的遗物"）
 │   - 背包 = 仓库（多拿几个遗物，全部生效，但占背包空间）
 │   - 取舍在"背包空间"而非"装备选择"——多带遗物 = 少带物资
- 数据：relicSlots[]（槽位引用）+ 背包内的遗物实例（都算持有）
- 生效判定：Session 里"持有遗物集合" = 槽位 ∪ 背包内遗物

★ 遗物效果结算（局外永久 / 局内生效 两类）：
 ├ 局外永久（每天开始时结算）：
 │   - 黑冠：每天开始时全属性 ×1.01（叠乘，day 层数=黑冠层数）
 │   - 结算时机：新的一天开始（舰船醒来）→ 应用到 player.stats
 │   - 存档保存：属性已并入 stats（Session 存最终值）
 │   - 例：day 10 的黑冠 = 属性 ×1.01^10 ≈ ×1.105
 ├ 局内生效（外出时处理）：
 │   - 能天使→攻速+ / 塞雷娅→护盾 / 银灰→CD- 等
 │   - 外出（进入 WORLD 模式）时应用修饰器到战斗 stats
 │   - 回舰船（模式切换）→ 修饰器移除（下一轮外出重新应用）
 ├ 实现：RelicEffectSystem
 │   - 结算点：每天开始（黑冠）+ 进入战斗模式（局内遗物）
 │   - 效果 = 属性修饰器表（relics.json 配置：效果类型+数值）
 │   - player.stats 存"基础值"，效果以修饰器叠加（不污染基础）
 └ 与 Session：黑冠层数存 Session；基础值存 Session；
     局内效果不存（每次外出重新应用）

### 6.1 对话数据结构
```
DialogueGraph（对话 = 有向图节点，配置驱动）：
 ├ 节点：DialogNode { id, speaker, text, portrait, options[], effects[] }
 │   - speaker：说话者 id（NPC/维什戴尔/旁白）
 │   - text：文本（支持变量插值，如 {playerName}）
 │   - portrait：立绘引用（可选）
 │   - options：选项列表 → 指向下一个节点
 │   - effects：节点进入时的效果（给物品/扣血/解锁…）
 ├ 选项：DialogOption { text, next, condition?, effects? }
 │   - condition：条件（持有某物/天数/好感…）→ 不满足则灰显
 │   - effects：选择后的效果（分支结果）
 └ 终端节点：无 options → 对话结束（可触发事件结果）
```

### 6.2 对话流程引擎
```
DialogueSystem（推进/状态/效果）：
 ├ 开始：dialogue.start(graphId, context)
 ├ 推进：显示节点 → 玩家选选项（或点继续）→ 进入 next 节点
 ├ 条件：选项 condition 检查（context 查 Session/持有/天数）
 ├ 效果：节点/选项 effects 执行（EventBus 发出：给物品/扣血…）
 ├ 结束：到达终端节点 → 对话完成 → 触发后续（事件结算/剧情）
 └ 上下文：对话期间可暂停游戏逻辑（战斗外），或允许旁白叠加（战斗中）
```

### 6.3 对话 UI（Canvas 自绘）
```
对话界面 = UIEngine 组件（见内容设计 UI 系统）：
 ├ 文本区：说话者名 + 文本（打字机效果可选）
 ├ 立绘区：speaker 立绘（背包/图鉴同款资源）
 ├ 选项区：纵向按钮列表（灰显不可选的）
 ├ 跳过：点击跳过打字机 → 直接显示全文
 └ 输入：走 InputActions.interact（桌面E/触屏点击）推进
```

### 6.4 事件系统（对话的容器）
```
EventSystem（地图事件 = 触发点 + 对话/选项 + 结果）：
 ├ 触发点：地图上的事件实体（走近触发 / 交互触发）
 ├ 事件配置：event.json
 │   - 遭遇幸存者：对话 → 选项（给物资/收留/无视）→ 结果效果
 │   - 发现干员残响：对话 + 遗物获得
 │   - 源石异变：环境事件（对话/警告 → 结果）
 ├ 流程：触发 → 启动对话 → 对话结束 → 执行结果效果
 ├ 一次性：事件执行后标记完成（每天新地图 → 事件重新布点）
 └ 与守卫/探索解耦：事件结果通过 EventBus 发给各系统
- 实现位置：systems/dialogue/（DialogueSystem + EventSystem）
```

## 8. 地图系统

### 8.0 地形渲染管线（2026-08-25 双纹理方案定稿，替代 08-23 版）

> ★ 地块丰富度/装饰纹理/地图装饰物的扩展层设计 → 见《地块与装饰架构.md》
> （TileDef.gameplay + DecorLayer 双模型 + PropDef 散布，2026-08-26）
>
> 设计原则：底色单一不是缺陷——形状信息由光照承载（方舟地形本质）。
> 一切装饰决策从 hash2(seed, cx, cz, ...) 派生：重建不漂移。
> ★ 光照哲学（定稿）：**默认整个地面是暗的，光是把亮度"加上去"的**——
> 环境项只是保底可见度，太阳直射承担主要照明；影子读作「光的缺席」
> 而非「涂上去的黑块」。

#### 三域架构（数据 → 烘焙 → 运行时）

```
━━ 数据域（确定性唯一真相源）━━
ChunkGenerator.generateChunk(seed,cx,cz) → ChunkData
RasterMap（活的服务；结构上满足烘焙契约 TerrainBakeSource）

━━ 材质组层（2026-08-28 融合定稿；原 RegionTheme 已删除并入组）━━
生物群系概念唯一化：材质组（TileGroups.GroupDef）= 成员地块 + 调色板 + 生成偏置
  palette {hueShift/satMul/lightMul}   ← 原 RegionTheme 视觉参数
  gen {densityBias/waterMul/pitMul}    ← 原 RegionTheme 生成参数
按【chunk 选中的组】查询（每 chunk 硬边界，肉鸽友好；无空间插值层）
调色调制四处同源消费：
  ① 生成：ChunkGenerator 读 panel.gen（迷宫密度/水体/坑洞比例）
  ② 烘焙：bakeCompute 读 q.palette（经 BakeQuery/BakeSnapshot 透传到 Worker；
     无材质地块的 albedo 调色）
  ③ 材质地块：ChunkManager 把 palette 调制进 uMatBase（2026-08-28 新能力——
     原材质地块不随区域变色，现 rock/grass/wood/moss 等随组呈色调差异）
  ④ 侧壁：ChunkWalls 按 chunk 的 groupKey 查 palette（墙顶点色与地面同源）
语义色保读性：水/坑只吃 SEMANTIC_THEME_MIX=45% 调制（警示红/深蓝不可洗掉）
⚠️ Boss4D 旧路径刻意不吃组调色（四维空间有自己的视觉语言）
⚠️ 已知限制：Minimap terrainColorAt 未接组调色——小地图色与地表暂不同步
⚠️ 行为变更（2026-08-28）：生成偏置从"空间插值渐变"改"按组恒定"，
  同 seed 地形与旧版不同；旧回归基线需重生成
高度档位：平台从固定1.8m 改为三档梯田 1.2/2.2/3.4（低频噪声分带，
  同档成片；档差≥0.9m > CAST_MIN_DEPTH → 侧壁自动补齐）

━━ 烘焙域（每 chunk 一次；重计算在 Worker，主线程零尖峰）━━
★ 异步管线（2026-08-26）：
  WorldMode.requestStandardBake
    → TerrainBaker.request（快照提取亚毫秒 + postMessage transfer）
    → terrainBake.worker（bakeCompute 纯计算，零 three 依赖，独立 5KB chunk）
    → resolve(RGBA 缓冲) → 主线程 assembleChunkMaps（canvas+CanvasTexture）
    → finishStandardChunk（几何/材质/物理）
  失败语义：resolve(null) 一律=回退 bakeChunkMaps 主线程同步烘（输出逐位一致）
  换代机制：bakeGen 计数器，dispose/切风格使在途结果作废；
    setMapStyle 把未建成 key 重新入队按新风格构建
  快照协议：主线程拷 3×3 chunk 原始数组（heights/blockTypes，~150KB，
    亚毫秒）——不走逐点查询（surfaceHeightAt 单次≈16 次 heightAt，
    逐点提取一张快照要 ~17 万次调用）。未加载 chunk 高度记 0（与
    heightAt 回退一致）。Worker 端 makeSnapshotSource 同公式重构。
★ 烘焙前数据环补齐（RasterMap.ensureData）：快照覆盖区 chunk 数据先
  确定性生成再拷贝——烘焙输出与加载顺序无关，射线永不见"未加载=0"
  的假邻域。推论：接缝重建只需重建几何，不再需要重烘焙。
★ 烘焙缓存（ChunkAppearance.bakeCache，2026-08-26）：纹理级 Map<seed|cx|cz>，
  消除两类浪费——①风格切换往返全量重烘；②接缝重建重烘（已因数据环
  而非必要）。所有权：入缓存后纹理归缓存所有（材质 userData.cached 标记，
  chunk 销毁跳过纹理释放）；模式退出 releaseBakeCache() 统一销毁。
  key 含 seed——换 seed 自然失配。天内不额外占显存（纹理本来就在用）。
TerrainBakeSource 契约 ◄─ 依赖倒置：heightAt/surfaceHeightAt/tileDefAt/worldSeed
  （新管线只消费 surfaceHeightAt/tileDefAt/seed；heightAt 仅剩旧路径）
像素计算 bakeCompute.computeChunkMapsRGBA() 双纹理输出：
  ├ albedo 256²   材质色图（调色板/抖动/斑块/描边/拉丝/斑驳——零明暗信息）
  └ lightmap 128² R = TOP_DIRECT × vis   G = AO(影区松绑)   B 预留
      vis: iq 软阴影标准公式 res=min(res, k·h/t)
           ·自适应步长(净空越大步越大) ·接触锐利/远端半影展宽
           ·台阶豁免 CAST_MIN_DEPTH=0.5 ·全影留底 SHADOW_FLOOR=0.12
      AO 影区松绑 SHADOW_ZONE_AO_RELIEF=0.65（防 直射umbra+天光遮挡+半影
      三重叠加贴墙死黑——同一遮挡物不扣两次钱）
★★ 采样统一（2026-08-26 定稿）：烘焙只消费「视觉面」surfaceHeightAt——
  与网格位移、角色贴地、影子贴地完全同源。且 surfaceHeightAt 是
  【三角形插值】（= PlaneGeometry 真实剖分：对角线 (lx,lz+1)-(lx+1,lz)，
  分割条件 fx+fz≤1，Raycaster 实测逐位一致）——双线性在斜坡过渡带
  （非平面格）与真实网格偏差可达 ~1m，禁止回退。块状 heightAt 仅剩 Boss4D。
BAKE_SUN 过肩光（hx=-0.342,hz=+0.94,45°）：主光必须在相机后上方
  （默认 yaw=0 相机在 +z 看 -z）——影子拖进视野、迎面墙朝阳亮。
  光位是构图决策不是物理决策。
  ★ 唯一权威来源 = bakeCompute.BAKE_SUN；ChunkWalls 墙明暗方向从它
  import（CAST_MIN_DEPTH 同理），手抄副本已清除（2026-08-26）。
ChunkWalls.buildChunkSideWalls() 断崖检测（落差≥0.5m）→ 独立侧壁几何，
  顶点色四层明暗：朝向×太阳 > 落差深度 > 天空可见度 > hash 微抖动
  （★ 墙不采样地面贴图——位移平面的"侧面"是贴图垂直拉伸，地面阴影
    梯度会被拉成墙面纵向渐变（上暗下亮），此路已封死）

━━ 运行时域（每帧常数成本）━━

```

#### 烘焙公式速查

```
albedo  = 基准HSL(Tiles.visual.baseHsl)
  × 逐地块抖动（4m格 hash2：H±0.8% S±3% L±5%）
  × 色阶化斑块（3档离散对称±4%，带内平台60%带缘smoothstep40%）
  × 地块内描边（贴边0.3m压暗≤13%）
  × 平台方向性拉丝（X向拉伸噪声±4%…实际0.08幅）
  × 大尺度斑驳（±6%）                          ← 以上全部无明暗语义

lightmap.R = TOP_DIRECT × (FLOOR + (1-FLOOR)×vis)
  vis = iq软阴影: min(k·h/t)，自适应步长，台阶豁免，射程16m
  TOP_DIRECT = wrapN·L 常数（顶面全平；不用逐像素法线——
               断崖边缘 ±1m 光晕伪影已由此根除）
lightmap.G = AO(8向环采半径2.5m，下限0.55) × 影区松绑

运行时 = albedo × (uAmbient×G + uSun×R)   ← 昼夜只动两个 uniform
```

#### 实体影子定案（2026-08-24 统一重构；2026-08-25 日照投影升级）

billboard 竖片的实时投影随视角坍缩（几何宿命），故所有实体的贴地影 =
**SilhouetteShadow 剪影影子**（角色机制推广到全实体，GroundBlobLayer 圆影层已删除）。

★ 影子 = 竖立精灵在太阳平行光下的**解析仿射投影**（精确非近似，脚跟锚定）：
```
锚点 = 脚点投影：P_xz + 太阳反方向 × 离地高/仰角比  ← 跳跃时整条影子外移
影长 L = 视觉高 h × 投影比(1/tan仰角)        ← 正午短贴脚、晨昏长拖尾
方向   = 与太阳水平分量反向（东升西落全天扫动）
宽轴 R = 贴片右向量地面投影（billboard 朝相机）；近共线退化垂直长轴
几何   = 深度 [0,1] 从脚跟长出（非居中对称），半影远端淡近端浓
→ 同一角色早晚影子形状/方向/长度都不同（特性，用户确认）
```

```
EntityBase.update 骨架⑦ syncShadow() 统一驱动：
  惰性创建 → setSource(剪影源, 内部去重) → renderManager.querySun() 取太阳 → 解析仿射基 {R,S}
  → followAffine(x,z, R,S,len, 采样器逐顶点贴地)
  → mesh.visible = 可见 ∧ viewLod<3 → setLodOpacity(viewLod, ×白昼因子)
```

子类只做声明（EntityBase 虚成员；剪影源默认自动取当前动画帧）：
| 声明 | 语义 | 角色 | 物品 | 子弹 |
|------|------|------|------|------|
| shadowShape | w/h/alpha；len=固定影长 | 太阳投影 w×h | 太阳投影 w×h | len=2.08 定向椭圆 |
| getShadowFrameData | 剪影源 | 默认（自动跟帧） | 默认（自动跟帧） | 覆写：共享画布 |
| shadowYaw | 固定模式朝向 | 不需要 | 不需要 | 弹道方向(+π，弹头朝前) |

封装原则——**机制归基类，差异声明化**（子类从"操作影子"变为"描述自己"）：

```
// 新实体想要影子的全部代码（太阳投影模式）：
protected override get shadowShape() { return { w: 1, h: 2 }; }
// 剪影源/投影/贴地爬坡/LOD 渐隐/日照浓度/隐藏联动/资源释放 全部默认；
// 仅非 FTX 资产才覆写 getShadowFrameData；自拉伸体才用 len + shadowYaw。
```

⚠️ 行为隐式化的代价：子类里看不到影子代码，排查问题必须知道 EntityBase.syncShadow
流程——本节 + EntityBase.ts 头部的声明契约注释就是权威文档，改机制必须同步这两处。

关键实现点：
- 剪影提取唯一实现在 SilhouetteShadow.extractSilhouette（阈值0.5 与 FTXQuad discard 对齐，
  影子形状=实际可见像素轮廓）；子弹用 makeSilhouetteCanvas 一次性提取共享画布。
- 有 FTX 动画资产的实体零配置获得"影子随动画帧变化"（基类默认取 state.frameIndex，
  帧去重：同一源对象跳过）。
- followAffine 把仿射直接烘进网格顶点（77 点重写 XZ+Y），不碰 matrix/matrixWorld，
  采样点与顶点同公式 → 任意剪切下仍严格贴合坡面。
- 半影质感：alphaMap 沿影长 V 方向渐变（共享静态纹理），远端淡近端浓；
  浓度 = LOD系数 × (0.2 + 0.8×daylight)——正午浓、晨昏淡、夜晚自然消失。
- 时间查询：实体只认 renderManager.querySun()（不直接依赖 SunCycle/GameLights）；
  RenderManager 持有时间模型，WorldMode 以 resetDay()/update(dt)/follow(pos) 三步驱动；
  GameLights 被动消费注入的太阳状态做位置/色温/强度。
- 子弹走固定长轴模式（高速运动体自拉伸沿弹道，不参与太阳投影）。
- visible setter 联动隐藏影子（池化回收/第一人称时 update 已停 → 防幽灵影子残留）。

实时投影已从 FTXQuad 移除（castShadow/customDepth 子系统整体删除）。
阴影图基建保留在 GameLights——给未来有体积的建筑/道具使用。

#### 高度采样三函数陷阱

| 函数 | 语义 | 用途 |
|------|------|------|
| heightAt | 原始格值 | AO启发式 / 物理查询 |
| vertexHeightAt | 格线交点=max(周围2×2)，只向负方向采 | 网格顶点构建 |
| surfaceHeightAt | 顶点值双线性插值 = **网格真实渲染高度** | 角色贴地 / canvas侧壁分类 |

坑tile内 heightAt 判 h>0 永远为负；悬崖低侧 vertexHeightAt 看不到对岸。
凡与渲染外观一致 → surfaceHeightAt。

#### 编码红线

1. 数据纹理 clear 强制黑透明并恢复原色
2. 禁止裸 GL 操作 three 托管状态（bindTexture 等）；重同步用 resetState()
3. 全局 clearColor 是显示层状态，数据管线不得隐式消费
4. 改全局渲染状态后必须回归所有离屏管线
5. 凡与渲染外观一致的逻辑一律 surfaceHeightAt
6. 每个 milestone 必须在生产构建上验收（dev 通过不算数）
7. AO 只存一处
8. PCFShadowMap（PCFSoft 已废弃）

  ├ 无法在游戏内解耦注入物理参数（流体作用在残差数据上）
  └ 无法运行时编辑扭动/变形（实体边界 + 位移纹理是数据，不是像素）

  ftx3 → FtxAsset.load → 帧纹理对（base+residual）
  .scene.zip → Asset.load → 帧纹理 + 实体网格 + 播放控制器

### 9.2a 素材体积预算（硬约束）
```
★ 目标：首发整包 ≤ 1.5MB（当前实测：代码 gzip 37KB + 素材 528KB）

  │    └ 技能特效（.scene.zip，多实体+VAT）≤ 500KB
  ├ 最终 Boss 纹理 + 特效（合计）      ≤ 1MB
  ├ 普通敌人/友军/道具/场景贴片         各 ≤ 几十 KB

  └ 公共物理参数（.phys.json）          ≤ 10KB（JSON，已含预算内）

  1. 帧数精简：动画 2~4 帧优先（循环动画帧间过渡由播放器插值）

  5. 尺寸限制：主角/Boss 全画幅，其他角色缩小画幅（bbox 越小越省）

审核：每次导出素材后记录体积，超预算 → 按上述手段裁剪（写进导出手册）
```

① 物理参数注入/取消（状态效果驱动）
   injectPhysics(config | .phys.json id)
     - 纯纹理包（FtxAsset）：注入 → 全图流体平流（无实体障碍物）
     - 特效包（Asset）：注入 → 覆盖该帧内嵌参数（实体边界仍作障碍物）
   clearPhysics()
     - 取消注入 → 恢复原样（无物理 或 恢复原内嵌参数）
   例：主角中毒
     StatusSystem 挂中毒 → fx.injectPhysics(公共库 poison 参数)
       → 播放器流体解算器重建 → 纹理出现毒雾扩散/色相偏移
     中毒解除 → fx.clearPhysics() → 恢复正常纹理
   ★ 公共参数库复用：同一份 poison.phys.json 可注入任意实体纹理

② 实体/扭动编辑（特效包专属，EffectSlot 持有）
   setDistort({ enabled, amplitude, frequency, speed, rotation })
     - 修改实体区域呼吸式扭曲（与编辑器参数一致，运行时可调）
     - 例：旗帜风速增强 → 提高 amplitude/frequency；风暴停 → 关闭
   setTextureTransform({ offset, scale, rotation })  # 底图变换
   后续扩展：替换实体边界/位移纹理（区域形变重塑）

③ 播放层编辑（控制器已有 + 扩展）
   setFps / setOrder / loop / goto / hold 等
   setFrameTextures(base, residual)  # 换皮（受伤/形态切换）

★ 与状态系统联动（EffectSlot 生命周期）：
   ├ 生成：AssetManager 加载 → 创建控制器 → 挂到实体
   ├ 状态注入：StatusSystem(中毒/着火/冰冻) → injectPhysics/clearPhysics
   ├ 环境编辑：WindSystem → setDistort（风速/风向）
   └ 销毁：实体销毁 → dispose（释放全部运行时资源）

④ 流体状态转移（跨资产，视觉/物理彻底解耦）
   需求：敌人被击杀（有血液流体效果）→ 血液"转移"到地面纹理
        → 地面继续流体解算（血泊扩散/渗入），敌人实体销毁
   技术：
   ├ FluidSolver 加状态转移 API：
   │    exportState() → 快照（colorGrid/velocityGrid/densityGrid）
   │    importState(state) → 写入/叠加到目标解算器
   ├ 或简化注入：groundFluid.injectAt(死亡点, {color: 血红, density})
   │    → 目标解算器自行演化（血液自然散开，不保形）
   ├ 决策：推荐"注入"（更符合血液落地扩散的物理直觉，实现简单）
   │       保形转移（transferFrom）作为后续增强
   流程：
   ├ combat 击杀判定 → EventBus 死亡事件 { position, bloodState? }
   ├ GroundFxService（services/fx 地面特效管理）：
   │    击杀点 → 地面 FtxAsset 按需激活流体（注入 blood.phys.json）
   │    → transferFrom(敌人流体) 或 injectAt(死亡点, 血液参数)
   └ 地面继续 step() → 血泊在地面解算/扩散
   性能/持久性：
   ├ 地面流体"按需启用"：有血液注入才激活解算器，平时零开销
   ├ 血泊属于战斗运行时状态：随地图卸载/每日新 seed 消失，不存档
   └ 地面 = FtxAsset + 可注入流体（与角色同一套管线，无特殊实现）
```

### 11.2 输入传递结构（InputFrame，避免参数蔓延）
```
★ 模式/实体统一消费一个 InputFrame（每帧打包一次，替代多参数传递）：
InputFrame = {
  moveAxis,      # 移动轴向（语义）
  lookAxis,      # 视角增量（鼠标/触屏拖拽）
  zoomAxis,      # 滚轮/捏合缩放增量
  held,          # 按住状态（★ attack=左键长按持续发射；跳跃=连跳等长按语义）
  pressed,       # 消费式按键（攻击/闪避/技能/交互）
  interactions,  # 交互事件队列（tap/hold/drag）
  cameraFrame,   # 相机坐标系（forward/right，角色移动/朝向用）
}
数据流：Binding(设备) → InputActions(语义) → 模式组包 InputFrame → 实体管线
好处：加新输入（跳跃/技能）不改方法签名，只扩字段
```

### 11.1 第三人称标准相机（已实现 CameraController）
```
★ 行业标准参数（原神/塞尔达/古墓丽影共识）：
 距离：3.5~5（角色高度的 2~4 倍）
 俯仰：20°~30°（0.35~0.52 rad）——默认 0.5（28.6°）
 lookAt：角色肩部~头顶（0.8~1.0 × 身高）——默认 0.9
 相机高度：角色半高 + 距离·sin(俯仰)
 角色位置：画面下 1/3（相机高于角色 + 俯视自然形成，非 lookAt 硬顶）
 准星：屏幕中心 = 前方远处地面（角色在下方不挡）

① 输入 → 目标角度（鼠标/触屏拖拽 → lookAxis 增量）：
   targetYaw（水平环绕）/ targetPitch（俯仰，clamp 0.2~1.1 rad）
   相机实际角度 = lerp(当前, 目标, 阻尼) —— 跟手但不瞬跳
   （鼠标控制的是"期望视角"，不是直接转相机）
   ★ 符号约定（标准 FPS/TPS，已踩坑反复两次）：
     targetYaw -= look.x·sens   → 鼠标右移 yaw 减小 → 相机绕玩家左转
       → 画面右转（第三人称相机绕转方向与画面滚动方向相反）
     targetPitch += look.y·sens → 鼠标上移 pitch 减小 → 抬头
     ⚠ 两个符号任一取反 → "手感奇差"且小地图箭头看似反了
   滚轮缩放：zoomAxis（增量）→ distance = clamp(distance + zoom·sens, 2.5, 12)
   —— 标准第三人称：滚轮 = 相机距离（视觉上高低/远近），非改俯仰角

② 球坐标定位（相机在角色后上方）：
   相机位置 = target + (sin(yaw)·D·cos(pitch),
                        角色半高 + D·sin(pitch),
                        cos(yaw)·D·cos(pitch))
   相机高度 = 角色半高 + 距离·sin(pitch)  ← 含角色半高，避免贴地被身体挡

③ 注视点（准星基准）：
   lookAt = target + (forward·lookAhead, 角色身高×1.1, forward·lookAhead)
   - lookAt 在角色头顶之上 → 角色落在画面下方，准星不被角色遮挡
   - lookAhead（前方视野偏移）与 pitch 共同决定"准星射线与地面的
     交点距离"：交点 ≈ 角色前方 2~3 世界单位（可打近处地面）

④ 相机坐标系（角色移动/朝向用）：
   forward（画面深处）= (-sin(yaw), 0, -cos(yaw))
   right（画面右侧）  = (cos(yaw), 0, -sin(yaw))
   角色移动 = right·左右轴 + forward·前后轴（相机相对移动，
   W 永远朝画面深处，视角转了也一样）
   角色朝向 = 移动方向与 forward/right 的夹角判定（前/后帧组 + flipX）

⑤ 准星（交互基准，与设备解耦）：
   准星固定屏幕中心（UI 层 Crosshair 组件）
   交互/攻击射线 = 从屏幕中心发出（NDC (0,0)）与地形求交
   —— 鼠标只控视角，瞄准始终以准星为准（触屏/手柄天然支持）

⑥ 与模式的关系：相机是独立服务（services/camera/），
   模式切换时 reset(yaw, pitch) 复用，不重建

### 11.1a 相机绑定角色（平滑聚焦点 + 脚步抖动）
```
★ 标准 TPS 跟随机制（参考 three.js OrbitControls 的 target 模式）：
  聚焦点 target = 角色位置 + 肩部高度 + 跳跃偏移（模式层传入 height）
  ├ smoothedTarget.lerp(期望点, dt × targetFollowDamp)   # 平滑聚焦点
  │   → 角色跳跃：聚焦点上移 → 相机跟着升（跟跳）
  │   → 角色高频抖动：lerp 过滤 → 相机稳定（抖动过滤）
  ├ ★ 人称差异化阻尼：第三人称 5（~0.2s 滞后）/ 第一人称 12（贴角色）
  │   ├ 动机：上/下高台时相机滞后于角色升降 → 画面中角色先动、相机
  │   │   再跟上 → 高度变化有明确反馈（阻尼过大时角色与相机同步升降
  │   │   = 相对位置不变，体感"角色没变化"）
  │   └ 第一人称必须贴角色（滞后 = 晕）
  ├ 相机位置 = smoothedTarget + 球坐标偏移（yaw/pitch/distance 不变）
  └ targetDamp 可调：大=更跟手 / 小=更稳

★ 第一人称脚步抖动（移动时，随机化）：
  ├ 触发：第一人称（distance ≤ 阈值）且角色在移动
  ├ 机制：每 beat（0.12~0.28s 随机节拍）重新随机
  │    幅度（基础值 × 0.5~1.5）/ 相位 → 不规则走路感
  ├ 原则：完全一致的 sin 抖动 = 机械感，不如不抖
  │    → 随机节拍 + 随机幅度 + 随机相位
  └ 参数：footstepShake { enabled, baseAmplitude, beatMin, beatMax }
```

### 10.1 main.ts 启动流程（BOOT → SHIP → WORLD 模式切换）

```

  ① 创建 WebAdapter → renderer + scene + camera

      renderer.render(scene, camera);

  }
  // 完全不知道当前是 ship 还是 world，只是委托

## 事故记录 #001：全局清屏色泄漏进流体场数据（2026-08-23）

> **严重级别：★★★★★** —— 特效系统整体不可用级别，且由一次毫不相干的 UI 改动引爆。
> 本节同时是**编码红线**的出处，新增渲染相关代码前必读。

### 症状

- 子弹特效开火首帧出现一大片近黑色块几乎铺满纹理，随后缓慢"消散"
- **周期性复现**（每次开火 reset 一次就重演一遍）
- 同一资产在独立播放器里播放**完全正常**

### 时间线

| 日期 | 事件 |
|------|------|
| 08-15~17 | 子弹管线定稿投入使用，此后未改动，"一直正常"（实为带病运行） |
| 08-22 | 抽卡 UI：main.ts 全局清屏色 `0x1a1a2e` → `0xcccccc`（c883d9f） |
| 08-23 | 黑色块爆发 |

### 根因链

1. `FluidSolver.clearGrid()` 用裸 `renderer.clear()` 清密度/速度/压力场——
   它写入的是**当前全局 clearColor**，而不是零：
   ```ts
   // 事故版本：没有任何 clearColor 保护
   private clearGrid(grid: FluidGrid): void {
     const prev = this.renderer.getRenderTarget();
     this.renderer.setRenderTarget(grid.write);
     this.renderer.clear(true, true, true);   // ← 写入全局清屏色！
     this.renderer.setRenderTarget(prev);
     grid.swap();
   }
   ```
2. scalar 模式 MCSDA 合成：`final_L = base_L − density/baseline × lMul`
   （本资产 baseline=0.674, lMul=0.8）
3. **旧清屏色** `0x1a1a2e` → R≈0.10 → reset 后全场假密度 0.10 → 只减亮 ~0.12，
   肉眼看不出 → **bug 潜伏一周**
4. **新清屏色** `0xcccccc` → R≈0.80 → reset 后全场假密度 0.80 →
   factor = 0.80/0.674 ≈ 1.19 → L 被减 ~0.95 → **整块近黑**
5. decayRate 每帧 −5% 缓慢消化假密度 → 表现为"消散"；每次开火 reset → "周期性"

实测佐证（`?dbg=1` 回读）：reset 后第 1 帧 `avg=0.748、hot>0.5 占 98.6%、
四带占比 25/24/25/25 完美均匀`——排除注入/平流/路点，直接锁定**初始化污染**。

### 为什么独立播放器正常

它页面的全局清屏色恰好是黑的，`clearGrid` 写出来碰巧是零。
**教训：依赖宿主环境隐式状态的代码，换一个宿主就是另一个行为。**

### 连带隐患：裸 GL 纹理绑定导致 three.js 缓存失同步

three r185 的 `WebGLState.bindTexture` 有缓存跳过逻辑（WebGLState.js:943）：
**缓存命中就跳过真正的 bindTexture**。曾用裸
`for(u=0..16) gl.bindTexture(TEXTURE_2D, null)` 断 feedback loop——
GL 里单元已被清空，但 three 的缓存仍认为旧纹理在绑 → 后续材质误判"已绑定"
跳过重绑 → **采样空纹理（黑帧/闪帧）**。已在全工作区改为官方 `renderer.resetState()`。

### 修复清单（2026-08-23，全工作区）

| 位置 | 修复 |
|------|------|
| vendor/player/fluid `clearGrid` | 强制黑透明清屏 + 保存恢复 |
| effects-player FluidSolver `clearGrid` | 同上 |
| 另起的绘画网页 FluidSolver `clearGrid` / `fillGrid` | 同上 / 删除冗余裸 clear |
| 绘画编辑器 FluidEditor `clearGrid` / `clearObstacles` / 障碍物初始化 | 同上（**掩码 R>0.5 视为墙，浅色污染 = 全场变墙**） |
| `GPUOps.render()` ×3 副本 | 内置保护性清屏（模块级 scratch Color，热路径零分配） |
| `AdvectionSolver.renderFullscreen()` ×3 副本 | 同上 |
| `OffscreenBake.begin()/end()` | 删裸 GL 清绑循环 → `renderer.resetState()` |
| 各处 `composite()` | `unbindTextureUnits()` → `renderer.resetState()`，并补 clearColor 保护 |

## 编码红线（由此事故确立，永久生效）

1. **数据纹理 ≠ 显示画布**：凡对 RT/场纹理调用 `renderer.clear()`，
   必须 `setClearColor(0x000000, 0)` 且保存恢复原值；只有最终显示画布可用主题清屏色
2. **禁止裸 GL 操作 three 托管的状态**（bindTexture / activeTexture / 手动 enable/disable）；
   需要断 feedback loop 或重同步，用 `renderer.resetState()`
3. **全局 clearColor 属于显示层**，数据管线不得隐式消费它，也不得依赖其具体取值
4. 改全局渲染状态（clearColor / autoClear / stencil 开关等）= 跨模块破坏性操作，
   改完必须回归**所有**离屏数据管线（子弹流体 / 抽卡背景流体 / 命中特效）
5. 新增离屏 GPU Pass 一律走 `GPUOps.render()`（已内置保护），不要手写
   `setRenderTarget + clear`

## 内置诊断工具（BulletVisual，URL 参数）

| 参数 | 作用 |
|------|------|
| `?dbg=1` | 每帧回读 density + velocity 统计行（max@位置 / avg / Σ / hot数 / 四带占比） |
| `?dbg=1&dbgn=N` | 每 N 帧输出一次 |
| `?nowp=1` | 剥离注入源 waypoints（排查路点瞬移剪切） |
| `?nogate=1` | 剥离 intermittent 门控 |
| `?nowave=1` | 剥离 wave 方向摆动 |

判读速查：`max@` 固定 `(x,1.0)` 且尾带% 独高 → 底边堆积；
`Σ` 周期暴涨 → 门控恢复爆发；`vel max` 恒顶 500 → 场饱和；
坐标 Y 向下为正，`(·,0)=弹头`、`(·,1)=尾部`。

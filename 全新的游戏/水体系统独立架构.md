# 水体系统独立架构（Water System Extraction）

> ⚠️ **本文是过程稿，架构以 `水体系统架构.md`（定稿）为准。** 本文保留的是「独立存储 + LOD」的推演过程与证据。
> 状态：**设计稿**（未动代码）· 2026-10-27 · 范围已按用户口径收窄
> **目标**：水体在地图里**独立存储**、脱离 chunk，从而**能做 LOD**（水体开销大）。
> **不做**：求解算法重写、玩法接口迁移、材质重写、挖坑联动流程 —— **这些一律不变**。
> 关联：`地形与渲染管线架构.md`（第四部分 = 现行水体管线）· `开发说明书.md`
> ★ **姊妹篇**：`水体离屏渲染方案.md` —— 用户进一步提出的离屏渲染方案 + 可行性分析
>   （唯一高度 / 离屏大水体 / 近岸单独算 / 涟漪掩码化）。本篇的「body 化」是那篇的前置条件。

---

## 0. 一句话结论

水体现在是"**chunk 的附属渲染物**"：水面 mesh 挂在 chunk group 下，chunk 一销毁水就没了，于是 LOD 也没法做（没有独立实体可挂 LOD）。

本方案只做一件事：**把水体从 chunk group 里搬出来，放进一个独立的 `WaterStore`**，由它持有水体的几何、归属与 LOD 档位。chunk 继续只管地形。**求解、材质、玩法、挖坑联动一行不改。**

跨 chunk 的水体（「一片海」）在存储层归并成**一个 body**，LOD 按 body 走 —— 这既是「一处实现」的落点，也正是 LOD 收益最大的地方。

## 1. 现状：证据链

### 1.1 水体当前依附 chunk 的 5 条硬证据

| # | 事实 | 位置 |
|---|---|---|
| E1 | `ChunkData` **没有 water 字段**；水体身份只存在于 `blockTypes[i] === TILE_WATER.id(4)` | `ChunkGenerator.ts:85-106` · `Tiles.ts:257-278` |
| E2 | 求解入口是 per-chunk：`buildWaterSurface(table: FaceTable, ...)`，`table.cells` = 15×15 | `WaterSurface.ts:723-728` · `FaceTable.ts:90-94` |
| E3 | 求解态按 chunk 分片：`waterStates = new Map<chunkKey, ChunkWater>`（LRU 32） | `WaterSurface.ts:156-197` |
| E4 | 运行时 mesh 登记以 chunkKey 为键：`terrainVisuals: Map<chunkKey, {top, wall, water, fineS}>` | `ChunkManager.ts:499` |
| E5 | 水 mesh 是 **chunk group 的子节点** → `destroyChunk` → `disposeVisual` 必删水几何 | `ChunkManager.ts:1890` · `:2347-2359` · `:3435-3462` |

> 现成文档也承认这条绑定：`地形与渲染管线架构.md:2640`「**chunk 卸载即弃水面**」。

### 1.2 跨 chunk 水体的真实规模（收窄后的重点）

| 水体类型 | 生成方式 | 规模 | 是否跨 chunk |
|---|---|---|---|
| **湖**（lake 预设） | 噪声扰动圆盘，R = 3.2~7.5 块（13~30m） | 约占 chunk 1/3 | **基本不跨**（圆盘直径 < 60m） |
| **海**（island 预设） | `roles.fill(ROLE_LIQUID)` —— **整个 chunk 填液体** | **满 chunk = 3600 quad / 3721 顶点** | **跨**（相邻海洋 chunk 连成一片） |
| 谷底深潭 | 单块 ROLE_LIQUID | 1 块 | 不跨 |

⇒ **真正的大水体 = 海洋 chunk 连成的一片海**。它同时是：
- 「跨 chunk 水体算一处」的**唯一真实场景**；
- **性能开销最大**的对象（满 chunk 3600 quad）；
- **LOD 收益最大**的对象（远处一望无际，却每 chunk 一个 draw call）。

**结论：独立存储 + LOD 的收益几乎全部落在海上。** 这与「水体开销大」的用户判断完全吻合。

### 1.3 跨 chunk 水体被切成 N 份（存储层，不是像素层）

**几何没有重复画**（chunk A 只发自己 60×60 的面，正好相接不重叠），重复的是**求解与状态**：

```ts
// WaterSurface.ts:231-247  ensureBlocks —— 只收本 chunk 的水块
const cell = table.cells[lbz * BPS + lbx];   // ★ 本 chunk 的 FaceTable
```
```ts
// WaterSurface.ts:326-353  initSolve —— BFS 被 occ 锁死在本 chunk
for (const bk of s.blocks.keys()) s.occ.add(bk);   // ★ occ 只有本 chunk 的块
```

⇒ 一片海被切成 N 个 `WComp`，**各自独立 `settleComp` 求水位 L**。三个可观察症状：

| 症状 | 机制 | 位置 |
|---|---|---|
| **边界处高度台阶** | 顶点 y = 池水位 L（`WaterSurface.ts:560`）；两半 L 由各自 chunk 内岸唇决定，**不保证相等** | `:359-432` · `:560` |
| **网格状"静止缝"** | 边界顶点一律 `border=1` → shader 里 `border<0.5` 才做 FFT 位移 | `:546-581` + `WaterMaterial.ts:273-275` |
| **边界处水色/透明度断层** | 逐顶点 `deep` 遇越界 cell 直接 `continue` → 边界水深算少 → alpha/体色突变 | `:563-575` + `WaterMaterial.ts:482` |

> ★ 这些是**求解层**的问题，**本方案不修**（收窄范围：其他不变）。但独立存储后它们**变成可修的**——因为"这一片水"终于有了单一身份，可以整体重解。这是独立存储的额外红利。

### 1.4 求解状态分裂在两个 worker 实例

| 路径 | worker | 状态落点 |
|---|---|---|
| 首建 | terrainPatch 池（**3 个** worker） | 各 worker 自己的模块级 `waterStates` |
| 破坏后 | WaterSolve（**1 个** worker） | 它自己的模块级 `waterStates` |

⇒ 两边不是同一个 Map → 破坏时 `s.inited === false` → 走 `initSolve` **全量重解**（`:756-757`）。

> 本方案**不改 worker 协议**（其他不变），但独立存储后可以把 `waterStates` 的**归属**从 worker 模块级挪到主线程 —— 属"可选优化"，不阻塞主线。

### 1.5 开销量级（LOD 的收益基线）

| 项 | 现状数字 | 位置 |
|---|---|---|
| 满水 chunk 网格 | **3600 quad / 7200 三角 / 3721 顶点**（1m 分辨率） | `WaterSurface.ts:509-595` |

## 3. 目标架构

### 3.1 三个新模块（其余不动）

```
src/services/map/water/
  ├─ WaterStore.ts     ★ 独立存储：水体仓库（归属表 + body 表 + 几何 + LOD 调度 + 生命周期）
  ├─ WaterBody.ts      类型：WaterBody / WaterBodyRef / 水位常量
  └─ WaterLOD.ts       LOD 档位常量 + 滞回 + 降采样（1m → 4m → 单 quad，纯函数）
```

**依赖方向**：`ChunkManager` → `WaterStore` → （既有）`WaterSurface` / `WaterMaterial`。
`WaterStore` **不 import three 的场景管理**，只持有 mesh（与 `ChunkManager` 同样持有 `THREE.Mesh` 的地位）。

### 3.2 核心概念

| 概念 | 定义 | 生命周期 |
|---|---|---|
| **WaterBody** | 一片连续水域（**跨 chunk 算一片**）。存储层的一处：成员块集合、包围盒、LOD 档、渲染 mesh 引用 | 随世界存在 |
| **WaterBodyRef** | 某个 chunk 参与的那一片 body 的引用（chunkKey → bodyId） | 随 chunk |
| **WaterStore** | 独立容器：挂场景的 `THREE.Group`（**不在任何 chunk group 下**）、归属表、body 表、LOD 调度 | 随模式 |

### 3.3 数据流

```
① 求解（★ 完全不变）
   ChunkGenerator → blockTypes[TILE_WATER]
   ChunkManager → terrainPatch worker → buildWaterSurface(table, src, patch)
                    └─► WaterSurfaceRaw（per-chunk，1m 网格，含 deep/border/level）
   ★★ 唯一改动：raw 的**去向**从「ChunkManager 直接建 mesh」改成「交给 WaterStore」

② 独立存储（新增）
   WaterStore 收到 raw（chunkKey, raw）
     ├─ 归属：把该 chunk 的水块并入全局水体分组 → bodyId
     ├─ 缓存：raw 存进 store 的 LRU（★ 回程不必重解）
     └─ 渲染：body → mesh（挂 store 自己的 group）

③ LOD（新增）
   每 0.5s 巡检：按 body 包围盒到相机距离 → 档位
     L0 近：per-chunk mesh（现状，1m）
     L1 中：降采样到 4m，按 body 合并
     L2 远：整 body 一个 quad

④ 挖坑（★ 不变）
   dig → waterSolve worker → 新 raw → 交回 WaterStore → 更新 body
```

### 3.4 归属：跨 chunk 怎么并成一片

**不重写求解**，只在存储层做一次「世界级水块连通」分组：

- 键：世界块坐标 `worldBlockKey(bx,bz)`（4m 块，`WaterSurface.ts:92-94` 现成）
- 算法：**union-find，union-by-min**（永远让块坐标字典序小的当 root）
  ⇒ 最终 root 与 union 顺序无关 ⇒ **bodyId 稳定**（先加载东边还是西边，结果一样）
- 表结构（按 chunk 分桶，**随 chunk 卸载可回收**）：
  ```ts
  // WaterStore 内部
  blockOwner: Map<number /*worldBlockKey*/, number /*bodyId*/>
  bodyOfChunk: Map<number /*chunkKey*/, Set<number /*bodyId*/>>
  bodies: Map<number /*bodyId*/, WaterBody>
  ```
- **bodyId = root 的规范化 hash**（root 用块坐标编码）⇒ 可复现、可跨存档一致
- **合并事件**：两片水接壤 → 小 id 保留、大 id 并入 → 触发该 body 的 LOD 网格重建（分帧预算）

> 为什么不在生成期做：生成期要改 `ChunkGenerator`/`TerrainPresets`（改动面大、且要先知道邻居是否也是水）。存储期做只需在 chunk 装配时扫一遍 `blockTypes`，**改动面小**。

### 3.5 ★ LOD 设计（主线）

**关键简化：LOD 降采样是「已解 raw 的后处理」，不重解、不改求解语义。**

| 档 | 距离（建议） | 几何 | 单位 | draw call | 顶点 |
|---|---|---|---|---|---|
| **L0** | < 80m | 1m 网格（**= 现状 raw 直接用**） | 每 chunk 一片 | ~25（构建环内） | 不变 |
| **L1** | 80~250m | **4m 网格**（= 4m 块尺度，降采样 raw） | 整 body 合并 | **1 / body** | 1/16 |
| **L2** | > 250m | **整 body 一个 quad**（deep 取平均、border=1） | 整 body | **1 / body** | ~1 |

**降采样规则（L1，1m → 4m）**：
- 顶点：每 4m 取一个角点（对齐块边界）
- `deep`：该 4m 格内 4×4 个 1m cell 的 `deep` 取平均
- `border`：该 4m 格内**只要有一个** 1m cell 是边界 → 置 1（保守，宁可钉死不可翘边）
- `level`：取该 body 的池水位（跨块同水位才合并，不同水位不合并 —— 与 `cornerKey` 的跨池不混点语义一致）
- 水帘（curtain）：L1/L2 **不生成**（远景看不见水帘；`deep<0` 分支不参与）

**切换策略**：
- 滞回带（对齐地形 `DETAIL_NEAR_DIST=60` / `DETAIL_FAR_DIST=70` 的做法）：升档阈值与降档阈值差 10m
- 切换代价 = 重建该 body 的网格 ⇒ **分帧预算**（每帧最多重建 N 个 body，超了排队），避免掉帧
- 相邻 body 档位不一致时 → 边界可能有一条 LOD 线 ⇒ 靠**档位带重叠**（L2 的 quad 覆盖到 L1 边界外 1 个 tile）掩盖

**收益（按现状数字估）**：

| 场景 | 现状 | 目标 |
|---|---|---|
| 站在海边看海（构建环内 25 个海洋 chunk） | 25 draw call × 3600 quad ≈ **9 万 quad** | 近处 L0 若干 + **远处整片海 1 个 quad** |
| 航行期粗块环（±6~12） | 最多 **625** 个粗水 draw call | 粗块静水并入 body 粗 quad ⇒ **个位数** |
| 远景海面顶点 | 3600 quad/chunk 全量 | **1 quad/body** |

## 5. 迁移路径（3 阶段，每阶段可独立验收 / 回退）

> 无 git → 每阶段改前备份 `.workbuddy/tmp/backup-water-2026-10-27/`。

### 阶段 0：抽 LOD 降采样为纯函数（**零行为变化**）

- 新建 `water/WaterLOD.ts`，只放**降采样纯函数**（1m raw → 4m raw → 单 quad）
- 写离屏探针：拿真实 `buildWaterSurface` 产出的 raw，降采样后校验
  - 顶点数比 = 1/16（±1，边界误差）
  - `deep` 平均值与原 raw 均值一致（误差 < 1e-3）
  - `border` 是原 raw 的**保守上界**（降采样后标记为 1 的位置 ⊇ 原为 1 的位置）
- **不改任何运行时路径**

**验收**：探针全绿；游戏行为零变化（不接线）。

### 阶段 1：独立存储（搬家）

- `WaterStore` 上线：持有 group、归属表、body 表、raw 缓存
- `ChunkManager` 把 raw 交给 `WaterStore`，**不再自己建水 mesh**
- 水 mesh 从 chunk group 挪到 `WaterStore.group`
- `destroyChunk` 不再 dispose 水

**验收**：
- 走出构建环再走回来：**水还在**（现状会随 chunk 销毁而重建，现在应保留）
- 挖坑后水帘仍正常（`waterSolve` → raw → store 链路通）
- 探针：跨 chunk 的湖/海，**body 数量**符合预期（相邻海洋 chunk 应归并为 1 个 body）

**回退**：把 `WaterStore` 的接线摘掉即回到现状（保留旧路径代码一行不删，直到阶段 2 验收通过）。

### 阶段 2：LOD 接线

- `WaterStore` 每 0.5s 巡检 body 距离 → 分档 → 分帧重建网格
- L1：降采样到 4m 并按 body 合并
- L2：整 body 一个 quad
- 粗块静水并入 body 粗 quad

**验收（可测数字）**：

| 指标 | 现状 | 目标 |
|---|---|---|
| 远景海面 draw call | 25（近环）+ 最多 625（粗环） | **≤ 5** |
| 远景海面顶点 | 3600 quad/chunk | **1 quad/body** |
| 近景水面 | 1m 网格 | **不变**（逐位一致） |
| chunk destroy 触发的水面重建 | 每次 | **0** |
| LOD 切换帧耗时 | — | **≤ 3ms/帧**（分帧预算） |

## 6. 风险与回归点

| 风险 | 说明 | 缓解 |
|---|---|---|
| **raw 缓存内存** | 每 chunk raw ≈ 3600 quad 的 Float32Array（~0.5MB/满水 chunk） | LRU 上限（按 body 或按字节）；**优先保 body 的 raw**（回程不必重解） |
| **body 归属内存无限增长** | 世界无限 | `blockOwner` 按 chunk 分桶，chunk 卸载即可回收；`bodies` 元数据 LRU |
| **合并事件抖动** | 玩家在海边移动 → 不断有海洋 chunk 加载 → body 反复合并 | union-by-min ⇒ 合并**单向**（大 id 并入小 id）⇒ 同一片海最多合并 N-1 次，之后稳定 |
| **LOD 切换掉帧** | 重建 body 网格有 CPU 成本 | 分帧预算 + 滞回带；降采样是纯计算（1m→4m 很快） |
| **LOD 线可见** | 相邻 body 档位不同 → 接缝 | 档位带重叠 1 个 tile；L1/L2 都用同一套水材质（颜色连续） |
| **降采样丢细节** | 4m 网格下小水洼消失 | 只对**远景**降采样；且 L1 仍保留 FFT 波形（shader 级，与现状一致） |
| **玩法误判** | 深水判定若依赖 `deep` | L0 附近逐位不变（N1）⇒ 玩法查询只读 L0 精度，不受 LOD 影响 |

# 游戏开发说明书（一步一步怎么做）

> 结合《架构设计.md》最终架构的完整开发路线。
> 每个阶段：目标 → 步骤 → 验证标准 → 完成后进下一阶段。
> 原则：先跑通再完善；每阶段结束都"能玩、能看、能测"。

---

## 阶段总览

```
阶段 0  环境搭建（半天）
阶段 1  M0 平台验证（1~2 天）      —— three.js + rapier + 播放器能跑
阶段 2  M1 最小战斗闭环（3~5 天）   —— 能移动/开枪/打敌人
阶段 3  M2 模式切换（2~3 天）      —— 舰船↔大世界往返
阶段 4  M3 地图生成（5~8 天）      —— chunk + 迷雾 + 小地图
阶段 5  M4 战斗完整（5~8 天）      —— AI + 掉落 + 背包
阶段 6  M5 抽卡+守卫（3~5 天）     —— 抽卡流程 + 舰船袭击
阶段 7  M6 Boss 决战（5~10 天）    —— 四维竞技场
阶段 8  M7 内容填充（持续）        —— 配置表批量加内容
阶段 9  M8 平台发布（2~3 天）      —— 微信/抖音打包
```

**贯穿全程**：每写一个模块，顺手测一个；每阶段结束跑通一个可玩闭环。

---

## 阶段 0：环境搭建

### 目标
开发环境就绪：能编译、能跑空场景。

### 步骤
1. **新建项目**：在 `全新的游戏/` 用 Vite + TypeScript 初始化
   ```
   npm create vite@latest . -- --template vanilla-ts
   ```
2. **装依赖**：three.js、rapier（@dimforge/rapier3d）、类型定义
3. **建目录**：按架构设计 0.1 的目录树（core/entity/systems/services/modes/ui/platform/config/assets）
4. **跑通空场景**：浏览器显示一个旋转的立方体（验证 three.js + Vite 工作）
5. **建最小 WebAdapter**：createCanvas/loadAsset/storage 三个空实现
6. **git 初始化**：提交"环境搭建"

### 验证
- `npm run dev` 能跑，页面显示 3D 场景
- 目录结构符合架构

### 产出
可运行的空壳项目 + git 仓库

## 阶段 1：M0 平台验证（最优先！）

### 目标
**验证三个核心依赖在目标平台（微信小游戏）能跑**——这是全项目最大技术风险，先验证，避免做完才发现跑不了。

### 步骤
1. **three.js 最小场景**：在微信小游戏环境跑一个方块（需要微信开发者工具 + 小游戏适配）
2. **rapier 最小验证**：加载 rapier WASM → 创建一个刚体 → 落体/碰撞
3. **播放器最小验证**：加载一个 .scene.zip → 播放一个特效
4. **三者合体**：一个场景里同时有 3D 方块 + 刚体掉落 + 特效播放

### 验证
- 微信真机（或开发者工具）能跑，不崩溃
- 记录：WASM 怎么加载、canvas 怎么桥接（这决定 WebAdapter 怎么写）

### 关键产出
- **WeChatAdapter 的核心实现验证**（canvas/资源加载）
- 技术风险清单第一条"微信真机兼容"确认

### ⚠️ 如果验证失败
- 换方案：降低 three.js 版本/换渲染适配库/rapier 换轻量方案——在阶段 1 解决，不拖后

## 阶段 2：M1 最小战斗闭环（第一个可玩版本）

### 目标
浏览器里跑通：**移动 billboard 角色 + 攻击发射子弹 + 敌人出现 + 命中伤害**。

### 步骤（按依赖顺序）
1. **GameLoop**：fixedUpdate/update/render 三段循环（core/）
2. **EventBus**：最小实现（core/）
3. **Session**：最小字段（day/player 位置）（core/）
4. **Entity + EntityManager**：Entity 容器 + 组件基础（entity/）
5. **Transform + RigidBody 组件** + **PhysicsWorld 最小封装**：
   - init/addBody/step/syncTransforms（services/physics/）
   - 验证：一个方块受重力掉落、撞地面停住
6. **Billboard 组件 + 渲染**：一个 2D 贴片角色面朝相机（services/render/）
   - 用一个测试贴图（先不用真素材）
7. **PlayerController**：WASD 移动 + 鼠标转向（modes/ + platform/input/）
   - InputActions 最小集：moveAxis/lookAxis/attack
   - 先用 DesktopBinding
8. **BulletSystem**：发射子弹（对象池最小版）→ 物理飞行（services/physics/ + systems/combat/）
9. **Health 组件 + StatsCalculator**：命中减血（systems/combat/）
10. **最小敌人**：一个站桩敌人（无 AI，就是个靶子），能被子弹打死
11. **相机**：越肩跟随（services/camera/）

### 验证
- 能控制角色在场景里走
- 开枪打靶子，靶子掉血死亡
- 帧率 > 60（简单场景应该轻松）

### 产出
**第一个可玩的战斗最小闭环**——角色移动 + 射击 + 敌人死亡

### 完成标准
阶段 2 结束前，代码量应该只有几百行核心——如果超过，说明做复杂了，回头简化

## 阶段 3：M2 模式切换

### 目标
舰船（日常）↔ 大世界（战斗）两个场景能切换，Session 数据保留。

### 步骤
1. **ModeManager**：switchMode/pushMode/popMode（core/）
2. **ShipMode**：一个简单的舰船场景（固定地板 + 玩家可走）
3. **WorldMode**：复用阶段 2 的战斗场景
4. **切换流程**：舰船走到"出发"区域 → 加载 WorldMode → 返回按钮 → 回 ShipMode
5. **SaveSystem 最小版**：Session 序列化 → storage.set/get
   - 在舰船存档点测试：存档 → 刷新页面 → 恢复（能回到舰船）

### 验证
- 舰船 ↔ 大世界往返切换不崩
- 存档/读档：刷新页面后能恢复
- 模式切换时实体正确卸载/加载（旧地图实体消失）

### 产出
日常/战斗双场景 + 基本存档

---

## 阶段 4：M3 地图生成

### 目标
大世界有真实地图：chunk 流式生成 + 迷雾 + 小地图。

### 步骤
1. **ChunkGenerator**：噪声高度场 → 网格（services/render/TerrainSystem.ts）
   - 先做"当天地图"：以舰船为原点，生成一块有界地形
2. **地形碰撞**：固定刚体（PhysicsWorld.addBody）
3. **ChunkActorGenerator 最小版**：随机放几个箱子/敌人/资源点
4. **每日新地图**：每天出击 = 新 seed 重新生成（换 seed 测试）
5. **FogOfWar**：黑雾掩码 + 静态地形层 + 实时层（systems/map/）
6. **小地图 UI**：Canvas 2D 画迷雾（ui/）
7. **LOD + 视锥最小版**：远处实体降细节（先做实体 LOD，地形 LOD 后补）

### 验证
- 地图能走、不穿地、有起伏
- 迷雾：探索过的地方亮、没探索的黑、怪物只在附近显示
- 换天/换 seed 地图不同

### 产出
能探索的 3D 地图 + 迷雾小地图

---

## 阶段 5：M4 战斗完整

### 目标
战斗成为"真游戏"：敌人 AI、掉落、拾取、背包。

### 步骤
1. **AIStateMachine**：通用解释器（读配置 → 行为表 → 转移）（systems/combat/）
   - behaviorTable 先注册 5 个行为：wander/moveToTarget/meleeSwing/shootBurst/death
   - conditionTable 先注册：seePlayer/inRange/outOfRange
2. **两种敌人**：近战兵（巡逻→追→砍）+ 远程兵（巡逻→追→射）
   - 用 enemies.json 配置（测试"加敌人=改配置"）
3. **掉落**：敌人死亡 → 掉落物品实体（掉地上，物理落地）
4. **拾取**：走近 → 交互 → 物品进背包
5. **背包网格**：InventoryGrid（canPlace/place/remove/stack）（systems/inventory/）
6. **背包 UI**：Canvas 网格界面 + 拖动（ui/）
7. **弹药/食物堆叠**：60 一组（stack 逻辑）

### 验证
- 两种敌人行为正确（会追、会打、会死）
- 打怪掉东西，捡起来进背包
- 背包能拖动、堆叠

### 产出
完整战斗循环：打怪 → 掉落 → 拾取 → 背包

---

## 阶段 6：M5 抽卡 + 守卫

### 目标
抽卡流程 + 舰船守卫，形成"日常→战斗"的核心循环。

### 步骤
1. **GachaPool**：加权随机 + pityCounter（systems/gacha/）
   - 50 抽 +2% 递增逻辑（可单测）
2. **抽卡 UI**：按钮 + 结果展示（先简单）
3. **抽卡分发**：抽到角色 → 友军；道具 → 背包；Boss → 决战占位（先弹提示）
4. **ShipGuardSystem**：袭扰波次（时间驱动）→ 敌人直奔舰船（systems/ship/）
5. **舰船 HP + 警报**：受击 → ShipAlertEvent → HUD 红点
6. **友军最小版**：抽到的角色可部署（站桩守卫舰船）→ 用 AIStateMachine 的 deployGuard 行为

### 验证
- 抽卡保底逻辑正确（50 抽后递增）
- 外出后舰船会被袭，警报提示，回防可解
- 抽到的友军能部署守卫

### 产出
**核心循环可玩**：抽卡 → 出击 → 探索守卫 → 回船

---

## 阶段 7：M6 Boss 决战

### 目标
四维 Boss 战（简化版能打）。

### 步骤
1. **BossRaidMode**：独立模式（模式切换复用阶段 3）
2. **BossArenaGenerator**：一个独立竞技场（不用 chunk 流式）
3. **Boss 实体**：大血条 + 多阶段（先 2 阶段）
4. **机制 1：超立方体投影**（先做视觉版）：
   - 竞技场几何体阶段切换时旋转重组
5. **机制 2：切片**（先做简化版）：
   - Boss 部分时间"不可见/不可命中"→ 玩家切视角才能打
6. **Boss 专属 HUD**：大血条 + 阶段提示
7. **抽到 Boss → 进决战**（接上阶段 6 的占位）

### 验证
- 抽到 Boss 能进决战
- Boss 有多阶段、有至少一个四维机制
- 能打死（平衡可后调）

### 产出
完整一局的核心：抽到 Boss → 决战 → 赢/输 → 结算

---

## 阶段 8：M7 内容填充（持续，边玩边加）

### 目标
批量加内容，调平衡，让游戏"好玩"。

### 步骤（按优先级）
1. **维什戴尔技能**：3 个技能具体化（CD 已就绪，加效果）
2. **敌人扩充**：5 种 → 10 种（多数复用行为，配置加）
3. **友军扩充**：抽到的干员行为（复用行为库）
4. **遗物**：黑冠（每日×1.01）+ 5 个局内遗物（RelicEffectSystem）
5. **合成**：弹药/食物配方（CraftingSystem）
6. **采集**：资源点 + 采集交互（GatheringSystem）
7. **对话/事件**：DialogueSystem + 几个事件（幸存者/残响）
8. **平衡**：敌人曲线 vs 玩家成长（黑冠+遗物+合成）——跑几局调数值

### 验证
- 每加一块内容：跑一局确认不崩、手感好
- 平衡：玩家能在 20~30 天内"够强"决战

### 产出
内容丰富的完整游戏

## 阶段 9：M8 平台发布

### 目标
打包到微信/抖音，包体 ≤ 20MB。

### 步骤
1. **WeChatAdapter 完善**：真机全功能（阶段 1 验证过的核心 + 音频/存储）
2. **分包**：主题区/Boss 素材分包
3. **包体瘦身**：WebP 纹理/压缩音频/特效低分辨率档
4. **真机测试**：全流程在真机跑（性能/内存/触摸）
5. **Canvas UI 触屏适配**：TouchBinding 真机验证
6. **发布**：微信后台提审 → 上线

### 验证
- 真机 30fps 保底
- 包体 ≤ 20MB
- 触屏操作顺手

## 每个阶段的通用检查清单

```
✅ 这阶段的目标"能玩/能看/能测"了吗？
✅ 代码量合理吗？（超出预期 = 过度设计，简化）
✅ 配置化了吗？（新内容走配置，不硬编码）
✅ 提交 git 了吗？（每阶段一个 commit）
✅ 跑过 tsc 类型检查吗？（无报错再继续）
```

## 开发纪律（重要）

1. **先跑通再优化**：别在阶段 2 优化粒子性能——那不是现在的事
2. **文档是地图，不是行李**：架构文档描述目标，实现时按阶段取用，不要试图一次实现全部
3. **每阶段结束都能玩**：任何一个阶段中断，你都有一份"能跑的东西"
4. **遇到卡点先简化**：如果某个机制做 2 天还没通，砍到最小能跑版本，回头再补
5. **测试一个加一个**：新增模块前，确认旧模块还活着（别等到最后一起炸）

## 水里持续游动音效降速（用户「降低在水里持续游动的音频播放速度」）

根因不是"触发太频繁"，是**素材时长 vs 节流间隔倒挂**：
`涉水.mp3` = **0.73s**，而 `playSfx('waterWade', 330)` 间隔 330ms → 每 0.33s 起一个新实例，
上层还没播完就叠下一个（≈2.2 层重叠）→ 听着像急促的连续噪声。
（`入水.mp3` = 1.54s / 节流 400ms，同样倒挂，但用户没提，未动。）

改动（4 处，tsc EXIT=0）：
1. `platform/PlatformAdapter.ts`：`playSfx(src, rate?)`
2. `platform/WebAdapter.ts`：`new Audio` 后 `a.playbackRate = rate`（**必须在 play() 之前设**）
3. `services/audio/Sfx.ts`：`playSfx(id, minGapMs, rate?)` → 透传
4. `WorldMode.updateWaterEntry`：`playSfx('waterWade', 700, 0.75)`
   —— 慢放 0.75（时长 0.73→0.97s，音调降） + 间隔 330→700ms。
   ★ 只改了音效节流，**没动水面泛波的 gap**（340 - speed*28），视觉波纹节奏不变。

   慢放范围 0.70~0.85 → **0.80~0.92**（<0.8 明显发闷，反而更听不清）。

- **这版 ffmpeg 的 `acompressor` 对短素材提不了响度**：threshold=0.08/ratio=14 把整体压掉

  **peak 已经贴顶（≈-1.2dBFS）时，压缩不是解药 —— 要么换选段，要么调播放音量。**

### ★★ 真 bug：循环轨淡入被每帧打断 →「在水里移动几乎没声」

用户反馈「几乎没声，不如最一开始的（点播版），但那个不连续」。查代码而不是继续调素材，找到：

- `updateWadeLoop` **每帧**调 `playLoopSfx`；`playLoopSfx` 在册分支里无条件 `fadeTo(vol)`；
- `fadeTo` 会先 `clearInterval` 上一个计时器、再从**当前音量**重新起一段 **BGM_FADE_MS=700ms** 淡入；
- 结果：淡入每帧被重置，音量按指数逼近，约 **1.5~2s** 才到目标 → 游一下就出水 = 等于没声。
  （引擎轨只在 phase 变化时调用，所以这个 bug 从来没暴露。）

修法（`WebAdapter`）：
1. `LoopTrack` 加 `target` 字段 → **只有目标音量真的变了才重新 fade**（每帧调用不再打断）。
2. `fadeTo` 加可选 `ms` 参数（默认仍 BGM_FADE_MS）→ 循环轨用 **`LOOP_FADE_MS = 220`**
   （循环轨跟的是秒级动作，700ms 淡入来不及）。
3. 起轨时 `target` 一并记录；`stopLoopSfx`（单轨 + 全停）也走 220ms。
   ★ 回归检查：play() 被自动播放拦截时 `el.paused` 仍为 true → 下一帧走 paused 分支重试，不会卡死在 0。

### 素材比例也反了 → 动作层改主层

**教训**：做"持续声"循环时，连续层只负责填空隙，**冲击/动作层必须是主层** ——
否则得到一段平坦底噪，在数据上达标（LUFS/RMS 都不差）但人耳完全注意不到。

## 爆裂黎明 shader（仿照参考帧复刻）

### 成熟做法：把「像不像」变成标量指标闭环

- ★★ **模型看不到图**（Read 图片 = Content filtered）→ 不能靠肉眼。
  解法：**用「红度 `R - max(G,B)`」当透镜**（能把白色 UI / 灰背景和红色特效分开），
  每帧算 `pct60 / pct150 / hot_rgb / core_rgb / radial[12] / 尖刺数 / r95n / rmaxn`。
- ★ 实测结论（16 帧，扣掉 ~1.8% 背景红地板后归一到峰值）：
  - **时间轴**：起爆极快（#3 几乎 0 → #4 冲顶），之后 `exp(-d/0.24)` 衰减。
    → 用 `rise = smoothstep(0.155,0.205,tn)` + `amp = rise*exp(-max(0,tn-0.19)/0.24)`。
  - **径向**：`pct150/pct60 ≈ 0.18`。平台型 `pow(1-r/Rc,e)` **最低只能到 ~0.39**；
    必须「**小热核 `exp(-(r/0.36)^0.78)` ×0.84 + 宽裙 `pow(1-r/1.65,0.75)` ×0.16**」
    （宽裙幅度压在 pct150 阈值以下，只贡献 pct60 的大面积）。
  - **尖刺**：外圈角向 ~14 个瓣，细长，刺尖 ≈ 主体半径 1.7 倍（本来就会被 quad 边裁掉）。
  - **配色**：外围暗红 (0.60,0.04,0.05) → 主体 (0.95,0.11,0.10) → 内芯只微微提亮 (1.00,0.26,0.24)。
    ★ **内芯不是白热**（实测核心 (231,55,56)，白热会把红度抵消掉，别做过曝）。
- 拟合残差：峰值 pct60 35.25→37.0、pct150 6.29→8.6、径向相关 0.94、
  hot_rgb (221,36,35)→(225,36,33)。**够用**。

### ★★ 关键技术手段：无头 Chrome 离屏渲染 + 文本读回

- 不需要 puppeteer，命令行直接：`chrome.exe --headless=new --enable-unsafe-swiftshader
  --use-angle=swiftshader --window-size=W,H --virtual-time-budget=10000
  --user-data-dir=<$TEMP> --screenshot=out.png file:///<$TEMP>/render.html`
  ★ 页面与输出**都放 ASCII 路径**（`$TEMP`）；**必须自带 --user-data-dir**
  （否则抢用户正在开的 Chrome 的 profile）。
- ★★ **盲拟合的命门 = `--dump-dom`**：页面里把 WebGL 版本 / shader 编译日志 /
  `gl.readPixels` 中心色 / 整图非黑像素占比写进 `<pre id="diag">`，
  再用 `--dump-dom` 抓文本 → **就能"用文本看见渲染结果"**。
- ★ 裸 WebGL **不能用 Three.js 的 `uv/position/projectionMatrix/modelViewMatrix`**，
  要换 `attribute vec2 a_pos; vUv=a_pos*0.5+0.5; gl_Position=vec4(a_pos,0,1);`
  （报错长得像"维度不匹配/未声明标识符"，容易误判）。
- 一次渲染一整格：离屏 WebGL canvas → `drawImage` 到 2D canvas 的 4×4 网格 → 一张截图。

### 抠背景（用户要求"去掉背景色"）

- 产物：`按序/抠图/01..16.png`（RGBA）、`按序/抠图_黑底/`、`ui页面/爆裂黎明_去背景_接触表.jpg`。

## ★★ 新敌军贴片悬空 → 接地补偿（同日晚）

- 用户反馈：「许多新敌人纹理需要下移确保接地，你可能需要检查一下」。**反馈属实**。
- **量出来的证据**（不是肉眼猜）：自己写 Python 解码 `.ftx3.gz` 拿到 `regionIdTex` 平面
  （= alpha 真源，见 `vendor/player/core/ftx.ts buildBaseHslData`），从最后一行往上找第一个不透明行：
  ★ **11 个包里 10 个底部有透明余量**：海怪 54px、爆炸飞行怪 59px、盾卫 27px、萨卡兹 20px、
  牢杰 9px、整合 8px、原石虫巨人 5px…（扩音术士是唯一 0）
  → 换算世界单位（`底透明px / bbox宽 × scale`）海怪 0.34m、盾卫 0.25m、爆炸飞行怪 0.22m。可见。
- ★★ **踩到的坑**：FTX 的长度字段是**小端** `getUint32(_, true)`，magic 才是大端 ——
  我一开始两个都用大端读，偏移飞到 3GB 直接崩。
- **为什么底部会有余量**：FTX 的 bbox 是导出器给的，不保证紧贴脚底（要留受击抖动/留白）。
  而贴片用**底部锚点**（quad 底边 = 地面）→ 那些空白行原样变成"角色悬空"。
- **修法（自动测量，不是手填）**：
  1. 新建 `src/services/fx/FootAnchor.ts`：`footSinkRatioOf(asset, frame)` 读
     `getFramePair().base.image.data` 的 alpha（Float32 → >0.5；Uint8 → >128），
     返回 `(h-1-lastOpaqueRow) / width` —— ★ 用**宽度**归一化，因为 quad 高是按宽高比撑出来的，
     用宽度才能与 quad 尺寸正交、两条渲染路径共用同一数值。
  2. `FTXQuad.setGroundSink(sink)`：`anchorLift = |baseScale.y|/2 - sink`
     （复用既有 `setAnchorLift`，不新增第二个锚点来源）。
  3. `EnemyBase` 新增 `groundSink?` opt，在 `applyRenderScale` **之后**下发；
     ★ 血条 `offsetY` 同步减 sink（否则贴片压下去了血条还悬着）。
  4. ★★ **L2 代理也要补偿**：`SwarmBatch` 的实例矩阵是 `gy + h/2`（同口径的悬空），
     不改就会出现"远看接地、近看悬空"。`buildBatch(scene, assets, sinks)` 多了 sinks 参数，
     `MobBatch.sink` 在 sync 里减掉（血条实例同步减）。
  5. `MobDef.groundSink`（世界单位）= `footSinkRatioOf(asset) * spec.scale + (spec.groundSink ?? 0)`；
     名册新增可选的 `groundSink` 手调量（正=再压低；负=抬高，给以后真正的空中单位用）。
  6. Boss 走同一函数（普瑞赛斯是 .scene.zip，读不到 alpha 时返回 0 → 行为不变）。
- **验证（两条独立路径互证）**：把 `FtxAsset` 用项目自带 esbuild 打包进 node 直跑，
  对 11 个包比 TS 侧 `footSinkRatioOf` 与 Python 侧解码结果 → **差值全为 0.0e+0**，且都是单帧包。
- **保留的工具**：`.workbuddy/tools/ftx_foot_measure.py`（离线量任意 FTX 包的脚底余量/quad 高，
  新素材进来先体检，不用启动游戏）。
- **顺带量到的事实（已告知，未擅自改）**：主角是 **2.0m**（bbox 256×256、scale 2.0、底透明 0），
  而 11 个敌军按 `scale × (bbox.h/bbox.w)` 算出来的实际高度是 1.12m（原石虫）~ **4.80m（原石虫巨人）**，
  牢杰 4.30 / 盾卫 4.38 / 整合 3.67 / 萨卡兹 3.59 —— 都明显高于玩家。
  ★ 根因：名册的 `scale` 语义是"quad **宽**"，高度被 bbox 宽高比放大。
  要统一身高应该改成"目标身高（米）"字段，但那会改动既有三兵种表现 → 等用户定。

## 受击染料：降频解算（"减运算帧数 + 反而更清楚"）

用户要求：「减流体注入运算帧数，提升性能的同时还能让流体扩散看的更清楚」。先查根因再动手。

### 根因（为什么降频反而更清楚）

- `FtxAsset.createHitDyeEffect` 的 `velocityScale: 0.85` 不是 `pow(0.85, dt)`，
  而是 `FluidSolver.step()` 里 **每调用一次就 `scaleVelocity(0.85)` 一次**（第 1108~1110 行，纯常量乘）。
  ⇒ 每秒衰减 = `0.85^N`，**N = 每秒 step 次数**。
- 实测账：60 步/s → `0.85^60 ≈ 6.03e-5`（一秒内速度基本归零 ⇒ 红团**原地糊住**）；
  30 步/s → `0.85^30 ≈ 7.63e-3`，速度留存多 **≈131×**（=`0.85^-30`）⇒ 红团真的会"流"开。
- 另：`step(dt)` 每帧调 = 每帧整条 solver 管线（重力/持续源/平流/压力 20 迭代/投影/限幅）≈ 十余趟 GPU pass。

### 改动（`src/entity/CharacterBase.ts`，单文件）

- 新增 `protected hitDyeStep = 1 / 30;` + `private hitDyeAccum = 0;`。
- `updateHitDye(dt)` 改为累积步进：`hitDyeAccum += dt`，到 `>= hitDyeStep` 才
  `hitDye.step(Math.min(hitDyeAccum, 1/10))` 并清零。
  ★ 计时仍按真实 dt 走（1.2s 总时长不变）；★ 单步 dt 用**累积量** ⇒ **物理时间守恒**（不是把流体变慢）；
  ★ 上限 1/10s ⇒ 卡顿一帧 300ms 时不会一次推进 300ms（防突兀跳变）。

### 稳定性核对（读源码确认，未跑游戏）

- `FluidEffect.step(dt)` 只是 `solver.step(dt)`；`solver.step` 用 dt 直接驱动，无内部固定步长累加器 ⇒ 传累积 dt 正确。
- CFL：`computeSubSteps(dt) = max(1, ceil(maxVel·dt/minGrid), ceil(gMag·dt/50))`；
  hit-dye `maxVelocity = 3000`、`gravity = {0,0}` ⇒ **阈值 `minGrid ≥ 3000/30 = 100px`**：
  minGrid ≥ 100px 的贴片（绝大多数敌人，quad 宽 1.6~3.6 对应纹理 100~230px）→ 仍 1 个子步；
  仅 < 100px 的最小档 → 平流那一趟升到 2 个子步。即便升 2 也只抵消 1 趟，其余十余趟仍砍半 ⇒ 净收益为正。
- 平流是半拉格朗日 ⇒ 无条件稳定，1/30 无失稳风险。
- 与既有约定一致：`WorldMode.sentinelFluidAccum`、`FluidIconAnimator.MAX_STEP` 同为 1/30。

## ★★ 受击染料"效果不明显"——参数体检 + 根因（同日，纠正上一节的推断）

用户问：「你觉得到底怎么做才能效果更明显，你先检查一下参数」。把注入→解算→合成全链路参数读完后，
发现**比"参数不够猛"更根本**的问题：整套流体在空转。

### ★★ 根因 1：速度场恒为零 ⇒ 零流动

- `CharacterBase.spawnHitDye` 注入 `velocity: { x: 0, y: 0 }`；
  `FtxAsset.createHitDyeEffect` 的 physics 里 `gravity: {0,0}`、**无 `continuousSources`**（默认 `[]`）、无爆炸；
  `FluidSolver.initFields()` 开头 `clearGrid(velocityGrid)`。
  ⇒ 速度场从 0 开始，且**没有任何来源**能把它变成非 0。
- 后果：`advect(velocity)` = 恒等；`advect(color)` 采样点 = 原像素（**零数值扩散，红色是冻结的印章**）；
  `solvePressure` 的 ∇·u ≡ 0 → p ≡ 0 → `applyPressureGradient` 恒等。
- ★ 但配置明显是**为"有速度的流体"写的**：`FtxAsset` 注释写"红色晕开后因阻尼停下"，
  且带 `velocityScale`(阻尼) / `maxVelocity: 3000` / `enablePressure + pressureIterations: 20`。
  ⇒ **注入速度给 0 属于漏给**，不是设计如此。

### ★★ 根因 2：`velocityScale` 是"每 step 乘一次"（与解算频率强耦合）

- `FluidSolver.step()` 第 1108~1110 行：`scaleVelocity(cfg.velocityScale)`，**纯常量乘，不按 dt 折算**。
- 0.85/步 @ 30 步/s ⇒ 1 秒后只剩 `0.85^30 ≈ 0.76%`。注释想表达"缓慢停下"，实际是"瞬间停下"。
- ★★ **自我纠正**：我上一节写的"降频 ⇒ 速度留存 131× ⇒ 扩散更清楚"**推断错误** ——
  速度恒为 0 时 `0×0.85 = 0`，比值不存在。**降频只兑现了省算（减半），没有兑现"更清楚"。**
  这也是"我没实测就下结论"的代价，以后这类"物理上应该更明显"的判断必须先在代码里找到非零量。

### ★ 根因 3：注入的"颜色"是残差空间（0.5 = 不变），所以 H=0 不是红

- `processInjectionQueue` → `injectColor(this.colorGrid, {h,s,l,a}, rate, opts, ch)`，
  而 `colorGrid` 在 `composite()` 里就是 `uResidual`。
- 合成公式（`FluidSolver.buildCompositeMat` vector 分支 + `FTXQuad` 同款）：
  `dH = (r*2-1)*0.5 = r - 0.5`，`finalH = fract(baseH + dH)`；S/L 同理，`finalA = max(baseA, residualA)`。
- ⇒ `hitDyeColor = [0, 0.95, 0.6, 0.9]` 的真实含义：
  dH = **−0.5（色相 −180°，即补色）**、dS = **+0.45**、dL = **+0.1（变亮）**、alpha 0.9。
  ⇒ 拿到的是"**补色的高饱和提亮版**"，对底色不同的敌人会变成不同色（蓝底→橙），**不是稳定的"红"**。
  ⇒ 想要真"染红"必须按像素算 `r = 0.5 − baseH`（需一张派生纹理/改代码，**纯调参数做不到**）。
- ★ 想"暗红/血色"应把 `l` 从 0.6 降到 ~0.3（dL 由 +0.1 → −0.2，变暗）。

### ★ 根因 4：又大又淡 + 硬起硬落

- `hitDyeRadius = 0.45` + shader `smoothstep(uRadius, 0.0, d)` ⇒ 从中心到 0.45 平滑衰减，
  **覆盖 ≈90% 贴片宽** ⇒ 大面积浅染，几乎没有对比度。
- `rate = 0.6` ⇒ 中心最多只走 60% 混合，边缘更低。
- vector 模式**没有颜色衰减**（`decayDensity()` 只在 scalar 分支调）⇒ 颜色一直保持，
  1.2s 后 `dispose()` 硬切回原本颜色 ⇒ 视觉是"啪一下出现、啪一下消失"，没有渗/褪的层次。
- `density: 1.0` 在 vector 模式被**完全忽略**（死参数）。

### ★ 根因 5：贴片是"整体替换"而非"叠加"

- `FTXQuad` 第 105~119 行：`if (uUseFluid > 0.5) { ... gl_FragColor = vec4(fluid.rgb, fa); return; }`
  ⇒ 流体生效时**整张贴片被流体纹理替换**（`return` 掉原分支），**不是**"在原贴片上叠一层红"。
  ⇒ 任何"叠加/发光/描边"式加强都得改 FTXQuad 增加混合模式，不是调参能做的。

## ★★ 受击染料第四轮：死亡动画小力度 + 去散度

用户原话：
> 「角色的死亡时注入力度是多大的，应该用比较小的力度，也不用散度注入」

### 先答"现在多大"（改动前的实测值）

- `DeathAnimEffect.play()`：速度冲量 `800 + random*1200` = **800~2000 px/s**（随机方向、一次性、radius 0.5）；
  推力 `gravity = 4000 px/s²`（随机方向）。
- **散度注入本就不存在**：`injectDivergenceSource` 只被 `FluidSolver.explode()` 调用，
  而 **全库 `.explode(` 零调用** ⇒ 旧版散度爆炸早已移除。但 `DeathAnimOptions.explodeStrength` /
  `explodeRadius` 两个字段**没人读**（死选项）⇒ 本轮删掉，消除误导。

### ★★ 关键坑：光把数字改小没用，得先算稳态流速

`step` 里是 `v ← (v + g·dt) × velocityScale(0.98)` ⇒ 流速收敛到
**`v_eq ≈ g / (步率 × (1 − velocityScale))` = g / (30 × 0.02) ≈ 1.63·g`**。

- `g = 160`（我第一版改的值）⇒ `v_eq ≈ 261` ⇒ **照样顶到 `maxVelocity = 50` 上限**，等于没变小。
- `g = 20` ⇒ `v_eq ≈ 33 px/s` ⇒ **真正落在上限之下**，才是"小力度"。

⇒ 教训（已写进 `MEMORY.md`）：**凡是"力度"参数，判据是稳态流速 < `maxVelocity`，不是"比原值小"**。
一次性的**冲量**不受此约束（它不累积，随 0.98 衰减），所以冲量给 20~40 就够了。

### 最终数值

| 项 | 改前 | 改后 |

| 推力 `gravity` | 4000 px/s² | **20 px/s²**（`DEATH_PUSH_FORCE`，稳态流速 ≈33 px/s） |
| 一次性冲量 `speed` | 800 + rand·1200 | **20 ~ 40 px/s**（`DEATH_IMPULSE_MIN/MAX`） |
| 散度注入 | 已无（但残留死选项） | 已无，且**删掉** `explodeStrength`/`explodeRadius` 死选项 |
| 死选项 `pushForce` | 声明但不读（`play()` 写死 4000） | **接线**为 `opts.pushForce ?? 20` |

1.2s 寿命内漂移 ≈ 40px（约贴片高 20%）⇒ 看得出在动，但不再"飞散"。

### ★★ 散度注入的符号必须先验，否则方向反了

`explode()` 的 `strength` **必须为负才是"向外"**。两条独立证据：
1. `ExplosionConfig.strength` 文档："负 = 向外爆炸（源），正 = 向内收缩（汇）"；
2. 代码 `radialSpeed = -strength × envelope × 0.12`，而 `injectRadialVelocity` 明确"**正 = 向外推**"
   ⇒ 需要 `-strength > 0` ⇒ `strength < 0`。

链路：`processExplosions` 在 **step 3.6**（压力投影之前）往 `divergenceGrid` 写源项 →
step 4 压力投影消费（∇²p = ∇·u + f）→ 压力梯度把流体从中心径向推开。
★ 散度场在 **step 4.5 `clearGrid`** 一次性清空 ⇒ 不会跨步累积；但 `duration` 内 `explode()` 自带
指数包络（decay 0.9/步、0.25s）持续注入，所以**调一次就够，绝不能每帧调**（会叠加成极端压力）。
★ 只在 `enablePressure = true` 时有效（散度源是压力方程的源项）。死亡流体一直是 true。

### ★★ levelSet 开启的三个坑（都实测确认）

1. **`surfaceTension > 0` 才真的施加**（`FluidSolver.ts:1080` `if (ls.surfaceTension > 0)`）
   ⇒ **负值是"等效关闭"**！scalar hit-dye 的 `-5000000` 是这个意思，不是"强力张力"。本轮用引擎默认 **10000**。
2. **`reinitIterations` 在 step 里没有兜底**（`:1050` `const iterations = ls.reinitIterations;`，直接透传）
   ⇒ 必须显式给。而且 `FluidSolver` 构造是 `levelSetConfig: {...config.levelSetConfig}` **浅拷贝、不并默认值**
   ⇒ 干脆整块给全（照 `Asset.createHitDyeEffect` 的字段集抄 12 个键）。
3. **开启后压力求解切成"自由表面模式"**（`:1100` 把 `phiGrid.read` 传给 `solvePressure`，只在液体内部解压力）
   ⇒ 观感变化不只是"多一个张力"。vector 模式 φ 由 `colorGrid.alpha` 推断，死亡帧的残差 alpha = 角色剪影。

★ 另一个坑：`reinitInterval` 的单位是**解算步**，降频 1/30 后 10 步 ≈ **0.33s**（不是 60fps 的 0.17s）。

- **未起游戏实测**（用户在玩）。这是三个叠加改动（限速放宽 + 散度爆发 + 自由表面），
  观感变化幅度大，需要用户实际看一眼再决定 `strength` / `surfaceTension` 要不要调。
- 开销估算：levelSet ≈ 2 趟/步 + 每 10 步一次重建（≈0.4 趟/步）；压力投影本来就 30 迭代。

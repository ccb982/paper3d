## 地形破坏 / 水体解耦（用户定调）

**问题**：打「有水 chunk」时坑洞更新极慢。根因——`PatchCompute.computeTableGeometry`
里 `buildWaterSurface(...)` 与 top/wall 几何**串行在同一个 terrainPatch worker 调用内**，
水体求解（initSolve/updateSolve + 5cm 边界探针点阵采样）拖慢整个几何返回；
且无水 chunk 也白走一遍（patch 分支会建 `waterStateFor` 状态）。

**用户设计（原话）**：「如果坑洞涉及区域没有水，就别更新水，更新水也是要先更新坑洞，
额外的 worker 慢慢算水」。

**改动**：
1. `PatchCompute.ts`
   - `computeTableGeometry` 新增末位参数 `waterMode: 'full' | 'none'`（默认 full）
     —— `'none'` 跳过 `buildWaterSurface`，返回 `water: null`
   - `PatchGeomRaw.water` 类型 → `WaterSurfaceRaw | null`
   - 新增导出 `computeWaterOnly(readChunk, seed, cx, cz, levels, dirty, levelAt)`
     —— 复用 `getRefinedSource` 缓存，只跑水体，不碰 top/wall/物理
2. 新文件 `waterSolve.worker.ts` —— 只算水的专用 worker
3. 新文件 `WaterSolve.ts` —— 主线程客户端，**单 worker 串行队列**
   - 每 chunk 终态收敛：新请求覆盖旧的（dirty 取并集），旧 promise 以 null 结清
   - worker 不可用 → 主线程同步 `computeWaterOnly` 回退
4. `terrainPatch.worker.ts` / `coarsePatch.worker.ts`：透传 waterMode，transferOf 判空
5. `TerrainPatch.ts`：compute 请求加 waterMode，透传主线程回退与 postMessage
6. `ChunkManager.ts`
   - `waterMaskCache` + `chunkWaterMask(cx,cz)`：4m 块液体位图（缓存）
   - `dirtyNearWater(cx,cz,dirty)`：dirty 块 ±4 块（16m）内是否有液体
   - `decideWaterMode()` → `'none'`（跳过）/ `'defer'`（异步慢算）
   - `patchRebuildChunk`：几何恒传 `waterMode:'none'`；defer 时投 `waterSolve.compute`
   - `replaceWaterMesh` 改**三态**：`undefined`=保持旧水面 / `null`或0-quad=拆掉 / 有值=换
   - 新增 `applyWaterResult`（只换水网格）、`stashWaterMesh`/`restoreWaterMesh`
     （全量换装前保住旧水，防水面闪没）
   - 切风格/dispose 两处加 `waterSolve.clearCaches()` + `waterMaskCache.clear()`
   - `digPerf` 新增 `waterSkip` / `waterDefer` / `waterApplied`

**关键设计点**：
- **单 worker 而非池**：`WaterSurface.waterStates` 是模块级 Map（每 worker 一份增量
  状态：occ/连通分量/边界探针/床面点阵）。同 chunk 跨 worker 漂移 → 状态丢失 →
  退化 initSolve 全量重解（更慢）。单 worker = 状态亲缘稳定 = 走 updateSolve 增量。
- **首建仍 waterMode:'full'**（`finishStandardChunk` 不传 = 默认 full）：首建没有
  「旧水面」可保持，必须同步出水面。waterMode:'none' 只用于破坏重建。
- **levels 双拷贝**：几何那份被 transfer 掉，水任务必须另拷一份
  （`new Uint8Array(levelsArr)` 两次），否则拿到 neutered 数组。
- 跨 chunk 场景自洽：水体状态 per-chunk，含水块的那个 chunk 会因跨块联动
  （`enqueuePatch`）自己重建并 defer，所以边界水也会更新。

**验证**：`tsc --noEmit` 0 错误；`vite build` 通过，`waterSolve.worker` 正确产出
独立 chunk（35.85 kB）。未做游戏内实测（避免与用户同开实例抢 GPU）。

## ★ 修正：分母（当天敌人总数）会自己变 —— 口径推翻重做

**用户反馈**：「敌人总数怎么还会变的？我的设计是当天的敌人会预计算好会有多少人，
和难度曲线动态调整有关」

### 根因：分母被三处地方改写

1. **远距回收扣分母**（前一版的错误设计）。我当时把"不算击杀"落地成
   「分子不加 + 分母扣 1」，结果玩家一跑动，HUD 上「当天总数」就自己往下掉。
   **这直接违背用户设计** —— 总数是开战前定好的计划值，不该被玩家行为改写。
2. **闸门用 `alive` 判定**：`alive < total - kills`。敌人被远距回收 → `alive` 掉下来
   → 立刻腾出名额 → 补刷 → 等于**无限刷**，分母永远追不上。
3. **`refHp`/`refAtk` 变化会改威胁档位**（仅存疑，非主因）：`computeThreat` 依赖
   参考属性，若中途重算会改 `ambientInterval` → 估算式结果不同。

### 修正口径（★ 定稿）

| 量 | 语义 | 是否冻结 |
|---|---|---|
| `quota` | 当天敌人总数（预计算） | **冻结**，换日才重算 |
| `kills` | 真击杀 | 只增 |
| `recalled` | 远距回收消失数 | 只增，**不影响 quota** |
| `spawned` | 当天累计生成过多少只 | 只增，**闸门依据** |

- **闸门改为 `quota − spawned > 0`**（原来是 `alive < total − kills`）。
  只看"生成过多少"，玩家跑动/回收都不影响 → 稳定，且不会无限刷。
- **回收只记 `recalled`，绝不碰分母**。分母冻结 = 用户要的"预计算好"。
- 新增 `remainingQuota(session)`（= quota − spawned）与
  `effectiveTotal(session)`（= quota − recalled，给进度条类 UI 用；
  HUD 默认仍展示原始 quota）。
- `ensureDayQuota` **幂等**：`quota > 0` 就原样返回、绝不重算 → 这才是"总数不变"的保证。
- 旧存档迁移：`ensureDayQuota` / `recordSpawn` 里补 `spawned ?? 0`。

### 分工（关键概念澄清）

- **定死的一份** = `quota`，只当分母，全天不变 → HUD 稳定、玩家知道还剩多少。
- **动态的一份** = 刷怪**节奏**（何时刷/刷多快），由 `ambientTarget`（存活数自适应）
  与导演 `budget` 限流 → 玩家清得快就补得快，但**不影响当天总数**。
  → 用户说的"动态调整"指的是节奏，不是总数。

## ★ 补上"打满"这一环：刷怪负责把 spawned 送到 quota

**用户定调**：「让角色打满是刷怪的部分负责的」

既然总数定死、分母冻结，那 `kills` 要能追平 `quota`，就必须保证
**刷怪最终会把 quota 只全都刷出来**。查下来有三处会让刷怪提前停：

1. **导演计划用尽**：`beginDay` 排定 n 场袭击，`plan` 走完就再无袭击，
   只剩环境散兵慢慢磨 → 磨不满。
2. **环境怪被存活数闸住**：`alive < ambientTarget` 才补 → 场上够多就
   不再生成新个体 → `spawned` 卡住。
3. **玩家低血停刷**：`playerHpRatio < 0.3` 完全不补（这条**保留**，
   是合理的低血保护）。

### 改动

- `src/systems/swarm/Director.ts`
  - `DirectorInputs` 新增 `quotaLeft?: number`（= quota − spawned；
    缺省 undefined → 按旧行为，兼容未接线调用方）
  - `calm` 阶段补怪逻辑改为：
    ```ts
    const left = inp.quotaLeft ?? 0;
    const backfill = left > 0;
    // 配额没刷完 → 节拍缩到 1/3（下限 1.2s），把缺口补上
    this.spawnTimer = backfill
      ? Math.max(1.2, this.threat.ambientInterval / 3)
      : this.threat.ambientInterval;
    // ★ alive 只在"配额已刷完"时才是硬闸；没刷完 → 允许越过 ambientTarget
    const aliveOk = backfill || inp.alive < this.threat.ambientTarget;
    if (aliveOk && inp.playerHpRatio >= 0.3) { ... }
    ```
  - 关键：**`alive` 从"硬闸"降级为"节奏闸"**。旧逻辑把它当硬闸 →
    场上够多就永远补不满，这正是打不满的根因之一。
- `src/modes/WorldMode.ts` —— `swarmDirector.update()` 调用处传入
  `quotaLeft: remainingQuota(this.session)`

### 为什么这样能自洽（三条路径的配合）

- **quota** 冻结 → 分母稳定，HUD 不跳
- **spawned** 只增 → 闸门稳定，不会因回收腾名额而无限刷
- **配额没刷完 → 环境补怪提速并越过 alive 闸** → `spawned` 必达 quota
- **`spawnWaveNear` 没放下的**（`want*10` 次尝试仍失败）→ 缺口留在
  `spawned` 的欠账里，由环境补怪兜底 → 两条路径天然互补
- lull（袭击后 18s 间歇）不补刷 —— 故意的呼吸感，时间很短，不构成缺口

## 地形破坏 / 水体解耦（用户定调）

**问题**：打「有水 chunk」时坑洞更新极慢。根因——`PatchCompute.computeTableGeometry`
里 `buildWaterSurface(...)` 与 top/wall 几何**串行在同一个 terrainPatch worker 调用内**，
水体求解（initSolve/updateSolve + 5cm 边界探针点阵采样）拖慢整个几何返回；
且无水 chunk 也白走一遍（patch 分支会建 `waterStateFor` 状态）。

**用户设计（原话）**：「如果坑洞涉及区域没有水，就别更新水，更新水也是要先更新坑洞，
额外的 worker 慢慢算水」。

**改动**：
1. `PatchCompute.ts`
   - `computeTableGeometry` 新增末位参数 `waterMode: 'full' | 'none'`（默认 full）
     —— `'none'` 跳过 `buildWaterSurface`，返回 `water: null`
   - `PatchGeomRaw.water` 类型 → `WaterSurfaceRaw | null`
   - 新增导出 `computeWaterOnly(readChunk, seed, cx, cz, levels, dirty, levelAt)`
     —— 复用 `getRefinedSource` 缓存，只跑水体，不碰 top/wall/物理
2. 新文件 `waterSolve.worker.ts` —— 只算水的专用 worker
3. 新文件 `WaterSolve.ts` —— 主线程客户端，**单 worker 串行队列**
   - 每 chunk 终态收敛：新请求覆盖旧的（dirty 取并集），旧 promise 以 null 结清
   - worker 不可用 → 主线程同步 `computeWaterOnly` 回退
4. `terrainPatch.worker.ts` / `coarsePatch.worker.ts`：透传 waterMode，transferOf 判空
5. `TerrainPatch.ts`：compute 请求加 waterMode，透传主线程回退与 postMessage
6. `ChunkManager.ts`
   - `waterMaskCache` + `chunkWaterMask(cx,cz)`：4m 块液体位图（缓存）
   - `dirtyNearWater(cx,cz,dirty)`：dirty 块 ±4 块（16m）内是否有液体
   - `decideWaterMode()` → `'none'`（跳过）/ `'defer'`（异步慢算）
   - `patchRebuildChunk`：几何恒传 `waterMode:'none'`；defer 时投 `waterSolve.compute`
   - `replaceWaterMesh` 改**三态**：`undefined`=保持旧水面 / `null`或0-quad=拆掉 / 有值=换
   - 新增 `applyWaterResult`（只换水网格）、`stashWaterMesh`/`restoreWaterMesh`
     （全量换装前保住旧水，防水面闪没）
   - 切风格/dispose 两处加 `waterSolve.clearCaches()` + `waterMaskCache.clear()`
   - `digPerf` 新增 `waterSkip` / `waterDefer` / `waterApplied`

**关键设计点**：
- **单 worker 而非池**：`WaterSurface.waterStates` 是模块级 Map（每 worker 一份增量
  状态：occ/连通分量/边界探针/床面点阵）。同 chunk 跨 worker 漂移 → 状态丢失 →
  退化 initSolve 全量重解（更慢）。单 worker = 状态亲缘稳定 = 走 updateSolve 增量。
- **首建仍 waterMode:'full'**（`finishStandardChunk` 不传 = 默认 full）：首建没有
  「旧水面」可保持，必须同步出水面。waterMode:'none' 只用于破坏重建。
- **levels 双拷贝**：几何那份被 transfer 掉，水任务必须另拷一份
  （`new Uint8Array(levelsArr)` 两次），否则拿到 neutered 数组。
- 跨 chunk 场景自洽：水体状态 per-chunk，含水块的那个 chunk 会因跨块联动
  （`enqueuePatch`）自己重建并 defer，所以边界水也会更新。

**验证**：`tsc --noEmit` 0 错误；`vite build` 通过，`waterSolve.worker` 正确产出
独立 chunk（35.85 kB）。未做游戏内实测（避免与用户同开实例抢 GPU）。

## 架构评审结论（用户问「架构很好了是吧」）

**骨架确实好**（有据可依，不是客套）：
- 三层分离干净：数据面 `RasterMap` / 计算面 Worker 纯函数 / 装配面主线程预算化
- 字节一致性靠「同函数同输入」保证，不靠人肉约定 → worker 挂了回退主线程结果也一致
- 增量几何 + Tier A/B 原地更新 + 物理分区，每层都有明确降级路径
- `digPerf` 常驻分项埋点（含本次新增 waterSkip/waterDefer/waterApplied）
- 每处优化留日期+原因（2026-09-15 装饰降级明显是实测后回退的产物）

**唯一明确腐化点**：`ChunkManager.ts` 2900+ 行 —— 命中解析 / 破坏重建 / 装饰 /
物理 / 粗块 LOD / 封存 / 装配预算 / 风格切换全塞一起。为加 4 个方法翻了很久。

**重复模式已到第 3 次，该抽了**：
- `platformFlagCache` → `waterMaskCache`：「扫 256 块 + 缓存 flag」同款，应抽
  `chunkFlagCache(key, predicate)`
- `makeLevelAt`：`TerrainPatch.ts` 一份 + `WaterSolve.ts` 一份（本次复制）

**注释误导（已修 2026-09-16）**：`TerrainPatch.ts` 头部原称「无 hash 亲缘…
退化为全量重解，可接受」。实际 `pickLeastBusy()` 在 cost 平局时取**最小编号** →
单发恒落 worker#0，亲缘性远好于注释所述；只有并发多 chunk 重建时才散到 #1/#2。
已重写该段（含亲缘性澄清 + 水体已不在本池持有），并同步修正了 compute() 的
`@param req.dirty` 语义与「流程」树里的「归属 worker」措辞（本就是非固定归属）。

### ★ 核心口径设计（易错点）

1. **分母 = 击杀可达上限，不是生成总数**。
2. **「远距清除不算击杀」的落地 = 分子不加 + 分母扣 1**（`recordRecall`）。
   只做"分子不加"的话分母永远打不满，进度条永远差一截。
3. **双路径严格互斥**：实体侧走 `EnemyBase.dispose()` → `eventBus.emit('enemy_killed')`；
   代理侧走 `swarmHooks.onAgentKilled` 直接记数。两条路绝不能同时触发。
4. **`killedByCombat` 标记**（`EntityBase` 新增）：默认 `true`；远距回收/降格路径
   **先置 `false` 再 `dispose()`** → 即使走 `dispose()` 也不上报。
5. **`spawnOne()` 是唯一收口点**：导演波次 / 扫描波次 / 压测全经过它，
   配额闸门只加这一处 → `quotaAllows()` =
   `alive < max(0, total - kills)`（alive = 实体数 + 代理数）。
6. **`everDeparted` 防同日重复清零**：存"已为哪一天初始化过配额"，
   否则同日第二次出击会把当天击杀进度清掉。

# 当前架构审计（2026-11-25）

> 项目已经迭代 55 天，代码主要由 AI 实现。
> 本文只写**设计层**，不要求记住函数名；函数细节可能和设计有偏差。
> 架构师只需要判断：命令层、执行层、优先级、状态源是否唯一。

## 1. 设计上正确的部分

```text
1. 命令层和执行层分开
2. 下盘两套 PD：
   A 组：髋 / 大腿 / 膝
   B 组：小腿 / 踝 / 脚
3. 脚/踝有最高优先级的“世界抓地”任务
4. 支撑力、姿态、阻尼是不同任务，不应互相抢写手
```

两套 PD 本身不是问题。问题是**同一个关节最终由谁写、按什么优先级写**没有完全固定。

## 2. 当前架构混乱点（按危险程度）

### 2.1 执行出口不唯一

同一个 `foot/2` 可能被这些路径写：

```text
lowerCommand.ankleComp        kind=angle
squatClean  squat.foot2.base  kind=ext
supportClean squat.foot2.cop  kind=ext
旧 squatFrame 的 foot2 路径
AnkleComp / FootAnkleModule
```

不同 `kind` 的仲裁语义不同：

```text
angle/direct 可能盖掉 ext
ext 又绕过 angle 的 PD/antiG/限幅
```

这是最危险的问题：不是“两个 PD 打架”，而是**执行出口不唯一**。

### 2.2 脚/踝命令源太多

```text
世界抓地：FootWorldTarget / AnkleComp / solveShankIKToFoot
局部策略：ankleLocal / ankleCoP / supportClean CoP
支撑：squatClean foot2 support
```

世界抓地之前外置，现在可以收敛进命令层做最高优先级；
但代码里仍存在多套“脚目标 + 局部修正”。

### 2.3 支撑力链路多套

```text
supportQp
supportDesired
fzBudget
supportWrench
supportWbc
solveStaticLegTorques
supportClean
sagittalBase
```

主链是 QP → 静态 ID → 踝/脚，但旧路径和 fallback 仍在，
容易“改了一条，另一条还在写”。

### 2.4 接触状态多份

```text
contact
loadValid
fzHeld
contactLatch
flat
supportContact
qpUse
pure.stable
```

每层自己判接触；CoP 也有多份：

```text
fc.cop
chain.cop
supportWrench.cop
ankleCoP
```

应统一成一个 contact/CoP 状态源。

### 2.5 两套 PD 是设计，不是冗余

```text
A 组：髋 / 大腿 / 膝
B 组：小腿 / 踝 / 脚
```

两套 PD 作用在不同位置、代表不同肌群，**不合并、不要求同一套 K/D**。
各组的 K/D/SRS/共收缩可以不同；这不是架构混乱。

唯一要防的是：**同一关节被两个组/两个命令层同时写**。

### 2.6 命令层时序不干净

当前主循环大致是：

```text
supportClean
→ advance（control.step / FootAnkleModule）
→ squatFrame
```

`FootAnkleModule` 读到的支撑命令可能是上一拍；
`pure.stable` / `__SQC_SUPPORT_QP` 也是上一帧状态。
这不是不能跑，但会制造一帧延迟和状态错位。

### 2.7 模式和全局状态太多

```text
baseState
actions
court
SQC_POSTURE_HOLD
SQC_SUPPORT_QP
SQC_SUPPORT_PURE
globalThis.__SQC_*
```

旧路径、fallback、死代码和重置不完整，
很容易出现“看起来改了，另一条路径还在写”。

## 3. 最小清理顺序

不要一次重写。按这个顺序：

```text
1. 一个 contact/CoP 状态源
2. 脚/踝一个命令入口 + 一个执行出口
   world grip 在入口内最高优先
3. 一个支撑力源
   旧 supportWbc/sagittalBase 明确关闭或归档
4. 两组 PD 都接同一个 computeMuscleDamping
5. 优先级改成语义，而不是 PRI/kind 碰巧谁赢：
   contact > support > posture > damping(?)
```

## 4. 脚/踝的正确设计

```text
命令层：
  world grip（最高优先级，常开）
  ankle local support / CoP（低一级）
  ankle damping / acceleration（最低）

执行层：
  只有一个最终写手
  输出一个 ankle angle（或一个明确的 angle+ff 结构）
  不允许第二个 foot/2 ext 写手
```

冲突时：

```text
world grip > support > damping
```

支撑力不能让脚失去接触；抓地目标优先。

## 5. 给架构师读代码的方法

不要从函数名猜优先级，只看三件事：

```text
1. 这个关节最终是谁写的？（proposal src）
2. 它的 pri/kind/channel 是什么？
3. 同一 dof 是否有另一个 kind 会覆盖它？
```

一个关节只允许：

```text
一个命令入口
一个执行出口
一个最终写手
```

## 7. 收敛顺序（逐个改、逐个验）

**串行求解是重中之重：抓地 → 支撑 → 加速度 → IK。**
不允许把 IK、支撑、CoM、CoP、加速度、阻尼塞进一个加权 QP 并行求解。

接触/抓地是硬约束；支撑力才是范围内近似可行。
Stage 0 输出接触可行集，Stage 1 输出支撑力包络；
阻尼可以修改支撑力/接触 wrench，但不能改接触状态、不能越 CWC/CoP/fz_min。

原则：**一次只改一个行为变量**；先加旁路/回读，再切换主链；每步都能单独回退。
不要同时动两个写手、接触状态和 PD 参数。

### Gate 0：基线冻结（不改行为）

```text
记录当前：
  footY max / footY>0.09 时间
  contact 丢失时间
  fzUse vs fzAct
  full probe hold
  Chrome frame probe
  每个 foot/hip/knee 的最终写手 src
```

验收：baseline 可重复；任何后续步骤对比这一份。

### Step 1：contact/CoP 单一读源（先只读，不改控制）

```text
建立 ContactState：
  contact / loadValid / fzHeld / copX / copZ / copVel
所有层只读这一份
旧字段保留为兼容别名
```

验收：

```text
同一帧所有层接触判断一致
footY/contact/fz 曲线与 baseline 一致
没有新写手
```

回退：保留旧函数作为 adapter，不改控制输出。

### Step 2：脚/踝单命令入口 + 单执行出口（最高收益）

```text
命令层：
  world grip（最高）
  ankle support/CoP（次之）
  damping（最低）
执行层：
  只允许一个 foot/2 最终写手
  angle 通道保留；不用 ext 直写
```

验收：

```text
同一 dof 只出现一个最终 src
Chrome 不再出现两个 foot 写手
footY 不早于 baseline 抬脚
fzAct 不长期低于 fzUse
```

回退：feature flag 切回旧 writer；旧路径先不删。

### Step 3：支撑力单一来源

```text
supportQp = 主链
supportWbc / sagittalBase / 旧 supportClean 支撑 = 明确归档或关闭
fzBudget 只做 reference
```

验收：

```text
Σfz = m(g+aY)
单脚时另一脚 fz=0
fzUse/fzAct 链路闭合
```

### Step 4：同关节命令源收敛（不是 PD 组）

```text
两套 PD 保留，各组 K/D 自己负责
只收敛同一关节/同一条命令路径的重复写手
当前重点：hip2/knee2 的 supportClean vs pdg
```

验收：

```text
同一 dof 不再同时有 angle + support ext 两个有效写手
footY/contact 不回退
full hold 不回退
```

注意：现在直接删 supportClean 的 hip2/knee2 会早抬脚；
这一步要等 contact/support 收敛后再做，不能先删。

### Step 5：语义优先级

```text
contact > support > posture > damping
不再用 PRI.direct / kind 碰巧覆盖
```

验收：

```text
冲突测试：抓地目标 vs support；support vs posture
抓地永远不被 support/姿态盖掉
```

### Step 6：清理旧路径

```text
删 supportWbc/sagittalBase 旧支撑
删重复 contact/flat/qpUse 判断
删全局 __SQC_* 旧开关
```

只在 Step 1~5 全部稳定、连续多次 probe 无回退后做。

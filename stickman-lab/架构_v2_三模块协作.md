## 0. 一句话架构

```
┌──────────────────────────────────────────┐
                 │ 状态机 gaitState（唯一相位真源）          │
                 │  显式 6 态：DOUBLE/LOAD/PUSH/THRUST/LIFT/SWING│
                 │  每拍只做两件事：                       │
                 │   ① 指定角色 support / swing            │
                 │   ② 验收：姿态是否符合**本状态**         │
                 │  ✔ **不发任何关节目标**（一条都不发）    │
                 └───────────┬──────────────────────┬───────┘
        状态 → 常量帧域表     │                      │  角色 + 验收结论 + 越界清单
        （按状态名自取，只读）  │                      │
                             ▼                      ▼
        ┌────────────────────────────┐   ┌──────────────────────────────┐
        │ 迈步系统 stepSystem         │   │ 平衡系统 balanceSystem       │
        │ 写：摆动腿（位置）           │   │ 写：承重腿（位置 + 力矩）      │
        │ 写：腰（位置，受 ±6° 限幅）  │   │ 写：中足（额状 CoP）           │
        │ ＋躯干反相旋转               │   │ **不写**摆动腿、**不写**腰    │
        │                            │   │ 只通过「参考通道」影响腰        │
        └────────────┬───────────────┘   └──────────────┬───────────────┘
                     │                                  │
                     └──────────► RigState ◄────────────┘
                            单一仲裁点：每根轴**恰好一个写者**
                                     │
                                     ▼
                              ragdoll 18 关节 × 3 轴
```

**协作不是靠优先级抢同一根轴，而是靠「角色分区」**：
状态机每拍指定哪条腿是 `support`、哪条是 `swing`，
迈步系统只碰 `swing` + 腰，平衡系统只碰 `support` + 中足。
⇒ **同一根轴永远只有一个写者**，「谁覆盖谁」这个问题在结构上不存在。

## 1. 三个模块的职责（判据 / 构造 / 修正）

| 模块 | 语义 | 每拍写什么 | **不写**什么 | 判据 |
|---|---|---|---|---|
| `gaitState` | **判据**：现在算不算「处在某个状态该有的姿态里」 | 状态标签（6 态显式）、角色（support/swing）、验收结论 `verified`、`violations[]`、驻留计时 | **任何关节目标 / 任何增益 / 任何 QP**；**一条关节指令都不发** | 状态 → 常量帧域表（Perry 区间）+ 接触 + 载荷 + 裕度 |
| `stepSystem` | **构造**：把**摆动腿与腰**推进该状态的帧域区间 | 摆动腿 `hip/1,2`、`knee/2`、`foot/2` 的位置；腰 `spine1/0,2` 的位置（±6° 限幅）；躯干反相旋转 | 承重腿任何轴、任何力矩 | 状态机的角色指派 + 锁定闸门 |
| `balanceSystem` | **修正**：让**全身**每帧都落在帧域内并保持稳定 | 承重腿的位置与力矩（踝矢状、膝伸展、髋矢状、**髋外展/内收**）；中足额状 CoP；**参考通道**里的躯干偏置 | 摆动腿任何轴、腰的**执行器** | `keyGuard`（帧域守卫）+ CoP 余量 + 稳定性裕度 |

**「状态机不发目标」是可以断言的**：状态 → 帧域是**一张常量表**，
两个系统按**状态名自己去查**（`STATE_DOMAINS[rs.state]`），
状态机本身只输出「现在处于哪个状态」和「验收过没过」。

⚠ 好处不只是干净：一旦状态机每拍下发目标，它就会隐含"谁的目标更对"的
仲裁问题；常量表 + 只读查表让**目标归属**回到两个系统自己手里，
而状态机只负责「说真话」。

### 1.1 为什么腰归迈步系统、平衡仍然能「控制体态」

用户要求「平衡系统每帧做全身修正」，但腰只有一根、只能有一个写者。
本架构的解法：**平衡系统不碰腰的电机，它碰腰的参考**。

- 迈步系统写 `spine1/0,2` 的**位置目标**（来自关键帧 + 平衡给的偏置）。
- 平衡系统每帧写 `rs.postureBias = { pitch, lat }`（一个**姿态参考偏置**，
  单位 rad，受 `waistSlotMax = 6°` 限幅）。
- 腰的实际目标 = `lerpKeyPose(key) + postureBias`。

这正是 Menga & Ghirardi（2017, *Robotics*）的双层结构：**外环改内环的参考角，
而不是覆盖内环的输出**。腰因此既被迈步系统驱动（关键帧），
又被平衡系统每帧修正（体态），而**始终只有一个写者**。

⚠ 这条边界必须由门禁强制，否则会退回「两个系统抢腰」的老问题（见 §9 `probe-coop`）。

## 2. 坐标系、判据与测量口径（不可协商的三条）

| 项 | 约定 | 依据 |
|---|---|---|
| 坐标 | `x` = 矢状（前后），`y` = 竖直，`z` = 额状（左右）；**`+z` = 左** | `skeleton.ts` |
| 关节轴 | 索引 `0` = 绕 X = **外展/侧摆**（髋），`1` = 绕 Y = 扭转，`2` = 绕 Z = 屈伸 | `skeleton.ts` + `HIP_ABD_AXIS = 0` |
| 符号 | 本 rig 髋/膝限位**负 = 屈**；脊柱正 = 躯干前倾；踝正 = 跖屈 | 实测标定 |
| **跌倒** | **唯一标准 = 头部触地**（`doll.headHitGround()`）。自碰撞关闭，头不可能碰到自己 | `sim.checkFall()` |
| 载荷 | `footLoadFrac(side)` / `footGrip(side)`：遍历**全部**鞋底碰撞块；`readCoP` 是压力中心 | `ragdoll.ts` |
| 时间 | `ticksDone` 单位是**控制拍 @120Hz**（`physicsHz=240`）；控制器 dt = 1/120 | `sim.ts` |

**站距**是这套架构的隐藏前提：Perry 规范步宽 **70~80mm**、髋间距 **280mm**；
本 rig 目前 `soleZ ≈ ±163mm`（**327mm**，4.4 倍）⇒ 所需重心横移从人类的
≈40mm 变成 **142mm**。

⚠ 旧门限 `handoverTolZ = 50mm`（人类尺度）**已随迁移判据一起退役**
（P2：判据换成「足相对身体的矢状位置」+ 载荷阈值，见 §3.5/§11）。
但站距问题本身没有消失：**每个周期仍要把重心移动 142mm**，
而 `hip/0` 的 τmax = 70 N·m 对应「重心相对髋的横向偏移 ≤ 102mm」
⇒ **单靠髋外展搬不完这 142mm**，必须靠 `LOAD` 相的两脚载荷互换补齐。

⇒ 设计决定（见 Q1）：站距由 `NORMATIVE_BIILIAC / NORMATIVE_STEP_WIDTH`
**推导**，不再写死 `±163mm`。这是把问题变成可解的第一步。

## 3. 状态机：显式 6 态，**验收过了就进下一个**

> 用户 2026-10-06 定调：
> 「状态机不需要每拍给目标。显式标明这几个状态，验收过了进下一个状态就行了。」

⇒ 状态机的全部职责是三件事：**指角色、说状态、判验收**。
它**不下发任何目标**；每个状态该有的姿态写在**常量表** `STATE_DOMAINS` 里，
两个系统按状态名**自己查**（只读）。

### 3.1 固定环形：一个迈步周期 = 走完这一圈

> 用户 2026-10-06 修正：「**迈步前需要先让重量转移到后脚啊**」
> —— 抬腿的**前提**是另一条腿已经承重。所以环里必须有一步
> 「**重量交接**」，它排在抬腿之前，而不是和抬腿同时。

```
   ┌──────────┐ 验① ┌──────────┐ 验② ┌──────────┐ 验③ ┌──────────┐ 验④ ┌──────────┐ 验⑤ ┌──────────┐
   │  DOUBLE  │────►│   LOAD   │────►│   PUSH   │────►│  THRUST  │────►│   LIFT   │────►│  SWING   │
   │ 双脚支撑  │     │ 重量交接  │     │ 提踵支撑  │     │ 卸载蹬离  │     │ 摆动腿离地│     │ 摆动→落地 │
   └──────────┘     └──────────┘     └──────────┘     └──────────┘     └──────────┘     └──────────┘
         ▲                                                                                    验⑥：落地 + 锁定
         └────────────────────────────────────────────────────────────────────────────────────────────┘
```

> **`PUSH` / `THRUST` 为什么要分（2026-10-06 决议，方案 B）**
> Perry 把终末支撑分成 `TerminalStance`（31~50%GC，提踵→反向跖屈，**全周期最强推进力**）
> 与 `PreSwing`（50~62%GC，卸载→膝屈 35°→踝跖屈 20%，为摆动做准备）。
> 两者的踝角、膝角、以及两个系统的职责都不同 ⇒ 分成两态。
> 依据见 §19.3（Usherwood 2012 的冲击—拱架—冲击）。

> ⚠ **自我纠正（2026-10-06）**：本节最初把 `PUSH` 标成「`MidStance` 被动拱架」并要求
> 「单支撑已建立」，**那是错的** ——
> ① Perry 的 `MidStance`（被动拱架，GRF 过踝、肌肉几乎不加载）是**新支撑腿**的中段支撑，
>    发生在**旧腿离地之后**，在我们环里落在 `LIFT`/`SWING` 期间，不在 `PUSH`；
> ② 我们的 `PUSH` 里两条腿都还着地（承接腿刚接完重量、后腿准备蹬离），
>    要求"单支撑"等于要求**承接腿离地**，与 `LOAD` 刚把它接过来直接矛盾。
> ⇒ 已改为 Perry 同一阶段内的两个相位（`TerminalStance` / `PreSwing`）。
> **拱架（被动段）落在 `LIFT`+`SWING`**：那一段新支撑腿确实处于单支撑中段，
> 平衡系统"少做"的要求写在 `STATE_ROLES.LIFT` / `.SWING` 里。

**唯一的硬前提（不变式）**：任一时刻**至多一条腿承重、另一条腿 unloaded**。
⇒ 「重量交接」必须是环上的**独立一步**，且排在抬腿之前。

**方向逐周期自动交替**：迈步时哪条腿承重，就往哪条腿交重量。
- 从静止起走、或需要后退再起步时，交接目标就是**后脚**
  （gait initiation：重心先后移到后腿再蹬出，Hess et al. 1999）。
- 稳态行走时：落地后承重的正好是**上一条摆动腿**（此刻它成了后脚），
  下一周期要抬另一条腿 ⇒ 交接目标自然轮到**前脚**。
⇒ 因此这个状态**不能按方向命名**，只能按角色命名：`LOAD` = 「交给承重腿」。

### 3.2 六个状态（显式，逐个写全）

| # | 状态 | 支撑数 | 承重腿（support） | 摆动腿 | Perry 对应 | 该状态存在的意义 | 迈步系统 | 平衡系统 |
|---|---|---|---|---|---|---|---|---|
| 1 | **`DOUBLE`** | 2 | 载荷大的一条 | —（双脚都在地上） | `MSt` | 建立/恢复稳定的双脚站立 | 不动 | `hold`；双脚载荷均衡 |
| 2 | **`LOAD`** | 2 | **正在吃重量的那条**（交接目标） | 未解锁 | `LR`→`MSt` | **把重量交出去** —— 抬腿的资格前提 | 不动（摆动腿不许动） | **`shift`**：承重腿改变 GRF 方向 + 两脚载荷互换 |
| 3 | **`PUSH`** | **2** | 同上 | **已解锁但仍留地** | `TSt` | **提踵**：踝走到全支撑期最大背屈 | 摆动腿小幅踝背屈（仍可留地） | 承重腿踝**背屈**（几何准备，力臂还没形成） |
| 4 | **`THRUST`** | **2** | 同上 | 同上 | `PSw` | **卸载 + 蹬离收尾**：踝反向跖屈、膝屈 35° | 后脚卸载、继续跖屈造离地间隙（**仍不抬腿**） | 承重腿踝**跖屈产力矩** + CoP 前移（唯一主动制造向前动量的地方） |
| 5 | **`LIFT`** | 1 | 同上 | **离地**（唯一允许离地的动作） | `ISw` | 建立单支撑（**新支撑腿从此进入被动拱架段**） | **抬摆动腿**（离地净空 ≥ MFC 5cm）+ 初始屈膝 | `hold`：踝矢状 + 髋外展托住重心。⚠ **拱架在此，平衡"少做"** |
| 6 | **`SWING`** | 1→2 | 同上 | 摆到底 → **落地锁定** | `MSw`→`TSw` | 走完摆动、落地、交接准备 | 摆动腿 `MSw→TSw`、落地、**触地即锁** | 持续 `hold`；落地瞬间准备接管 |

⚠ **解锁语义**（用户 2026-10-03：「触地即锁、不许预先锁；后腿解锁」）：
`LOAD` 摆动腿**仍锁定**（不许动）；`PUSH`/`THRUST` **解锁但仍留地**（允许预屈膝准备）；
`LIFT` 起才允许离地。锁定期内 `requestSwingLegAngle` 会被闸门否决
⇒ 「未解锁」与「预屈膝」不能同时出现在一行。

⚠ **离地只发生在 `LIFT`**（`PUSH`/`THRUST` 全程双脚着地）。
「支撑数」列指的是**该状态结束时**的支撑脚数（`LIFT` 结束 = 1，`SWING` 结束 = 2）。
必须写死，否则"哪一刻离地"会有两个答案 —— 旧实现就有这个问题。

顺序 `DOUBLE → LOAD → PUSH → THRUST → LIFT → SWING → DOUBLE` 是**唯一真源**
（`STATE_ORDER` / `NEXT_STATE`，`rigState.ts`）；与 Perry 8 相的映射 `STATE_TO_GAIT`
以及每态姿态区间 `STATE_DOMAINS` 都在 `keyframe.ts`。两处都不许散落字面量。
旧的 `PHASE_ORDER` / `PHASE_TO_GAIT` 已随改名退役。

| `STEP` | **`SWING` 的后半** | 落地 + 锁定 |

### 3.2.1 ★★★ 角色锁存：**承重腿 / 前后腿不许在态内切换**（用户 2026-10-06 强调）

> 用户原话：「我是有锁定腿这样的操作的。**承重腿、前后腿应不该允许状态机随意切换**，仅此而已。」

这条**不是新发明**，是文档早有的要求被代码漏掉了。本文档多处已经写明：

- §3.2 的 `LOAD` 行：摆动腿**仍锁定**（不许动）；`PUSH`/`THRUST` 解锁但仍留地；
  `LIFT` 起才允许离地。**「锁定期内 `requestSwingLegAngle` 会被闸门否决」**。
- `rigState.ts` 的 `supportLeg()` 注释原文：**「锁定期内支撑腿恒定」**
  —— `ω₀`、`waistTrim` 符号、驱动目标 `soleZ[sup]`、CoP 护栏**全部拿到固定目标**。

**代码现状（2026-10-06 审计）—— 只做了一半**：

| 机制 | 是否用了锁定 | 说明 |
|---|---|---|
| `supportLeg()` | ✅ | `if (locked.l) return 'l'` —— 锁定优先于测量 |
| `stepPermit.P3_未锁定` | ✅ | 用 `rs.locked[sw]` |
| **`VERIFY` 的判据** | ❌ | 全部用 `recv` / `rear` / `sup`，而这三个**每拍重算** |

`recv`/`rear`/`sup` 的原实现：

```ts
const recv: Side = rs.lastSwing ?? rs.frontLeg();   // ← 每拍求值
const rear: Side = recv === 'l' ? 'r' : 'l';
const sup  = this.bearer;                            // ← 载荷迟滞，也是每拍
```

两个问题：
1. 文档本意是「`frontLeg()` 只在 **t=0** 做**一次性引导**」，代码却写成每拍求值
   ⇒ 在 `lastSwing` 仍为 `null` 的**整个第一周期**里，等于每拍重新掷骰子
   （`frontLeg()` 是 |Δx| > 3mm 的几何判据，可来回翻）。
2. 即使 `lastSwing` 已就绪，触地边沿也会在**态中途**改写它，角色随之换腿。

**实测后果（这就是"一瞬间过了三个检测、关节却没动"的机制）**：

`probe:domain`，`LOAD` 段，t=0.39→0.40 **一拍（16 ms）**：

| 量 | t=0.39 | t=0.40 | 变化 |
|---|---|---|---|
| 承接踝跖屈 | −2.44° | **+11.88°** | **Δ = 14.31°** |
| 承接膝屈 | 4.89° | **14.51°** | Δ = 9.62° |
| 承接载荷 | 0.726 | **0.280** | Δ = −0.446 |
| 阻塞项 | 承接踝跖屈 −2.44/6.00 | **—（全过）** | 迁移发生 |

而**前后两拍的关节读数都是 ±0.1°/拍 的平线**（真关节根本没动）。
唯一变的是「判据在测哪条腿」—— 换到的那条腿碰巧满足门槛，于是验收通过、状态前进。

#### ★★★ 腿角色只有两种：**承重腿 + 摆动腿**（用户 2026-10-06 定调）

> 用户原话：「**往前迈的是摆动腿。一个承重腿，一个摆动腿。**」
> 以及完整循环：「承重腿一开始是后腿，后腿锁定承重，然后前腿往前迈；
> 然后前腿锁定承重，转移重心，再迈后腿，再锁后腿承重，**这样循环往复**。」

**这条推翻了我们此前的角色模型。** 我们原来有**四个**角色名在跑：
`recv`（承接腿）/ `rear`（后腿）/ `sup`（承重腿）/ `sw`（摆动腿），
而它们之间是**互相推导**的（`rear = other(recv)`、`sw = rear`、`sup` 由载荷迟滞定）
⇒ 三者可以互相矛盾（实测 UI 出现「前腿 · 摆动」而状态机认为它是 `rear`）。

**正确的模型（本节即真源）**：

| 角色 | 定义 | 数量 |
|---|---|---|
| **承重腿** | 当前**承担体重**的那条 | **恰好 1 条** |
| **摆动腿** | **正在往前方迈**的那条 | **恰好 1 条** |

- **「前腿 / 后腿」不是角色，是位置描述**（哪条脚更靠前而已，随姿态变化）。
  它们**不得**参与判据、不得决定锁定、不得决定谁摆动。
- **两者互补**：任一时刻恰好一条承重、一条摆动。
- **角色在一个周期内只交换一次**，交换时刻 = **摆动腿落地那一拍**
  （`touchdown[sw]`）：旧的摆动腿变成承重腿，旧的承重腿变成摆动腿。
  ⇒ 角色是**滞回量**，不是每拍由载荷/几何重新推断的量。
  （这正是"承重腿不该随意切换"的机制保证：它只在落地事件上换，不在噪声上换。）

**逐周期的循环（用户描述）**：

```
 ① 承重腿锁定（一开始是位置靠后的那条）
 ② 摆动腿往前方迈
 ③ 摆动腿落地 → 【角色交换】它变成承重腿并锁定
 ④ 重心转移到新的承重腿
 ⑤ 新的摆动腿（= 刚才的承重腿）往前方迈
 ⑥ 回到 ①，左右互换
```

**对代码的直接影响（待实现）**：

1. `sw` **不得**再由 `rear = other(recv)` 推出，`sup` **不得**再由载荷迟滞单独决定；
   二者改为**互为补集**的一对滞回角色，交换点固定在 `touchdown[sw]`。
2. `recv`（承接腿）这个名字应退役或**明确等价于"摆动腿落地后的身份"**
   —— 它不该是一个与 `sup`/`sw` 并行的第四个量。
3. 判据里所有 `recv`/`rear` 的用法按上表重写（`LOAD` 的"承接腿"= 刚落地的摆动腿）。
4. `STATE_LEGS` 的 `front`/`rear` 字段名改为 `bearer`/`swing`，
   避免继续用位置词当角色词。

**★ 逐态显式声明（用户 2026-10-06：「每个状态，状态机都要显式指定前后腿、锁定腿」）**

代码对应物 `STATE_LEGS`（`gaitState.ts`）。三档自由度：
`locked`（完全不许动）/ `grounded-unlocked`（解锁但必须留地）/ `free`（可离地）。

| 态 | 承接腿(front) | 后腿(rear) | 说明 | 出处 |
|---|---|---|---|---|
| `DOUBLE` | **locked** | **locked** | 双腿承重，谁都不许走 | Perry 双支撑；此时抬腿=没交接就偷跑 |
| `LOAD` | **locked** | **locked** | 交接完成前不许动后腿（抬腿前提） | 用户 2026-10-06「先让重量转移到后脚」 |
| `PUSH` | **locked** | grounded-unlocked | 后腿解锁但留地（允许预屈膝） | Perry `TerminalStance`；离地只允许在 `LIFT` |
| `THRUST` | **locked** | grounded-unlocked | 同上，蹬离 | Perry `PreSwing` |
| `LIFT` | **locked** | **free** | **唯一允许离地** | Perry `InitialSwing` |
| `SWING` | **locked** | **free**（触地即锁） | 摆到落地，触地瞬间锁 ⇒ 与 `DOUBLE` 声明衔接 | Perry `MidSwing→TerminalSwing` |

**施加方式**：`update()` 每拍**按本状态的声明幂等施加**（`rs.locked[recv/rear]`），
不再依赖"触地时写一次、LIFT/SWING 时清一次"的边沿逻辑 ——
锁定从此是**状态的函数**，不是历史的函数（可读、可断言、不会态内漂移）。
`SWING` 的"触地即锁"作为额外的即时规则保留（声明为 `free` 的腿一旦触地立即锁）。

**UI/遥测**：`telemetry.legPlan` 逐字给出
`前(承接)右 锁定　后(摆动)左 解锁留地`，面板直接渲染 ——
"这个态哪条腿能动"不再需要读代码。

**规格（本节即真源）**：

1. **角色在进态时解析一次，态内恒定**。解析式仍为
   `roleRecv = lastSwing ?? frontLeg()`（`frontLeg` 只在**尚无历史**时引导），
   `roleSup = 载荷迟滞的当前值`。**态内任何一拍都不得重解析。**
2. **重解析只发生在迁移那一拍**（含 `Tmax` 兜底与 reset）。
3. `VERIFY` 的所有判据、`STATE_ROLES` 的读法、两个系统取的目标，
   **一律用锁存值**（`rs.roleRecv` / `rs.roleSup`），不得自己再算一份
   （否则又回到"两套口径"，见 §18）。
4. 角色的**合法切换**只有一条路径：走完一圈回到 `DOUBLE` / 迁移到新状态时重解析。
   **不存在"因为载荷抖了一下就换承重腿"这种路径。**

### 3.3 每个状态的「验收项」= 结构（数值见 §11）

验收是**逐项布尔**的，每一项都必须能单独回读（`rs.violations[]` 给出
「哪一项、差多少」）。

> ⚠ **本节只列"验收哪几类"，一个数字都不写** —— 阈值、出处、标定方式全部集中在
> **§11**。曾经这里和阈值全表各写一套（一边用重心投影、一边用矢状足位置），
> ⇒ **同一件事有两个答案 = 没收敛**。现在 §11 是唯一真源。

| 状态 | 姿态验收（帧域，`STATE_DOMAINS`） | 前置条件验收（只列类别） |
|---|---|---|
| `DOUBLE` | 承重腿髋/膝/踝 + 躯干 pitch/lat 落在区间内 | **接触**：双脚接地；**载荷**：轻腿仍有载荷；**裕度**：倾角、MoS（Perry：只有支撑中期接近静态站姿） |
| `LOAD` | 承接腿在交接区间；**被卸载腿不许塌**（仍在 `DOUBLE` 区间） | **签名(Perry LR)**：承接踝跖屈 ≥6°（足底着平）、承接膝屈 ≥12°（吸振）；*辅助*：承接腿载荷、后脚未离地、承接脚矢状位置、手性交替、节奏间隔 |
| `PUSH` | 承重腿在**被动拱架**区间（踝背屈中、膝髋渐伸） | **签名(Perry MSt)**：后脚踝背屈进行中；**接触**：承重腿在位；**裕度**：倾角、帧域 |
| `THRUST` | 承重腿在**蹬离**区间（踝跖屈峰、膝伸、髋伸） | **签名(Perry TSt/PSw)**：后脚踝背屈达峰 ≥10°（提踵）→ 跖屈 ≥3°；**接触**：承重腿在位；*辅助*：矢状位置、倾角 |
| `LIFT` | 承重腿在站立区间；摆动腿在初始屈曲区间 | **签名(Perry PSw→ISw)**：摆动踝跖屈 ≥12°（离地 20°）、摆动膝屈 ≥21°（35°）；*辅助*：已卸载、已离地、净空、膝屈曲、MoS |
| `SWING` | 摆动腿在 `MSw→TSw` 区间；承重腿仍在站立区间 | **签名(Perry MSw/TSw)**：摆动膝屈峰值 ≥36°（60°）、落地踝背屈 ≥7°（12°）；*辅助*：落地事件、落地矢状、膝角速度 |

⚠ **四类判据的分工**（审计结论，值得单独写）：

| 类别 | 例子 | 规矩 |
|---|---|---|
| **接触** | 接地 / 离地 / 落地 | 事实，最可靠，直接用 |
| **载荷** | `loadFrac`、`soleBlockLoad` | 事实，但**必须带双阈值 + 最小驻留**（载荷真实会以 ~0.75s 周期摆动，只靠幅值迟滞会出现 50ms 级翻转） |
| **几何** | `sagPosRel`（足相对身体，以腿长归一） | **必须用足相对身体的位置**，绝不用重心相对脚的位置 —— 后者被控制器自己的动作推着走（实测 243mm 永不收敛） |
| **姿态** | 帧域区间、膝角、角速度 | 区间优先于点；进严保持松（两段式迟滞） |

**禁止两类判据**（旧实现都犯过）：
① **导数判据**（如 `d(loadFrac)/dt ≥ 0`）—— 噪声放大，且没有一篇实现这么判；
② **"意图"判据**（如"平衡系统说有推进意图"）—— **自指**：用自己的输出去判自己能否推进。

**验收通过 ⇒ 立刻进下一个状态**。就这样，没有别的推进条件。

推进逻辑就这么几行（`gaitState.update()` 的全部职责）：

```ts
// 每拍：① 评估本态 → ② 过了就进下一态 → ③ 写角色 + 结论
const ok = verify(rs.state);            // 逐项布尔，结果进 rs.violations[]
rs.verified = ok;
if (ok && dwellOk(rs.state)) rs.state = NEXT_STATE[rs.state];   // 固定环
rs.loadBearer = this.bearer;            // 承重腿 = 载荷双阈值 + 最小驻留
// ④ 若硬项越界持续超时 → rs.safe = true（**模式标志，不是第六个状态**）
```

⇒ 「固定几个状态」+ 「验收过了自动进下一个」= **一个环形 FSM**，
没有相位积分、没有权重调度、没有"该不该走"的自由裁量。

### 3.4 文献里的步态状态机长什么样（三个独立实现 + 一个安全态设计）

> ⚠ **文献范围刻意收窄**（用户 2026-10-06：「状态机我觉得不需要查很多吧，
> 状态分清楚、各个状态的判定范围查清楚即可」）：
> 状态机这边**只查"有哪几个状态、每态的转换判据"**——四个实现已经足够互证（§3.4 表）。
> 剩下的工作量不是查文献，而是**在本 rig 上把每个判据的范围标定出来**（§11）。
> 平衡与迈步两侧才需要深查，各自查各自的方向：**§16 平衡 / §17 迈步**。

用户 2026-10-06：「找找论文」⇒ 下面是**四个可查的实现**，全部是
「**阈值验收 → 自动进下一个**」，没有一个用计时器推进相位。

| 实现 | 状态 | 迁移判据（全部是阈值） |
|---|---|---|
| **SCONE** `GaitStateController`（开源仿真框架） | **5 个**：`Landing / EarlyStance / LateStance / LiftOff / Swing` | ① 足载阈值（以体重为单位）② **相对腿长的矢状足位置**阈值（`landing/late_stance/liftoff_threshold`）③ 对侧腿载荷 |
| **EPFL** 神经肌肉假体反射调制（infoscience） | **5 个/腿**：`ES / MS / PS / IS / LP` | 对侧足事件（**对侧趾离**=单支撑起点、**对侧触地**=双支撑起点）+ 同侧触地/趾离；`LP` 用**屈伸角速度 < −1°/s**；足载阈值 **10 N** |

| **Vughuma & Verlinden 2022**（*EECSS*，踝足矫形器） | 4 个 + `Init` + **每个正常态派生安全态** | 足底 heel/foreoot 两传感器 4 种组合（`11/01/00/10`）；每个安全态带 **`Tmax`** |

**四条可直接抄进本设计的共识**：

1. 迁移判据只用 **接触/载荷阈值 + 关节角阈值（可含角速度阈值）+ 几何位置阈值**
   —— **没有任何一个实现用计时器推进相位**。
2. **最短驻留是防抖参数**（OSL `min_time_in_state = 0.20s`），**不是推进条件**。
3. 每个正常态都要派生**安全态**，并带 `Tmax` 时间上限（Vughuma 的明确要求）。
4. 状态之间的**角色交接用「对侧足事件」触发**（对侧趾离 / 对侧触地），
   而不是自己那条腿的时间。

⚠ **一条重要的否定证据**：这四个实现**没有一个**把「重心是否在支撑脚正上方」
（`comOverFoot`）当迁移判据 —— 它们用的是**足相对身体的矢状位置** + **足底载荷**。
⇒ 本设计原方案里的 `comOverFootZ` 既不符合文献、又在实测中永不收敛
（`soleZ` 自己会动，实测 243mm）⇒ **退役它是有文献依据的，不是调参**。

**周期级 ↔ 腿级的对照**（文献的 FSM 是**每条腿**一个，本设计是**每周期**一个）：

| 本设计（周期级） | SCONE（腿级） | EPFL（腿级） |
|---|---|---|
| `DOUBLE` 双脚稳定 | 两个腿分别处于 `Landing` 与 `LateStance/LiftOff` | `ES/PS` 的重叠 |
| `LOAD` 重量交接 | `EarlyStance`（承重腿开始吃重） | `MS`（由**对侧趾离**触发） |
| `PUSH` 蹬离 | `LateStance` | `PS` |
| `LIFT` 摆动腿离地 | `LiftOff` | `IS`（由**对侧触地**触发） |
| `SWING` 摆动→落地 | `Swing`→`Landing` | `LP`→`ES` |

⇒ 两条设计判据被文献直接支持：**「重量交接」是一个独立状态**（= `EarlyStance`/
`MS`，由对侧事件触发），**「抬腿」只有在承重腿卸载到阈值以下之后才允许**
（= `LiftOff` 的判据就是 `leg_load < swing_load_threshold`）。

### 3.5 ★ 现有代码状态机的逐条审计（对不对？）

用户 2026-10-06：「参照论文，我现在的状态机的状态和验收标准都对吗」
⇒ 逐条判 **`对` / `错` / `缺`**，判据只用上面 §3.4 的四篇。

**A. 状态集**

| 现有状态 | 判定 | 依据 |
|---|---|---|
| `DOUBLE` | **对** | 双支撑必须独立成态（EPFL：单支撑起点 = **对侧趾离**；SCONE：两腿状态部分重叠） |
| `SHIFT` | **对，但名不副实** | 语义就是重量交接 = SCONE `EarlyStance` / EPFL `MS`；只是名字没说清 |
| `SINGLE` | **错** | 名义「单支撑」，实测**抬起量为 0**（`step.ts:222` 的 `hold` 不含 `SINGLE`）⇒ 它其实是「等待区」，而真正的单支撑在 `STEP` 里 |
| `PUSH` | **错** | 判据 `stepPermit.all && both` 要求**双脚仍接地** ⇒ 它其实是「抬腿前的等待区」，没有任何推进动作（只发 `shiftDemandF`，那是额侧向力） |
| `STEP` | **缺一半** | 它把「抬腿 + 单支撑 + 摆动 + 落地」四件事挤在一起 ⇒ 违反 Perry 的 `ISw/MSw/TSw` 三段，也没法对「离地净空」单独验收 |

⇒ 修法（就是 v2 的环）：**`SINGLE` → `LIFT`**（离地单独成态，负责"抬起"与净空验收）；

### 3.6 帧域是**常量表**，不是每拍下发的目标

`keyframe.ts` 现在给的是**点**（`KeyPose`）。Perry / Oberg 的规范值本身
就是**区间**（中支撑膝 男 15–24°/女 12–20°；摆动膝峰 65–68°；
髋总程随步速变化 ⇒ 必须按相位取，不能用常数）
⇒ **帧域是区间**，控制律必须是「往区间里推」而不是「追一个点」。

```ts
// src/core/keyframe.ts（新增，常量；**只读**，状态机不写它）
interface StateDomain {                 // 一项 = 一个关节/轴在某个状态的可接受区间
  state: 'DOUBLE' | 'LOAD' | 'PUSH' | 'THRUST' | 'LIFT' | 'SWING';
  leg: 'support' | 'swing' | 'trunk';
  axis: 'hipFlex' | 'hipAbd' | 'kneeFlex' | 'ankle' | 'trunkPitch' | 'trunkLat';
  lo: number; hi: number;               // deg，闭区间
  tolIn: number; tolOut: number;        // 进入严、保持松（两段式迟滞）
  hard: boolean;                        // 越界是否算异常
}
const STATE_DOMAINS: readonly StateDomain[];   // 唯一真源
```

### 3.7 ★★★ 判据调理层：**判定条件本身必须先可信**（2026-10-06 重写）

> 用户 2026-10-06：「我觉得这个状态检测条件不行。**如果实在没论文的话，就得靠我们自己研究了**。」

这一节分两部分：
- **A. 文献给过的**（防抖/兜底，沿用）；
- **B. 文献**没有**、我们必须自研的**（测量噪声下的判据可信性）。
  **B 部分全部标注为「本项目自研，无文献依据」**，因为
  Perry / SCONE / OSL 定义判据时都**默认传感器干净、相位已知**；
  没有任何一篇讲"当一个 σ=9° 的踝角读数去卡 6° 门槛时该怎么办"。

#### A. 文献/惯例（沿用，四条）

1. **最短驻留**：验收通过后仍需停留 ≥ `minDwellSec`（初值 0.20s，OSL `min_time_in_state`）。
   是**防抖**，不是"时间到了就走"。
2. **迟滞**：进入用严容差 `tolIn`，保持/回退用 `tolOut = 2·tolIn`
   （Rezazadeh et al. 2018 的两段式 FSM）。
3. **`Tmax` 兜底**：停留 > `tmaxSec`（初值 2.0s）⇒ 回 `DOUBLE`。是**防卡死**，
   **不是**推进方式。
4. **安全态 `rs.safe`**（模式标志，不是第六个状态）：`hard` 项越界持续 > `graceSec`
   ⇒ 置位，**迈步系统停手、平衡系统全权接管**；`rs.state` 不变。

#### B. 本项目自研（**无文献依据**，但实测必需）

**B0. 前提：判据只能读"调理后"的信号，不读原始量。**
原始 `rs.pos` 保留给诊断与 UI；判据读状态机自己的滤波值。理由见 B2。

**B1. 角色锁存（§3.2.1）** —— 角色在态内恒定。这一条单独就能消灭
"换腿造成假过"（实测 Δ=14.31°/16ms）。

**B2. 门槛必须高于噪声**：判据的**门槛值**必须显著大于该信号的**逐拍噪声**，
否则判定等于掷硬币。实测（`probe-readout`，安静站立 0.5s）：

| 信号 | 标准差 σ | 逐拍最大跳变 | 当时门槛 | 判定 |
|---|---|---|---|---|
| 膝角 | 2.17° | 6.04° | 12° | ⚠ 勉强 |
| **踝角** | **9.35°** | **21.12°** | **6°** | ❌ **门槛 < σ，纯噪声** |
| 髋角 | 3.15° | 4.47° | — | — |
| **膝角速度** | **410.3°/s** | **1069.4°/s** | **2°/s** | ❌ **门槛是噪声的 1/200** |

⇒ **规则**：新增判据时必须先测该信号的 σ；若 `门槛 < 3σ`，该判据**不许**作为
迁移条件使用，只能作为诊断（或必须先滤波/换信号）。
**这条规则当场判死了两个现有判据**：`承接踝跖屈(≥6°)` 与
`背屈推进中(踝角速度 < −2°/s)`、`踝已转为跖屈向(> +2°/s)`。
（`背屈推进中`/`踝已转为跖屈向` 现在读的正是 σ=410 的角速度
⇒ 它们在实测里表现为 198.56 / 145.00 这类荒谬值。）

**B3. 保持才认（hold-to-pass）**：单个判据必须**连续成立 N 拍**（初值 5 拍 = 83ms）
才算"过"；退出闸门要求**所有判据同时保持**。单采样满足一律不算。
理由：噪声尖峰是单拍的，真实物理量是持续的。

**B4. 尖峰不可推进**：若某判据的信号**单拍跳变**超过物理可信上限
（角：3°/拍；角速度：50°/s/拍），该拍**标为可疑**，判据不得据此判"过"。
⇒ 尖峰只能**卡住**状态机，不能**推进**它。（这条是 B1 的兜底：
即便将来又出现别的身份漂移，也不会再让状态机被一帧噪声推走。）

**B5. 转移类判据用 Δ（相对进态值），不用绝对姿态**：
`LOAD` 的语义是"重量**交出去**"，所以它的判据应是
`loadFrac[recv] − 进态值 ≥ X`，而不是"承接腿载荷 ≥ 0.60"这种绝对线。
否则一个"本来就 60/40 站着"的静止姿态会立刻满足 `LOAD`，
**状态机在物理上什么都没发生时就走完了**。

**B6. 载荷项恢复为阻塞判据**：`cfg.loadBlocks` 之前被设成 `false`
（当时理由是"载荷读数不可信"）。**2026-10-06 该理由已消除**：
L0 口径已收敛为唯一来源（`soleForceProfile`，`numSolverContacts` + 世界坐标
+ 法线对齐），`probe:readback` 已断言 `逐块和 == 脚合力`。
⇒ `loadBlocks` 应改回 `true`，让"重量真的交出去了"成为**硬条件**。

**B7. 不可判时要"说不可判"，不许默认通过**：
若信号不可信（CoP `copValid=false`、力链 `trustable=false`、或 B2/B4 判定该拍可疑），
对应判据必须**阻止迁移**并显式说明原因（进 `violations` / `telemetry`），
**不许静默算通过** —— 这正是本项目反复栽的"静默失效"模式。

#### 这一层的门禁（§9 补充）

- **B2 检查**：每个判据的信号 σ 与门槛同时打印，`门槛 < 3σ` 即失败。
- **B1 检查**：态内 `roleRecv`/`roleSup` 发生变化 ⇒ 失败。
- **B4 检查**：任何一次迁移，若其"过"的判据在那一拍有可疑跳变 ⇒ 失败。
- **B3 检查**：迁移时统计各判据已连续保持的拍数，`< N` ⇒ 失败。
- **B5 检查**：`LOAD`/`LIFT` 等转移类判据必须含至少一个 Δ 形式。
- **回归样本**：把 t=0.39→0.40 这一幕固化成断言
  （"Δ踝 > 3°/拍 时不得迁移"）。

### 3.8 状态机**不做**的事

- **不发任何关节目标**（一次都不发）——可由门禁静态断言（§9）。
- 不决定增益、不解 QP、不写 `keyDomain` 之类"下发物"。

## 4. 迈步系统：目标是一个**区间**

迈步系统**按当前状态自己查常量表**（状态机不下发目标）：
`STATE_DOMAINS[rs.state]` 取出 `swing` 那一组区间。
但**目标是区间**，所以每根轴的命令是「当前值 → 区间」的方向与幅度：

```ts
// 新增：src/core/keyframe.ts
function towardDomain(q: number, lo: number, hi: number, step: number): number
// q < lo  ⇒ 往 lo 推，但不超过 lo+step（不越界冲过头）
// q > hi  ⇒ 往 hi 推，但不低于 hi-step
// 否则    ⇒ 保持（不发指令，这就是「在帧域内 ⇒ 不干预」）
```

- 足净空：摆动相膝屈峰 60~68°（Perry / Oberg），最小离地净空 MFC = 5cm。
- 摆动轨迹两端速度为零（`sin(πs)` 钟形）。
- 躯干反相旋转 6°（Takemura 2007；骨盆横断面旋转，Mann 1975）——
  注意这是**代偿**，不是平衡机构（见第 6 节）。
- 落地即锁、不预锁（用户 2026-10-03 定调，保留）。

## 5. 平衡系统：增强承重脚 + 承重脚侧向发力

> ### ★★★ 职责再划分（用户 2026-10-06 定调，**本条优先于下文一切旧表述**）
>
> 用户原话：
> 「**搬重量是迈步系统做的**。平衡系统是在**尽量在符合下阶段判定阈值**的情况下去**维持平衡**，
> 给出一个**全身的完整的修正建议**。」
>
> **① 搬重量（重心转移）归迈步系统，不归平衡系统。**
>   把 CoM 从一条腿搬到另一条腿 = **迈步系统**的动作。平衡系统**不负责搬运**，
>   它不该有"把重心移到支撑脚"这样的目标。
>   （§20.4 表里 `LOAD` 那行"把重量从 rear 搬到 recv"**归属写错了**，已在该处改正。）
>
> **② 平衡系统的目标**：
>   · **硬目标：不倒**（CoM 在支撑面内、`τ` 有余量、承重腿按本态要求接触）；
>   · **不偏离迈步系统的计划**；对"搬得太过"（CoM 越界 / τ 转负 / CoP 出脚）有
>     **否决 / 限幅权**，但**不得改变目标本身**。
>   ⚠ **"逼近下一态阈值"归迈步系统**（用户 2026-10-06 第二次纠正），
>     曾把它写成平衡的"软目标"是**归属错误**，已删。详见 §21.4。
>
> **③ 输出 = 全身完整的修正建议向量**（全身各轴的 ΔΘ 建议），
>   下层按权限与 `τmax` 分配执行。
>
> **③′ ★ 逐态作用不同：平衡系统只管"承重腿"，不管"摆动腿"**（用户 2026-10-06 追加）
>
>   用户原话：
>   「平衡系统在**不同阶段下作用不一样**。**迈步的腿平衡系统就不要强制要求着地**，
>    而是平衡系统**控制另一条腿**，侧向发力什么的，**保持单腿平衡**。」
>
>   ⇒ 这条**纠正了本节 ③ 里"两脚都维持接触"的写法**（那是错的归属）：
>
>   | 腿 | 谁管它 | 平衡系统要不要管它的接触 |
>   |---|---|---|
>   | **承重腿** | **平衡系统**（侧向发力、踝、CoP 维护） | **要**——它是平衡的执行对象 |
>   | **摆动腿** | **迈步系统**（按住/预摆/抬起/落下） | **不要**——**不得强制它着地** |
>
>   逐态的含义：
>   - `DOUBLE` / `LOAD` / `PUSH` / `THRUST`：摆动腿**本来就在地上**，
>     但"让它保持在地上"是**迈步系统**的事（它负责摆动腿的位置）；
>     平衡系统**只驱动承重腿**，不许去按摆动腿。
>   - `LIFT` / `SWING`：摆动腿离地，**单腿平衡完全归平衡系统**；
>     它靠承重腿的**侧向发力**（髋外展 + 中足 CoP，§15）把 CoM 控在支撑面内。
>
>   ⇒ **实测 `双脚接地 1/2` 卡死 `DOUBLE` 的归属更正**：
>     摆动腿飘起来 **不是平衡系统的错**（它不该管），是**迈步系统没有把摆动腿按住**。
>     平衡系统只驱动承重腿是**符合规格**的；缺的是 `step.ts` 在
>     `DOUBLE`/`LOAD` 下对摆动腿的**位置保持**（按住 + 不许漂）。
>
> **④ 平衡系统必须"听"状态机**：角色（`roleSup`/`roleSw`）与状态（`rs.state`）
>   都由状态机显式决定，平衡系统按指定维持平衡，**不得自己推断角色**
>   （旧实现通过 `supportLeg()` 五层回落去"猜"角色 = 让噪声决定，见 §3.2.1）。
>   但"听"≠"只驱动那一条腿"——见 ③。
>
> **⑤ `balance.ts` 当前三处缺陷（实测确认）**：
>   1. 只读角色（3 处）、几乎不读 `rs.state`（1 处）、基本不读力链（§20.3）
>      ⇒ **没有"朝下一态阈值收敛"这回事**；
>   2. 输出是"驱动承重腿"，不是全身修正 ⇒ 另一条腿摆烂；

这是本架构的**核心机制**（用户 2026-10-06 定义），分三条子任务。

### 5.1 竖向/矢状：增强承重脚的发力

| 通道 | 机制 | 文献 | 作用轴 |
|---|---|---|---|
| `ankleCop` | 踝跖屈肌**刚度伺服**：`τ_a = K_a·q_vip + C_a·q_vip'`，`Ke ≈ 850 N·m/rad` | Winter 1998 *J Neurophysiol* 80:1211；Loram & Lakie 2002 | 承重 `foot/2` |
| `hipStiff` | 髋侧**被动刚度**（欠临界踝的兜底）：`τ_h = K_h·q + B_h·q'` | Morasso 2019/2022（DIP）；Horak & Nashner 1986 | 承重 `hip/2` |
| `stanceExt` | 支撑膝**主动刚度**（不是追一个屈曲目标） | Li & Levine 2010（站立时膝角近似恒定）；J Ab 2021 承重侧 GMED +58% | 承重 `knee/2` |

**硬约束（写进设计余量）**：竖向地面反力**不由关节力矩「造」**。
法向力是接触的量（`f_y` 来自物理解算），关节力矩只负责**力矩平衡**
（把压力中心搬到该在的位置）。
⇒ 附录 C.7 的教训必须保留：`Στᵢ(axisᵢ×rᵢ) = F_des` 这类**只含水平两行**的等式
不能承担体重；一旦把 `f_y = m·g` 塞进关节力矩的等式里，就会与位置伺服的
支撑力矩**双计**（实测 0.25s 内 CoM 从 0.962 掉到 0.866）。

### 5.2 额状：**三层**（粗调 / 精调 / 交接），不是一条律

> 完整机制与文献见 **§15 柔性足与侧向发力**。这里给控制侧的分层。

| 层 | 子任务 | 目标 | 执行器 | 何时开 | 判据 |
|---|---|---|---|---|---|
| **① 粗调（主力）** | `hold` | 重心停在支撑脚正上方（**不产生位移**） | 承重 `hip/0` 外展刚度伺服：`τ = a·m·(ω₀²(z_ref−z) + 2ζω₀(−ż))`，`ω₀=√(g/h)` | 单支撑全程 | τ ≤ 70 N·m；死区 8 N·m |
| **① 粗调（主力）** | `shift` | 重心**横移**到承接脚（人类尺度 `Δz ≈ 40mm`；**本 rig 因站距 327mm 实际需要 ≈142mm**，见 §2） | 承重 `hip/0` 内收/外展改变 GRF **方向**（van Mierlo 2022/2024：CMP 可以合法出支撑面） | `LOAD` 相 | 压力中心余量 ×2 + τmax（下） |
| **② 精调（快速）** | `copTrim` | **只搬 CoP 的横向位置**，不造 net 力 | 中足 `midfoot/0` 旋前/旋后（距下关节）。内翻→CoP 外移、外翻→CoP 内移 | **中支撑期最有效**，蹬离期无效 | 权限随 `contactN` 缩放；夹在 CoP 侧缘余量内 |
| **③ 交接（主力）** | `handover` | 双支撑期**两脚载荷互换** | 力学（`loadAccept`/`loadRelease` 阈值） | `LOAD` 相 | 承接腿载荷 ≥ 0.60、后脚 ≤ 0.15 |
| 附带 | 躯干代偿 | 减小髋外展负荷 | 腰的 `postureBias`（参考通道） | 全程 | ±6° 限幅 |

⚠ **②的窗口限制是文献结论，不是保守设定**：PLOS Comp Biol 2023 实测
「接触点减少后 CoP 位移能力显著下降」，且**内/外翻力矩产生的额状 CoP 变化
大于跖屈力矩、且几乎不产生竖向速度副作用** ⇒ 额向调节应当走中足而不是踝。
⚠ 但人的踝内/外翻肌力矩很小（落地仿真 <10 N·m）⇒ 中足是**精调不是主力**，
主力永远是①。

**为什么承重脚侧向发力就够**（用户的方案在此处有文献支撑）：
人类 40mm 的横向重心转移是**准静态**的，不需要大的横向剪力；
Winter 1998 的机制是**两腿载荷互换**（unload one / load the other），
而不是"用脚推"。支撑髋外展改变的是 **GRF 方向**，CMP 可以合法地跑到
支撑面之外（van Mierlo 2022/2024）。

**四条护栏（任一不过 ⇒ 本拍不做 `shift`）**：

1. 目标脚压力中心**侧缘余量** ≥ `latShiftCopMargin`（把压力推出鞋底就救不回）。
2. 承重脚压力中心**侧缘余量** ≥ 同一门限（横向力先改变载荷分配）。
3. `τ ≤ τmax`（`hip/0` 上限 **70 N·m**；由此得硬约束：
   重心相对该髋的横向偏移 ≤ `70/(m·g) ≈ 102mm`）。
4. ★ **接触点预算**：CoP 权限随 `contactN` 缩小（PLOS 2023）。
   蹬离期接触点减少 ⇒ `shift`/`copTrim` 的权限必须同步收缩，
   否则会把 CoP 顶出支撑面。

⚠ **若 `shift` 在护栏内不可行**，`balanceSystem` 必须
`rs.lateralTask.infeasible = true` **如实上报**，
由状态机决定「延长 `LOAD` 驻留」或「放弃这一步」——
**不允许**硬推到底（实测旧实现把 `com.z` 推到 ±800mm）。

### 5.3 摆动腿的蹬地：**矢状**归平衡，**额状**不做

- 矢状向前的蹬地反力（F_x）在 `PUSH` 相由**承重腿**踝跖屈肌 + 髋伸展提供。
- 额状**不由摆动腿推**（旧实现块⑤ 用摆动腿横向驱动，
  `shiftDemandF` 只看相位、不查消融 ⇒ 曾是「消融工具说谎」第四次复发）。
  本架构把额状搬运交给承重腿 + 载荷再分配（5.2）。

### 5.4 `keyGuard`：平衡如何「尽量不背离关键帧」

| 情形 | 平衡系统的权限 | 数据标志 |
|---|---|---|
| 姿态**在**帧域内 | 只做**微调**（增益 × `keyGuard ∈ [0.15, 1]`） | `rs.verified = true` |
| 姿态**出**帧域（可恢复） | **接管**该轴，`keyGuard = 1`，全力修正 | `rs.verified = false` + `violations[]`（含差多少） |
| 要跌倒（CoP 触边 / MoS < 预算 / 头高快速下降） | **强制接管**，无视帧域（生存优先） | `rs.safe = true`（与状态机的安全态**同一个标志**） |

这三档必须**显式**且**可回读**，不允许靠优先级暗中覆盖。
⚠ 安全态是**模式标志、不是第六个状态**：它不破坏固定环（否则环就不固定了），
而是让「迈步停手、平衡全权」这件事有一个单一真源（Vughuma 的安全态语义）。

## 6. 腰：不是平衡机构（已量化的结论）

用户要求「平衡系统能控制体态」，但**腰作为平衡执行器是错的**，依据：

| 文献 | 结论 |
|---|---|
| Winter 1996 *J Neurophysiol* 75:2334 | 静立两个机构**完全分离**：矢状 = 踝跖屈、额状 = 髋外展；**腰在两张表里都不出现** |
| Winter 1998 80:1211 | `Ke ≈ 850 N·m/rad` 在踝跖屈肌；`Ma = R·p_x`；额状靠髋**换载荷** |
| Horak & Nashner 1986 | 踝策略远端→近端传播，躯干最后被动参与 |
| Jeffs / Kiefer / Shirazi-Adl | 安静站立时腰椎肌肉激活极低、接近被动 |

实测（`probe-readout` ⑤）：腰作为全链 QP 的**冗余自由度**时，
0.25s 内被折到限位 **3.2 倍**（`spine1/2` −1.4° → −43.9°，τ 打满 120 N·m）；
把腰移出该 QP 后，三段全部回到限位内（`spine1/0` +55.8° → **−2.04°**，
`spine1/2` −53.8° → **−2.11°**），τ 峰值 **120 → ≤15.5 N·m**。

⇒ 腰的正确角色：**抵抗自重折叠（静态 ~3% MVC）+ 承受躯干反相旋转的代偿
（Mann 1975 是「用躯干卸载髋外展肌」，属减小负荷，不是平衡机构）**。
体态的动态修正走 §1.1 的**参考通道**。

**唯一的执行者与唯一的修正者**（用户 2026-10-06：「平衡系统是给全局的唯一修正」）。

## 14. 命令系统（完整规格）

用户 2026-10-06：「**需要重新整理命令系统**」「总之就是一个状态机，两套系统协作」

### 14.0 为什么现在整理（零件够了，缺的是命令层）

| 层 | 现状 | 结论 |
|---|---|---|
| 零件 | 18 关节 ×3 轴 + 限位 + τmax + 被动刚度保护；**柔性足 6 块真实鞋底**（足跟/外侧柱/内侧弓·后/内侧弓·前/跖骨头/趾）+ 弓关节（距下关节，ForceBased K≈400 N·m/rad） | **够用，不加零件** |
| 测量 | `footLoadFrac` / `footGrip` / `readCoP` / `soleBlockLoad` / `footSoleBounds` / `com` / `dcm` | **够用** |
| 执行 | `motorTarget`（PD）+ `tauOut`，相加后按 τmax 饱和 | **够用** |
| **命令层** | 一堆 `request*` + 优先级表 + 逐轴消融门 | **← 缺口在这** |

论文里的命令系统都是**分层 + 任务槽位**（MultiContactController：FSM→Manager→Task→QP；
FreeGait：whole-body abstraction layer；Impedance MPC：三层优先级 + 零空间投影），
共同点是：**上层开"任务槽位"，下层填数值，越权被结构性禁止** —— 而不是靠优先级抢同一根轴。

### 14.1 四层结构

```
┌─ L0 判据层 ── gaitState ─────────────────────────────────────────┐
│  只出：state / stateT / support / swing / verified /            │
│        violations[] / safe / lastSwing / cycleCount / stepPermit│
│  禁：任何关节/力矩指令（门禁 probe-pure-sm 静态断言）             │
└───────────────┬──────────────────────────────┬──────────────────┘
                │ 只读                        │ 只读
     ┌──────────▼─────────┐        ┌───────────▼──────────┐
     │ L1a step 意图       │        │ L1b balance 意图      │
     │ rs.stepIntent      │        │ rs.balanceIntent     │
     │ · footTarget 落点   │        │ · lateralTask        │
     │ · jointBands 区间   │        │ · copTarget / sagTask│
     │ · waistRef          │        │ · postureBias        │
     │ · liftProfile       │        │ · keyGuard / envelope│
     └──────────┬─────────┘        └───────────┬──────────┘
                │ 摆动腿+腰（位置）             │ 承重腿+中足（位置/力矩）+ 任务
     ┌──────────▼──────────────────────────────▼──────────┐
     │ L2 任务层 ── grfQp（λ-QP）：接触扳手 λ + 姿态任务     │
     │  输入 copTarget/sagTask + 接触集合 + 帧域 + τ 上限    │
     │  输出 τ_cmd[] + grfCmd + feasible/infeasible          │
     └──────────┬──────────────────────────────────────────┘
     ┌──────────▼──────────────────────────────────────────┐
     │ L3 执行层 ── 每 (轴,模式) 每拍**恰好一个写者**         │
     │  位置 setAngle(axis, θ_ref) ｜ 刚度 setImpedance(k,b) │
     │  力矩 addTorque(axis, τ) ｜ 让位 requestHold(axis)     │
     └──────────┬──────────────────────────────────────────┘
                ▼  motorTarget + tauOut → ragdoll（相加后按 τmax 饱和）
```

**层间只允许两种耦合**（这是"协作"的全部机制）：
1. **只读别人的输出**（step 读 `postureBias`；balance 读 `state`/`verified`）。
2. **写自己的意图对象**（L1），由 L2/L3 统一执行。
⇒ **没有任何一条路径让一个系统直接写另一个系统的目标。**

### 14.2 L0 判据层：状态机输出（穷举）

| 输出 | 类型 | 语义 | 消费者 |
|---|---|---|---|
| `state` | `WalkState` | 固定环上的当前状态 | step / balance / 门禁 / UI |
| `stateT` | number (s) | 本状态驻留时间（**仅防抖与 `Tmax`**） | step（轨迹进度）/ UI |
| `supportLeg()` / `swingLeg()` | `Side` | **角色分区**（由接触事件历史决定，不由几何 `Δx` 决定） | step / balance |
| `verified` | boolean | 本拍**全部**验收项通过 | balance（`keyGuard`）/ UI |
| `violations[]` | `{state,item,value,tol}[]` | 差多少都能读 | balance / UI / 门禁 |
| `safe` | boolean | 安全模式标志（**不是第六个状态**） | step（停手）/ balance（全权） |
| `lastSwing` | `Side \| null` | 上一周期摆动腿（手性 + 角色历史） | step / balance / 门禁 |
| `cycleCount` | number | 已完成周期数 | 门禁 |
| `stepPermit` | `Criteria` | 允许动摆动腿的许可（派生视图） | step |
| `gaitKey` / `keyPose` | `GaitKey` / `KeyPose` | Perry 关键帧只读映射 | step / balance |
| `authority` | 0..1 | 腰参考偏置的权限预算 α(t) | step |

**禁止**：关节目标、力矩、增益、阻抗、QP 变量。

### 14.3 L1 意图层：两个系统各写一个对象

```ts
// ── 迈步系统的意图（L1a）：它只说「我要什么姿态/落点」，不说怎么用力 ──
interface StepIntent {
  swing: Side;                              // 要动的腿
  footTarget: { x: number; y: number; z: number; yaw: number };
  //            ↑ 落点（米）。**新增**：步长/落点必须可指令化 ——
  //              ML 稳定的主策略就是落足（能补偿约 10× 于踝策略，代价是慢 ~100ms）
  jointBands: {                             // 帧域**区间**（deg），不是点
    hipFlex: [number, number];
    kneeFlex: [number, number];
    ankle: [number, number];
  };
  liftProfile: { height: number; tSwing: number };
  waistRef: { pitch: number; lat: number }; // = keyPose.trunk* + balance.postureBias
}

// ── 平衡系统的意图（L1b）：全局唯一修正者 ──
interface BalanceIntent {
  lateralTask: 'none' | 'hold' | 'shift' | 'copTrim';
  infeasible: boolean;                      // 护栏不满足 ⇒ 如实上报，不硬推
  copTarget?: { z: number };                // 任务层：要求 CoP 到足内某位置（米）
  sagTask: { mode: 'none' | 'push' | 'brake'; impulse: number };
  postureBias: { pitch: number; lat: number };  // 躯干参考偏置（≤6°），step 读
  keyGuard: number;                         // 帧域守卫增益：域内 0.15，越界 1.0
  envelope: 'nominal' | 'correct' | 'emergency';
  //         └ emergency = 生存优先，无视帧域（CoP 触边 / MoS 崩 / 头高快速下降）
}
```

**关键约束（可断言）**：
- `BalanceIntent.lateralTask` 由 **balance 自己**从 `state==LOAD` + 载荷/几何算出。
  旧实现把额侧向力意图交给 step 写（`shiftDemandF`）⇒ 与"平衡是唯一修正器"冲突，**退役**。
- step **不得**读 `BalanceIntent` 里的任何力/任务字段，只能读 `postureBias`。
- 两个意图对象都要进 `snapshot()`，UI/门禁可回读（**"意图"必须可见**，否则又是一句"探针说谎"）。

### 14.4 L2 任务层：λ-QP（`grfQp` 接入运行时）

```
决策变量：接触扳手 λ（每个接触点 6 维）+ 驱动行关节力矩 τ
等式：    M(q)·a_des + C(q,q̇) + g(q) = Sᵀτ + Σ Jᵀλ
不等式：  λ_n ≥ 0（单边）｜ ‖λ_t‖ ≤ μ·λ_n（摩擦锥，μ=0.8）｜ CoP ∈ 支撑多边形
目标：    min Σ wᵢ·τᵢ² + w_cop·‖CoP − copTarget‖² + w_posture·‖躯干姿态误差‖²
```

| 规则 | 内容 |
|---|---|
| **竖向不设目标** | `f_y` 由接触给出，**不写 `f_y = m·g`**（附录 C.7 的双计教训） |
| 姿态作为**任务** | 躯干姿态进目标函数，而不是让腰当冗余自由度被动分摊（§6） |
| 接触集合 | 只有 `supportLeg()` 那只脚的 `soleCols`；`copTrim` 的权限随 `contactN` 缩放 |
| 无解 | 返回 `infeasible=true` + `grfSat`，**降级**为「位置伺服 + 报告」，不硬解 |
| 退役 | `wholeBodyQp`（水平两行等式）**退役**，`fDesY` 路径彻底删 |

### 14.5 L3 执行层：每轴单写者

| 接口 | 语义 | 写者 | 备注 |
|---|---|---|---|
| `setAngle(axis, θ_ref)` | 目标角 | 摆动腿+腰 → step；承重腿+中足 → balance | 归一化后进 `motorTarget` |
| `setImpedance(axis, k, b)` | **逐轴刚度/阻尼** | balance | **新增**；帧域宽度 = `k` 的物理含义 |
| `addTorque(axis, τ)` | 力矩**累加** | balance（L2 输出） | 不压制、不删他人 |
| `requestHold(axis)` | 位置环退化为纯阻尼 | balance | 让位机制 |
| 底层 | `motorTarget` + `tauOut` → 相加 → 按 τmax 饱和 | `ragdoll.driveMotors` | 唯一物理出口 |

**不变式（门禁可断言）**：每 `(轴, 模式)` 每拍**恰好一个写者**
（`AXIS_OWNERSHIP` 表已是这个模型，见 §7 与门禁 A/C）。

### 14.6 每拍时序（120 Hz）

```
① 读物理：接触 / loadFrac / soleBlockLoad / readCoP / q / q̇ / com / dcm
② L0：verify(state) → state / roles / verified / violations / safe / stepPermit
③ L1a：step 写 stepIntent        （读 state + STATE_DOMAINS + postureBias）
④ L1b：balance 写 balanceIntent  （读 state + verified + 物理 + 帧域）
⑤ L2 ：grfQp(balanceIntent) → τ_cmd + feasible
⑥ L3 ：仲裁 → motorTarget / tauOut / holdMask（每轴单写者，冲突记 axisConflicts）
⑦ 物理步进（240 Hz）
```

⚠ **顺序不可换**：L1b 必须晚于 L0（要用 `verified`/`safe` 决定 `keyGuard`/`envelope`），
L2 必须晚于 L1b，L3 必须最后（它只做仲裁，不做决策）。

| 探针 | 断言 |
|---|---|

| `probe-intent` | ① 两个意图对象字段齐全且进 snapshot；② step **不读** balance 的力/任务字段；③ balance **不读** step 的关节目标；④ `infeasible` 时 τ 必为 0 |

### 14.8 命令层的实施顺序（接在 §10 的 P 序列后）

| 阶段 | 内容 | 完成判据 |
|---|---|---|
| **C1 意图对象** | `StepIntent` / `BalanceIntent` + snapshot 回读（**不改任何控制律**） | `probe-intent` 的 ①② 绿 |
| **C2 落点接口** | `footTarget`（落点指令）+ step 用它生成摆动轨迹 | 能指令化步长/落点宽度 |
| **C3 逐轴刚度** | `setImpedance` + `keyGuard` 接入（帧域宽度 = 刚度） | 消融 `qp`/`hip` 后存活差异符合预期 |
| **C4 任务层上线** | `grfQp` 接入；退役 `wholeBodyQp` 与 `shiftDemand*`；`copTarget` 生效 | `probe-l2` 绿；`infeasible` 路径有实测 |
| **C5 全门禁** | `probe-coop` / `probe-intent` / `probe-interface` / `probe-l2` 全绿 | `axisConflicts ≡ ∅` |

⚠ **顺序理由**：C1 是纯观测（零风险）；C2 引入新的自由度（步长）；
C3 改变闭环形状（刚度）；C4 换求解器（风险最高）。**先观测、再加自由度、再改形状、最后换求解器。**

## 15. 柔性足：怎么让脚**侧向发力**

用户 2026-10-06：「我还实现了柔性足，想让脚侧向发力应该怎么弄」

### 15.1 先搞清楚"脚侧向发力"在物理上是哪一种力

足底能改变的是**压力中心（CoP）在足内的位置**，不是凭空造出横向力。
净横向地面反力 `F_lat` 满足 `F_lat / F_y = ΔCoP_z / h_coM`（`h_coM` ≈ CoM 高度）：

| 要什么 | 靠什么 | 量级 |
|---|---|---|
| **调 CoP 横向位置**（改变 GRF **方向**） | 中足（距下横关节=subtalar）**内翻/外翻** | 见 15.2 |
| **造净横向力**（真的推） | 承重**髋外展/内收** + 双支撑期**两脚载荷互换** | 髋力臂仅 ~119mm（本 rig 实测），`τmax = 70 N·m` |
| **被动回中** | 柔性足弓的弹性（不是发力，是**支撑**） | 屈曲刚度 |

⇒ **柔性足给的是「可调节的 CoP + 被动支撑 + 缓冲」，不是「横向推进力」。**
这个区分很重要：把足弓刚度当成"侧向力权限"会得到错误结论。

★ **本 rig 已经把这个结构做出来了**（`ragdoll.ts` 的 `soleBlockLoad` 注释）：
鞋底 6 块 = 足跟 / **外侧柱** / **内侧弓·后** / **内侧弓·前** / 跖骨头 / 趾，
内侧弓天生离地 22mm；`arch_l/r` 绕足长轴 = 距下关节旋前/旋后（ForceBased，K≈400 N·m/rad）。
⇒ 代码里已经写明结论：「**重心压到支撑腿内侧 ⇒ 内侧弓应接近 0（它离地），
外侧柱/跖骨头承重 ⇒ 侧向 CoP 权限就是这么来的（不需要中足关节）**」。

⇒ **对设计的修正**：额向搬运的主力是**柱间载荷转移**（由 λ-QP 直接命令），
中足/弓关节只是**精调与被动回中**，不是主力。这比"用中足发力"更省事、更符合结构。

### 15.2 论文怎么说（中足内/外翻是最有效的横向调节手段）

| 文献 | 结论 |
|---|---|
| **Simulation of ankle PF + inversion-eversion exoskeleton torques**（*PLOS Comp Biol* 2023, 19:e1010712） | ① **内翻力矩把 CoP 推向横向（外侧），外翻力矩推向内侧**；② **内/外翻力矩产生的额状 CoP 变化 > 跖屈力矩**，也就是**额向最有效的关节是（距下）横关节，不是踝跖屈**；③ 内/外翻力矩**几乎不产生竖向速度副作用**（跖屈会），所以额向控制可以很"干净"；④ 效果随接触点减少而衰减 ⇒ **中支撑期最有效，蹬离期最弱**；⑤ 人的踝内/外翻肌力矩很小（落地仿真 <10 N·m）⇒ 足内/外翻是**精调**，不是主力 |
| **MacKinnon & Winter**（经 *Front. Aging Neurosci* 综述转引） | 「**距下关节与髋在单支撑期协同控制额状平衡**」；ML 额状平衡最有力地受**足相对躯干的 ML 位置**影响 |
| **Hof / Vlutters / van den Bogaart** | ML 方向**落足（stepping）是主策略**（可补偿约 10× 于踝策略的扰动），踝策略**反应快约 100ms** ⇒ 两者是「粗调 + 快精调」的互补 |
| **Winter 1996/1998** | 额状平衡主力是**髋**（换载荷），踝与足内/外翻肌贡献小 |

### 15.3 落到本 rig 的具体做法（三层，各司其职）

```
第 1 层（粗调，主力）：承重髋 hip/0 内收/外展
   · 目的：把 CoM.z 拉向/推离支撑脚（`hold`）、或改变 GRF 方向（`shift`）
   · 文献：Winter 1998（额状刚度伺服）、Pandy 2010（外展把 CoM 加速**向内** = 承重）
   · 护栏：τ ≤ 70 N·m ⇒ CoM 相对该髋的横向偏移 ≤ 70/(m·g) ≈ 102mm；死区 8 N·m
   · 四条护栏（CoP 侧缘余量 ×2 + τmax + 接触点预算）任一不过 ⇒ 本拍不做 shift

第 2 层（精调，快速）：中足 midfoot/0 旋前/旋后（= 距下关节内/外翻）
   · 目的：**只搬 CoP 的横向位置**，不产生大 net 力，但让 GRF 方向变
   · 文献：PLOS 2023（内翻→CoP 外移、外翻→CoP 内移；额向效果 > 跖屈；无竖向副作用）
   · 适用窗口：**单支撑中段（`LIFT`/`SWING`）与 `LOAD` 末**，蹬离期无效（接触点减少）
   · 量程：本 rig 中足行程有限 ⇒ 只允许 ±几度的**精调**，并且必须夹在压力中心余量内

第 3 层（交接期主力）：双支撑期两脚**载荷互换**
   · 目的：`LOAD` 相把重量从后脚交到前脚 —— 这是**准静态**的，不需要大剪切力
   · 文献：Winter 1998「unloading one limb / loading the other」
   · 与状态机的关系：**这就是 `LOAD` 状态的物理内容**，也是"迈步前先把重量转移到后脚"的实现

（柔性足弓本身：提供**被动回中刚度 + 冲击缓冲**，
 在**支撑末期**按 Kelly et al. 2014 的结论应"变成刚性杠杆"用于蹬地 ——
 也就是说：柔韧在落地/缓冲，蹬地时要锁住。这对控制器的含义是
 **足弓刚度应该随相位切换**（又一个"逐相阻抗"的必要性证据，见 §13.3）。）
```

### 15.4 柔性足带来的两条额外义务（论文要求，控制器必须实现）

| 义务 | 文献 | 控制器含义 |
|---|---|---|
| **接触点数量随相位变化 ⇒ CoP 权限随之变化** | PLOS 2023：接触点减少时 CoP 位移能力显著下降 | `shift` 的**权限预算必须随 `contactN` 缩放**，否则蹬离期会把 CoP 推出支撑面 |
| **柔性/肌肉系统会让响应比理想刚体模型小很多** | PLOS 2023：加入肌肉与软组织特性后，CoM 速度变化**约减半** | 用刚体模型算出来的力矩要**打折**；标定必须在**本 rig 的柔性足**上做，不能照抄文献的关节力矩 |

## 16. 平衡系统：文献依据（**只查平衡这一侧**）

> 用户 2026-10-06：「平衡系统和迈步系统都要查，**而且两者要查不同方面的论文**」。
> 本节只回答一个问题：**平衡回路该长成什么样、增益取多少、死区多大**。

### 16.1 反馈结构：人是"间歇 PD"，不是连续 PD

| 文献 | 结论 | 对本设计的含义 |
|---|---|---|
| **Asai 等 / A Model of Postural Control in Quiet Standing**（PMC2704954） | ① 踝**内禀刚度不足以稳定**；② 神经传导延迟约 **200 ms**；③ 连续 PD 的稳定区在 `P–D` 参数空间里**非常窄**；④ **间歇 PD**（相平面切换 + 死区）稳定区大得多，且**可用小得多的增益**；⑤ 人的摇摆形态 = 沿鞍点稳定流形慢速滑行（PD 关）与螺旋回摆（PD 开）的**交替** | ⇒ 平衡**必须带死区/间歇**，不能连续高增益。这正是 `keyGuard ∈ [0.15,1]` 与 `latHipDead = 8 N·m` 的理论依据 |
| **Li & Levine**（ACC 2009，最优控制姿势调节模型） | 人的摇摆幅度**大于**"无延迟线性反馈"所能产生的幅度 ⇒ 摇摆不是噪声，是策略的产物 | ⇒ **不要把目标定成"零摇摆"**；MoS 留够余量即可，过度调参会把摇摆压到失稳边界 |
| **Reeves 等**（*Sci Rep* 2021，扰动响应） | 扰动响应像**临界阻尼**；拟合出的增益落在 `node–spiral` 分界线的**稳健分支**上；「最快」假设被否，「非振荡 + 稳健」被接受 | ⇒ 增益选点原则：**非振荡（临界阻尼附近）+ 稳健优先于最快** |

### 16.2 增益与延迟：可用的定量锚点

| 量 | 文献值 | 备注 |
|---|---|---|
| 踝内禀刚度 K | ≈ **91–92%** 的倾倒力矩 | McKee & Neale（*PLOS One* 2019）实测复核；与 Loram & Lakie 的 91% 一致 ⇒ 本 rig 的 `kVipAnkle` 定标应以"占倾倒力矩的比例"为口径 |
| 主动反馈增益（踝，PD） | `Kp ≈ 750 N·m/rad`，`Kd ≈ 350 N·m·s/rad` | Popovic & Vette（Toronto FES）生理辨识；命令可**领先**身体摇摆 100–200 ms |
| 神经环路延迟 | **80–135 ms** 可补偿；实测 125–300 ms（个体差异大） | 同上 + McKee 2019；⚠ 本 rig 无神经延迟 ⇒ **允许的增益上限比人高**，但别照抄人的 Kp |
| 活跃区占比 | 相平面 **75–80%** 的区域有主动反馈（另一说 64%） | McKee 2019 / Tietäväinen |
| 摇摆噪声底 | CoP：AP 18mm / ML 6mm | Nigg 2006（本 rig 实测噪声更大 ⇒ 阈值需按实测重标） |

### 16.3 三条可直接落地的平衡律

1. **死区先行**：`keyGuard` + 关节死区让平衡在"域内几乎不动"（对应"PD 关"）。
2. **非振荡优先**：出现振荡先怀疑增益落在稳定区外（`P` 过大），而不是加 `D`。
3. **摇摆是允许的**：验收看 MoS 与帧域，**不看**"抖动变小"。

## 17. 迈步系统：文献依据（**只查迈步这一侧**）

> 本节只回答：**摆动腿轨迹怎么生成、落点与净空怎么指令化**。
> 与 §16 刻意不重叠（那边讲反馈结构，这边讲轨迹生成）。

### 17.1 摆动腿是"目标构型 + 最小跃度"，不是"手调峰值"

| 文献 | 结论 | 对本设计的含义 |
|---|---|---|
| **A neuromuscular model of human locomotion**（PMC9114145） | 摆动腿按**任务层目标构型 + 目标时刻**控制，轨迹用**最小跃度（5 阶多项式）**，执行中**持续更新**；**平衡控制方程给出摆动腿在中摆与落地前的目标角，并可为了维持平衡而修改**；FSM 只组织 early swing / late swing / stance 的切换 | ⇒ ★ **摆动腿的目标应由平衡参与给定**（与 `postureBias` 同构，只是对象换成摆动腿目标角）⇒ 这是两系统协作的**第二个参考通道** |
| **TWIN 外骨骼踝轨迹**（Giannattasio 等，IEEE TNSRE 2024） | 步态风格由**步长 SL 与净空 CL** 两个参数化；摆动相用**最小跃度 + QP 安全约束**：① 地面净空曲线 `c1`；② 早期摆动再加 1.5 cm 安全余量 `c2`（绊倒高风险段）；③ 马达限位 `c3`（踝 0.35 rad）；边界条件对**位置/速度/加速度**都约束（`a_start = a_end = 0`） | ⇒ 步态风格必须是 **(SL, CL) 两个可指令参数**；摆动轨迹要有**净空安全曲线**与**加速度连续**边界；这些都比"膝屈峰 60°/63° 手调常数"更接近文献 |
| **Toe clearance prediction**（*Gait Posture* 2019, PMID 31485267） | 摆动相**最大/最小足净空**可由摆动相开始时的髋/膝/踝角度、角速度、角加速度预测，RMSE **2.3–4.0 mm** | ⇒ `LIFT` 的净空验收可以做成"**由关节状态预测净空**"，与 §18 的回读网关天然配套 |
| **Chen 等**（2021，摆动足轨迹） | 摆动腿轨迹应**最小化速度与加速度** | ⇒ 轨迹评价指标应是 jerk / 速度峰值，不是"跟得像" |
| **Park 等**（2021，脑卒中步长不对称） | 减小步长不对称会**损害**动态平衡 | ⇒ 落点指令（§14 的 `footTarget`）必须带**对称性**约束，不能只管单侧 |

### 17.2 起步（gait initiation）也要按文献

- Hess 等 1999：起步先**重心后移**到支撑腿，再蹬出 ⇒ 与 §3.1 的 `LOAD` 语义一致，
  且说明**第一个 `LOAD` 的承接目标就是后脚**（不是"因为起始腿是 l"）。

## 18. ★ 关节回读权限：**状态机是唯一网关**（用户 2026-10-06 定调）

> 「我想把唯一的各个关节回读权限给状态机，**两套系统都从状态机做查询**。」

### 18.1 为什么这条值得做成硬约束

本项目栽过的同一类错误，已经第四次出现：**同一个量被两处用不同口径读**：

| 坑 | 表现 |
|---|---|
| 轴索引错位 | 侧向通道一直写在 `axis 1`（扭转）而不是 `axis 0`（外展）⇒ 力矩差 10 倍 |
| 符号相反 | 髋与膝的屈伸符号约定相反，照抄即翻转 |
| 量纲错 | 把"目标角比例"当"力矩"传；腰阻尼项量纲不平衡单独饱和 |
| 单位混用 | deg（Perry 表）与 rad（`rs.angle`）混用 ⇒ 阈值形同虚设 |

⇒ **回读口径必须只有一个出处**。而"验收用的量"与"控制用的量"如果来自不同代码路径，
就会出现**验收说合格、控制却在往外推**这种无法归因的局面。

### 18.2 规格

```ts
// src/core/jointQuery.ts（新增）：**只读**网关，唯一持有 q / q̇ 的对外接口
export interface JointQuery {
  readonly state: WalkState;
  readonly verified: boolean;
  readonly safe: boolean;
  readonly violations: readonly StateViolation[];

  /** 关节角（deg）。轴口径唯一真源：0=绕X(外展) 1=绕Y(扭转) 2=绕Z(屈伸) */
  angleDeg(joint: JointName | number, axis: 0 | 1 | 2): number;
  /** 关节角速度（deg/s） */
  velDegPerSec(joint: JointName | number, axis: 0 | 1 | 2): number;

  /** 本状态对该腿/轴的帧域区间（deg，只读常量表的拷贝视图） */
  band(leg: 'support' | 'swing' | 'trunk', axis: DomainAxis): StateDomain;
  /** 帧域验收结果（越界多少） */
  inDomain(leg: 'support' | 'swing' | 'trunk', axis: DomainAxis):
    { ok: boolean; errDeg: number; tolDeg: number };

  supportLeg(): Side;
  swingLeg(): Side;
  trunkPitchDeg(): number;   // 与 `rs.pitchDeg` 同源，但只读
  trunkRollDeg(): number;
}
```

**所有权规则（三条，可断言）**：

| 规则 | 内容 |
|---|---|
| R1 唯一读者 | `rs.pos` / `rs.vel` 只允许 **物理写入 → `gaitState`/`jointQuery` 读取**。`balance.ts` / `step.ts` **禁止**直接访问 |
| R2 只读 | 网关**没有任何 setter**，也没有 `request*` 通道 ⇒ 状态机"纯判据"性质不被破坏（与 §3.8、`probe-pure-sm` 一致） |
| R3 第二条通道 | **物理量**（`loadFrac`、`readCoP`、`soleBlockLoad`、`com`、`dcm`）仍由 `rigState` 持有 —— 它由物理写、不由控制器写；两个系统只读。这也是唯一的第二条读通道 |

**接线**：`Controller` 先建 `GaitState`，再把 `gaitState.query` 注入
`stepSystem` / `balanceSystem`（参数或字段），两者**不再**拿到 `rs.pos/vel` 的访问权。

**收益（每一条都对应一个已发生的坑）**：
① 轴索引、符号、单位只有一处定义；② **验收用的量就是控制用的量**（同一个网关）；
③ 可在网关里统一做滤波/去抖（现在各系统各自读、各自滤波）；
④ 门禁可以静态断言"两个系统不碰 `pos`/`vel`"。

### 18.3 门禁

| 探针 | 断言 |
|---|---|
| `probe-readback` | **静态**：`balance.ts` / `step.ts` 里 `\.pos\[` `\.vel\[` `\.angle\(` `jointVel\(` `jointPos\(` 出现 **0** 次；**运行时**：网关返回的 `angleDeg` 与物理值逐拍一致（防"网关自己算错"） |
| `probe-pure-sm` | 网关与状态机里**零**关节需求接口（既有门禁，扩展到 `jointQuery.ts`） |

### 18.4 实施顺序（接在 §14.8 的 C 序列前，作为 R0）

| 阶段 | 内容 | 完成判据 |
|---|---|---|
| **R0** | 新增 `jointQuery.ts`，两个系统**同时**读网关与旧路径，**逐拍比对相等** | 比对全绿（证明网关是恒等映射） |
| **R1** | 两个系统切换到只读网关；删掉直读 | `probe-readback` 静态绿 |
| **R2** | `rs.pos/vel` 收窄为内部可见；补运行时一致性检查 | `probe-readback` 运行时段绿 |

⚠ **R0 必须先做**：直接切换会在网关有任何口径差异时**静默改变控制行为**
（这正是本项目最怕的失败模式）。先证明恒等，再切。

## 19. ★★★ 逐状态判定标准与两个系统分工（**以人类运动文献为第一依据**）

> **用户偏好（2026-10-06 定调，长期有效）**：
> 「我的偏好是查**有关人类运动**的文献，尽量别查机器人相关的，
> **游戏角色关节应该更接近真人**。」
>
> ⇒ 本项目的判据**第一依据是人类步态分析**；机器人文献（SCONE / OSL / EPFL / Lim 2004）
> **降级为交叉验证**，只用在人类文献没覆盖的地方。
> 代码对应物：`HUMAN_REF`（人类参考值）、`VERIFY`（判据）、
> `STATE_ROLES`（分工）、`THRESHOLDS`（阈值出处）。

### 19.1 人类文献怎么说：**相位由关节角签名定义，不是由载荷分数定义**

**Perry & Burnfield《Gait Analysis》**（Rancho Los Amigos 八相位）与
**Winter《Biomechanics of Walking》** 都按**关节角/角速度**划分相位。
八相位归为三项任务：**WeightAcceptance → SingleLimbSupport → LimbAdvancement**。

| 相位 | %GC | 任务 | 角度签名（成人正常值） |
|---|---|---|---|
| Initial Contact | 0–2 | WA | 踝 ≈3° 跖屈；膝 0–5° 屈；髋 30° 屈 |
| Loading Response | 2–10 | WA | **足底着平**：踝跖屈 ~10° 后反向；**膝屈到 20°**；胫骨垂直 |
| Mid Stance | 10–31 | SLS | 踝由 5° 跖屈渐背屈，**末达 +10° 背屈（全支撑期最大）= 提踵** |
| Terminal Stance | 31–50 | SLS | 踝由 +10° 背屈反向至 **5° 跖屈**；Perry：**全周期最强推进力** |
| Pre-Swing | 50–62 | SLS | **踝跖屈 20°；膝屈 35°**；离地 |
| Initial Swing | 62–73 | SLA | 膝快速屈向峰值 |
| Mid Swing | 73–87 | SLA | **膝屈峰值 60°**；髋 15–25° 屈 |
| Terminal Swing | 87–100 | SLA | **膝伸到 0–5°；踝背屈 10–15°** 准备脚跟着地 |

**这一条推翻了我们原来的判据骨架。** 我们原来用「载荷分数」（`loadFrac ≥ 0.6`）
当 `LOAD` 的主判据 —— 那是 SCONE/机器人的口径，而且我们自己的接触模型载荷读数
还不自洽（`grounded=00` 却 `loadFrac≈0.5`）。现在改成：

| 我们的态 | Perry 相位 | **主判据（角度签名）** | 辅助判据 |
|---|---|---|---|
|---|---|---|---|
| `DOUBLE` | 初始/终末双支撑 | 双脚接地（Perry 明确：**双支撑并非等分重量**） | 轻腿载荷、帧域、倾角、MoS |
| `LOAD` | `LoadingResponse` | 承接踝**跖屈 ≥6°**（足底着平 10°×0.6）、承接膝**屈 ≥12°**（吸振 20°×0.6） | 承接腿载荷、后脚未离地、矢状位置、手性、节奏、帧域、倾角 |
| `PUSH` | **`MidStance`（被动拱架）** | 后脚踝**背屈进行中**（朝 +10° 峰值走）；单支撑已建立 | 承重腿在位、承重帧域、倾角 |
| `THRUST` | **`TerminalStance`+`PreSwing`** | 后脚踝**背屈达峰 ≥10°**（提踵）、随后**跖屈 ≥3°**（回到蹬离位） | 矢状位置、承重腿在位、承重帧域、倾角 |
| `LIFT` | `PreSwing`→`InitialSwing` | 摆动踝**跖屈 ≥12°**（离地 20°×0.6）、摆动膝**屈 ≥21°**（35°×0.6） | 已卸载、已离地、净空 ≥5cm、承重在位、膝屈曲、帧域、MoS |
| `SWING` | `InitialSwing`→`TerminalSwing` | 摆动膝**屈 ≥36°**（峰值 60°×0.6）、摆动踝**背屈 ≥7°**（落地准备 12°×0.6） | 落地事件、落地矢状、膝角速度、承重帧域 |

**六态的环**：`DOUBLE → LOAD → PUSH → THRUST → LIFT → SWING → DOUBLE`。
拆出 `THRUST` 的理由见 §19.3 —— 人类把终末支撑分成 `TerminalStance`（提踵→反向跖屈，
**全周期最强推进力**）与 `PreSwing`（卸载、膝屈 35°、踝跖屈 20°）两个相位。

> ⚠ **「被动拱架」落在哪里（自我纠正，2026-10-06）**：
> 拱架（`MidStance`，GRF 过踝、肌肉几乎不加载）是**新支撑腿**的中段支撑，
> 发生在**旧腿离地之后** ⇒ 在我们环里是 **`LIFT` + `SWING`** 那一段，
> **不是** `PUSH`。`PUSH` 里两条腿都还着地。
> 所以"平衡系统在拱架期该少做"这条要求落在 `STATE_ROLES.LIFT` / `.SWING`，
> 而"主动蹬离"落在 `STATE_ROLES.THRUST`。

**`×0.6` 的取法**：Perry 给的是**完整步态周期**的签名值，我们只在单一相位内采样，
所以取 60% 作为"至少走到这一步"的门槛。**这是工程取值，不是文献值** —— 标定后要回填。

角度一律读**帧域**（`+` 屈 / 踝 `+` 跖屈），符号由 `jointQuery.degOf` 唯一换算
（实测依据见 `probe-readback`）。

### 19.2 人类步态的结构事实：**推离与交接是重叠的**（⚠ 对我们环序的挑战）

动态行走（倒立摆）文献给出的实测事实：

- **单支撑期** CoM 沿倒立摆弧运动；**双支撑期不是摆动**，它是「步态到步态过渡」
  （step-to-step transition），作用是**把 CoM 速度从一条弧重定向到下一条弧**。
- **人类蹬离的正功开始于对侧脚跟着地之前**，结束于离地；
  **碰撞负功始于脚跟着地、结束于对侧离地之后**
  （Adamczyk/Delaney/Donelan 等，PMC2726857）。
  实测：按速度方向定义的重定向时长 `τvel` ≈ 步幅的 **27%**，
  而双支撑 `τDS` 只有 **14%** ⇒ **过渡区间明显长于双支撑**。
- 步长越长、步宽越大，重定向代价越高（做功率 ∝ 步长⁴ / 步宽²）。

**⇒ 对我们固定环的挑战**：我们的环把「交接」当**一次性事件**，
必须在 `PUSH` 之前完成；而人类是**蹬离与交接重叠**（正功始于对侧 IC 之前）。

**这里要分清两个不同的问题**：

1. **「被动拱架 vs 主动蹬离」必须分开** —— ✅ **已解决（2026-10-06，方案 B）**。
   拆出 `THRUST` 态，见 §19.3。这与交接是否重叠无关。
2. **「蹬离与交接在时间上重叠」** —— ❌ **仍未解决**。
   人类蹬离正功始于对侧脚跟着地**之前**；我们要求交接完成后才进 `PUSH`。
   彻底对齐需要把「交接」从**事件**改成**连续量**（权限迁移进度 `0→1`），
   那样 `LOAD` 与 `THRUST` 就不再互斥 —— 与"严格互斥固定环"的核心约束冲突。
   **暂按互斥处理**，记为已知偏差，等两个系统重做后用实测决定是否放开。

### 19.3 人类步态的"冲击—拱架—冲击"（Usherwood 2012, J R Soc Interface 9:2396）

这是"两个系统每态显式做不同的事"的**人类版本**，比机器人文献直接：

| 支撑期阶段 | 力学事件 | 人类肌肉做什么 | 对应我们的系统 |
|---|---|---|---|
| **极早支撑** | 足跟受载，踝**跖屈**，力臂在踝前 | **小腿肌（胫前）离心** → **耗散冲击** | 平衡系统：踝限"吸振"，不做推进 |
| **中期拱架（vault）** | 足底平，GRF **过踝**，力臂 ≈0 | **被动**，几乎不加载肌肉 | 平衡系统：倒立摆 passively 过去，只控额状 |
| **极晚支撑** | 足在踝**前方**受载 → 力臂产生 | **小腿肌（腓肠肌/比目鱼）向心** → **蹬离做功** | 平衡系统：踝产生蹬离力矩 + CoP 前移 |

Perry 的肌肉分期（OANDP 教材版）同向：
早支撑 = 髋膝伸肌**离心** + 踝背屈肌**离心**控制跖屈力矩；
中期 = 小腿肌**离心**允许胫骨前进、髋外展肌维持骨盆稳定；
晚支撑 = 小腿肌**向心**（峰值）、趾屈肌最活跃；
摆动早期 = 胫前/趾长伸肌/腓骨第三肌快速收缩抬脚；
终末摆动 = 髋伸肌与股四头肌开始激活，为落地做准备。

**⇒ 这张表就是"方案 B 拆态"的直接依据**：`MidStance`（被动）与
`TerminalStance`（主动）在**肌肉激活与力臂上完全不同**，而我们原来一个 `PUSH`
把两者装了 ⇒ 平衡系统不知道此刻该"少做"还是"多做"。拆成 `PUSH`（拱架）+`THRUST`（蹬离）后，
两态的判据与两个系统的职责都能分开写（见 `STATE_ROLES.PUSH` / `.THRUST`）。

**⇒ 落进架构的两条**：

1. **平衡系统在中期应该"少做"。** 倒立摆在单支撑中段**天然省力**，
   此时踝只该做**稳定**（Perry：「小腿肌提供渐进背屈让胫骨前进」），
   不该主动推进 —— 推进留到极晚支撑。
2. **蹬离只在极晚支撑发生，且靠"足在踝前方受载"这个几何条件。**
   ⇒ 我们的 `PUSH` 判据必须包含**踝的角度**（提踵 → 跖屈），
   不能只判矢状位置 —— 几何条件才是产生力臂的原因。

### 19.4 人类比例尺（Q1 站距的直接依据）

### 20.1 人类文献依据（四条，全部来自人，不来自机器人）

**① 踝策略 = CoP 策略，髋策略 = CoM 策略**（Morasso 2020，见 Frontiers Comput Neurosci 2022;10:956932 / PMC9713939）
- **踝策略**：身体作为单段倒立摆绕踝旋转，用踝力矩**直接调控 CoP 位置**，
  让 CoP 去"预判" CoM 投影的晃动。
- **髋策略**：踝**不向地面传主动力矩**，所以调不了 CoP；只能靠**上半身局部 CoM
  前后摆**来带动全局 CoM ⇒ 间接控制。
- **默认策略是踝策略**；只有在支撑面太窄/太软导致 CoP 可行范围太小时才退到髋策略。
- **踝策略比髋策略更鲁棒**（间歇控制增益的可变范围更大）。

**② A/P 归踝、M/L 归髋；CoP 散点 = 两条独立控制线叠加**
（Winter 1996, *J Neurophysiol* 75(6):2334 — 并步/串联/45° 三种站姿的统一理论）
- **并步（side-by-side）站姿**：
  - **前后向（A/P）平衡完全由踝机制（跖屈/背屈肌）控制**；
  - **内外侧向（M/L）平衡由髋机制（外展/内收肌）控制**。
- 空间图上：两脚 CoP 的连线 = **load/unload 线**（由髋机制控制，负责把重量在两脚间搬运）；
  与它**垂直**的方向 = **踝控制线**（由踝肌控制，负责前后倾）。
- "随机"的 CoP 散点图，其实就是**这两张各自规则的图的时空叠加**。
- **站距变窄 ⇒ 踝作用下降、髋作用上升**（A/P 方向尤其明显；Gatev 1999、Winter 1996 一致）。

**③ 脚掌是内置测力台，CoP 估计的第一来源就在脚上**
（Wright et al. 2012；Morasso 2020 转述）
- 脚掌有**双重感觉运动功能**：机械上它是**柔性的**（能感受微小形变）、摩擦系数合适，
  保证力/力矩能可靠传给地面；感觉上它是**接触力分布的敏感装置** ——
  等于一块**内置测力台**，给中枢提供 CoP 的在线估计。
- ⇒ **"平衡链路从脚步开始算"不是设计偏好，是文献结论**：
  CoP 不是"算出来的目标"，而是"脚底测出来的结果"。

**④ 平衡不只是反馈，还有前馈**（Gatev 1999, *Exp Neurol*）
- 安静站立时腓肠肌活动与 CoG/CoP 的前后向运动**正相关且有相位超前**
  ⇒ 踝肌在**预测** CoP/CoM 将怎么动，据此建立"刚好够用的最小踝刚度"。
- 提示：我们不该等倾角已经大了才出力，应按**状态机的相位**前馈给出踝刚度。

**⑤ 肌肉分工**（Proske 等，PMC2697307）
- **比目鱼肌（soleus）是安静站立的主激动肌**（71~81% 的时间是激动角色）。
- 腓肠肌个体差异大；胫前肌主要不是激动肌，而是**最好的本体感觉源**
  （未调制肌肉的肌梭信息最干净），并通过**交互抑制**作用于小腿肌。
- ⇒ 对我们的映射：**踝矢状/额状是主执行器**（不是腰），腰只在上层微调。

### 20.2 力链：自下而上六层（"力度与方向"就在 L1~L3）

```
L0  鞋底接触      每脚 7 个 collider（foot 4 + arch 2 + mfoot 1）
                   → 逐块法向 ny、切向 (tx,tz)、接触点坐标
      ▼  ⚠ 当前 footLoadFrac 会在「两脚都没受力」时回退 [0.5,0.5]，且 loaded 会 1/0 跳变
         ⇒ L0 必须先修（见 §20.6）
L1  足底压力分布 → **CoP（每脚）** = Σ(ny·p) / Σny ；合力大小 |F|
      ▸ 这是"力度"的一半：压力大小分布
      ▸ 这是"方向"的源头：CoP 位置决定了后续所有力臂
      ▼
L2  地面反力 GRF  = Σ(所有接触的法向+切向)
      ▸ **大小** |GRF| ≈ 体重（竖向），切向分量为水平分量
      ▸ **方向**  GRF 的方向 ⇔ CoP 必须落在支撑面内（否则力矩无法平衡）
      ▼
L3  踝力矩  τ_ankle = (CoP − 踝中心) × F_vertical          ← **力臂的物理含义**
      ▸ **CoP 不偏离踝心 ⇒ 踝力矩为 0**（Usherwood 2012 的 vault）
      ▸ CoP 前移 ⇒ 跖屈力矩（蹬离 / 前倾）；后移 ⇒ 背屈力矩（吸振 / 后仰）
      ▸ 这就是"调整脚部发力的方向"能改变踝输出的**唯一途径**
      ▼
L4  膝 / 髋       额状：髋外展力矩（M/L 主执行器，Winter 1996）
                   矢状：膝与髋在小腿上叠加大角度（并步站姿下是次要通道）
      ▼
L5  腰参考偏置    最后手段。Perry/Usherwood：**只有前几级都不够时才动腰**
                   （"mid-vault 时肌肉几乎不加载"⇒ 不许在不该动的时候动腰）
```

**关键换算（要写进门禁，不是写在注释里）**：

| 量 | 公式 | 用途 |
|---|---|---|
| 踝矢状力臂 | `arm_sag = copX − ankleX` | 踝跖屈/背屈力矩的来源 |
| 踝额状力臂 | `arm_lat = copZ − ankleZ` | 踝内/外翻力矩的来源 |
| 重力倾覆力矩 | `M_topple = m·g·(comX − copX)`（矢状）<br>`m·g·(comZ − copZ)`（额状） | **站不住就是它压过了踝/髋的可用力矩** |
| 踝需求力矩 | `τ_req = M_topple + m·a·h` | 与 `τmax` 比较，超了就必然倒 |
| 全局 CoP | `cop = Σ n_i · cop_i / Σ n_i` | M/L 平衡的判据 |

### 20.3 状态机拥有的力链分析（用户要求："放在状态机里，供平衡系统使用"）

**为什么归状态机**：CoP/GRF/力臂是**测量层**，只有状态机同时握有
「接触原始量 + 帧域 + 承接/承重角色 + 本态驻留时间」，能把它算成**逐态可用**的量；
而 `balance.ts` 不该、也无法自己重建这套口径（此前栽过：两套口径打架，
UI 与状态机说法不一致）。所以：**状态机算，平衡系统只读**。

```ts
/** 单个鞋底块的接触力（力量"分布"的最小单元） */
export interface SolePatch {
  block: number;        // 块序号 0..6
  ny: number;           // 法向（N）
  tx: number; tz: number;  // 切向（N）
  cx: number; cz: number;  // 接触点世界坐标
}
/** 单脚：CoP + 合力 + 逐块分布 */
export interface FootForce {
  contactN: number;     // 接触块数
  fz: number;           // 竖向合力（N）
  fx: number; fzTan: number;  // 切向合力（N）
  copX: number; copZ: number;  // ★ 该脚 CoP（世界坐标，m）
  copValid: boolean;    // ★ 合力太小 ⇒ CoP 不可信（噪声被放大）
  patches: SolePatch[]; // 逐块分布（柔性足 §15 要用）
}
/** Winter 1996 的两条控制线 */
export interface ControlLines {
  /** load/unload 线：两脚 CoP 的连线（髋机制：搬运重量） */
  luX0: number; luZ0: number; luX1: number; luZ1: number;
  /** 踝控制线：与 load/unload 线垂直（踝机制：前后倾） */
  ankleNx: number; ankleNz: number;
}
/** ★ 状态机每拍发布的力链快照 */
export interface ForceChain {
  l: FootForce; r: FootForce;
  /** 全局 CoP（两脚按 n 加权）—— M/L 平衡的总判据 */
  copX: number; copZ: number; copValid: boolean;
  /** 全局地面反力：大小与方向（用户要的"力度和方向"） */
  grfX: number; grfY: number; grfZ: number;
  grfAngleDeg: number;   // GRF 相对竖直方向的倾角（"方向"的可读形式）
  lines: ControlLines;
  /** 相对承重脚的踝力臂（踝力矩的唯一来源） */
  armSag: number; armLat: number;
  /** 重力倾覆力矩（N·m，矢状/额状） */
  toppleSag: number; toppleLat: number;
  /** 踝需求力矩与余量（负 = 必然倒） */
  tauReqSag: number; tauMarginSag: number;
  tauReqLat: number; tauMarginLat: number;
  /** 逐态可信度：L0 不可信时为 false（见 §20.6） */
  trustable: boolean;
  /** 不可信的原因（人话，给 UI） */
  trustNote: string;
}
```

**消费规则（写进门禁）**：
- `balance.ts` / `step.ts` **只准读 `rs.forceChain`**，不得自己读接触/CoP。
- 与关节角一样，违反 ⇒ `probe:readback` 静态门禁报错。
- UI 显示的力链数字全部来自 `telemetry.force`（已格式化字符串），不二次换算。

### 20.4 逐态的平衡需求（用户："不同状态下都需要调整"）

状态机给每态一个**目标**（不是增益表），平衡系统去追：

| 态 | 平衡系统的任务 | 主要执行器 | 目标量（`STATE_BALANCE_TARGET`） |
|---|---|---|---|
| `DOUBLE` | 双脚均匀承重，**CoP 在双脚之间** | 髋额状 + 踝矢状 | `loadFrac → 0.5/0.5`；`comZ → 双脚 CoP 中点` |
| **`LOAD`** | ⚠ **搬重量归迈步系统**（§5 职责再划分）。平衡系统的任务：**两脚都维持接触** + 朝下一态阈值收敛 | 全身修正建议（不限于承重腿） | 硬：`tauMargin ≥ 0`（承重腿）；软：逼近 `VERIFY[NEXT_STATE]` 各项。摆动腿位置由**迈步系统**保持（§5 ③′） |
| `PUSH` | 单腿**被动**拱架，踝只维持稳定 | 踝矢状（小幅）+ 髋额状 | `tauReqSag` 绝对值小；**不追求推进** |
| `THRUST` | **主动蹬离**：踝跖屈 + CoP 前移到前脚掌 | 踝矢状 | `copX` 前移至 `> ankleX + armMax`；`tauReqSag` 在跖屈方向 |
| `LIFT` | 单腿硬支撑，全部额状权限集中 recv | 髋额状 + 中足 CoP | `|comZ − copZ| ≤ latTol`；`tauMarginLat ≥ 0` |
| `SWING` | 单腿支撑 + **重心开始后移**铺路 | 髋额状 + 踝矢状 | `loadFrac[recv]` 开始下降；`copZ` 向 nextRecv 预移 |

**A/P 与 M/L 分工（Winter 1996，本文最重要的一条工程结论）**：
- **矢状（A/P）主执行器 = 踝**，能力 = `armSag = copX − ankleX`。
  ⇒ 想改前后向平衡，**必须先把 CoP 移到踝心前方/后方**；只拧腰没用。
- **额状（M/L）主执行器 = 髋**（外展/内收），能力 = `armLat` 经髋力臂放大。
- ⇒ 我们之前的错误结构是"腰当主执行器"。腰应该是 **L5 最后手段**。

### 20.5 第一步：`LOAD` 站住的验收（用户："首先先保证重心转移的状态下能站住"）

**必须同时成立**（缺一即不算站住）：

| # | 条件 | 判据 | 为什么 |
|---|---|---|---|
| A1 | 搬运真的发生 | `loadFrac[recv]` 从 0.5 单调升到 ≥0.65 | 否则"站住"只是没动 |
| A2 | **没倒** | `max|τ_req_sag| ≤ τmax_sag` **且** `max|τ_req_lat| ≤ τmax_lat` | 关节余量，不是倾角 |
| A3 | CoP 可用 | 每拍 `copValid`，且 `|copX − ankleX| ≤ 0.8·(足长/2)` | CoP 跑出脚外 ⇒ 力矩无从产生 |
| A4 | 力链自洽 | `Σ n_i·cop_i / Σn_i` 与实测 Σ 冲量一致（残差 < 5%） | 防"CoP 是算出来的假数" |

**A2/A5 失败**（躯干倾角 20°→75° 单调发散，1.22s 摔），
A3/A4 尚无法判定（力链分析还没实现）。
⇒ 这就是下一步要做的事，**不是**继续调 `LOAD` 的验收阈值。

### 21.2 状态机（完整设计）

**职责三项**（就这三项，多一项都不要）：
① **显式决定角色**：任一时刻恰好一条**承重腿**、一条**摆动腿**；
② **判定能否迁移**：本态验收项**全部**满足（经 §3.7-B 调理层）才进下一态；
③ **发布力链与遥测**：`rs.groundChain`（脚→GRP→力臂→τ 余量）、
   `telemetry.sigs/ring/legPlan/force` —— 这是"为什么卡住"的唯一答案。

**环**（六态，闭合）：

```
DOUBLE ──► LOAD ──► PUSH ──► THRUST ──► LIFT ──► SWING ──┐
   ▲                                                        │
   └────────────────────────────────────────────────────────┘
```

**角色规则**（**事件驱动 + 显式**，不含任何测量推断）：

1. 初始化一次：`roleSup = cfg.startBearer`，`roleSw` = 另一条；
2. **交换点固定**在「摆动腿落地」：`lastSwing` 成为新 `roleSup`，旧 `roleSup` 变新 `roleSw`；
3. 由 `lastSwing` 的变化触发 ⇒ 一个周期至多交换一次；
4. **「前腿/后腿」只是位置描述，不是角色**，不参与判据/锁定/谁摆动。

**逐态表**（这是状态机的完整规格）：

| 态 | 承重腿 | 摆动腿 | 摆动腿自由度 | 主判据（角度签名，域口径） | 本态想让身体变成什么 |
|---|---|---|---|---|---|
| `DOUBLE` | `roleSup` | `roleSw` | **按住**（不许动） | 双脚接地 + 轻腿仍有载荷 + 帧域 + 倾角 + MoS | 静态双支撑，准备交接 |
| `LOAD` | `roleSup`（承接） | `roleSw` | **按住**（交接完成前不许动） | 承接踝跖屈 ≥6° + 承接膝屈 ≥12° + 承接腿已触地 | 重量真正落到 `roleSup` |
| `PUSH` | `roleSup` | `roleSw` | 解锁·**留地** | 后脚踝进入背屈（≤5°）+ 背屈推进中（踝角速度） | 提踵，建立踝力臂 |
| `THRUST` | `roleSup` | `roleSw` | 解锁·**留地** | 已提踵 + 反向跖屈 ≥12° + 后脚膝屈 ≥21° + 踝已转跖屈向 | 卸载，蹬离 |
| `LIFT` | `roleSup` | `roleSw` | **自由**（唯一允许离地） | 摆动腿已卸载 + 已离地 + 净空 ≥5cm + 摆动膝屈 | 单支撑成立 |
| `SWING` | `roleSup` | `roleSw` | **自由**（触地即锁） | 摆动膝屈峰值 + 落地踝背屈 + 落地事件 | 摆动→落地→交换角色 |

**★★★ 状态机的闭环与时序（用户 2026-10-06 定调；这是"周期性"的正式定义）**

> 用户原话：
> 「状态机要**显式说明谁是承重腿、谁是摆动腿、谁锁定**」
> 「这个要**真的是周期性的**」
> 「状态机还要**对姿态验收**，验收过才进下一个状态，**公布新的承重腿摆动腿**什么的；
>  否则就**迈步系统和平衡系统不断修正，进入阈值以内**」
> 「验收**姿态和关节数据**啥的」

**一拍内的时序（唯一执行顺序，不许换序）**：

```
① 状态机【公布】本态的运行契约：
     · 角色：承重腿 = roleSup，摆动腿 = roleSw（**显式，每拍都发布**）
     · 锁定：STATE_LEGS[rs.state] 给出两条腿各自的自由度
     · 目标：本态的姿态要求 = 帧域区间（STATE_DOMAINS）+ 角度签名（VERIFY 的判据）
   ↓
② 迈步系统 + 平衡系统【按契约不断修正】：
     · 迈步：搬重量 + 控制摆动腿（按住/预摆/抬/摆/落）
     · 平衡：控承重腿维持不倒；对"搬得太过"有否决/限幅权
     · 两者的任务就是**把姿态推进到判据的阈值以内**
   ↓
③ 状态机【验收】（每拍）：
     · 数据 = **关节角（经网关）+ 接触 + 载荷（力链）+ 裕度**
     · 全部判据满足（经 §3.7-B 调理层）⇒ `verified = true`
   ↓
④ 验收过 + 最短驻留到 ⇒ 【公布下一态与新角色】：
     · `rs.state = NEXT_STATE[rs.state]`
     · 角色在「摆动腿落地」处交换（旧摆动腿 → 新承重腿）
     · 若验收不过 ⇒ **留在本态**，②继续修正（这就是"否则就不断修正"）
   ↓
⑤ 回到 ①（**这就是"周期性"**：六个态走完一圈 = 一个迈步周期；角色恰好交换一次）
```

**由这条时序推出的四条硬要求**（缺一条，闭环就断）：

| # | 要求 | 代码现状 |
|---|---|---|
| 1 | **角色每拍显式发布**（不是让两个系统去推断） | ✅ `telemetry.roleSup/roleSw` + `legPlan` |
| 2 | **验收对象是姿态与关节数据**（帧域 + 签名 + 力链），不是时间 | ✅ `VERIFY` + `STATE_DOMAINS`（但见下方缺口） |
| 3 | **验收不过就留在本态**，让两系统继续修正 | ✅ 迁移条件 = `verified && dwellOk` |
| 4 | **周期是真的**：走完一圈、角色交替、下一圈照旧 | ⚠ **未验证**（从未走完一个周期；0 cycles） |

**当前断点（按依赖排序）**：

1. **迈步系统在 `DOUBLE`/`LOAD` 缺"按住摆动腿"** ⇒ 摆动腿漂起 ⇒ `后脚未离地` 失败
   ⇒ 闭环在 ② 就断了（系统没能把姿态推进到阈值以内）。**这是第一优先。**
2. **平衡系统不读 `rs.state`** ⇒ 它不知道"本态的契约"是什么 ⇒ ② 的"按契约修正"只剩一半。
3. **两个判据退化成恒真**（`手性交替`、`承接腿已触地`）⇒ ③ 的验收在这一项上是**假的通过**。
4. `PUSH` 之后四个态**从未被真实数据检验** ⇒ ④ 的"公布新角色"只走过一次（DOUBLE→LOAD）。

**★ `locked` / 「按住」的语义边界（用户 2026-10-06 强调）**

> 用户原话：「**DOUBLE 是俩腿都不动，但是不妨碍重心转移和脚部承重腿的发力啊**。」

`locked`（以及 `STATE_LEGS` 里的一切「锁定」）**只锁一件事：该腿的「迈步/摆动」运动**
——即**它的落点位置不得被移动**（不许被 step 抬起、前移、后撤）。

它**不锁**下面两件事，而且这两件事在 `DOUBLE` 下**必须照常发生**：

| 照常进行的 | 谁做 | 怎么实现（不靠腿的摆动） |
|---|---|---|
| **重心转移** | **迈步系统** | 靠**躯干/髋/踝的整体调整**把 CoM 推过去，而不是靠摆动腿迈步 |
| **承重腿的发力** | **平衡系统** | 踝力矩（跖屈/背屈）、髋外展（侧向发力）、中足 CoP 微调 |

**⇒ 两个后果，写进实现约束**：

1. **`locked` 不得被实现成「冻结该腿的执行器」或「停止对该腿出力」。**
   锁定的是**位置目标**，不是**力矩/增益**。
   （实测教训：曾把「承重腿也锁」误当成「两条腿的伺服都停」，整机 GRF 从 687N 掉到 58N。）
2. **`DOUBLE` 不是一个「什么都不做」的状态。** 它是：
   - 位置层面：两腿都不许迈（`locked`）
   - 力学层面：**重心可以（也常常需要）移动**，**承重腿持续发力**
   ⇒ 状态机在 `DOUBLE` 的判据（`双脚接地` + 轻腿仍有载荷 + 帧域 + 倾角 + MoS）
     正是在检查「重心移动有没有把身体带出可行域」，而**不是**「身体有没有完全静止」。

**判定调理层**（§3.7-B，自研，**优先级高于判据表**）：角色锁存 / 门槛必须 >3σ /
保持才认 / 尖峰不可推进 / 转移类用 Δ / 载荷项恢复阻塞 / 不可判要说不可判。

### 21.3 迈步系统（完整设计）

**职责两条**：① **搬重量（重心转移）**；② **控制摆动腿的位置**。

> 用户：「**搬重量是迈步系统做的**」「迈步的腿……平衡系统就不要强制要求着地」。

**逐态行为**：

| 态 | 搬重量 | 摆动腿 |
|---|---|---|
| `DOUBLE` | **不是「不动」**（§21.2 语义边界）：按状态机的角色把 CoG 往 `roleSup` 的支撑面收；**承重腿持续发力** | **按住**：摆动腿锁在当前落点（不许漂、不许抬）；但**重心转移照常** |
| `LOAD` | **开始搬**：把 CoM 的投影从 `roleSw` 一侧推向 `roleSup` 的支撑面（额状 + 矢状），
直到 `VERIFY[LOAD]` 的接承项满足 | **继续按住**（这是它能不能被抬的前提） |
| `PUSH` | 搬重量收尾（CoM 已基本在 `roleSup` 上） | 解锁：允许**脚跟抬起的预摆**（踝背屈），**不离地** |
| `THRUST` | 不再搬（重量已交完） | 后脚继续跖屈、膝屈，**仍不离地** |
| `LIFT` | 不搬（单支撑已成立） | **抬起**：髋/膝追最小跃度轨迹，踝做净空保持 |
| `SWING` | 不搬 | **摆动→落地**：踝由背屈转跖屈准备触地、膝伸展减速、落点修正 |

**输出**：`requestSwingLegAngle(...)`（只对摆动腿）+ 搬运意图（`shiftDemand*`）。
**禁止**：写承重腿任何轴；在非 `LIFT`/`SWING` 抬摆动腿。

**当前缺口（实测）**：`DOUBLE`/`LOAD` 缺"按住"机制 ⇒ 摆动腿漂起 ⇒ `双脚接地 1/2`。
**这是要修的第一件事。**

### 21.4 平衡系统（完整设计）

> **用户 2026-10-06 第二次纠正（本条优先）**：
> 「**逼近下一态也是迈步系统干的**，平衡系统只是**尽可能在不偏离**的情况下去调整平衡；
> 比如不碰摆动腿（摆动腿归迈步系统）。
> 但平衡系统**有权力修正**：**重心转移不得太过了**。」

**职责三条（修正版）**：

① **硬目标：不倒。** 在**不偏离迈步系统计划**的前提下，
   把 CoM 控在支撑面内、保持 `τ` 余量、让**承重腿**按本态要求接触。

② **执行对象只有承重腿** —— 侧向发力、踝、CoP（§15）。
   **不碰摆动腿**（那是迈步系统的）。

③ **对"重心转移"有否决 / 限幅权**（这是平衡系统唯一的"权力"）：
   迈步系统搬得**太过**时——CoM 越出可用支撑域、`τ` 余量转负、CoP 出脚——
   平衡系统**可以削减或否决这一次搬运**，
   但**不得改变搬运的目标本身**（不能自己给自己定一个新目标）。

**⇒ "逼近下一态阈值"不是平衡系统的任务。**
早前把它写成平衡系统的"软目标"是**归属错误**，已删除。
正确的分工是：

| 谁 | 决定什么 |
|---|---|
| **迈步系统** | 目标、搬运计划、摆动腿轨迹、**逼近下一态** |
| **平衡系统** | 该计划下的**稳定性**；对**过头的动作**有**否决/限幅权**；不偏离计划 |

这就是一个**参考调节 / 安全滤波**结构：
**迈步系统提出计划 → 平衡系统只在计划"会失稳"时削减它，从不重新规划。**

**逐态作用**（用户：「平衡系统在不同阶段下作用不一样」）：

| 态 | 平衡在做什么 | 主要执行器 |
|---|---|---|
| `DOUBLE` | 稳住 `roleSup`；为即将到来的交接**准备可行域**（不主动搬） | 承重腿踝 + 髋额状 |
| `LOAD` | **两脚都在地时维持不倒**；对迈步系统的搬运**限幅/否决**（不得太过） | 承重腿踝/髋 |
| `PUSH` | **少做**（被动拱架：GRF 过踝、力臂≈0） | 承重腿踝维持稳定 |
| `THRUST` | 承重腿踝跖屈产力矩、CoP 前移到前脚掌 | 承重腿踝 |
| `LIFT` | **单腿平衡全权**：侧向发力把 CoM 控在承重脚支撑面内 | 承重腿髋外展 + 中足 CoP |
| `SWING` | 单腿平衡；对落地前的过冲**限幅** | 同上 |

**输入**：`rs.state`、`roleSup`/`roleSw`、`rs.groundChain`（**只用它读载荷/CoP，不许自读接触**）、
迈步系统的搬运需求（`shiftDemand*`）。
**禁止**：搬重量、定目标、逼近阈值、按摆动腿、自己推断角色。

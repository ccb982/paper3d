## 0. 一句话架构

```
┌──────────────────────────────────────────┐
                 │ 状态机 gaitState（唯一相位真源）          │
                 │  显式 5 态：DOUBLE/LOAD/PUSH/LIFT/SWING│
                 │  每拍只做两件事：                       │
                 │   ① 指定角色 support / swing            │
                 │   ② 验收：姿态是否符合**本状态**         │
                 │  ✔ **不发任何关节目标**（一条都不发）    │
                 └───────────┬──────────────────────┬───────┘
        状态 → 常量帧域表     │                      │  角色 + 验收结论 + 越界清单
        （按状态名自取，只读）  │                      │
                             ▼                      ▼
        ┌────────────────────────────┐   ┌──────────────────────────────┐
        │ 迈步系统 stepSystem         │   │ 平衡系统 balanceSystem       │
        │ 写：摆动腿（位置）           │   │ 写：承重腿（位置 + 力矩）      │
        │ 写：腰（位置，受 ±6° 限幅）  │   │ 写：中足（额状 CoP）           │
        │ ＋躯干反相旋转               │   │ **不写**摆动腿、**不写**腰    │
        │                            │   │ 只通过「参考通道」影响腰        │
        └────────────┬───────────────┘   └──────────────┬───────────────┘
                     │                                  │
                     └──────────► RigState ◄────────────┘
                            单一仲裁点：每根轴**恰好一个写者**
                                     │
                                     ▼
                              ragdoll 18 关节 × 3 轴
```

**协作不是靠优先级抢同一根轴，而是靠「角色分区」**：
状态机每拍指定哪条腿是 `support`、哪条是 `swing`，
迈步系统只碰 `swing` + 腰，平衡系统只碰 `support` + 中足。
⇒ **同一根轴永远只有一个写者**，「谁覆盖谁」这个问题在结构上不存在。

> 平衡系统可以增强承重脚的发力并且让承重脚侧向发力来维持稳定啊。」

## 1. 三个模块的职责（判据 / 构造 / 修正）

| 模块 | 语义 | 每拍写什么 | **不写**什么 | 判据 |
|---|---|---|---|---|
| `gaitState` | **判据**：现在算不算「处在某个状态该有的姿态里」 | 状态标签（5 态显式）、角色（support/swing）、验收结论 `verified`、`violations[]`、驻留计时 | **任何关节目标 / 任何增益 / 任何 QP**；**一条关节指令都不发** | 状态 → 常量帧域表（Perry 区间）+ 接触 + 载荷 + 裕度 |
| `stepSystem` | **构造**：把**摆动腿与腰**推进该状态的帧域区间 | 摆动腿 `hip/1,2`、`knee/2`、`foot/2` 的位置；腰 `spine1/0,2` 的位置（±6° 限幅）；躯干反相旋转 | 承重腿任何轴、任何力矩 | 状态机的角色指派 + 锁定闸门 |
| `balanceSystem` | **修正**：让**全身**每帧都落在帧域内并保持稳定 | 承重腿的位置与力矩（踝矢状、膝伸展、髋矢状、**髋外展/内收**）；中足额状 CoP；**参考通道**里的躯干偏置 | 摆动腿任何轴、腰的**执行器** | `keyGuard`（帧域守卫）+ CoP 余量 + 稳定性裕度 |

**「状态机不发目标」是可以断言的**：状态 → 帧域是**一张常量表**，
两个系统按**状态名自己去查**（`STATE_DOMAINS[rs.state]`），
状态机本身只输出「现在处于哪个状态」和「验收过没过」。

⚠ 好处不只是干净：一旦状态机每拍下发目标，它就会隐含"谁的目标更对"的
仲裁问题；常量表 + 只读查表让**目标归属**回到两个系统自己手里，
而状态机只负责「说真话」。

### 1.1 为什么腰归迈步系统、平衡仍然能「控制体态」

用户要求「平衡系统每帧做全身修正」，但腰只有一根、只能有一个写者。
本架构的解法：**平衡系统不碰腰的电机，它碰腰的参考**。

- 迈步系统写 `spine1/0,2` 的**位置目标**（来自关键帧 + 平衡给的偏置）。
- 平衡系统每帧写 `rs.postureBias = { pitch, lat }`（一个**姿态参考偏置**，
  单位 rad，受 `waistSlotMax = 6°` 限幅）。
- 腰的实际目标 = `lerpKeyPose(key) + postureBias`。

这正是 Menga & Ghirardi（2017, *Robotics*）的双层结构：**外环改内环的参考角，
而不是覆盖内环的输出**。腰因此既被迈步系统驱动（关键帧），
又被平衡系统每帧修正（体态），而**始终只有一个写者**。

⚠ 这条边界必须由门禁强制，否则会退回「两个系统抢腰」的老问题（见 §9 `probe-coop`）。

## 2. 坐标系、判据与测量口径（不可协商的三条）

| 项 | 约定 | 依据 |
|---|---|---|
| 坐标 | `x` = 矢状（前后），`y` = 竖直，`z` = 额状（左右）；**`+z` = 左** | `skeleton.ts` |
| 关节轴 | 索引 `0` = 绕 X = **外展/侧摆**（髋），`1` = 绕 Y = 扭转，`2` = 绕 Z = 屈伸 | `skeleton.ts` + `HIP_ABD_AXIS = 0` |
| 符号 | 本 rig 髋/膝限位**负 = 屈**；脊柱正 = 躯干前倾；踝正 = 跖屈 | 实测标定 |
| **跌倒** | **唯一标准 = 头部触地**（`doll.headHitGround()`）。自碰撞关闭，头不可能碰到自己 | `sim.checkFall()` |
| 载荷 | `footLoadFrac(side)` / `footGrip(side)`：遍历**全部**鞋底碰撞块；`readCoP` 是压力中心 | `ragdoll.ts` |
| 时间 | `ticksDone` 单位是**控制拍 @120Hz**（`physicsHz=240`）；控制器 dt = 1/120 | `sim.ts` |

**站距**是这套架构的隐藏前提：Perry 规范步宽 **70~80mm**、髋间距 **280mm**；
本 rig 目前 `soleZ ≈ ±163mm`（**327mm**，4.4 倍）⇒ 所需重心横移从人类的
≈40mm 变成 **142mm**。

⚠ 旧门限 `handoverTolZ = 50mm`（人类尺度）**已随迁移判据一起退役**
（P2：判据换成「足相对身体的矢状位置」+ 载荷阈值，见 §3.5/§12）。
但站距问题本身没有消失：**每个周期仍要把重心移动 142mm**，
而 `hip/0` 的 τmax = 70 N·m 对应「重心相对髋的横向偏移 ≤ 102mm」
⇒ **单靠髋外展搬不完这 142mm**，必须靠 `LOAD` 相的两脚载荷互换补齐。

⇒ 设计决定（见 Q1）：站距由 `NORMATIVE_BIILIAC / NORMATIVE_STEP_WIDTH`
**推导**，不再写死 `±163mm`。这是把问题变成可解的第一步。

## 3. 状态机：显式 5 态，**验收过了就进下一个**

> 用户 2026-10-06 定调：
> 「状态机不需要每拍给目标。显式标明这几个状态，验收过了进下一个状态就行了。」

⇒ 状态机的全部职责是三件事：**指角色、说状态、判验收**。
它**不下发任何目标**；每个状态该有的姿态写在**常量表** `STATE_DOMAINS` 里，
两个系统按状态名**自己查**（只读）。

### 3.1 固定环形：一个迈步周期 = 走完这一圈

> 用户 2026-10-06 修正：「**迈步前需要先让重量转移到后脚啊**」
> —— 抬腿的**前提**是另一条腿已经承重。所以环里必须有一步
> 「**重量交接**」，它排在抬腿之前，而不是和抬腿同时。

```
   ┌──────────┐ 验收①  ┌──────────┐ 验收②  ┌──────────┐ 验收③  ┌──────────┐ 验收④  ┌──────────┐
   │  DOUBLE  │───────► │   LOAD   │───────► │   PUSH   │───────► │   LIFT   │───────► │  SWING   │
   │ 双脚支撑  │        │ 重量交接  │        │ 蹬离     │        │ 摆动腿离地│        │ 摆动→落地 │
   └──────────┘        └──────────┘        └──────────┘        └──────────┘        └──────────┘
         ▲                                                                       验收⑤：落地 + 锁定
         └──────────────────────────────────────────────────────────────────────────────┘
```

**唯一的硬前提（不变式）**：任一时刻**至多一条腿承重、另一条腿 unloaded**。
⇒ 「重量交接」必须是环上的**独立一步**，且排在抬腿之前。

**方向逐周期自动交替**：迈步时哪条腿承重，就往哪条腿交重量。
- 从静止起走、或需要后退再起步时，交接目标就是**后脚**
  （gait initiation：重心先后移到后腿再蹬出，Hess et al. 1999）。
- 稳态行走时：落地后承重的正好是**上一条摆动腿**（此刻它成了后脚），
  下一周期要抬另一条腿 ⇒ 交接目标自然轮到**前脚**。
⇒ 因此这个状态**不能按方向命名**，只能按角色命名：`LOAD` = 「交给承重腿」。

### 3.2 五个状态（显式，逐个写全）

| # | 状态 | 支撑数 | 承重腿（support） | 摆动腿 | Perry 对应 | 该状态存在的意义 | 迈步系统 | 平衡系统 |
|---|---|---|---|---|---|---|---|---|
| 1 | **`DOUBLE`** | 2 | 载荷大的一条 | —（双脚都在地上） | `MSt` | 建立/恢复稳定的双脚站立 | 不动 | `hold`；双脚载荷均衡 |
| 2 | **`LOAD`** | 2 | **正在吃重量的那条**（交接目标） | 未解锁 | `LR`→`MSt` | **把重量交出去** —— 抬腿的资格前提 | 不动（摆动腿不许动） | **`shift`**：承重腿改变 GRF 方向 + 两脚载荷互换 |
| 3 | **`PUSH`** | 2→1 | 同上（开始蹬离） | 未解锁 | `TSt`→`PSw` | 蹬离，制造向前/向上的反力 | 摆动腿预屈膝准备（仍可留地） | 承重腿踝跖屈 → 膝伸展 → 髋伸展 |
| 4 | **`LIFT`** | 1 | 同上 | **离地**（唯一允许离地的动作） | `ISw` | 建立单支撑 | **抬摆动腿**（离地净空 ≥ MFC 5cm）+ 初始屈膝 | `hold`：踝矢状 + 髋外展托住重心 |
| 5 | **`SWING`** | 1→2 | 同上 | 摆到底 → **落地锁定** | `MSw`→`TSw` | 走完摆动、落地、交接准备 | 摆动腿 `MSw→TSw`、落地、**触地即锁** | 持续 `hold`；落地瞬间准备接管 |

顺序 `DOUBLE → LOAD → PUSH → LIFT → SWING → DOUBLE` 是**唯一真源**
（`PHASE_ORDER`）；与 Perry 8 相的映射 `PHASE_TO_GAIT` 在 `keyframe.ts`。
两处都不许散落字面量。

**与现有代码的对照**（迁移时按这张表改名，不改语义）：

| 现用名 | 新名 | 说明 |
|---|---|---|
| `DOUBLE` | `DOUBLE` | 不变 |
| `SHIFT` | **`LOAD`** | 语义就是「重量交接」，只是名字没说清 |
| `SINGLE` | **`LIFT` + `SWING` 的前半** | 现在的 `SINGLE` 把「抬腿」和「稳住」混在一个态里 |
| `PUSH` | `PUSH` | 不变 |
| `STEP` | **`SWING` 的后半** | 落地 + 锁定 |

### 3.3 每个状态的「验收项」= 该状态该有的姿态 + 该状态的前置条件

验收是**逐项布尔**的，每一项都必须能单独回读（`rs.violations[]` 给出
「哪一项、差多少」）：

| 状态 | 姿态验收（帧域，常量表） | 前置条件验收 |
|---|---|---|
| `DOUBLE` | 双脚 `grounded`；承重髋 ∈ [−10°, 5°]、承重膝 ∈ [0°, 10°]、承重踝 ∈ [−8°, +2°]；躯干 pitch ∈ [−3°, +3°] | 两脚载荷都在 [0.25, 0.75]（不是一条腿吃满）；`\|tiltDeg\|` ≤ 8° |
| **`LOAD`** | 双脚 `grounded`；**被卸载腿的姿态不许塌**（仍在其 `DOUBLE` 区间内） | `loadFrac[承接腿] ≥ 0.60`；`com` 水平投影落在**承接腿足底范围**内（`\|Δx\| ≤ tolX`、`\|Δz\| ≤ tolZ`）；重心搬运趋势正确（`d(loadFrac)/dt ≥ 0`） |
| `PUSH` | 承重踝 ∈ [−5°, +5°]（跖屈峰）、承重膝 ∈ [0°, 5°]、承重髋 ∈ [−20°, 0°] | 矢向推进意图 > 0；`CoP` 离前缘余量 > 0（否则蹬不出去）；摆动腿载荷已降到 ≤ 0.1 |
| `LIFT` | 前脚 `grounded`、摆动腿**离地**；承重膝 ∈ [0°, 10°]、承重踝 ∈ [−8°, +2°]、承重髋 ∈ [−10°, +5°] | 离地净空 ≥ MFC 5cm；**摆动腿载荷 ≤ 阈值**（SCONE：`leg_load < swing_load_threshold`；OSL：0.15 BW）；承重腿 ≥ 0.60；`\|tiltDeg\|` ≤ 10°；`mos` ≥ 预算 |
| `SWING` | 摆动腿过 `MSw→TSw` 帧域（膝 30°→3°、髋 30°→25°）；承重腿仍在 `LIFT` 区间 | **落地事件**（SCONE：`sagittal_pos > landing_threshold`，即足相对身体的矢状位置越过阈值；EPFL：同侧触地）；**落地即锁定**；距上次抬脚 ≥ 1.0s（节奏下限） |

**验收通过 ⇒ 立刻进下一个状态**。就这样，没有别的推进条件。

推进逻辑就这么几行（`gaitState.update()` 的全部职责）：

```ts
// 每拍：① 评估本态 → ② 过了就进下一态 → ③ 写角色 + 结论
const ok = verify(rs.state);            // 逐项布尔，结果进 rs.violations[]
rs.verified = ok;
if (ok && dwellOk(rs.state)) rs.state = NEXT[rs.state];   // 固定环 NEXT 表
rs.support = roleOf(rs.state);          // 由状态 + 载荷/几何决定，不自由发挥
rs.swing   = other(rs.support);
// ④ 若硬项越界持续超时 → rs.safe = true（**模式标志，不是第六个状态**）
```

⇒ 「固定几个状态」+ 「验收过了自动进下一个」= **一个环形 FSM**，
没有相位积分、没有权重调度、没有"该不该走"的自由裁量。

### 3.4 文献里的步态状态机长什么样（三个独立实现 + 一个安全态设计）

用户 2026-10-06：「找找论文」⇒ 下面是**四个可查的实现**，全部是
「**阈值验收 → 自动进下一个**」，没有一个用计时器推进相位。

| 实现 | 状态 | 迁移判据（全部是阈值） |
|---|---|---|
| **SCONE** `GaitStateController`（开源仿真框架） | **5 个**：`Landing / EarlyStance / LateStance / LiftOff / Swing` | ① 足载阈值（以体重为单位）② **相对腿长的矢状足位置**阈值（`landing/late_stance/liftoff_threshold`）③ 对侧腿载荷 |
| **EPFL** 神经肌肉假体反射调制（infoscience） | **5 个/腿**：`ES / MS / PS / IS / LP` | 对侧足事件（**对侧趾离**=单支撑起点、**对侧触地**=双支撑起点）+ 同侧触地/趾离；`LP` 用**屈伸角速度 < −1°/s**；足载阈值 **10 N** |
| **opensourceleg (OSL)** 外骨骼 | 4 个 + `Init`：`e_stance / l_stance / e_swing / l_swing` | 足载阈值（**0.25 / 0.15 / 0.40 BW**）+ **膝角阈值**与**膝角速度阈值**（`knee>50° ∧ knee_vel<3`）；**最短驻留 0.20s** |
| **Vughuma & Verlinden 2022**（*EECSS*，踝足矫形器） | 4 个 + `Init` + **每个正常态派生安全态** | 足底 heel/foreoot 两传感器 4 种组合（`11/01/00/10`）；每个安全态带 **`Tmax`** |

**四条可直接抄进本设计的共识**：

1. 迁移判据只用 **接触/载荷阈值 + 关节角阈值（可含角速度阈值）+ 几何位置阈值**
   —— **没有任何一个实现用计时器推进相位**。
2. **最短驻留是防抖参数**（OSL `min_time_in_state = 0.20s`），**不是推进条件**。
3. 每个正常态都要派生**安全态**，并带 `Tmax` 时间上限（Vughuma 的明确要求）。
4. 状态之间的**角色交接用「对侧足事件」触发**（对侧趾离 / 对侧触地），
   而不是自己那条腿的时间。

⚠ **一条重要的否定证据**：这四个实现**没有一个**把「重心是否在支撑脚正上方」
（`comOverFoot`）当迁移判据 —— 它们用的是**足相对身体的矢状位置** + **足底载荷**。
⇒ 本设计原方案里的 `comOverFootZ` 既不符合文献、又在实测中永不收敛
（`soleZ` 自己会动，实测 243mm）⇒ **退役它是有文献依据的，不是调参**。

**周期级 ↔ 腿级的对照**（文献的 FSM 是**每条腿**一个，本设计是**每周期**一个）：

| 本设计（周期级） | SCONE（腿级） | EPFL（腿级） |
|---|---|---|
| `DOUBLE` 双脚稳定 | 两个腿分别处于 `Landing` 与 `LateStance/LiftOff` | `ES/PS` 的重叠 |
| `LOAD` 重量交接 | `EarlyStance`（承重腿开始吃重） | `MS`（由**对侧趾离**触发） |
| `PUSH` 蹬离 | `LateStance` | `PS` |
| `LIFT` 摆动腿离地 | `LiftOff` | `IS`（由**对侧触地**触发） |
| `SWING` 摆动→落地 | `Swing`→`Landing` | `LP`→`ES` |

⇒ 两条设计判据被文献直接支持：**「重量交接」是一个独立状态**（= `EarlyStance`/
`MS`，由对侧事件触发），**「抬腿」只有在承重腿卸载到阈值以下之后才允许**
（= `LiftOff` 的判据就是 `leg_load < swing_load_threshold`）。

### 3.5 ★ 现有代码状态机的逐条审计（对不对？）

用户 2026-10-06：「参照论文，我现在的状态机的状态和验收标准都对吗」
⇒ 逐条判 **`对` / `错` / `缺`**，判据只用上面 §3.4 的四篇。

**A. 状态集**

| 现有状态 | 判定 | 依据 |
|---|---|---|
| `DOUBLE` | **对** | 双支撑必须独立成态（EPFL：单支撑起点 = **对侧趾离**；SCONE：两腿状态部分重叠） |
| `SHIFT` | **对，但名不副实** | 语义就是重量交接 = SCONE `EarlyStance` / EPFL `MS`；只是名字没说清 |
| `SINGLE` | **错** | 名义「单支撑」，实测**抬起量为 0**（`step.ts:222` 的 `hold` 不含 `SINGLE`）⇒ 它其实是「等待区」，而真正的单支撑在 `STEP` 里 |
| `PUSH` | **错** | 判据 `stepPermit.all && both` 要求**双脚仍接地** ⇒ 它其实是「抬腿前的等待区」，没有任何推进动作（只发 `shiftDemandF`，那是额侧向力） |
| `STEP` | **缺一半** | 它把「抬腿 + 单支撑 + 摆动 + 落地」四件事挤在一起 ⇒ 违反 Perry 的 `ISw/MSw/TSw` 三段，也没法对「离地净空」单独验收 |

⇒ 修法（就是 v2 的环）：**`SINGLE` → `LIFT`**（离地单独成态，负责"抬起"与净空验收）；
**`PUSH` 保留但要给它真实内容**（`TSt→PSw` 的蹬离：踝跖屈 → 膝伸 → 髋伸），
判据从「双脚接地」改成「**后脚矢状位置越过 `sagLiftOffThr`**」（SCONE `LateStance→LiftOff`）；
`SHIFT` 改名 `LOAD` 并明确它是「重量交接 = 抬腿的资格前提」。
⇒ 环：`DOUBLE → LOAD → PUSH → LIFT → SWING`。

**B. 验收判据**

| 现有判据 | 判定 | 依据 |
|---|---|---|
| `X1` 前脚接地 | **对** | 全部四篇都用接触 |
| `X5` `loadFrac ≥ 0.45/0.60` | **对** | OSL 用 0.25/0.40 BW；SCONE 用体重归一阈值 |
| `X7` MoS、`X8` 倾角 | **缺但合理** | 四篇都没有（它们的设备测不到）；本 rig 有这个量 ⇒ 属于**加强**，不是错 |
| `X2/X3` `comOverFootX/Z ≤ tol` | **错** | **四篇没有一处用重心位置做迁移判据**；它们用「足相对身体的矢状位置」（SCONE `sagittal_pos`）与足载。且实测永不收敛（243mm，`soleZ` 自己会动） |
| `X4` 驻留 0.30s | **对**（定位为防抖） | OSL `min_time_in_state = 0.20s` |
| `X6` 间隔 ≥ 1.0s | **对**（节奏，不是资格） | 与四篇的 `Tmax`/最短驻留同类，但**不能**用它推进状态 |
| `SINGLE → PUSH`：`phaseT ≥ 0.5s` | **错** | **纯计时器推进**，四篇一致地不用；EPFL 明确批评两态 FSM「捕捉不到子相位内的反射通路」 |
| `PUSH → STEP`：`stepPermit.all && both` | **错** | 迁移判据里混入**行为条件**；且 `both`（双脚接地）与「即将单支撑」自相矛盾 |
| 摆动腿姿态验收 | **缺** | OSL 用 `knee > 50° ∧ knee_vel < 3`；EPFL 用 `LP` 的**角速度 < −1°/s**；本 rig 一项都没有 |
| 落地验收 | **对但太弱** | 现在只判 `touchdown[swing]`（接触事件），缺 SCONE 的 `sagittal_pos > landing_threshold`（足已到身体前方）与落地**姿态**验收 |
| 落地即锁（不预锁） | **对** | 与用户 2026-10-03 定调一致 |
| 超时回退 | **对** | Vughuma 的 `Tmax`；EPFL 亦用 0.05 s 离地容差 |
| 安全态 `SAFE` | **缺** | Vughuma：**每个**正常态都要派生安全态，本 rig 一个都没有 |

**C. 状态之外的两个结构问题（论文里没有对应物 ⇒ 是本项目自己的坑）**

1. **锁定方向反了**：现有实现是「交接开始时锁**前**脚（承重腿）、解锁后脚」。
   而四条共识都是「承重腿由**载荷**决定」（SCONE/MS 由对侧趾离触发、
   OSL 用足载阈值）。⇒ 承重腿**不应该被锁**。
2. **手性没有规定**：SCONE/EPFL 是**每条腿**一个 FSM，落到环上就**自动保证左右交替**；
   本 rig 是**周期级** FSM，必须显式写一条手性不变式，否则「一直用同一条腿摆动」
   在结构上是允许的。

**结论**：状态**集**基本对（缺 `LIFT`、两个等待态要合并），判据**一半对一半错**
（错的全集中在 `comOverFoot*` 与两处计时器推进），另外缺安全态与摆动腿姿态验收。
逐条修法见 §10 的实现状态（P1/P2 已做，P3 部分）。

### 3.6 帧域是**常量表**，不是每拍下发的目标

`keyframe.ts` 现在给的是**点**（`KeyPose`）。Perry / Oberg 的规范值本身
就是**区间**（中支撑膝 男 15–24°/女 12–20°；摆动膝峰 65–68°；
髋总程随步速变化 ⇒ 必须按相位取，不能用常数）
⇒ **帧域是区间**，控制律必须是「往区间里推」而不是「追一个点」。

```ts
// src/core/keyframe.ts（新增，常量；**只读**，状态机不写它）
interface StateDomain {                 // 一项 = 一个关节/轴在某个状态的可接受区间
  state: 'DOUBLE' | 'LOAD' | 'PUSH' | 'LIFT' | 'SWING';
  leg: 'support' | 'swing' | 'trunk';
  axis: 'hipFlex' | 'hipAbd' | 'kneeFlex' | 'ankle' | 'trunkPitch' | 'trunkLat';
  lo: number; hi: number;               // deg，闭区间
  tolIn: number; tolOut: number;        // 进入严、保持松（两段式迟滞）
  hard: boolean;                        // 越界是否算异常
}
const STATE_DOMAINS: readonly StateDomain[];   // 唯一真源
```

Perry 8 相的规范值（供 `STATE_DOMAINS` 取值，**deg**）：

| 关键帧 | GC% | 支撑髋 | 支撑膝 | 支撑踝 | 摆动髋 | 摆动膝 | 主动肌 |
|---|---|---|---|---|---|---|---|
| IC | 0–2 | 25° | 0–5° | 0° | 25° | 0–5° | 踝跖屈肌（制动） |
| LR | 2–12 | 25° | **15–20°** | 10–15°跖 | 24° | 18° | 股四头（离心） |
| **MSt** | **12–31** | **0°** | **5°** | **5°背屈** | 15° | 40° | **臀中肌 + 阔筋膜张肌** |
| TSt | 31–50 | 0–20°伸 | 0–5° | 10°背屈 | 5° | 45° | 腓肠肌-比目鱼肌 |
| PSw | 50–62 | 0° | **40°** | 20°跖屈 | 2° | 20° | 腘绳肌 + 内收肌 |
| ISw | 62–75 | −5° | 5° | −5° | 20° | **60°(峰)** | 髂腰肌 + 股直肌 |
| MSw | 75–87 | 0° | 3° | 0° | **30°** | 30° | （被动钟摆） |
| TSw | 87–100 | 0° | 3° | −2° | 25° | 3° | 腓肠肌-比目鱼肌 |

Perry 原文（关键）：
「Body weight passes over supporting foot」；「Only in the mid point of the stance
period does body alignment approximate that of a stable quiet-standing posture」
⇒ **`MSt` 就是「平衡态」的可写定义**（旧 `架构设计.md` 附录 A.1 的结论保留）。

### 3.7 四条防抖 / 兜底规则（**都不是**推进条件）

1. **最短驻留**：验收通过后仍需在本状态停留 ≥ `minDwellSec` 才允许迁移。
   初值**统一 0.20s**（OSL `min_time_in_state`），后续可按状态给表
   （`LOAD` 需要更长：交接是要时间的）。作用是**防抖**，不是"时间到了就走"
   —— 没有它，接触噪声会让状态在两个都验收通过的状态之间逐帧跳。
2. **迟滞**：进入用 `tolIn`（严），保持/回退用 `tolOut = 2·tolIn`（松）——
   Rezazadeh et al.（2018, *J Biomech Eng*）的 FSM 就是两段式
   （`q > q₄₁` 进 S2、`q < q₄₃` 回 S1）。
3. **`Tmax` 超时兜底**：本状态停留 > `tmaxSec`（初值 2.0s）⇒ 回 `DOUBLE`
   （Vughuma 的时间上限，防卡死；**不是**推进方式）。
4. **安全态 `rs.safe`（模式标志，不是第六个状态）**：任一 `hard` 项越界持续
   > `graceSec`（初值 0.5s）⇒ 置 `rs.safe = true`：
   **迈步系统立即停手，平衡系统全权接管**。
   它**不改变 `rs.state`**（否则固定环就不固定了），只让"该降级了"这件事
   有一个单一真源。
   （Vughuma & Verlinden 2022, *EECSS* 的 FSM 明确要求安全状态处理非预期转移。）

### 3.8 状态机**不做**的事

- **不发任何关节目标**（一次都不发）——可由门禁静态断言（§9）。
- 不决定增益、不解 QP、不写 `keyDomain` 之类"下发物"。
- 不用「会被自己推着走的量」做验收：现实现用 `comOverFootZ`，
  而 `soleZ`（支撑脚中心）本身随姿态移动 ⇒ 实测 `comOverFootZ = 243mm`
  且永不收敛 ⇒ 状态机卡死 `DOUBLE`（实测 20 拍全 `DOUBLE`、`authority ≡ 0`）。
  ⇒ **验收只用：帧域（关节角）、接触、载荷、裕度。**

## 4. 迈步系统：目标是一个**区间**

迈步系统**按当前状态自己查常量表**（状态机不下发目标）：
`STATE_DOMAINS[rs.state]` 取出 `swing` 那一组区间。
但**目标是区间**，所以每根轴的命令是「当前值 → 区间」的方向与幅度：

```ts
// 新增：src/core/keyframe.ts
function towardDomain(q: number, lo: number, hi: number, step: number): number
// q < lo  ⇒ 往 lo 推，但不超过 lo+step（不越界冲过头）
// q > hi  ⇒ 往 hi 推，但不低于 hi-step
// 否则    ⇒ 保持（不发指令，这就是「在帧域内 ⇒ 不干预」）
```

- 足净空：摆动相膝屈峰 60~68°（Perry / Oberg），最小离地净空 MFC = 5cm。
- 摆动轨迹两端速度为零（`sin(πs)` 钟形）。
- 躯干反相旋转 6°（Takemura 2007；骨盆横断面旋转，Mann 1975）——
  注意这是**代偿**，不是平衡机构（见第 6 节）。
- 落地即锁、不预锁（用户 2026-10-03 定调，保留）。

## 5. 平衡系统：增强承重脚 + 承重脚侧向发力

这是本架构的**核心机制**（用户 2026-10-06 定义），分三条子任务。

### 5.1 竖向/矢状：增强承重脚的发力

| 通道 | 机制 | 文献 | 作用轴 |
|---|---|---|---|
| `ankleCop` | 踝跖屈肌**刚度伺服**：`τ_a = K_a·q_vip + C_a·q_vip'`，`Ke ≈ 850 N·m/rad` | Winter 1998 *J Neurophysiol* 80:1211；Loram & Lakie 2002 | 承重 `foot/2` |
| `hipStiff` | 髋侧**被动刚度**（欠临界踝的兜底）：`τ_h = K_h·q + B_h·q'` | Morasso 2019/2022（DIP）；Horak & Nashner 1986 | 承重 `hip/2` |
| `stanceExt` | 支撑膝**主动刚度**（不是追一个屈曲目标） | Li & Levine 2010（站立时膝角近似恒定）；J Ab 2021 承重侧 GMED +58% | 承重 `knee/2` |

**硬约束（写进设计余量）**：竖向地面反力**不由关节力矩「造」**。
法向力是接触的量（`f_y` 来自物理解算），关节力矩只负责**力矩平衡**
（把压力中心搬到该在的位置）。
⇒ 附录 C.7 的教训必须保留：`Στᵢ(axisᵢ×rᵢ) = F_des` 这类**只含水平两行**的等式
不能承担体重；一旦把 `f_y = m·g` 塞进关节力矩的等式里，就会与位置伺服的
支撑力矩**双计**（实测 0.25s 内 CoM 从 0.962 掉到 0.866）。

### 5.2 额状：**三层**（粗调 / 精调 / 交接），不是一条律

> 完整机制与文献见 **§14 柔性足与侧向发力**。这里给控制侧的分层。

| 层 | 子任务 | 目标 | 执行器 | 何时开 | 判据 |
|---|---|---|---|---|---|
| **① 粗调（主力）** | `hold` | 重心停在支撑脚正上方（**不产生位移**） | 承重 `hip/0` 外展刚度伺服：`τ = a·m·(ω₀²(z_ref−z) + 2ζω₀(−ż))`，`ω₀=√(g/h)` | 单支撑全程 | τ ≤ 70 N·m；死区 8 N·m |
| **① 粗调（主力）** | `shift` | 重心**横移**到下一支撑脚（`Δz ≈ 40mm` 人类尺度） | 承重 `hip/0` 内收/外展改变 GRF **方向**（van Mierlo 2022/2024：CMP 可以合法出支撑面） | `LOAD` 相 | 压力中心余量 ×2 + τmax（下） |
| **② 精调（快速）** | `copTrim` | **只搬 CoP 的横向位置**，不造 net 力 | 中足 `midfoot/0` 旋前/旋后（距下关节）。内翻→CoP 外移、外翻→CoP 内移 | **中支撑期最有效**，蹬离期无效 | 权限随 `contactN` 缩放；夹在 CoP 侧缘余量内 |
| **③ 交接（主力）** | `handover` | 双支撑期**两脚载荷互换** | 力学（`loadAccept`/`loadRelease` 阈值） | `LOAD` 相 | 承接腿载荷 ≥ 0.60、后脚 ≤ 0.15 |
| 附带 | 躯干代偿 | 减小髋外展负荷 | 腰的 `postureBias`（参考通道） | 全程 | ±6° 限幅 |

⚠ **②的窗口限制是文献结论，不是保守设定**：PLOS Comp Biol 2023 实测
「接触点减少后 CoP 位移能力显著下降」，且**内/外翻力矩产生的额状 CoP 变化
大于跖屈力矩、且几乎不产生竖向速度副作用** ⇒ 额向调节应当走中足而不是踝。
⚠ 但人的踝内/外翻肌力矩很小（落地仿真 <10 N·m）⇒ 中足是**精调不是主力**，
主力永远是①。

**为什么承重脚侧向发力就够**（用户的方案在此处有文献支撑）：
人类 40mm 的横向重心转移是**准静态**的，不需要大的横向剪力；
Winter 1998 的机制是**两腿载荷互换**（unload one / load the other），
而不是"用脚推"。支撑髋外展改变的是 **GRF 方向**，CMP 可以合法地跑到
支撑面之外（van Mierlo 2022/2024）。

**三条护栏（任一不过 ⇒ 本拍不做 `shift`）**：

1. 目标脚压力中心**侧缘余量** ≥ `latShiftCopMargin`（把压力推出鞋底就救不回）。
2. 承重脚压力中心**侧缘余量** ≥ 同一门限（横向力先改变载荷分配）。
3. `τ ≤ τmax`（`hip/0` 上限 **70 N·m**；由此得硬约束：
   重心相对该髋的横向偏移 ≤ `70/(m·g) ≈ 102mm`）。
4. ★ **接触点预算**：CoP 权限随 `contactN` 缩小（PLOS 2023）。
   蹬离期接触点减少 ⇒ `shift`/`copTrim` 的权限必须同步收缩，
   否则会把 CoP 顶出支撑面。

⚠ **若 `shift` 在护栏内不可行**，`balanceSystem` 必须
`rs.lateralTask.infeasible = true` **如实上报**，
由状态机决定「延长 `LOAD` 驻留」或「放弃这一步」——
**不允许**硬推到底（实测旧实现把 `com.z` 推到 ±800mm）。

### 5.3 摆动腿的蹬地：**矢状**归平衡，**额状**不做

- 矢状向前的蹬地反力（F_x）在 `PUSH` 相由**承重腿**踝跖屈肌 + 髋伸展提供。
- 额状**不由摆动腿推**（旧实现块⑤ 用摆动腿横向驱动，
  `shiftDemandF` 只看相位、不查消融 ⇒ 曾是「消融工具说谎」第四次复发）。
  本架构把额状搬运交给承重腿 + 载荷再分配（5.2）。

### 5.4 `keyGuard`：平衡如何「尽量不背离关键帧」

| 情形 | 平衡系统的权限 | 数据标志 |
|---|---|---|
| 姿态**在**帧域内 | 只做**微调**（增益 × `keyGuard ∈ [0.15, 1]`） | `rs.verified = true` |
| 姿态**出**帧域（可恢复） | **接管**该轴，`keyGuard = 1`，全力修正 | `rs.verified = false` + `violations[]`（含差多少） |
| 要跌倒（CoP 触边 / MoS < 预算 / 头高快速下降） | **强制接管**，无视帧域（生存优先） | `rs.safe = true`（与状态机的安全态**同一个标志**） |

这三档必须**显式**且**可回读**，不允许靠优先级暗中覆盖。
⚠ 安全态是**模式标志、不是第六个状态**：它不破坏固定环（否则环就不固定了），
而是让「迈步停手、平衡全权」这件事有一个单一真源（Vughuma 的安全态语义）。

## 6. 腰：不是平衡机构（已量化的结论）

用户要求「平衡系统能控制体态」，但**腰作为平衡执行器是错的**，依据：

| 文献 | 结论 |
|---|---|
| Winter 1996 *J Neurophysiol* 75:2334 | 静立两个机构**完全分离**：矢状 = 踝跖屈、额状 = 髋外展；**腰在两张表里都不出现** |
| Winter 1998 80:1211 | `Ke ≈ 850 N·m/rad` 在踝跖屈肌；`Ma = R·p_x`；额状靠髋**换载荷** |
| Horak & Nashner 1986 | 踝策略远端→近端传播，躯干最后被动参与 |
| Jeffs / Kiefer / Shirazi-Adl | 安静站立时腰椎肌肉激活极低、接近被动 |

实测（`probe-readout` ⑤）：腰作为全链 QP 的**冗余自由度**时，
0.25s 内被折到限位 **3.2 倍**（`spine1/2` −1.4° → −43.9°，τ 打满 120 N·m）；
把腰移出该 QP 后，三段全部回到限位内（`spine1/0` +55.8° → **−2.04°**，
`spine1/2` −53.8° → **−2.11°**），τ 峰值 **120 → ≤15.5 N·m**。

⇒ 腰的正确角色：**抵抗自重折叠（静态 ~3% MVC）+ 承受躯干反相旋转的代偿
（Mann 1975 是「用躯干卸载髋外展肌」，属减小负荷，不是平衡机构）**。
体态的动态修正走 §1.1 的**参考通道**。

| `requestAngle(j, ax, rad)` | 目标角（归一化 → PD） | step（摆动腿/腰）、balance（承重腿） | **唯一**的角度命令 |
| `requestTorque(j, ax, τ)` | 力矩，先到先得 | balance | 会压制后来者 |
| `addTorque(j, ax, τ)` | 力矩**累加** | balance（QP） | 唯一同时"不被压制且不删他人"的写法 |
| `forceTorque` / `requestHold` / `clearHold` | 顶替 / 让位 | balance | `hold` = 位置环退化为纯阻尼 |
| `requestSwingLegAngle(...)` | 摆动腿角度（带锁定闸门） | step | 锁定腿直接否决 |
| `requestWaistSlot(j, ax, rad)` | 腰的目标角（±6° 限幅） | step | 这是**腰唯一的写入口** |
| `postureBias`（待实现） | 躯干**参考**偏置 | balance 写、step 读 | §1.1 的参考通道 |

底层真正作用到物理的只有两条（`ragdoll.driveMotors`）：
`motorTarget`（角度通道，PD）与 `tauOut`（力矩通道），两者**相加后按 τmax 饱和**。

### 13.3 缺什么（按论文逐条对照）

| 缺的接口 | 论文里的样子 | 为什么本 rig 需要 | 优先级 |
|---|---|---|---|
| **逐轴刚度/阻尼**（`setImpedance(j, k, b)`） | OSL 每相切 `k`/`b`；Menga 的 `Y_des = diag(k_i, b_i)` | 现在承重腿的"帧域 + 刚度"只能靠**位置目标**与**独立 τ 通道**两条路凑，等价性靠标定维持；有了它，「帧域 = 区间、刚度 = 宽度」才能直接对应 | **高** |
| **任务层 GRF / CoP 目标** | Menga：外环算 `CoP_prev`，通过 LQR 出 `CoĠ_ref` 修正**内环参考角**；λ-QP：接触扳手作决策变量 | 现在额状 `shift` 只能给一个 `shiftDemandF`，没有"要求 CoP 到某处"这种接口 | **高** |
| **足位（步长）指令** | 人类 ML 稳定性**主要靠落足**（Hof/Vlutters/van den Bogaart：足位能补偿约 **10×** 于踝策略的扰动，代价是反应慢 ~100ms） | 现在步长由关键帧隐式决定，状态机无法"落远一点/收窄一点" | 中 |
| **关节角速度指令** | EPFL 的 `LP` 用角速度阈值 | 验收能读，但下不了速度命令 | 低 |
| **重力/逆动力学前馈** | Menga 的 2-DOF 前馈；λ-QP 的 `M a + C + g` | 现在竖向靠 PD 顶，`idyn` 缺失 | 中（P6） |
| **真·逆动力学接口** | `M(q)a + C + g = Sᵀτ + JᵀF` | `wholeBodyQp` 只有两行水平等式，结构上做不到（C.7） | 中（P4） |

### 13.4 两个系统怎么用这些接口（分工表）

| 接口 | 迈步系统 | 平衡系统 | 为什么这么分 |
|---|---|---|---|
| 摆动腿角度 | ✅ 唯一写者 | ❌ 绝不写 | 角色分区（§0）⇒ 同轴单写者 |
| 承重腿角度 | ❌ | ✅（= 帧域目标） | 同上 |

## 14. 柔性足：怎么让脚**侧向发力**

用户 2026-10-06：「我还实现了柔性足，想让脚侧向发力应该怎么弄」

### 14.1 先搞清楚"脚侧向发力"在物理上是哪一种力

足底能改变的是**压力中心（CoP）在足内的位置**，不是凭空造出横向力。
净横向地面反力 `F_lat` 满足 `F_lat / F_y = ΔCoP_z / h_coM`（`h_coM` ≈ CoM 高度）：

| 要什么 | 靠什么 | 量级 |
|---|---|---|
| **调 CoP 横向位置**（改变 GRF **方向**） | 中足（距下横关节=subtalar）**内翻/外翻** | 见 14.2 |
| **造净横向力**（真的推） | 承重**髋外展/内收** + 双支撑期**两脚载荷互换** | 髋力臂仅 ~119mm（本 rig 实测），`τmax = 70 N·m` |
| **被动回中** | 柔性足弓的弹性（不是发力，是**支撑**） | 屈曲刚度 |

⇒ **柔性足给的是「可调节的 CoP + 被动支撑 + 缓冲」，不是「横向推进力」。**
这个区分很重要：把足弓刚度当成"侧向力权限"会得到错误结论。

### 14.2 论文怎么说（中足内/外翻是最有效的横向调节手段）

| 文献 | 结论 |
|---|---|
| **Simulation of ankle PF + inversion-eversion exoskeleton torques**（*PLOS Comp Biol* 2023, 19:e1010712） | ① **内翻力矩把 CoP 推向横向（外侧），外翻力矩推向内侧**；② **内/外翻力矩产生的额状 CoP 变化 > 跖屈力矩**，也就是**额向最有效的关节是（距下）横关节，不是踝跖屈**；③ 内/外翻力矩**几乎不产生竖向速度副作用**（跖屈会），所以额向控制可以很"干净"；④ 效果随接触点减少而衰减 ⇒ **中支撑期最有效，蹬离期最弱**；⑤ 人的踝内/外翻肌力矩很小（落地仿真 <10 N·m）⇒ 足内/外翻是**精调**，不是主力 |
| **MacKinnon & Winter**（经 *Front. Aging Neurosci* 综述转引） | 「**距下关节与髋在单支撑期协同控制额状平衡**」；ML 额状平衡最有力地受**足相对躯干的 ML 位置**影响 |
| **Hof / Vlutters / van den Bogaart** | ML 方向**落足（stepping）是主策略**（可补偿约 10× 于踝策略的扰动），踝策略**反应快约 100ms** ⇒ 两者是「粗调 + 快精调」的互补 |
| **Winter 1996/1998** | 额状平衡主力是**髋**（换载荷），踝与足内/外翻肌贡献小 |

### 14.3 落到本 rig 的具体做法（三层，各司其职）

```
第 1 层（粗调，主力）：承重髋 hip/0 内收/外展
   · 目的：把 CoM.z 拉向/推离支撑脚（`hold`）、或改变 GRF 方向（`shift`）
   · 文献：Winter 1998（额状刚度伺服）、Pandy 2010（外展把 CoM 加速**向内** = 承重）
   · 护栏：τ ≤ 70 N·m ⇒ CoM 相对该髋的横向偏移 ≤ 70/(m·g) ≈ 102mm；死区 8 N·m
   · 三条护栏（CoP 侧缘余量 ×2 + τmax）任一不过 ⇒ 本拍不做 shift

第 2 层（精调，快速）：中足 midfoot/0 旋前/旋后（= 距下关节内/外翻）
   · 目的：**只搬 CoP 的横向位置**，不产生大 net 力，但让 GRF 方向变
   · 文献：PLOS 2023（内翻→CoP 外移、外翻→CoP 内移；额向效果 > 跖屈；无竖向副作用）
   · 适用窗口：**中支撑（`SINGLE`/`LOAD` 末）**，蹬离期无效（接触点减少）
   · 量程：本 rig 中足行程有限 ⇒ 只允许 ±几度的**精调**，并且必须夹在压力中心余量内

第 3 层（交接期主力）：双支撑期两脚**载荷互换**
   · 目的：`LOAD` 相把重量从后脚交到前脚 —— 这是**准静态**的，不需要大剪切力
   · 文献：Winter 1998「unloading one limb / loading the other」
   · 与状态机的关系：**这就是 `LOAD` 状态的物理内容**，也是"迈步前先把重量转移到后脚"的实现

（柔性足弓本身：提供**被动回中刚度 + 冲击缓冲**，
 在**支撑末期**按 Kelly et al. 2014 的结论应"变成刚性杠杆"用于蹬地 ——
 也就是说：柔韧在落地/缓冲，蹬地时要锁住。这对控制器的含义是
 **足弓刚度应该随相位切换**（又一个"逐相阻抗"的必要性证据，见 §13.3）。）
```

### 14.4 柔性足带来的两条额外义务（论文要求，控制器必须实现）

| 义务 | 文献 | 控制器含义 |
|---|---|---|
| **接触点数量随相位变化 ⇒ CoP 权限随之变化** | PLOS 2023：接触点减少时 CoP 位移能力显著下降 | `shift` 的**权限预算必须随 `contactN` 缩放**，否则蹬离期会把 CoP 推出支撑面 |
| **柔性/肌肉系统会让响应比理想刚体模型小很多** | PLOS 2023：加入肌肉与软组织特性后，CoM 速度变化**约减半** | 用刚体模型算出来的力矩要**打折**；标定必须在**本 rig 的柔性足**上做，不能照抄文献的关节力矩 |
| 额向 CoP 能力随足型/承重历史变化 | barefoot 足弓更宽、前趾展开、**额状 CoP 位移更大**；旋后型足的外侧 CoP 行程更大（*JAPMA* 2008） | 柔性足的**标定值不是常数**，要在不同时刻/不同载荷下重测 |

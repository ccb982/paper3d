1. 架构全景图（三层结构）
我们将系统拆分为 核心层（Core）、求解器层（Solvers） 和 管理编排层（Manager）。
核心层：负责 GPU 纹理内存管理（Ping-Pong 双缓冲）、分辨率定义、通道映射。
求解器层：纯函数式（或纯无状态类）。每个求解器只做一件事：平流、压力投影、Level Set 重初始化。它们不持有纹理，只接收输入纹理，写入输出纹理。
管理编排层：持有速度场、颜色场等具体实例，按固定顺序调用求解器，并处理外力注入。
2. 核心层设计：FluidGrid 与 Field
设计要点：彻底解耦“数据存储”和“数据含义”。
FluidGrid：持有一个分辨率（如 256x256）和两个 WebGLRenderTarget（双缓冲 A/B）。它只负责提供 swap() 方法和当前/下一个纹理的引用。
Field：是对 FluidGrid 的“视图”包装。它指定了纹理中 R/G/B/A 四个通道各自代表什么物理量。
例如 ColorField：{ R: "Hue", G: "Saturation", B: "Lightness", A: "Alpha" }。
例如 VelocityField：{ R: "VelocityX", G: "VelocityY", B: "Unused", A: "Unused" }。
关键创新（针对你只平流 S/L 的需求）：所有求解器在运行时都必须接受一个 ChannelMask（通道掩码） 参数（例如 vec3(0, 1, 1)），指定哪些通道参与计算。未标记的通道（如 Hue）在平流时直传，不做任何插值。
3. 求解器层设计（三大独立模块）
每个求解器都是一个独立的类，没有内部状态（State），只有配置参数（Params）。
A. 半拉格朗日平流求解器（AdvectionSolver）
职责：输入源场 + 速度场 + 通道掩码 + dt → 输出平流后场。
算法：标准反向追踪 + 双线性插值。
特殊处理（专为你定制）：
反向追踪时，掩码为 0 的通道（如 H）直接返回当前像素值，不参与 texture2D(backUv) 采样。
这样，H 固定在原地，而 S/L 自由流动，完美满足你的需求。
配置项：最大追踪步长限制（Clamp Step），边界模式（Clamp/Repeat/Zero）。
B. NS 方程压力投影求解器（PressureSolver）
职责：输入散度场 → 输出压力场，或输入速度+压力 → 输出无散速度。
算法：标准 Poisson 方程，GPU 迭代（Jacobi 或 PCG）。
专为特效优化：压力迭代次数不追求物理精确，5~10 次即可。多出的迭代只会抹平细节，不利于火球/闪电的尖锐感。
配置项：迭代次数，过松弛因子（可选）。
C. Level Set 界面追踪求解器（LevelSetSolver）
职责：输入 Level Set 场（SDF） + 速度场 → 输出平流后的 SDF。
附加功能：包含窄带重初始化（Reinitialization），保持 SDF 距离场的性质（虽然技能特效不严格需要，但后续做“水/火交界”时极其有用）。
4. 管理编排层：FluidSimulation（新建）
这是唯一持有状态的地方。它包含：
velocity（速度场，2 通道）
color（颜色场，4 通道，存 HSL加透明度）
density（密度/能量场，可选，用于火球亮度）
完整帧迭代流程（一个 Tick）：
注入外力（技能触发点）：向 velocity 添加径向爆炸力、旋转力（龙卷风）、上升浮力（火）。
速度平流：调用 AdvectionSolver.forward(velocity, velocity, mask=R/G, dt)。速度自己平流自己。
涡度限制（Vorticity Confinement）：这一步不放在独立求解器，而是作为管理层的后处理函数。计算速度旋度，增强卷曲细节（这是技能特效“锋利感”的灵魂）。
压力投影：调用 PressureSolver.solve(velocity)，强制速度散度为零（模拟不可压流，让流动看起来有“质量感”）。
颜色/残差平流：调用 AdvectionSolver.forward(color, velocity, mask=G/B, dt)。H 固定，S/L 流动。
边界处理（可选）：将边缘速度强制归零，防止能量泄露。
5. 针对“技能特效”的独有优化设计（加分项）
分辨率隔离：速度场可以跑 128x128（省性能），颜色场跑 256x256（精细）。平流时，颜色场采样速度场时自动做纹理坐标缩放。这就解决了性能与质量的矛盾。
时间步长自适应（Sub-stepping）：特效爆炸时速度极大，单步追踪会飞出去。管理层自动根据最大速度计算子步数（substeps = ceil(maxVel / threshold)），将 dt 拆分为更小的子步循环执行。

2. 平流求解器接口（支持逐通道掩码）
typescript
// 平流配置（每个通道独立开关）
interface AdvectionMask {
  r: boolean;  // true = 参与平流，false = 静止直传
  g: boolean;
  b: boolean;
  a: boolean;
}

class AdvectionSolver {
  // 核心方法：传入掩码，决定哪些通道“流动”，哪些“钉住”
  advect(
    input: THREE.Texture,      // 输入场（RGBA）
    velocity: THREE.Texture,   // 速度场（RG，像素/秒）
    dt: number,
    mask: AdvectionMask        // { r: true, g: false, b: true, a: false }
  ): THREE.Texture;
}
3. GPU 着色器的核心实现（通道混合采样）
这是新架构的灵魂所在。着色器不再是“全通道平流”，而是逐通道选择采样源：

glsl
uniform vec4 uMask; // 对应 r/g/b/a，1.0=流动，0.0=静止

void main() {
    vec2 uv = vUv;
    
    // 1. 反向追踪（如果至少有一个通道需要流动才计算，否则跳过）
    vec2 backUv = uv - (texture2D(uVelocity, uv).rg * uDt / uResolution);
    backUv = clamp(backUv, 0.0, 1.0);
    
    // 2. 采样两个位置的值
    vec4 staticVal = texture2D(uInput, uv);        // 当前像素（静止）
    vec4 flowVal = texture2D(uInput, backUv);      // 回溯像素（流动）
    
    // 3. 按通道混合（掩码选择）
    vec4 output;
    output.r = mix(staticVal.r, flowVal.r, uMask.r);
    output.g = mix(staticVal.g, flowVal.g, uMask.g);
    output.b = mix(staticVal.b, flowVal.b, uMask.b);
    output.a = mix(staticVal.a, flowVal.a, uMask.a);
    
    // 4. 可选：针对色相（H）的特殊环绕保护（如果你把 H 放在 R 通道）
    // 如果 H 流动，插值后做 fmod(output.r, 1.0)
    gl_FragColor = output;
}
注意：mix(static, flow, mask) 在 mask=0 时退化为直传，在 mask=1 时为纯平流。如果你想做“半平流”（如 50% 混合），甚至可以把 mask 设为 0.5，产生拖尾/残影效果——这也是技能特效常用的手法。

1. 核心原则：数据语义与物理通道的强绑定（写入架构文档）
在 FluidSimulation 管理层，定义一个全局语义映射，所有模块（平流、渲染、注入）都必须遵守：

typescript
// 这是你引擎的“宪法”
const COLOR_SPACE_MAPPING = {
  r: 'hue',        // 0.0 ~ 1.0 (循环)
  g: 'saturation', // 0.0 ~ 1.0
  b: 'lightness',  // 0.0 ~ 1.0
  a: 'alpha'       // 0.0 ~ 1.0
} as const;
强制规定：

任何地方禁止在平流、外力注入、压力投影阶段对 HSLA 数据进行 RGB 转换。

唯一的转换点（HSLA → RGB）发生在最终渲染（后处理阶段），即你准备显示或编码为 RGB565 的前一刻。

2. 针对“一字节/二字节通道计算”的纹理格式选型
你提到最终要转为 RGB565（5-6-5，共 16 位）。这意味着最终输出时，R/G/B 各通道的精度需求并不一致（G 最高 6 位）。

但在平流计算阶段，我强烈建议你使用 THREE.UnsignedByteType（即 8-bit 归一化整数，范围 0-255）：

格式	每通道字节数	精度	推荐理由
UnsignedByteType	1 字节	8-bit (256 级)	与 RGB565 的 5/6-bit 完美匹配。平流产生的中间值可以直接映射到最终输出，几乎没有二次量化损失。显存带宽仅为 Float32 的 1/4。
HalfFloatType	2 字节	16-bit 浮点	虽然精度高，但你的最终目标是 5-6-5 bit，用 16-bit 浮点平流是“大材小用”，而且带宽翻倍。
FloatType	4 字节	32-bit 浮点	绝对不要用。技能特效不需要物理级精度，纯粹浪费带宽和性能。
结论：你的纹理应该使用 UnsignedByteType（一字节通道）。如果你未来想尝试更高精度（如渐变过渡更平滑），最多升级到 HalfFloatType（二字节通道），但初始版本用 UnsignedByteType 完全足够。

4. 平流 Shader 的“无色相环陷阱”保护（专门针对 H 通道）
由于 H（色相）是环形的（0.0 和 1.0 是同一个颜色），双线性插值在边界处会产生错误（例如 0.9 和 0.1 插值出 0.5，实际应该是 0.0）。你的旧代码曾通过 normalizeHue 处理，但新架构需要将它内置于平流模块。

解决方案：在 AdvectionSolver 中，如果检测到 logicalChannel === 'hue' 且启用了平流，在采样后强制执行：

glsl
// 只对存储 Hue 的通道做环形修正
float hue = texture2D(uInput, backUv).r;
// 如果采样值因双线性插值出现负值或超 1，用 fmod 包裹
hue = fract(hue + 1.0); // 处理 -0.1 → 0.9
// 如果 Hue 通道被禁用平流（直传），则不需要此修正
这个修正只针对 R 通道（H），不影响 S/L/A（它们是线性空间，直接插值即可）。

5. 最终 RGB565 转换层（后处理 Shader）
你的最终渲染（或导出） Shader 应该这样写：

glsl
uniform sampler2D uDynamicField; // HSLA 场 (RGBA_UnsignedByte)
uniform float uGlobalAlpha;      // 如果有固定透明度需求

varying vec2 vUv;

// 辅助：HSLA → RGBA (标准转换)
vec3 hsl_to_rgb(float h, float s, float l) { /* 标准函数 */ }

void main() {
    vec4 hsla = texture2D(uDynamicField, vUv);
    
    // 如果某些通道被禁用（未启用平流），它们的值可能为 0 或默认值，
    // 此时你可以在 CPU 端或 Uniform 中传入备用的 H/S/L/A 值。
    // 但为了正确性，请确保所有 4 个通道都有值（即使未平流，初始也要赋值）。
    
    vec3 rgb = hsl_to_rgb(hsla.r, hsla.g, hsla.b);
    float alpha = hsla.a;
    
    // 输出标准 RGBA（显示器用），或者你可以在 JS 端读取此纹理后打包为 RGB565。
    gl_FragColor = vec4(rgb, alpha);
}
打包成 RGB565：如果你要在 JavaScript 中生成 Uint16Array，只需读取这个后处理纹理的像素值，然后执行：

javascript
const r5 = Math.round(r * 31);
const g6 = Math.round(g * 63);
const b5 = Math.round(b * 31);
const rgb565 = (r5 << 11) | (g6 << 5) | b5;
6. 更新后的完整架构规格（融入 HSLA 语义）
层级	组件	职责	关于 HSLA 的约束
管理层	FluidSimulation	持有 channelConfig，触发重建	将 config.r/g/b/a 映射到 hue/sat/light/alpha 语义
核心层	FluidGrid	分配物理纹理（UnsignedByteType，动态通道数）	不关心数据含义，只负责搬运
求解器层	AdvectionSolver	动态生成 Shader，执行半拉格朗日平流	强制为 H 通道（物理 R）添加 fract 环形保护
后处理层	RenderShader	将 HSLA 转为 RGBA（显示）或打包为 RGB565	唯一进行 HSLA→RGB 转换的地方
注入层	ForceGenerator	向速度场或颜色场添加外力	修改颜色场时，必须以 HSLA 值注入（例如“提高饱和度”= 修改 G 通道）
总结
物理通道 = RGBA，逻辑语义 = HSLA，这是你引擎的最高法则。

使用 UnsignedByteType（一字节/通道），完美匹配 RGB565 的精度，且带宽极低。

动态通道选择依然生效：选 2 通道就是 2 字节/像素，选 4 通道就是 4 字节/像素。

环形保护只针对 H 通道（R 通道），其他通道正常线性插值。

颜色空间转换严格锁定在最终渲染环节，平流管道内保持纯净的 HSLA 数据搬运。

现在你可以放心开工了！这个设计确保了 “数据在物理通道中以 RGBA 形式存储，在逻辑上以 HSLA 被理解，在最终输出时以 RGB565 被交付” 的完美闭环。




1. 致命的隐式约束：速度场的“单位”必须是“像素/秒”（Pixel/s）
这是当前设计最容易出问题的地方。

你的着色器公式：backUv = uv - vel * uDt / uResolution。

推导：vel 必须是以“像素/秒”为单位的物理速度。例如，速度 100px/s，dt=0.016，则单步移动 1.6 像素。

隐患：如果你从 FluidSimulator（旧版）直接拿速度纹理，旧版虽然也除以 resolution，但它的速度场生成（如爆炸）通常输出的是归一化速度（-1~1 或 0~1），乘以一个巨大的系数（如 strength）后勉强算作像素速度。

建议：在 AdvectionSolver 的文档中显式警告，并要求传入速度场前自行确保单位正确。或者，你可以增加一个 velocityScale 的 Uniform，让上层调用者可以自由缩放。

2. 数值耗散（模糊）是被刻意引入的，你无法在 Solver 层面关闭
你的 FluidGrid 使用了 LinearFilter（双线性插值）：

typescript
minFilter: THREE.LinearFilter,
magFilter: THREE.LinearFilter,
半拉格朗日平流 + 双线性插值 = 强数值耗散（画面会快速变模糊）。

这其实是好事：对于技能特效，耗散能消除高频锯齿，让能量涌动看起来更平滑。

代价：细节（如尖锐的闪电、清晰的边界）会被抹平。

解决方案（无需改动代码）：如果你未来需要保留锐利边缘，可以在调用 advect 后，额外调用一个 “锐化（Unsharp Mask）” 或 “涡度限制（Vorticity Confinement）” 后处理来补偿。
